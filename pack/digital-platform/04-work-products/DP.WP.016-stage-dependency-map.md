# Stage Dependency Map

## 1. Определение

**Stage Dependency Map** — формат рабочего продукта Аналитика ограничений (DP.ROLE.054), описывающий план работы по устранению идентифицированного ограничения системы. Это **dependency graph без временного измерения**:

- **Узлы** = этапы. Каждый этап содержит одну или несколько параллельных работ / РП, которые могут выполняться независимо друг от друга.
- **Рёбра (внутренние)** = жёсткая зависимость. «Следующий этап начинается только после завершения предыдущего». Не «желательная последовательность», не «приоритет» — именно жёсткая блокировка.
- **External-рёбра** = зависимости от работ вне target-системы. Указывают на конкретный РП / репо / внешнего поставщика, который должен быть завершён, прежде чем этап может стартовать.

## 2. Назначение

Без формата ответ Аналитика «делать сначала X, потом Y» оставляет вопросы: «X и Y могут идти параллельно? X блокирует только начало Y или весь Y? Что делать с зависимостью от другого РП?». Stage Dependency Map даёт явный ответ.

Артефакт служит:
- Пилоту — карта работы на ближайшие N этапов с явными границами
- Декомпозитору (R29 / DP.ROLE.053) — вход для декомпозиции каждого этапа на физические артефакты с приёмкой
- Стратегу — input для НЭП-обсуждения, какие из этапов покрыты текущими РП, какие требуют новых

## 3. Различия с похожими форматами

| Формат | Что есть | Чего нет в Stage Dependency Map |
|--------|----------|----------------------------------|
| **PERT** (US Navy) | Узлы=события, рёбра=задачи с оценками времени | Оценки времени, critical path |
| **Gantt** | Задачи по календарной шкале | Календарь, абсолютные даты |
| **Kanban** | Колонки status (todo/doing/done) с WIP-limits | Status-колонки, WIP-limits |
| **CCPM Network** | Dependency + buffer management | Feeding buffers, project buffer |
| **MS Project network** | Dependency + ресурсы + длительности | Ресурсы, длительности |

Stage Dependency Map — **чистая структура зависимостей**. Это сознательное ограничение: добавление дат → tendency к premature commitment; добавление status → дублирование Kanban-board; добавление ресурсов → задача Декомпозитора, не Аналитика.

## 4. Структура

### YAML-схема

```yaml
stage_dependency_map:
  target: WP-NNN | project-name | rcs-profile:<account_id>
  constraint_ref: "<ссылка на Constraint Brief>"
  generated_at: YYYY-MM-DD
  generated_by: DP.ROLE.054 / .claude/skills/bottleneck-pick

  stages:
    - id: stage_1
      label: "<краткое имя этапа, существительное-артефакт>"
      goal: "<какое состояние достигается этим этапом>"
      parallel_works:
        - "<работа A>"
        - "<работа B>"
        - "<работа C — может быть РП-ссылкой WP-NNN>"
      external_deps:
        - target: "WP-MMM в DS-other-repo"
          required_state: "<что должно быть достигнуто там>"

    - id: stage_2
      label: "..."
      goal: "..."
      parallel_works: [...]
      external_deps: [...]

  edges:
    - from: stage_1
      to: stage_2
      type: hard_dependency
      reason: "<почему stage_2 не может начаться без stage_1>"

    - from: stage_2
      to: stage_3
      type: hard_dependency
      reason: "..."
```

## 5. Правила построения

### Обязательные

1. **Каждый этап имеет цель.** Не «сделать X», а «достигнуто состояние Y». Цель = состояние системы после этапа.
2. **Параллельные работы внутри узла действительно параллельны.** Если работа B зависит от работы A — они в разных этапах, не одном.
3. **Edge = жёсткая зависимость.** Не «желательно сначала», не «логично сначала» — именно «иначе не сможем».
4. **External-зависимости указывают конкретный target.** Не «зависит от другого РП», а «зависит от WP-MMM, требуется status=in_progress phase Ф7».
5. **Без дат, часов, дней.** Формат структурный, не временной.
6. **Без status-колонок (todo/doing/done).** Это задача Kanban, не Stage Map.
7. **Этап = существительное-артефакт.** «Activation 9 ранних пилотов», не «Активировать пилотов».

### Запрещённые

- Циклы (Stage A → Stage B → Stage A) — топологическая сортировка обязательна
- Edges с типом, отличным от `hard_dependency` — soft-зависимости («желательно бы») не существуют в Stage Map
- Date-fields (`due`, `start`, `end`)
- Resource-fields (`assigned_to`, `hours_required`)
- Status-fields (`status`, `progress_percent`)

## 6. Пример

**Target:** WP-250 (зонтичный РП первой когорты), bottleneck = operational gap (activation).

```markdown
## Stage Dependency Map: WP-250

### Этап 1: Активация 9 ранних пилотов
**Цель:** ≥5 пилотов из 9 совершили первое целевое действие (открыли репо + получили руководство + ответили на 1 вопрос).

**Параллельные работы:**
- Доставка персонального руководства (через managed-канал, WP-309)
- Отправка вечернего сообщения с инструкцией активации
- Check-in от Навигатора через TG (опциональный, не блокирует)

**External-зависимости:**
- WP-310 (Аттестатор daily-run) — должен работать стабильно, без этого нет фиксации `cp_assessment`

### → Этап 2: Wave-rollout 5→15→30
> Может начаться только после завершения Этапа 1 (причина: без подтверждённой conversion ≥50% на 9 пилотах wave-2/3 даст ту же operational-gap-картину, инфляция Inventory без Throughput).

**Параллельные работы:**
- Bulk-onboarding SQL для wave-2 (15 человек)
- Подготовка broadcast-сообщений wave-2
- Solo-smoke pre-flight перед каждой волной

**External-зависимости:**
- WP-188 Ф17.9 TG-broadcast — должен быть оттестирован

### → Этап 3: Когорта 50 пилотов, daily-rhythm стабилизация
> Может начаться только после завершения Этапа 2 (причина: rhythm работает только когда есть mass для daily-ритма; на 9-15 пилотах rhythm не виден).

**Параллельные работы:**
- Daily Aist-bot ping
- Weekly check-in от Навигатора
- Monthly retro

**External-зависимости:** нет
```

## 7. Использование Декомпозитором (handoff)

После получения Stage Dependency Map от Аналитика, Декомпозитор (DP.ROLE.053) **берёт каждый этап** и применяет к нему свой метод декомпозиции:

| Что делает Аналитик | Что делает Декомпозитор |
|----------------------|------------------------|
| Stage 1: «Активация 9 пилотов» — параллельные работы | Stage 1 → стадии с физическими артефактами на входе/выходе каждой |
| Параллельные работы как список | Каждая работа → чеклист приёмки |
| External-зависимость как target | Декомпозитор детализирует, какое именно состояние external-target нужно |

Sequencing: Аналитик (куда смотреть) → Декомпозитор (как сделать).
