# State-Based Management vs Task-List Management

## 1. Определение

**State-Based Management** — режим планирования, в котором единица отслеживания — это **состояние значимого объекта** (договор в стадии «согласование», кандидат в стадии «оффер выслан», рабочий продукт в стадии «draft»). Прогресс измеряется как изменение состояний.

**Task-List Management** — режим, в котором единица — это **запланированное действие** (задача с дедлайном). Прогресс измеряется как чек у задачи.

Это **режим управления**, не формат документа. Один и тот же канбан можно вести в обоих режимах.

## 2. Тест темпо-адекватности

```
Частота смены реальности > Частота review плана? → state-based
Частота смены реальности ≤ Частота review плана? → task-list ОК
```

**Примеры:**
- Корпоративный продакшн с 50+ параллельными договорами → состояния меняются ежедневно, review раз в неделю → task-list даёт устаревшую картину → state-based.
- Личный быт (5 встреч в неделю) → реальность стабильна → task-list работает.
- WP-151 (характеристики и состояния деятеля): десятки слотов RCS меняются непрерывно от каждого ритуала → state-tracking, не список задач.

## 3. Эмпирический якорь

Кейс корпоративной группы Хохланд (Лаборатория МИМ, 7 мая 2026): переход с task-list на state-tracking сдвинул проекты, которые годами стояли. Анатолий: «Мы теперь в проектах отслеживаем состояния важных объектов. Управляем этим вместо списка задач. **Проекты сдвинулись**.» Левенчук: «Это и есть моделирование. Список объектов.»

Также подтверждается архитектурой ECS/ECM в game-dev (entities + components + systems вместо to-do очередей задач игровым агентам) и event sourcing в backend (state как fold по событиям, не как императивный список).

## 4. Связь с D.053

State-based management — **инструмент конвертации Проблема → Задача** (DP.D.053). Когда не понятно «что делать дальше» (Проблема), список объектов и их текущих состояний выводит из ступора: вижу, что объект X в состоянии Y, следующий шаг — переход в Z. Task-list этого не делает, потому что не моделирует объекты.

## 5. Антипаттерны

| Антипаттерн | Симптом | Правильно |
|-------------|---------|-----------|
| Task-list при быстрой реальности | План устаревает к концу review-цикла; задачи отмечаются формально | Перейти на state-tracking значимых объектов |
| State-tracking без определения объектов | Доска с непонятными статусами; никто не знает, что значит «in progress» | Сначала список объектов (FPF Object), потом состояния (FPF Description), потом носители (FPF Carrier) |
| Смешение: задачи и состояния в одной колонке | «Сделать X» рядом с «Согласовано» — нельзя сравнить прогресс | Раздельные доски: задачи на нижнем уровне (исполнение перехода между состояниями), состояния на верхнем |

## 6. Revision criterion

- Would change if empirical data shows that task-list режим даёт сопоставимый эффект на корпоративных проектах с >50 параллельных объектов.
- Would change if FPF темпо-адекватность переформулирует тест более строго (ожидается update до конца мая 2026).

## 7. Применение в наших РП

- **WP-151** (характеристики и состояния деятеля) — state-tracking как канон, не список метрик-снимков.
- **WP-117** (nudge-система) — правила nudge должны срабатывать на изменение состояний, не на отсутствие задач/событий.
- **WeekPlan / DayPlan** — состояния активных РП (Inventory, Goldratt) важнее списка «что сделать сегодня».
