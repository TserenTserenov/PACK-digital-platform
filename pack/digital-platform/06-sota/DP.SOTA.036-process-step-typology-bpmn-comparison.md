# DP.SOTA.036 — Типология шагов процесса vs BPMN-движки

## SoTA-статус

**Current.** BPMN (Business Process Model and Notation, с версии BPMN 2.0, 2011 год) — устоявшийся индустриальный стандарт декларативной типизации шагов процесса. Движки Camunda и Zeebe реализуют BPMN уже 20 лет, с явным полем типа элемента диаграммы (`userTask`, `serviceTask`, `scriptTask`) как частью формальной схемы процесса, а не побочным эффектом кода.

## Что нового относительно BPMN (находка WP-482)

BPMN покрывает оркестрацию потоков и типизацию задач, но не покрывает:

1. **Различение рефлекс/ИИ внутри одного автомата, с динамикой** — тип шага не фиксирован на момент проектирования; ИИ-шаг после накопления повторений и согласия пилота становится рефлекс-шагом. BPMN-типы статичны на момент моделирования диаграммы.
2. **Четыре типа исполнителя шага**: рефлекс (lookup по сигнатуре, без LLM), ИИ (LLM при неопределённости), пилот (human-в-петле, решение принципиально не автоматизируется), интеграция (внешняя система).
3. **Формальная FSM трёхэтапной кристаллизации**: `A(raw) → B1(reflex-lookup) → B2(async pack-matcher) → B3(pilot-approved) → C(executable)`. Кристаллизация проходит через явные стадии (`pilot_approved → async pack-matcher → executable`), не одномоментно.
4. **Demuxer-контракт** `RawReflexSchema → CardSchema[]` — формальная схема преобразования сырого повторяющегося решения в кандидата на кристаллизацию.

## Симметричные ожидающие состояния

Waiting-состояния (например ожидание approve пилота) — симметричны, без автоматических отмен. Счётчики reformulation/snooze ограничены (≤3) до эскалации — предотвращает бесконечное ожидание без сигнала.

## Тест применимости типологии

«Нужно объяснить системе, какой агент отвечает за шаг, и при каком условии происходит переход к следующему?» Да → данная типология применима.

## Revision criterion

Появление индустриального SOTA-решения, покрывающего динамическую типизацию (не статичную, как BPMN) с явной кристаллизацией через накопление повторений — пересмотреть статус.
