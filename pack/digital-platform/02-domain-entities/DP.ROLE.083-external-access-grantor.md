# External Access Grantor (DP.ROLE.083)

<!-- see DP.SC.190, WP-5, фаза «Подключение внешних AI-клиентов» -->

> **Kind:** Service role (текущий носитель — бот-процесс, `handlers/` + `/connect_external`; целевой носитель для будущей миграции — открытый вопрос, см. §9).
> **Owner Role:** Платформенный архитектор (bootstrap) — до формализации отдельного владельца.

## 1. Миссия

Быть единственной точкой выдачи пропуска внешнему ИИ-клиенту (claude.ai, VS Code) для доступа к знаниям платформы. Не важно, кто инициировал выдачу — бот проактивно предложил (push) или пользователь запросил сам (`/connect_external`, pull) — обе дорожки приводят к одному и тому же коду выдачи, не к двум независимым реализациям.

**Отличие от DP.ROLE.040 (OAuth Orchestrator):** OAuth Orchestrator — это ВХОДЯЩЕЕ направление, платформа как OAuth-клиент подключается к сторонним провайдерам (GitHub, Linear, Google Calendar). External Access Grantor — ИСХОДЯЩЕЕ направление, платформа сама выступает как сервер авторизации для внешних ИИ-клиентов, которые хотят читать данные платформы. Роли зеркальные, не взаимозаменяемые.

## 2. Обязанности

| Обязанность | Метод | Триггер |
|-------------|-------|---------|
| Проверить тир пользователя перед выдачей | `detect_ui_tier()` ≥ T3 | Запрос на выдачу пропуска (push или pull) |
| Выдать пропуск (`ict_` токен) | Генерация + запись в `ory_client_tokens` (БД `health`) | Тир подтверждён ≥ T3 |
| Обновить истёкший пропуск | Refresh `irt_→ict_` | Пропуск близок к истечению |
| Настроить VS Code одним действием | Передать конфигурацию расширению без ручной вставки | Пользователь нажал «Подключить VS Code» |
| Отказать явно при недостаточном тире | Сообщение с причиной, не тихая заглушка | Тир < T3 на момент запроса |
| Логировать факт выдачи | Через DP.SC.025 capture-bus | Каждая выдача/отказ/сбой |

## 3. Полномочия

- **Читает** тир пользователя (`detect_ui_tier`) — не кэш `public.users.tier` напрямую (см. известную ловушку устаревания в CLAUDE.md бота §12).
- **Пишет** в `ory_client_tokens` (БД `health`) — новые и обновлённые пропуска.
- **Читает** `persona.user_integrations` — индикатор существующих подключений (не дублировать выдачу активному подключению).
- **Не решает**, кому предлагать push проактивно за пределами момента смены тира — массовая рассылка существующим пользователям вне этого триггера требует отдельного решения пилота (см. DP.SC.190 «Не гарантирует»).
- **Не хранит** бизнес-логику самого шлюза (`introspectBotToken`, `validateOryToken`) — это `gateway-mcp`, роль только выдаёт пропуск, не проверяет его на входе.

## 4. Границы роли

| Делает | НЕ делает |
|--------|-----------|
| Выдача/обновление пропуска по тиру | Не проверяет пропуск на входе в шлюз (это `gateway-mcp`) |
| Единая точка для push и pull инициации | Не решает решение о массовой рассылке (пилот) |
| One-click настройка VS Code | Не хранит бизнес-данные знаний (это MCP-серверы) |
| Явный отказ при недостаточном тире | Не создаёт identity (это Ory) |

## 5. Артефакты

**Входы:**
- Событие смены тира пользователя (push-триггер) ИЛИ команда `/connect_external` (pull-триггер).
- Текущий тир пользователя.

**Выходы:**
- Строка в `ory_client_tokens` (новый или обновлённый пропуск).
- Сообщение пользователю (успех/явный отказ).
- Capture-bus событие (выдача/отказ/сбой).

## 6. Носители (carriers)

**Текущий инстанс (на 2026-07-11):** бот-процесс (`DS-IT-systems/aist_bot_newarchitecture`, обработчик `/connect_external`) — до отдельного решения о миграции.
