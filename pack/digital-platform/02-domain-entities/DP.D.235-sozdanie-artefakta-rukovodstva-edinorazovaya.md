# DP.D.235: Создание артефакта-руководства (единоразовая работа) ≠ Конвейер его обновления (recurring process)

**Контекст:** При работе с долгоживущими руководствами (guide, playbook, стандарт) легко
смешать акт создания артефакта с его системой поддержки в актуальном состоянии.

**Различение:**

- **Создание артефакта-руководства** — единоразовая работа: написать, структурировать,
  согласовать, опубликовать. Owner = автор/команда. Триггер = один раз. Результат: текстовый
  артефакт в определённый момент времени.
- **Конвейер обновления** — recurring process: мониторить изменения в практиках/требованиях,
  триггерить перегенерацию/ревизию, публиковать обновлённую версию. Owner = отдельный процесс
  (pipeline, cron, responsible role). Триггер = изменение upstream (практики, стандарты, данные).
  Результат: живой артефакт, актуальный в любой момент.

**Почему важно разделить:**

Без явного конвейера обновления руководство деградирует: через N месяцев практики изменятся,
а текст останется прежним. Создать документ ≠ поддерживать его — разные артефакты, разные
owner и lifecycle.

**Прецедент:** WP-362 создал универсальные руководства ЛР. Процесс их обновления при
изменении FMT-практик не был специфицирован → WP-453 явно закрыл этот gap (конвейер:
FMT-практика изменилась → раздел 7 guide.system-school.ru обновляется).

**Тест:** «Если FMT-практика изменится завтра — когда и кто обновит руководство?»
Нет ответа → конвейер обновления не описан.
