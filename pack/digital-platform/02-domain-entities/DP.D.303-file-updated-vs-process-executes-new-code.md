# DP.D.303 Файл на диске обновлён ≠ живой процесс исполняет новый код

| Аспект | Файл на диске | Живой процесс |
|--------|---------------|----------------|
| **Что меняется** | mtime файла скрипта/бинаря обновляется сразу после git pull / записи на диск | Код в памяти долгоживущего процесса (launchd/systemd демон) не меняется, пока процесс не перечитает файл — обычно только при рестарте |
| **Наблюдаемый факт без проверки** | «Файл обновлён» | Ошибочно принимается за «изменения уже действуют» |
| **Реальный разрыв** | — | Процесс, запущенный ДО обновления файла, продолжает исполнять старую версию в памяти неограниченно долго, если не перезапущен |

## Правило

Три уровня свежести деплоя долгоживущего демона: репозиторий → диск (mtime файла) → память процесса (время старта процесса). Отчёт о доставке изменений («задеплоено», «обновил копию») обязан называть, до какого именно уровня дошло — обновление файла на диске не равно применению изменений исполняющимся процессом.

## Тест

«Когда стартовал процесс, который исполняет этот файл, и раньше ли это mtime файла?» Если время старта процесса РАНЬШЕ mtime файла — процесс исполняет старую версию, нужен перезапуск.

## Пример

Напарник отчитался «детектор в репозитории, нужно обновить копию» — реальный разрыв был не в репозитории/диске (файл уже обновлён с 09:10), а в том, что живой процесс сторожа был запущен 3 сентября и продолжал крутить старый код в памяти. Фикс — перезапуск процесса, не синхронизация файлов.

## Применимо к

Эксплуатации любого долгоживущего демона (launchd, systemd, supervisord), где код обновляется через git pull/копирование файла независимо от жизненного цикла процесса. Смежные failure modes: DP.FM.194 (launchd не перезапускает сервис из-за stale-pid на порту — иной механизм: там launchd явно пытается и не может перезапустить; здесь launchd вообще не пытается, процесс формально «жив и здоров»), DP.FM.143 (PPID-fallback на stale PID в pidfile).
