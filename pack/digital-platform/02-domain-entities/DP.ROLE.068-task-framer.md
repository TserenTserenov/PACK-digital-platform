# DP.ROLE.068 — Постановщик задачи IWE

> **Kind:** Human role (человек T4+).
> **Owner Role:** R14 Заказчик (пилот) / DP.ROLE.071 Ведущий разработчик.
> **Текущий исполнитель:** члены команды T4+ (TD1).

---

## 1. Миссия

Гарантировать, что любая работа, попадающая в конвейер, имеет чёткое начало (триггер), измеримый конец (приёмка) и правильную маршрутизацию (куда писать код, куда — знание).

**Граница:** Постановщик не решает КАК реализовывать (это Разработчик-исполнитель + Архитектор) и не назначает приоритет вне бэклога команды (это Ведущий разработчик).

---

## 2. Обязанности

| Обязанность | Как выполняется |
|-------------|-----------------|
| Определить триггер | «Что случилось, что требует работы» |
| Выбрать тег маршрутизации | Код → DS-репо; Знание → Pack/шаблон; Процесс → AGENTS.md/CLAUDE.md |
| Назначить класс верификации | V1 (чеклист Haiku) / V2 (сверка эталон) / V3 (peer-review) / V4 (problem-framing) |
| Сформулировать критерий приёмки | «Задача закрыта, когда…» (конкретно, проверяемо) |
| Привязать к цели | Связь с R6/неделей/кварталом |
| Проверить барьер входа | Исполнитель — T4+; если ниже — передать в онбординг (WP-349), не в конвейер |

---

## 3. Граница с DP.ROLE.058 Артефактор-Постановщик

| Аспект | DP.ROLE.058 (агент) | DP.ROLE.068 (человек T4+) |
|--------|---------------------|---------------------------|
| **Что делает** | Структурирует сырой запрос в РП с routing-tag | Определяет стратегическую ценность, acceptance criteria, привязку к R6 |
| **Проверяет барьер входа** | Нет | Да — T4+ в конвейер, T1–T3 → онбординг |
| **Связь с целью** | Нет | Да — привязка к неделе/кварталу |
| **Ответственность** | Формат | Содержание и приоритет |
| **Триггер** | Автоматический (Маршрутизатор) | Ручной (член команды или Ведущий) |

**Тест:** DP.ROLE.058 формализует запрос. DP.ROLE.068 решает, стоит ли эта задача делаться вообще и кто её примет.

---

## 4. Входы / Выходы

**Входы:**
- Сырая нужда: баг-репорт, идея, замечание, техдолг.
- Контекст: стратегические цели (R6), текущий бэклог команды.

**Выходы:**
- Оформленная карточка задачи с frontmatter (wp, verification_class, acceptance_criteria, routing_tag).
- Задача в очереди Диспетчера (при команде >1).

---

## 5. Ограничения (инварианты роли)

1. **Без карточки — нет конвейера.** Задача без `wp:` и `verification_class` не передаётся Разработчику-исполнителю.
2. **Барьер T4+.** Задачи для исполнителей ниже T4 направляются в WP-349 (OnboardingMarkers), не в конвейер WP-403.
3. **Не назначает исполнителя.** Постановщик определяет ЧТО, не КТО. Назначение — Ведущий разработчик или pull из очереди.
