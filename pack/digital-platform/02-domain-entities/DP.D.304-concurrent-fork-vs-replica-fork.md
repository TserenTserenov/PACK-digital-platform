# DP.D.304 Конкурентный форк ≠ Репличный форк

| Аспект | Конкурентный форк | Репличный форк |
|--------|--------------------|-----------------|
| Причина расхождения | Гонка часов — оба писателя одновременно авторизованы и записали одновременно | Две реплики реестра расходятся в изоляции друг от друга (offline-first), каждая валидна сама по себе |
| Когда виден конфликт | В момент записи (два процесса пишут одновременно) | Только в момент слияния реплик |
| Требование к тестовому стенду | Две независимые ОС-песочницы с протоколом синхронизации (аналог общего предка/ветки/конфликта VCS, без автослияния) | Не нужна вторая ОС-песочница — тестируется уже сейчас против резолвера через union-/overwrite-слияние |
| Природа расхождения | Свойство гонки исполняющихся процессов | Свойство содержимого записи |

## Тест на различение

«Конфликт обнаруживается сравнением содержимого при слиянии, или только наблюдением двух процессов, пишущих одновременно?» Сравнение при слиянии → репличный форк, вторая песочница не нужна. Наблюдение гонки в моменте записи → конкурентный форк, нужна вторая изолированная ОС-песочница.

## Контекст открытия

Пир-сессия (Kimi — критик структуры) разделила тезис «одна дыра» на два разных инварианта: авторизация (кто вправе писать) и конкурентная консистентность (кто побеждает при одновременной записи). При разборе второго нашёлся третий, более узкий класс — репличный форк — который изначально не был описан отдельно от конкурентного форка. Тестировать репличный форк вживую в конкурентном стенде без специальной инфраструктуры = переигрывать уже принятый консенсус без новых оснований.

## Переносимость

Применимо к любой системе с распределённым/реплицируемым состоянием (registry, БД, конфиг): перед тем как проектировать тестовый стенд для «конфликта записи», проверить тестом выше — не все расхождения требуют гонки двух процессов, часть требует только сравнения содержимого при слиянии.
