# Принцип триады учёт-доступ-аудит (DP.KR.030)

## 1. Определение

**Триада учёт-доступ-аудит** — принцип организации институционального контроля: три функции, которые необходимо структурно разделить, чтобы контроль работал без конфликта интересов.

| # | Функция | Вопрос | Инвариант |
|---|---------|--------|-----------|
| **Учёт** (KR.030) | Что происходит? | Фиксировать события, состояния, транзакции | Полнота + неизменность записи |
| **Доступ** (KR.031) | Кто что видит? | Управлять правами на просмотр и изменение | Минимальные привилегии + явное разрешение |
| **Аудит** (KR.032) | Соблюдаются ли правила? | Проверять соответствие учёта и доступа нормативу | Независимость + read-only к проверяемому |

> KR.031 (Доступ) и KR.032 (Аудит) — отдельные принципы, создаются при WP-214 Ф4 миграции.

## 2. Проблема

Без явного разделения три функции естественно «слипаются» в одну роль:
- Роль, которая **ведёт учёт**, хочет сама же **ограничивать доступ** к своим данным.
- Роль, которая **управляет доступом**, заинтересована в **положительном аудите**.
- Роль, которая **аудирует**, при совмещении с учётом проверяет сама себя.

Результат слипания: аудит теряет независимость, учёт — полноту, доступ — непредвзятость. Система переходит из «Парламента» (три независимых контроля) в «Президента» (один агент всё видит и всё контролирует) — см. DP.D.xxx (различение Парламент-модель ≠ Президент-модель).

**Конкретная проблема IWE (исходная):** До WP-224 роли R23-R26 (VR-контроль) не были отделены от операционных ролей (R8 Синхронизатор, R11 Наладчик). Аудитор мог запускаться тем, чьи артефакты проверяет. Учёт событий (Activity Hub) и управление доступом к нему жили в одном сервисе без явного разделения.

## 3. Принцип (ядро триады)

**Триада — не иерархия, а три независимые оси контроля:**

```
       ┌─────────────────┐
       │    Операционный  │  ← создаёт, изменяет, синхронизирует
       │    слой          │    (R8, R11, R6, ...)
       └────────┬────────┘
                │ действия
       ─────────┼────────── граница контроля ──────────
                │
       ┌────────┴──────────────────────────────────┐
       │              Контрольный слой              │
       │  ┌─────────┐  ┌─────────┐  ┌───────────┐  │
       │  │ Учёт    │  │ Доступ  │  │ Аудит     │  │
       │  │ KR.030  │  │ KR.031  │  │ KR.032    │  │
       │  │ «что?»  │  │ «кто?»  │  │ «верно?»  │  │
       │  └─────────┘  └─────────┘  └───────────┘  │
       └───────────────────────────────────────────┘
```

Три ветки контрольного слоя не управляют операционным слоем — они **наблюдают** его. Это принцип DP.D.080 (контроль ≠ операция) в архитектурном масштабе.

## 4. Элементы триады в IWE

### 4.1 Учёт — «Что происходит?»

**Задача:** регистрировать события, состояния, транзакции в неизменяемом журнале.

**Архетип:** бухгалтерская книга — каждая запись неизменна, список записей полный.

**В IWE:** Activity Hub (`learning.domain_event`) — поток событий действий пользователя. R10 Статистик (metrics collection). R32 Event Ingester.

**Инвариант:** Учётчик не может удалять или редактировать уже внесённые записи. Иначе аудит не имеет смысла — нечего проверять.

### 4.2 Доступ — «Кто что видит?» *(KR.031, создаётся при WP-214 Ф4)*

**Задача:** управлять правами на чтение и изменение в системе по принципу минимальных привилегий.

**Архетип:** привратник — разрешает или запрещает вход, не создаёт и не проверяет содержимое.

**Инвариант:** Управляющий доступом не является потребителем данных, к которым управляет доступом. Иначе появляется мотивация для злоупотреблений.

### 4.3 Аудит — «Соблюдаются ли правила?» *(KR.032, создаётся при WP-214 Ф4)*

**Задача:** проверять соответствие учёта нормативу и полноту покрытия.

**Архетип:** аудитор бухгалтерии — проверяет книги, не ведёт их.

**В IWE:** DP.ROLE.024 Аудитор (VR.R.002), R23 Верификатор (VR.R.001). Методы: VR.M.002 (кросс-контекст), VR.M.004 (полнота).

**Инвариант:** Аудитор (KR.032) не является учётчиком (KR.030) и не управляет доступом (KR.031). Нарушение любого из двух разделений делает аудит недействительным.

## 5. Применение к ролям IWE

### 5.1 Маппинг ролей на ветки триады

| Ветка | Роли в IWE | Выход | Owner |
|-------|------------|-------|-------|
| **Учёт** | R10 Статистик, R32 Event Ingester, DP.ROLE.041 Аттестатор (расчёт) | events, metrics, stage_transitions | Платформа |
| **Доступ** | Пока не формализовано как роль. Реализовано через RLS-политики Neon + ORY auth | permission grants | Платформа |
| **Аудит** | R23 Верификатор, R24 Аудитор, R25 Рецензент | отчёт, verdict | Внешний заказчик |

> **R24 — единственная аудитная роль с Owner Role ≠ Платформа.** Это не случайность — это прямое следствие DP.KR.030: если платформа владеет и аудиторской ролью, триада вырождается. Подробнее: DP.ROLE.024 §1.

### 5.2 Тест применения (Парламент vs. Президент)

| Вопрос | Ответ «да» → | Ответ «нет» → |
|--------|-------------|---------------|
| Может ли одна роль и вести учёт, и аудировать? | Нарушение KR.030 (Президент) | Триада соблюдена |
| Может ли учётчик скрывать записи? | Нарушение инварианта учёта | Полнота обеспечена |
| Является ли заказчик аудита аудитуемой системой? | Конфликт интересов (организационный) | Методологическая независимость достаточна |

## 6. Инварианты принципа

1. **Разделение учёта и аудита:** Роль, ведущая учёт, не аудирует сама себя.
2. **Разделение доступа и аудита:** Роль, управляющая доступом, не аудирует систему доступа в изоляции.
3. **Разделение учёта и доступа:** Роль, ведущая учёт, не управляет правами чтения к своим записям.
4. **Контрольный слой ≠ Операционный:** Ни одна ветка триады не изменяет операционное состояние системы (DP.D.080).

## 7. Примеры нарушений

| Нарушение | Симптом | Последствие |
|-----------|---------|-------------|
| Аудитор = создатель проверяемого | «Сам написал — сам проверил» | Независимость аудита нулевая |
| Учётчик удаляет записи | Gap в истории событий | Аудит на неполных данных |
| Доступ-роль сама заказывает аудит себя | Нет независимости | Аудит может быть заказан в удобное время / форме |
| Платформа — Owner R24 | Платформа проверяет свои же компоненты | KR.030 §5.1 нарушен |

## 9. Серия KR.030–039 — зарезервирована

Серия **DP.KR.030–039** зарезервирована под принципы триады учёт-доступ-аудит и их расширения:

| KR | Статус | Тема |
|----|--------|------|
| **KR.030** | ✅ Этот файл | Принцип триады (foundation) |
| **KR.031** | 🔲 WP-214 Ф4 | Принцип управления доступом (Доступ) |
| **KR.032** | 🔲 WP-214 Ф4 | Принцип аудитной независимости (Аудит) |
| KR.033–039 | 🔲 Резерв | Расширения триады (будущие принципы серии) |

> **Нумерация по порядку зависимости:** учёт (030) → доступ (031) → аудит (032). Аудит стоит последним, потому что зависит от обоих предшественников: нечего аудировать без учёта, и аудит невозможен без управления доступом к данным учёта.
