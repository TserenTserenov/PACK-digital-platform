# DP.D.249: SC (Service Clause) ≠ Метод верификации (Verification Method)

| Service Clause | Метод верификации |
|---|---|
| Обещание **потребителю**: гарантирует изменение состояния потребителя | Инструмент **автора**: возвращает список находок автору материала |
| Выход: изменённое состояние (Лид → Участник, Trial → Subscriber) | Выход: «список находок» — что улучшить в материале |
| Режим отказа: описан в контракте, наблюдаем потребителем | «Отказ» = находки, видимы только автору |
| Потребитель — субъект изменения | Потребитель — не видит результата верификации |

**Тест:** «Выход инструмента идёт потребителю (меняет его состояние) или автору (помогает улучшить материал)?»
- Потребителю → это SC
- Автору → это метод верификации, SC не нужен

**Диагностика:** quality gate, линтер, чеклист, панель экспертов — если их выход идёт **автору** материала, а не конечному потребителю продукта — это метод, не SC. Попытка назначить таким инструментам SC = избыточность (SC описывает контракт с потребителем, которого у метода нет).

**Пример (WP-251 Ф0):** «Банк персон-скептиков» (ECO.M.024) — метод верификации: автор проверяет материал через банк → получает список где «не убедительно». Это метод, не SC. SC — это «Конвейер продвижения доводит Лида до покупателя» (если такое обещание есть).

**Смежно:** [DP.D.058] (SC ≠ Carrier — соседняя ось: обещание vs кто выполняет), [DP.D.062] (SC-потребитель — роль, не канал). Источник: WP-251 Ф0 пир-сессия claude+kimi, session-close 2026-07-10 (commit a3699fcae).
