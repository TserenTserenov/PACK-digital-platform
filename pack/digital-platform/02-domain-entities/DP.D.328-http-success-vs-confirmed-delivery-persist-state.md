# DP.D.328 — HTTP-успех ≠ подтверждённая доставка

## Различение

| | HTTP-успех (транспортный уровень) | Подтверждённая доставка (прикладной уровень) |
|---|---|---|
| **Что проверено** | Запрос дошёл до API и вернул успешный код, клиент (`curl`) не сообщил об ошибке | Прикладное поле ответа подтверждает приём сообщения (`jq -e '.ok == true'`) |
| **Ошибка, если не так** | Уведомление считается отправленным и ретрай израсходован, хотя сообщение не доставлено: Telegram может вернуть HTTP 200 с телом `{"ok": false}` | — |
| **Действие** | Состояние «отправлено» не записывается, ретрай не расходуется | Хэш состояния записывается атомарно (`mktemp` + `mv`), после этого доставка считается подтверждённой |

## Механизм

Первая версия обёртки уведомления на systemd-таймере (коммит b42b18e) считала уведомление отправленным по факту успешного `curl` — это транспортный уровень. Когда Telegram отвечал HTTP 200 с `ok=false`, сообщение не доставлялось, а ретрай терялся. Холодное ревью (Codex) потребовало прикладной проверки ответа до записи хэша состояния. Запись хэша сделана атомарной (`mktemp` + `mv`), чтобы сбой между отправкой и сохранением не оставлял файл состояния записанным частично. Гарантия at-least-once выбрана осознанно: крах после доставки, но до записи хэша, может продублировать сообщение.

## Тест различения

«Состояние „отправлено“ записывается по прикладному полю ответа (ok=true), а не по коду HTTP или выходу клиента? Запись атомарна? При ok=false ретрай остаётся доступным?» Нет → воспроизведена ошибка: недоставленное уведомление числится доставленным.

Fail-loud: при повреждённом или пустом выводе источника (например, число отклонённых записей CSV считается структурным парсером, а не по физическим строкам, потому что значения могут содержать переносы строк) обвязка завершается явной ошибкой, а не тихо обнуляет состояние доставки.

## Границы

Различение применимо к обвязкам уведомлений и алертинга над внешними API, которые могут вернуть транспортный успех при прикладной неудаче, и где состояние доставки или дедупликации сохраняется между запусками. Карточка не утверждает exactly-once: при at-least-once допустим дубль сообщения при краше между доставкой и записью состояния.
