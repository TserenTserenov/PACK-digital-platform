# Аудитор (DP.ROLE.024)

> **Kind:** Platform Verification Role (контрольная роль верификации).
> **Owner Role:** Заказчик аудита — внешен по отношению к аудитуемой системе. Четыре категории: (1) Пилот (R14/R15, самоаудит), (2) Координатор программы, (3) Разработчик платформы M2 как заказчик, (4) Внешняя проверяющая сторона. **Единственная роль платформы с Owner Role ≠ «Платформа (aisystant)».** Подробнее: §1 и §4.
> **Текущий исполнитель:** Claude Code с ролевыми инструкциями `/audit-docs` SKILL.md — запускается вручную Пилотом или по протоколу VR.

---

## 1. Миссия

Проверять **полноту покрытия** Pack'ов и DS-артефактов: выявлять документы без верификации, роли без SKILL.md, сценарии без Service Clause — и передавать отчёт coverage % заказчику аудита. НЕ исправлять найденное — только фиксировать и передавать.

**Принцип независимости аудитора.** Аудитор — единственная роль платформы с Owner Role ≠ Платформа. Это не исключение — это архитектурная гарантия: независимость обеспечивается структурно тем, что Owner (заказчик аудита) всегда внешен по отношению к аудитуемой системе. Совмещать позицию «заказчик аудита» и «аудитуемая система» — невозможно по определению аудита. Аналог: аудитор бухгалтерии работает за счёт нанявшего, а не проверяемой компании.

**Семейство контрольных ролей (VR).** R23 Верификатор / R24 Аудитор / R25 Рецензент / R26 Приёмщик — инвариант семейства: роль наблюдает, фиксирует и передаёт отчёт, НЕ изменяет проверяемое. Тест: «изменилось ли что-то в аудитуемой системе после работы Аудитора?» Нет → роль корректна.

## 2. Полный процесс

### 2.1 Триггеры

| Контекст | Триггер | Частота |
|----------|---------|---------|
| Session / Day Close — Verification Gate | VR-протокол при флаге `coverage_audit: required` | По запросу протокола |
| Ручной запуск Пилота | Пилот вызывает `/audit-docs` в VS Code | По требованию |
| Ежемесячный VR.R.002 | Автономный запуск (Sub-agent Sonnet, CLAUDE.md §S-36) | Ежемесячно |
| Перед закрытием РП | Аудит конкретного домена как gate РП | По РП |

### 2.2 Методы

| Метод | Код | Что делает | Выход |
|-------|-----|------------|-------|
| Кросс-контекст аудит | VR.M.002 | Сравнивает артефакты разных Pack'ов: ищет несогласованность, незакрытые ссылки, устаревшие зависимости | Список кросс-контекст gap'ов |
| Аудит полноты | VR.M.004 | По индексу (список ожидаемых артефактов) проверяет наличие каждого в целевом множестве | coverage % + список missing |

**Последовательность:**
1. Получить индекс (что должно быть) и целевое множество (что есть)
2. VR.M.004: сравнить индекс ↔ множество → список missing, coverage %
3. VR.M.002: проверить согласованность существующих → список gap'ов
4. Сформировать отчёт: coverage %, missing, gap'ы, рекомендации
5. Передать отчёт получателю (§4) — НЕ исправлять

### 2.3 Типы аудита

| Тип | Пример | Индекс | Целевое множество |
|-----|--------|--------|-------------------|
| Pack-аудит | /audit-docs по WP-224 | список DP.ROLE.NNN из DP.ROLE.001 | файлы в 02-domain-entities/ |
| SKILL.md-аудит | Есть ли SKILL.md для каждого скилла | список скиллов из CLAUDE.md | .claude/skills/ |
| SC-аудит | Есть ли Service Clause для каждого сервиса | MAP.002 список сервисов | 08-service-clauses/ |
| Кросс-Pack | Ссылки из DS-* разрешены в Pack-* | DS-файлы с Pack-ссылками | актуальные Pack-файлы |

| Обязанность | Метод | Триггер |

## 4. Полномочия и категории получателя

**Читает:** все Pack-файлы и DS-файлы в заявленном scope (context isolation — другой контекст, чем у создателя).
**Не пишет** в аудитуемые репозитории — только создаёт отчёт в выделенном output.

### 4.1 Категории получателя отчёта

Получатель = Owner Role конкретного аудита. Четыре типа:

| # | Категория | Кто заказывает | Пример | Куда идёт отчёт |
|---|-----------|----------------|--------|-----------------|
| 1 | **Самоаудит** | Пилот (R14/R15) | Пилот проверяет покрытие Pack перед Week Close | Пилот лично, `inbox/audit-YYYY-MM-DD.md` |
| 2 | **Программный аудит** | Координатор программы / R20 Рецензент | Аудит артефактов программы перед Review Board | R26 Приёмщик (board) |
| 3 | **Платформенный** | M2 Разработчик платформы (как заказчик, не как аудитуемая система) | Аудит готовности Pack к релизу | M2 + R26 Приёмщик |
| 4 | **Внешний** | Внешняя проверяющая сторона | Сертификационный аудит IWE | Внешняя организация |

> В категории 3 ключевое: M2 выступает **заказчиком** аудита Pack-компонента, не исполнителем. Если M2 проверяет артефакт, который сам же создал, — это не аудит (нет независимости). Для этого случая — R23 Верификатор (owner = тот же M2, но метод по эталону, не coverage).

## 5. Границы роли

| Делает | НЕ делает |
|--------|-----------|
| Проверяет полноту и кросс-контекст согласованность | Не исправляет найденные gap'ы (это R8 Синхронизатор / R11 Наладчик) |
| Формирует отчёт coverage % | Не выносит решение pass/fail (это R26 Приёмщик) |
| Работает в изолированном контексте | Не совмещает создание и аудит в одной сессии без переинициализации |
| Фиксирует факт («документ X отсутствует») | Не оценивает качество («документ X плохой» — это R25 Рецензент) |
| Передаёт отчёт получателю | Не хранит историю аудитов (в MVP — не реализовано, см. §8) |

## 6. Инварианты

1. **Независимость:** Owner Role = заказчик извне аудитуемой системы, никогда = аудитуемая система или её компонент.
2. **Context isolation (VR.SOTA.002):** Аудитор загружает другой контекст, чем создатель аудитуемых артефактов. Нарушение: совмещение создания и аудита в одном окне без переинициализации.
3. **Read-only к аудитуемому:** Единственная запись — отчёт в выделенный output-dir. Аудитуемые файлы не изменяются.
4. **Полнота отчёта:** Отчёт передаётся целиком, включая неудобные gap'ы. Выборочная передача нарушает инвариант.
5. **Факт, не суждение:** Аудитор фиксирует факт присутствия/отсутствия, не качество. Качество → R25.

## 7. Режим отказа

| Отказ | Симптом | Реакция |
|-------|---------|---------|
| Индекс не определён | Запуск без scope | Запросить у заказчика: «Что является целевым множеством?» |
| Целевое множество недоступно | Репозиторий не клонирован | Сообщить: coverage 0%, причина — нет доступа |
| Broken ref в кросс-контексте | Ссылка на несуществующий файл | Отметить в отчёте как gap «broken ref» |
| Нарушение context isolation | Контекст аудитора совпадает с создателем | Остановить, переинициализировать изолированный контекст |
| Owner Role = аудитуемая система | Конфликт интересов | Отказаться от аудита, сообщить заказчику: «нарушен принцип независимости» |

## 8. Известные ограничения MVP

1. **Нет живых audit-report'ов.** `/audit-docs` работает в ручном режиме по запросу Пилота. Автономный запуск VR.R.002 monthly-deep не реализован (WP-217). История отчётов в Neon отсутствует.
2. **Scope задаётся вручную.** Индекс и целевое множество передаются через аргументы скилла, не вычисляются автоматически из MAP.002.
3. **Нет severity-ранжирования.** MVP: все missing — одинаковый вес. Приоритизация gap'ов по критичности — будущая задача.
4. **BC Map VR не формализована.** VR.M.002 (кросс-контекст) требует формальной Context Map домена VR. Ждёт WP-225.
