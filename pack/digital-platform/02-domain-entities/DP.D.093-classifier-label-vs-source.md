# DP.D.093 — Метка классификатора ≠ Источник ошибки

## Суть

В системе с error_classifier log-запись `[category/level] message` содержит две вещи:
1. **Классификация** — что классификатор решил про ошибку (категория, severity).
2. **Источник** — где ошибка возникла (модуль, трейсбек, корневая причина).

Анти-паттерн: читать `[scheduler/L1]` как «ошибка scheduler-модуля». На самом деле классификатор приписал scheduler любую ошибку из контекста маршрута — реальный источник может быть внешний (Anthropic API), процессинг (None-валидация), FSM-состояние.

## Тест

«Может ли это сообщение появиться при разных корневых причинах?» Да → метка ≠ источник.

## Следствие для разбора инцидентов

При разборе залогированных ошибок отделять метку категории от traceback'а. Отсутствие traceback в логе = диагностический blind spot, требующий правила «full log».

## Применимость

- Sentry tags.
- Datadog facets.
- Custom error routers с категоризацией.

## Связь

- DP.M.168 (post-deploy регрессия) — разбор после деплоя требует traceback, не только метки.
