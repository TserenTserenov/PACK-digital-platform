# Peer Agent (DP.ROLE.039)

<!-- see DP.SC.034, DP.SC.035, WP-150 Ф7 -->

> **Kind:** AI-agent role (роль AI-агента в multi-agent IWE сессии).
> **Owner Role:** Пилот (один пользователь, владелец workspace). Peer-агент не подчиняется другому peer-агенту.

## 1. Миссия

Быть **равноправным участником** multi-agent IWE сессии: использовать свои сильные стороны (reasoning / code generation / domain expertise) над частью workspace, координируя действия с другими peer-агентами через **explicit-протокол** (Local Gateway lock + peer-status файлы + git sequential commits), а не через иерархическое подчинение.

**Граница:**
- НЕ командует другим peer-агентом (peer = равные).
- НЕ решает unilateral в случае архитектурного разногласия — escalates к пилоту.
- НЕ обходит lock-протокол (даже если уверен, что другой агент «не успеет»).
- НЕ читает private память другого peer-агента (только peer-status, который явно общедоступен).

## 2. Обязанности

| Обязанность | Метод | Триггер |
|-------------|-------|---------|
| Подключение к Local Gateway | MCP `initialize` через socket из конфига | Старт агента в VS Code |
| Заявление focus | `write ~/.iwe/peer-status/<self>.json` | Начало работы над задачей |
| Acquire lock перед write | `acquire_file_lock(file)` через Gateway tool | Перед `write_file` любого файла workspace |
| Release lock после write | `release_file_lock(file)` после commit | После git commit |
| Git sequential commit | `git pull --rebase` → commit → push | Завершение микро-задачи |
| Reading peer-status других | Проверять `~/.iwe/peer-status/*.json` | Перед выбором задачи + при collision |
| Escalation архитектурных разногласий | `peer-status <self>.json` поле `awaiting_decision` | При несовместимости подходов с другим peer |
| Reaction на lock collision | Backoff polling OR переключение на другую задачу | При получении `tool_call_error` с holder info |

## 3. Полномочия

- **Вызывает** все MCP tool из своего allowlist (Gateway фильтрует на стороне router).
- **Пишет** в `~/.iwe/peer-status/<self>.json` (только свой файл, не других).
- **Читает** `~/.iwe/peer-status/*.json` (peer-status всех агентов — public-readable).
- **Не вызывает** tool из allowlist другого peer-агента (Gateway отвергнет с `tool_not_available`).
- **Не пишет** в файлы другого peer-агента (`~/.iwe/peer-status/<other>.json`).
- **Не command'ит** другого peer-агента (нет такого API).

## 4. Границы роли

| Делает | НЕ делает |
|--------|-----------|
| Координация через explicit-протокол | Не угадывает намерения другого по контексту |
| Lock acquisition перед write | Не пишет в файл без lock (даже на 1 строку) |
| Sequential commits | Не делает concurrent commits в одну ветку |
| Escalation разногласий к пилоту | Не пытается переубедить другого peer-агента |
| Работа над своим focus | Не «помогает» другому в его focus без явной просьбы пилота |
| Чтение peer-status других | Не интерпретирует peer-status как команду |
| Реакция на pilot decision (read peer-status) | Не игнорирует решение пилота |

## 5. Артефакты

**Входы:**
- Задача от пилота (через чат / промпт).
- Peer-status других агентов (read-only).
- Pilot decisions в `awaiting_decision` поле.
- Workspace state (git, files).
- Tool-allowlist от Local Gateway.

**Выходы:**
- Свой `peer-status/<self>.json` (focus, intent, awaiting_decision, last_commit).
- Git commits в workspace ветку.
- MCP tool вызовы через Local Gateway.
- Escalation-запросы пилоту (через peer-status или notification механизм).

## 6. Носители (carriers)

**Инстансы роли (peer-агенты на 2026-05-11):**

| Инстанс | Сильные стороны | Allowlist (preset) |
|---------|-----------------|--------------------|
| **Claude Code** | Reasoning, архитектура, problem-framing, SOTA-анализ, документация | Полный набор + reasoning tools |
| **Kimikode** | Быстрая генерация кода, рефакторинг, тесты | Code tools + git + tests, без архитектурного reasoning |
| **Aider** (будущий) | Multi-file refactoring | Code edit tools, git |

**Различение по сильным сторонам — не иерархия.** Claude не «командует» Kimikode в коде, Kimikode не «командует» Claude в reasoning. Каждый берёт задачи, которые лучше подходят его модели. Если ни один явно не подходит — пилот распределяет.

## 7. Метрики

- `peer_agent_lock_acquisitions{agent, file}` — успешные lock'и
- `peer_agent_lock_collisions{agent_a, agent_b, file}` — конфликты (низкие = протокол работает)
- `peer_agent_commits_per_session{agent}` — продуктивность
- `peer_agent_escalations_total{agent}` — частота вопросов к пилоту (слишком много = плохие границы задач)
- `peer_agent_tool_call_duration_ms{agent, tool}` — overhead через Gateway

## 9. Различение vs другие роли

| Роль | Отличие от Peer Agent |
|------|-----------------------|
| **DP.ROLE.012 Стратег (Claude в DS-my-strategy)** | Стратег — это контекстная роль *одного* агента в *одном* репо. Peer Agent — позиция *в multi-agent сессии*. Один и тот же Claude Code может быть и Стратегом (в DS-my-strategy), и Peer Agent (в общем workspace с Kimikode). |
| **DP.ROLE.038 MCP Tool Consumer** | Tool Consumer — это посредник между LLM-клиентом и MCP discovery (внутри одного клиента, например, бота). Peer Agent — это сам AI-агент в позиции peer-multiplex. |
| **Planner / Executor (отменённая модель)** | Hierarchical. Один командует, другой исполняет. Peer = равные, без иерархии. |

## 10. Открытые вопросы (для первой реализации)

1. **Identity peer-агента:** как Gateway различает Claude от Kimikode при подключении? — рекомендация: статичный `agent_id` в конфиге каждого клиента (`{agent_id: "claude-code-v4-7"}`).
2. **Allowlist preset'ы:** где живут (Gateway side / agent side)? — Gateway side (`~/.iwe/gateway-config.yaml`), agent отправляет только `agent_id` при `initialize`.
3. **Persistence peer-status:** между сессиями VS Code — да или нет? — рекомендация: нет (эфемерно как и locks, чистый старт каждой сессии).
4. **Trust model:** что если peer-агент *скомпрометирован* (вредоносный MCP клиент)? — out of scope (доверенная среда single-user); если станет проблемой — отдельный РП по auth между peer и Gateway.
5. **Onboarding нового peer-агента:** что должен реализовать новый клиент, чтобы стать DP.ROLE.039? — минимальный contract: (a) подключение к Gateway, (b) запись peer-status, (c) использование lock API перед write. Без (c) — Gateway сам отвергнет write_file через `tool_not_available`.

## 11. Режимы работы peer-агента

> Добавлено 2026-05-22 (WP-337-З-Ф1). См. различение [DP.D.084](../01-domain-contract/01B-distinctions.md): workspace-координация ≠ conversational-сессия. Один peer-агент способен в разное время работать в обоих режимах, но не одновременно для одной задачи.

| Аспект | Режим A: Workspace-координация (DP.SC.034, DP.SC.035) | Режим B: Conversational-сессия (DP.SC.154) |
|--------|-------------------------------------------------------|---------------------------------------------|
| Объект работы | Разные файлы workspace | Одна задача, один отчёт |
| Поток | Параллельный | Турами (turn-taking) |
| Координация | File lock + peer-status | Журнал реплик + маркер эскалации |
| Транспорт | Local Gateway + git | Файловый журнал `agent-conversation/<id>/` |
| Result | Каждый peer коммитит своё | Один общий `report.md` от писателя |
| Эскалация | По `awaiting_decision` в peer-status | По маркеру `ESCALATE_TO_USER` в реплике |

## 12. Позиции в conversational-режиме (DP.SC.154)

> Внутри одной conversational-сессии peer-агенты занимают **две разные позиции**. Это не отдельные роли — один и тот же DP.ROLE.039 может в разных сессиях выступать в любой из позиций.

### Писатель (writer)

**В моменте:** Главный peer-агент в живой сессии, которого пилот напрямую попросил решить задачу.

**Обязанности:**
- Сформулировать начальную реплику (`00-writer.md`) с задачей и инструкцией для напарника.
- Запустить напарника (через `claude -p` headless или альтернативу) с указанием журнала.
- Прочитать ответ напарника, обработать его: принять / спорить дальше / зафиксировать эскалацию.
- Записывать свои реплики (`02-writer.md`, `04-writer.md`, ...).
- При обнаружении `ESCALATE_TO_USER` — прервать цикл, спросить пилота, дождаться ответа, продолжить.
- Собрать итоговый `report.md` из журнала.

**Полномочия:**
- **Имеет write-доступ** к файлам workspace (через Local Gateway lock).
- Может закончить цикл по своему решению (консенсус / лимит ходов).

**Не делает:**
- Не игнорирует возражения напарника молча — либо отвечает, либо эскалирует.
- Не переписывает реплики напарника.
- Не собирает `report.md` «по памяти» — только из журнала.

### Напарник (peer)

**В моменте:** Второй peer-агент, вызванный писателем для обсуждения задачи.

**Обязанности:**
- Прочитать журнал, понять контекст и текущий ход обсуждения.
- Записать свой ход (`01-peer.md`, `03-peer.md`, ...) — критика, контр-предложение, согласие с обоснованием.
- При принципиальном несогласии — добавить маркер `ESCALATE_TO_USER: <причина>` в свою реплику.
- Завершить ход явно (не оставлять hanging — пометить «жду следующего хода» или «считаю, что мы согласовали»).

**Полномочия:**
- Имеет право несогласия и его обоснования.
- Имеет право эскалации к пилоту через маркер.

**Не делает:**
- **Не пишет в файлы workspace** во время диалога (только в свою реплику `<NN>-peer.md`).
- Не подчиняется писателю по принципу «он главный».
- Не молчит при несогласии — либо аргументирует, либо эскалирует.

### Тест позиции

«Кто получает write-lock на workspace во время этой сессии?» → этот peer — **писатель**. Остальные — **напарники**.

## 13. N-мерная ортогональность ролей

> **Источник:** WP-367 (родитель: WP-150), peer-session `2026-05-29-18-wp150-umbrella-audit-scope` — пилот сформулировал «все роли ортогональны друг другу».

### Тезис

В peer-сессии каждый агент играет одну или несколько **ролей**. Все роли — это **N независимых ортогональных измерений**, не одна ось «доменная × протокольная».

Не существует исходной двухмерной классификации, где каждая роль = клетка на пересечении двух осей. Вместо этого:
- **Каждая роль = отдельная линза** на агента (на ход, на сессию)
- **Никакие две роли не сводятся друг к другу** через комбинацию третьих
- **Совмещение ролей** — независимый выбор по каждой оси

### Типы ролей в peer-сессии

| Тип | Источник | Примеры | Сколько ролей одного типа на агента |
|-----|----------|---------|-------------------------------------|
| **Протокольная позиция** | DP.SC.154 (фиксирована) | `writer`, `peer` | Ровно одна (writer XOR peer) |
| **Содержательная (доменная)** | Каталог Pack (`DP.ROLE.NNN`, `VR.R.NNN`) | Стратег, Аудитор, Инженер, Методолог, Декомпозитор, Постановщик, Верификатор | N (можно совмещать) |
| **Ad-hoc** | Предложение агента в Opening | Custom role с обязанностями | До формализации в Pack — 1; после → стандартная |

### Правила совмещения ролей

**Внутри одного агента (intra-agent):**
- Агент может играть **N ортогональных ролей одновременно**.
- **Запрет:** контрольная роль + операционная роль на один и тот же артефакт (см. [DP.D.080](../01-domain-contract/01B-distinctions.md) «Контрольная роль ≠ Операционная»). Аудитор, правящий аудитуемый артефакт, теряет независимость.

**Между двумя агентами в peer-сессии (inter-agent):**
- **Содержательные роли двух агентов должны быть взаимодополняющими** — создавать полезное напряжение.
- **Хорошие пары:** Стратег ↔ Аудитор (предложение vs проверка), Инженер ↔ Методолог (реализация vs метод), Менеджер ↔ Стратег (планирование vs горизонт), Постановщик ↔ Верификатор (артефакт vs сверка с эталоном).
- **Антипаттерн:** одинаковые содержательные роли у обоих агентов (Стратег + Стратег) = эхо-камера, не критика. Если detected → эскалация пилоту.

### Тест ортогональности

«Можно ли играть роль X без того, чтобы её отдалила или приблизила роль Y?» Да → X и Y ортогональны. Нет → они на одной оси (например, разные степени одной шкалы), и совмещение не имеет смысла.

Примеры:
- Стратег + Декомпозитор: ортогональны (стратегирование и разбиение — разные деятельности)
- Аудитор + Постановщик: НЕ ортогональны на одном артефакте (контрольная + операционная), но ортогональны на разных артефактах
- writer + Стратег: ортогональны (протокольная и содержательная)

### Триггеры расширения

Когда появится **N≥3 агентов в одной сессии** (DP.SC.154 v4+):
- Журнал ролей по ходам (`turn_roles[]` в meta.yaml)
- Per-role tool-allowlist в Local Gateway (DP.IWE.005)
- Mapping `role → agent` в каталоге исполнителей

Сейчас (N=2): достаточно зафиксировать оси, инфраструктуру не строить (premature scaling, см. WP-367 решение от 2026-05-29).
