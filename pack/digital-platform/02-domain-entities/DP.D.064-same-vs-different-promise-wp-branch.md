# DP.D.064: То же обещание ≠ Другое обещание (scope-дискриминатор при закрытии РП)

При обнаружении смежной работы во время реализации или закрытия РП — критерий выбора между расширением текущего РП (фаза) и созданием нового РП.

| Аспект | То же обещание | Другое обещание |
|--------|----------------|-----------------|
| **Что затронуто** | Исходный Service Clause (или эквивалент) — обещание потребителю | Новое обещание / новый потребитель / новый класс верификации |
| **Решение** | Фаза в текущем РП (даже после `status: done`) | Новый РП, не phase creep |
| **Артефакт** | `Ф{N+1}` в WP-context файле | Новый `WP-NNN-{slug}.md` через `wp-new` |
| **Тест** | «Затронут ли исходный SC?» | «Это другое обещание / другой потребитель?» |

**Тест:** Затронут ли исходный Service Clause (или эквивалент обещания текущего РП)?
- **Да** → фиксы в том же РП как фаза, даже если они «после deploy» и `status` уже был ✅
- **Нет** → отдельный РП, не phase creep

**Пример (WP-320, 16 мая 2026):** один и тот же РП получил фазу «Пост-деплой баги» (tz-mismatch + bot_id isolation — баги исполнения обещания Notification Dispatcher), но Ф4 calendar integration вынесена как новый РП (другое обещание — интеграция календаря, не доставка уведомлений).

**Failure modes без дискриминатора:**

1. **`status: done` при невыполненном DoD** — баг найден после deploy, но РП закрыт. См. `memory/feedback_fixes_as_phases_not_separate_wp.md`.
2. **Phase creep** — смежная область съедает бюджет, РП тянется 7+ фаз без точки закрытия.

**Признак явного дискриминатора в WP-context:** оба решения зафиксированы рядом в одной секции «Осталось», с короткой fail-mode-formulation для каждого.
