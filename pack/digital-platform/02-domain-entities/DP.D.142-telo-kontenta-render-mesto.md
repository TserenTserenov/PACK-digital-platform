# DP.D.142: Тело контента (рендер-в-место) ≠ Уведомление о контенте (сообщение)

| Тело (рендер-в-место) | Уведомление (сообщение) |
|----------------------|-------------------------|
| Артефакт открывается в своём месте | Короткий пинг прилетает в чат |
| Доставка через pull (git-репо, личная страница, `/lesson pull`) | Доставка через push (Telegram-нудж класса `capped`) |
| Полный контент (документ, плейлист, отчёт, персональное руководство) | Триггер открыть контент (CTA: «занятие готово / руководство обновлено») |
| Контракт места рендера | Контракт очереди сообщений |
| Размер не ограничен политикой Доставщика | Учитывается потолком «≤N/день» |

**Почему важно**: Гнать тело руководства через очередь сообщений = спутать рендер-в-место с транспортом сообщений. Поверхности разные: место рендера хранит и отдаёт по запросу; очередь сообщений доставляет push-импульс. Раздельные SLA, разные failure modes, разные политики приватности.

**Тест**: «человек получает это, открыв сам (pull/страница), или ему прилетает в чат (push)?» Тело — открывает сам; уведомление — прилетает.

**Применение**: при проектировании доставки любого крупного артефакта (документ, отчёт, плейлист, персональное руководство) — отделить тело (рендер-в-место) от уведомления (сообщение). Долг (WP-418 Ф4): мёртвый push-путь тела (`engines/tailor/delivery.py:notify_tailor_lesson`, `BotTailorAdapter` — ноль живых вызовов после WP-301) вычистить или явно переподтвердить git-канал в Pack.
