# DP.D.069: Артефакт-режим ≠ артефакт

## Различение

- **Артефакт** — то, что РП производит как результат (Оркестратор, Notification Dispatcher, Agent Inbox). Уникален по обещанию.
- **Режим артефакта** — канал доставки, latency budget, контекст исполнения (batch ночью / real-time через MCP, sync API / async очередь, foreground / background). Один артефакт может работать в N режимах.

## Тест

**«Если убрать слово-модификатор режима из имени РП, теряется ли уникальность артефакта?»**

- **Нет** → это режим. Открыть фазу в существующем РП артефакта.
- **Да** → разные артефакты с разными обещаниями. Открыть отдельные РП.

## Пример (WP-324, май 2026)

Соблазн: «Оркестратор уже работает в ночном пакете (batch). Real-time Оркестратор через MCP — обещание другое, latency другая → новый РП "Real-time Оркестратор".»

Проверка тестом: убираем «real-time» → остаётся «Оркестратор». Уникальность не теряется (артефакт тот же — компонент, принимающий решение о следующем шаге). Обещание тоже одно (принять решение); различаются только канал доставки и latency.

Решение: НЕ новый РП. Активировать отложенную фазу WP-203 Ф3 «Inference pipeline — latency оркестрации» + добавить Ф6 «MCP-канал».

## Анти-паттерн

«Каждый канал доставки артефакта = отдельный РП» → реестр инфлируется, scope размывается, owner один и тот же грузится двумя сессиями.

## Различение с DP.D.064

- **DP.D.064** (same-vs-different-promise-wp-branch) — общий дискриминатор «когда фаза vs новый РП». Применяется ко всем случаям.
- **DP.D.069** — частный случай DP.D.064 для пар «batch / real-time», «sync / async», «foreground / background». Даёт быстрый тест-on-name без полного анализа обещаний.

DP.D.069 ⊂ DP.D.064 (специализация).

## Применимость

- Notification Dispatcher (real-time vs scheduled) — один артефакт, два канала.
- Agent Inbox (CCR-execution vs human-execution) — один артефакт, два исполнителя.
- Любые системы с multiple consumers одного артефакта.
- Скрипты IWE с поддержкой `--dry-run` и `--apply` — один скрипт, два режима, не два скрипта.
