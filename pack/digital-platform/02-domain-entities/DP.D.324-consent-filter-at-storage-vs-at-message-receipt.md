# DP.D.324 — Фильтр согласия на хранение ≠ фильтр на получение сообщения платформой

## Различение

| | Фильтр на уровне логирования/хранения | Фильтр на уровне получения |
|---|---|---|
| **Что контролирует** | Пишется ли сообщение в БД/лог платформы | Доходит ли сообщение до процесса бота вообще |
| **Технически достижимо?** | Да — код бота может не вызвать запись/лог | Нет — Telegram Bot API доставляет апдейт процессу бота независимо от прикладного статуса согласия |
| **Что значит «отозвать согласие»** | Прекратить запись новых сообщений участника | Не может значить «бот перестаёт получать сообщения» — это не в руках прикладного кода |

## Механизм

При проектировании хранилища переписки наставник-участник (WP-578 Ф0) пир-сессия уточнила по критике напарника: согласие участника — прикладной гейт, решающий, писать ли сообщение в `learning`-схему и в лог. Но сам факт получения сообщения ботом — свойство транспорта (Telegram Bot API доставляет апдейт в процесс подписанного бота), и прикладной код не может на это повлиять никаким статусом согласия. Смешение этих двух уровней приводит к архитектурно недостижимому обещанию: «отозванное согласие останавливает получение данных ботом».

## Тест различения

«Может ли отзыв согласия физически помешать процессу бота получить сообщение от платформы, или он может только остановить запись/лог уже полученного сообщения?» Только запись/лог → фильтр относится к границе персистентности, не к границе получения; формулировки вида «данные не поступают боту при отсутствии согласия» для этого канала некорректны.

## Границы

Применимо к интеграциям через управляемые сообщенческие платформы (Telegram Bot API и аналоги), где доставка апдейта процессу-подписчику — свойство транспортного уровня, не приложения. Не применимо там, где сам прикладной код контролирует транспорт (например, собственный сервер приёма вебхуков с возможностью выборочного игнорирования до разбора).
