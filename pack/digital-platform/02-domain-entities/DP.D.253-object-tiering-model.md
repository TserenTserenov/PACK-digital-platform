# DP.D.253 — Модель тиров объектов IWE (платформенное / командное / личное)

> **Не путать с DP.ARCH.002 «Тиры платформы» (T0-T4).** Общее слово «тир», разные оси. DP.ARCH.002 классифицирует, что́ получает **пользователь платформы** по мере оснащения (подписка, доступ к ЦД, роль ИИ). Этот документ классифицирует **объекты самой платформы** (код, паки, скиллы, сервисы) по тому, **с кем они разделяются** (все пользователи / команда разработки / один участник) — ось про распространение артефактов и сервисов внутри системы создания, а не про доступ конечного пользователя. Тест: «речь о том, что получает учащийся на своём пути (T0-T4) — или о том, кому принадлежит/куда доставляется код и сервис самой платформы?»

## 0. Главное за 30 секунд

- Объекты делятся на два **рода**: **доставляемый артефакт** (копируется в каждую установку — пак, скилл, база стиля, правило) и **работающий сервис** (один инстанс, к нему подключаются — бот, MCP-сервер, шлюз).
- **Артефакт** имеет тир: **платформенный** (всем пользователям IWE), **командный** (нашей команде разработки), **личный** (одному участнику). У командных есть пометка трека (А/В).
- **Сервис** описывается тройкой: дом/трек (Мир/Россия/канон/личное) × поколение архитектуры (старая/новая) × тенантность (один общий инстанс / на пользователя).
- Тир задаётся **обещанием** (кому объект адресован), а не тем, где файл лежит сейчас. Разрыв «обещан платформе, фактически у команды» допустим только под оформленную задачу промоции со сроком.
- Три оси не путать: **тир** (кто разделяет) ≠ **дом/трек** (география назначения — Мир/Россия) ≠ **поколение** (старая архитектура / новая). Трек А = Россия, Трек В = Мир — это география, не «старое/новое»; оба трека идут на новую архитектуру.

## 1. Два рода объектов: артефакт и сервис

Главное различение, без которого классификация ломается на ботах и MCP-серверах.

- **Доставляемый артефакт** копируется/доставляется в каждую установку: паки, скиллы, базы стиля, правила, хуки, протоколы. Вопрос к нему: «кому этот объект доставляется?» → тир совместности.
- **Сервис** — это один работающий инстанс, к которому подключаются много пользователей: боты, MCP-серверы, воркеры, шлюз. Вопрос к нему: «где он работает (страна/инфра), на какой архитектуре, где граница пользователей на одном инстансе?» → дом/трек × поколение × тенантность.

**Почему это нужно.** В каталоге бот марафона помечен «платформенный · российский · трек А» — платформенный, но трек-специфичный. Для артефакта это противоречие (платформенное = для всех = оба трека). Для сервиса противоречия нет: бот — один мультитенантный инстанс в российском доме, обслуживает трек А. «Платформенность» сервиса = «общий инстанс на многих», а не «копия у каждого».

**Смешанный репозиторий** (код сервиса + его документация-артефакт в одном git-хранилище) инвентаризуется построчно: код = строка-сервис, документация = строка-артефакт. Инвентаризуем объекты, не хранилища-монолиты.

## 2. Тир доставляемого артефакта

| Тир | Кто разделяет | Канал доставки | Примеры |
|-----|---------------|----------------|---------|
| **платформенный** | все пользователи IWE везде | шаблон движка (FMT) → update.sh | базы стиля L0, базовые скиллы, протоколы ОРЗ, FPF/SPF/ZP, базовые хуки, formatting.md |
| **командный** | команда разработки платформы (треки А + В) | командные репо (governance, паки) | канонический набор паков, граф понятий (артефакт), SYNC-CORE, реестр репо |
| **личный** | один участник | остаётся локально, не доставляется | персональное руководство, авторские надстройки L1/L3, персона, память, личный governance-хаб |

**Правило отнесения (тест):** «Получит ли новый внешний пользователь IWE этот объект через update.sh без доп. настройки?» Да → платформенный. «Нужна ли для него командная экосистема разработки (набор паков, мультиагент)?» Да → командный. «Уникально для одного человека?» → личный.

**Обещанный тир ≠ фактический.** Тир = кому объект **адресован** (суть), а не где файл лежит сейчас. Поэтому у артефакта два поля:
- `target_tier` — кому адресован (стабильно).
- `current_tier` — где фактически доставлен.
- **Разрыв** (`target` ≠ `current`) легитимен ТОЛЬКО при оформленной задаче промоции: есть рабочий продукт/фаза + владелец + критерии приёмки + срок ≤ 2 контрольных точки. Иначе `current_tier` = факт, и «обещание платформе» не засчитывается. Это не даёт объектам годами висеть «как бы платформенными».

## 3. Классификация сервиса

Сервис не «доставляется» — к нему подключаются. Три измерения:

- **Дом / трек:** мировой (Мир, трек В) / российский (Россия, трек А) / канон-IWE / личный. Трек — это география назначения, см. §5.
- **Поколение архитектуры:** старая (legacy) / новая (IWE). Цель миграции — всё на новую.
- **Тенантность:** один общий инстанс на всех (multi-tenant) / инстанс на пользователя (per-user) / одиночный.

## 4. Три оси — не путать

- **Тир (кто разделяет):** платформа / команда / участник — только для артефактов.
- **Дом / трек (география назначения):** мировой (трек В) / российский (трек А) / канон / личный. Трек А/В — это значения этой одной оси, а не отдельная ось: трек = страна назначения и её инфраструктура.
- **Поколение архитектуры (ось миграции):** старая (legacy) / новая (IWE). Текущая работа = переход старая→новая; цель — оба трека на новой архитектуре.

Плюс колонка **владелец** как метаданные, не ось.

## 5. Треки А и В — это география, и обе ветки на новой архитектуре

**Трек = страна назначения, не поколение продукта.**

- **Трек А = Россия.** Российская инфраструктура, рубли. Держит существующих подписчиков на старой платформе и одновременно переходит на новую архитектуру.
- **Трек В = Мир.** Мировая инфраструктура (Google Kubernetes + европейский вход). Сразу на новой архитектуре.

**Старое vs новое — ОТДЕЛЬНАЯ ось (поколение архитектуры).** Переход со старой архитектуры (legacy: вход через прежнюю платформу, состояние в боте, расписания cron) на новую (IWE: Ory, Персона, выводимая память, шлюз знаний, проекционные воркеры). **Цель — оба трека на новой архитектуре.**

## 6. Как разработчик работает в команде — по ролям

- **Разработчик пака.** Пишет доменный пак = **командный артефакт** (канон, оба трека). Базовые принципы (FPF/SPF/ZP) приходят как **платформенный артефакт** через update.sh.
- **Разработчик графа понятий.** Правит **командный артефакт** (граф = канон). Доступ к графу для всех — через сервис умного поиска (**платформенный сервис**, мультитенант). Артефакт и сервис-доступ — два объекта.
- **Разработчик кода/сервиса.** Строит **сервис**: классифицирует по дом/трек × поколение × тенантность. Секреты деплоя — отдельно, не в коде.
- **Личная сборка любого участника.** Свои надстройки стиля (L1), личные скиллы (L3), персона, память, личный хаб = **личный тир**, остаётся локально, не реплицируется другим.

## 7. Как объект разлетается по местам и языкам

Только артефакты «разлетаются»; сервисы стоят на месте, к ним подключаются.

Один канонический артефакт расходится по трём осям проекции:
1. **Язык** — граф понятий собирает английскую версию рядом с русской.
2. **Регистр и аудитория** — база стилей собирает версии под аудиторию.
3. **Площадка** — витрины (мировой дом) тянут английскую версию; российский дом тянет русскую + российскую надстройку.

Тир при этом сохраняется: платформенный артефакт остаётся платформенным во всех проекциях; меняется только дом и язык конкретной проекции.

## 8. Механизм (что делать с моделью на практике)

1. **Поле `audience: platform | team | participant`** в метаданные артефактов (обобщает `layer: L1/L3` у скиллов) — классификация, не новый слой в архитектуре инструкций.
2. **Командный канал доставки** — командные репо. Платформа → шаблон/update.sh; команда → командные репо; участник → локально.
3. **Реестр разрывов доставки** — список объектов `target≠current` с задачей промоции, владельцем, сроком. Без задачи объект числится по факту.
4. Сервисы инвентаризовать отдельным реестром (дом/трек × поколение × тенантность), не смешивая с артефактами.

## 9. Открытые вопросы

- Реализация поля `audience` и реестра разрывов доставки — отдельная задача (инструмент + миграция метаданных), не начата на момент промоции в Pack.
- Конфликт двух нумераций L0-L3 (инструкции агента vs базы стиля) — найден при формулировке модели, решение нумерации за пилотом, не входит в эту модель.
