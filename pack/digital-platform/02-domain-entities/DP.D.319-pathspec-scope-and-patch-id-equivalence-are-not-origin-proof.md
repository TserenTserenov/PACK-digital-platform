# DP.D.319 — Pathspec и patch-id не доказывают происхождение и идентичность содержимого

## Различение

| Инструмент | Что доказывает | Что НЕ доказывает |
|---|---|---|
| `git commit -- <pathspec>` | Какие пути попадут в коммит | Откуда взялось изменение в этих путях — правка может молча принадлежать другому автору/процессу |
| `git patch-id` / `git cherry -v` | Эквивалентность патча (нормализованный дифф совпадает) | Идентичность происхождения или побайтовое содержимое — разные патчи могут иметь общий patch-id при разной судьбе |

## Механизм

Git фиксирует текущее СОСТОЯНИЕ файла в коммите независимо от того, кто и когда его изменил — pathspec ограничивает МНОЖЕСТВО путей, но не проверяет, что изменение внутри них принадлежит текущему автору коммита. В общем чекауте с параллельными агентами чужая правка в том же файле может попасть в коммит молча, если она физически присутствует в рабочем дереве на момент `git commit -- <pathspec>`.

`patch-id` хеширует нормализованный дифф — полезно для распознавания «этот патч уже применён в другом месте» (см. `DP.M.439`), но эквивалентность патча — это НЕ то же самое, что идентичность содержимого или происхождения. Блокирующий гейт «оба чекаута чистые перед синком» не закрывает окно гонки между `git status` и `git commit` (секунды) — момент проверки и момент фиксации разнесены во времени.

## Границы

Различение не говорит, что pathspec/patch-id бесполезны — оба остаются правильным первым инструментом (ограничение объёма коммита; быстрое распознавание уже перенесённых патчей между ветками, `DP.M.439`). Проблема — в том, чтобы не принимать их как ДОСТАТОЧНОЕ доказательство происхождения/идентичности там, где это критично (общий чекаут, параллельные агенты, решение «это дубль — можно не пушить»).

## Проверка

До коммита с explicit pathspec — зафиксировать ожидаемое состояние затрагиваемых путей. После коммита — сверить `git diff --cached -- <pathspec>` (или `HEAD^..HEAD`) на примесь чужого содержимого; при расхождении — не пушить, откатить, эскалировать. Для признания коммита «дублем» перед rebase — safety-ветка + именованный stash (с untracked) в обоих репозиториях, и побайтовое сравнение с уже запушенным блобом, не только совпадение `patch-id`.
