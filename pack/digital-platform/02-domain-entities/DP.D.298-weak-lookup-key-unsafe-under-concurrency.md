# DP.D.298 Позиционный/эвристический ключ небезопасен при параллельной записи

## Правило

Lookup-key, идентифицирующий целевое состояние по позиции (порядковый номер) или по эвристике (тот же владелец, но не тот же слаг), а не по точному/контент-адресуемому идентификатору, даёт систематический риск при параллелизме: слияние по такому ключу выбирает «последнего/ближайшего», а не «правильного».

## Проявление 1 — конфликт публикации общего документа (merge-семантика)

Два параллельных агента заняли один порядковый номер фазы в общем документе — конфликт-резолвер публикации отбросил содержимое одной стороны вместо трёхстороннего слияния. Потеря невидима локально (рабочее дерево автора всё ещё показывает его содержимое) и всплывает только при сверке опубликованного состояния с origin постфактум.
**Фикс:** контент-адресуемый/уникальный идентификатор для новых разделов, либо гарантия настоящего трёхстороннего слияния (не last-writer-wins) на пути публикации; сверять с origin после любой публикации, где был конфликт.

## Проявление 2 — fallback-поиск по родственному, не идентичному ключу (порядок веток)

Fallback-поиск терминальности сессии по ВЛАДЕЛЬЦУ (не по точному слагу) маскировал СОБСТВЕННУЮ отменённую карточку того же слага более старой завершённой карточкой того же владельца.
**Фикс:** fallback-путь по родственному, но не идентичному ключу обязан быть строго уже основного пути — срабатывать только когда основной путь по точному ключу гарантированно пуст, и располагаться в коде ПОСЛЕ всех веток, которые могут дать самодостаточный ответ по точному ключу.

## Тест

«Ключ, по которому ищется/сливается состояние, — точный/уникальный идентификатор или позиция/эвристика (номер по порядку, тот же владелец)?» Позиция/эвристика при параллельном доступе → риск слияния не туда или подмены состояния более широким/старым совпадением.

## Применимо к

Любая система с параллельной записью в общий документ/состояние по позиционному или эвристическому ключу — не только git-публикация и session-guard.

## Дополнение 2026-09-21 (РП-170)

### Проявление 3 — резолвер для чужого сценария применён там, где точный ключ уже был известен

Чтение записи о пропуске рефлексии (close-intent) шло только через многоисточниковый резолвер сессии (run_map → owner → семафор), спроектированный для ДРУГОЙ задачи — поиска файла, который пишет ВНЕШНИЙ процесс. Резолвер «уверенно», но неверно вернул чужой/устаревший идентификатор. Запись лежала под точным, буквально известным ключом текущего процесса (значение его переменной окружения), но эта прямая проверка не была опробована первой — сработало умолчание «ответ пилота ещё нужен».
**Фикс:** для записи, которую пишет мой же процесс, — сначала точный известный ключ; резолвер только как fallback там, где точного ключа действительно нет. Рецидив трёх прошлых починок (02.09, 14.09, 17.09), чинивших regex-детектор фразы, а не сам путь чтения: симптом принимали за причину три раза подряд.

### Диагностический критерий — когда точный ключ заведомо доступен

«Свой процесс знает буквальный ключ, внешний — нет.» Запись пишет мой же процесс (в его окружении есть буквально то значение, что использовалось при записи, например переменная окружения) → точный ключ известен без резолвинга: пробовать его первым, резолвер — фолбэк. Запись пишет ВНЕШНИЙ процесс (другая сессия, раннер, независимый агент) → точный ключ читателю заведомо неизвестен, резолвер остаётся единственным путём, а не запасным.
Отвергнуты при разборе: писать под уже резолвленным (не буквальным) идентификатором — переносит неопределённость на работающий write-путь; читать по обоим ключам, но резолвер раньше точного — тот же риск ложного «уверенного» совпадения; писать в оба ключа сразу — умножает места записи одного факта.

### Что значит «certain» у многоисточникового резолвера

«certain» означает однозначность внутри выбранного источника, а не совпадение с ключом, под которым запись реально сделана. Если run_map недоступен для конкретного run_id, render.sh уходит на источник 2 (owner, certain), а append.sh — сразу на источник 3 (semaphore, certain); они могут разойтись в разные значения, оба валидно certain по своей локальной логике. Проверка `confidence == certain` как условие «результату можно доверять» ложно успокаивает: уверенность — свойство ветки резолвера, не свойство отношения «результат ↔ запись».
Следствие для дизайна: где есть точный ключ, статус уверенности не нужен вовсе; где его нет, «certain» читать как «источник N однозначен», а не «это та самая запись». Смежно: `DP.M.417` (единый resolver — лечение асимметрии), `DP.D.318` (наблюдение ≠ доказательство; другой предмет).
