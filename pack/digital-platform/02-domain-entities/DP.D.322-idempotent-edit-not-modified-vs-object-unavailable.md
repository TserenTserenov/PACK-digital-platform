# DP.D.322 — Отказ на идемпотентном редактировании («не изменено») ≠ объект недоступен

## Различение

| | Идемпотентное редактирование отклонено («не изменено») | Редактируемый объект недоступен |
|---|---|---|
| **Что отвечает сервер** | Не-2xx с явным признаком «состояние уже равно запрошенному» (Telegram: HTTP 400 `message is not modified`) | Не-2xx с признаком отсутствия цели или доступа (`message to edit not found`, chat not found, 403) |
| **Истинное состояние у получателя** | Цель достигнута: у получателя ровно тот текст/состояние, которое мы хотели | Цель не достигнута: объекта нет или он нам недоступен |
| **Правильная реакция** | Успешный no-op: зафиксировать состояние, выйти с кодом 0, ничего не пересоздавать | Пересоздать объект (или эскалировать), обновить сохранённый идентификатор |
| **Ошибка при смешении** | Пересоздание на каждом тике → флуд дублями от самого антифлуд-механизма | Трактовать как no-op → счётчик молча перестаёт обновляться у получателя |

**Почему важно:** оба ответа — «не-2xx», и код, различающий только «успех/не успех», обязан выбрать одну реакцию на оба. Любой выбор ломает один из двух штатных случаев: либо флуд пересозданий, либо молчаливо замёрзший объект. Для стоячих (редко меняющихся) объектов отказ «не изменено» — не редкий edge-case, а самый частый ответ.

## Механизм

Стоячий счётчик простаивает бо́льшую часть времени: текст тика не меняется, значит `editMessageText` тем же текстом отклоняется каждым тиком. Прежний код любой не-2xx на редактирование трактовал как «сообщение исчезло у получателя» и заново создавал и закреплял сообщение — 14 дублей за 8 минут, пока не поймали. Фикс детектирует именно эту фразу в теле ошибки и трактует её как успешный no-op (запись состояния, exit 0). Важно, что детект точечный — по документированной фразе/коду, а не «любой 400»: иначе симметрично сломается второй столбец (реально удалённое сообщение будет считаться «не изменённым», и счётчик замрёт).

## Тест различения

«Ответ не-2xx означает, что целевое состояние объекта УЖЕ совпадает с запрошенным?» Да → успешный no-op, состояние фиксируется, пересоздание запрещено. Нет → отдельная ветка (пересоздание/эскалация). Проверка признака — по документированному коду или фразе конкретного API, никогда по классу «любой не-2xx» или «любой 400».

## Границы

Применимо к любому внешнему API, которое отвергает приведение объекта к уже имеющемуся состоянию вместо того, чтобы принять его идемпотентно (Telegram Bot API `editMessageText`/`editMessageCaption`/`editMessageReplyMarkup` — основной прецедент). Не распространяется на API, где повторная запись того же значения возвращает 2xx: там различение не нужно. Не заменяет DP.D.107 (подтверждение обработчика ≠ подтверждение побочного эффекта): здесь вопрос «что означает отказ», там — «что означает успех».
