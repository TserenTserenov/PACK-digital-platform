# DP.D.302 Путь в NFC-форме ≠ путь в NFD-форме

| Аспект | NFC (composed) | NFD (decomposed) |
|--------|-----------------|-------------------|
| Кто обычно выдаёт | Аргумент командной строки, большинство внешних инструментов | Файловая система macOS (нормализует Unicode-имена при хранении) |
| Байтовое представление | Один code point на визуальный символ (напр. «é» = U+00E9) | База + комбинирующий диакритик (напр. «é» = U+0065 U+0301) |
| Видимость проблемы | Имя выглядит идентично в обоих случаях — разница не видна глазом | — |

## Правило

macOS файловая система нормализует Unicode-имена файлов в форму разложения (NFD), тогда как git и большинство инструментов на входе обычно оперируют формой композиции (NFC) — визуально идентичное имя файла может прийти в двух разных байтовых представлениях в зависимости от того, откуда взята строка (аргумент командной строки vs вывод `git diff --name-only`).

## Тест

Сравниваются ли два пути побайтово (строковое равенство) без явной нормализации? Если да и хотя бы один путь может содержать не-ASCII символы — на macOS это ненадёжно: возможны как ложное несовпадение (один файл считан за два разных пути), так и ложное совпадение защиты, пропускающей путь мимо проверки.

## Применимо к

Любое сравнение путей с не-ASCII именами на macOS (или между macOS и Linux/git-объектами), особенно в security/scope-проверках, сравнивающих «путь из pathspec» с «путь из списка изменённых файлов»: сравнивать после явной нормализации в одну форму (обычно NFC), не полагаться на побайтовое равенство строк.
