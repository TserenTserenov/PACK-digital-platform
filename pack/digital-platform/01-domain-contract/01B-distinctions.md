# Core Distinctions: ИТ-платформа и цифровой двойник

## Обязательные различения

### DP.D.001: Объект ≠ Модель

| Объект (реальный) | Модель |
|-------------------|--------|
| Созидатель как человек | Формализованное описание |
| Существует независимо | Создаётся намеренно |
| Меняется непрерывно | Дискретное обновление |
| Бесконечная сложность | Конечное упрощение |

**Почему важно**: Модель — всегда упрощение. Нельзя путать модель с реальностью.

---

### DP.D.002: Модель ≠ Данные

| Модель | Данные |
|--------|--------|
| Структура | Значения |
| «Что измеряем» | «Сколько» |
| Версионируется | Накапливаются |
| Меняется редко | Меняются постоянно |

**Почему важно**: Изменение модели и изменение данных — разные операции с разными последствиями.

---

### DP.D.003: Данные ≠ Представление (view)

| Данные | Представление |
|--------|---------------|
| Внутренние значения | Внешний вид |
| Одни данные | Много представлений |
| Структурированы по модели | Структурированы под задачу |
| Для вычислений | Для восприятия |

**Почему важно**: Одни и те же данные могут быть представлены по-разному для разных целей.

---

### DP.D.004: Индикатор ≠ Факт

| Индикатор | Факт |
|-----------|------|
| Измеряемый показатель | То, что есть |
| Может быть неточным | Реальность |
| Зависит от метода измерения | Не зависит |
| Часть модели | Вне модели |

**Почему важно**: Индикатор указывает на факт, но не является фактом. Погрешность измерения неизбежна.

---

### DP.D.005: Входной индикатор ≠ Производный индикатор

| Входной индикатор | Производный индикатор |
|-------------------|----------------------|
| От пользователя | Вычисляется системой |
| Субъективен | Детерминирован (при тех же входах) |
| Может содержать ошибки ввода | Зависит от формулы |
| Первичен | Вторичен |

**Почему важно**: Ошибка во входном индикаторе распространяется на производные.

---

### DP.D.006: Генеративный текст ≠ Source-of-truth

| Генеративный текст | Source-of-truth |
|--------------------|-----------------|
| Создаётся ИИ | Зафиксировано в pack |
| Интерпретация | Определение |
| Может содержать галлюцинации | Проверено |
| Вспомогательный | Нормативный |

**Почему важно**: ИИ-сгенерированные интерпретации данных — не истина, а помощь в осмыслении.

---

### DP.D.007: Качество модели ≠ Качество данных

| Качество модели | Качество данных |
|-----------------|-----------------|
| Полнота охвата | Точность значений |
| Корректность связей | Актуальность |
| Валидность структуры | Согласованность |

**Почему важно**: Хорошая модель с плохими данными бесполезна. Хорошие данные в плохой модели — тоже.

---

### DP.D.008: Синхронизация ≠ Копирование

| Синхронизация | Копирование |
|---------------|-------------|
| Двусторонняя связь | Однократная операция |
| Отслеживание изменений | Снимок |
| Поддержание актуальности | Фиксация момента |

**Почему важно**: Цифровой двойник требует синхронизации, а не разовых копий.

---

### DP.D.009: ИИ-агент ≠ ИИ-ассистент (режимы одной системы, не разные типы)

| ИИ-агент | ИИ-ассистент |
|----------|-------------|
| Ориентация на систему | Ориентация на человека |
| Автономная инициатива | По запросу пользователя |
| Программный интерфейс (API, MCP) | Диалоговый интерфейс |
| Выполняет функцию | Ведёт диалог |

**Почему важно**: Агент и ассистент — это **виды** ИИ-системы, а не разные архитектурные слои. Вид определяется классификационными признаками (ориентация, инициатива, интерфейс). Одна и та же ИИ-система может работать в обоих режимах в зависимости от сценария.

**Тест**: Можно ли описать компонент, изменив только интерфейс (диалоговый ↔ программный), сохранив логику? Да → это одна ИИ-система, способная работать как агент и как ассистент.

---

### DP.D.010: Архитектурная характеристика ≠ Архитектурный принцип

| Характеристика | Принцип |
|----------------|---------|
| Измеряемое качество | Правило проектирования |
| Отвечает на «насколько хорошо?» | Отвечает на «как строить?» |
| Эволюционируемость, масштабируемость, скорость | Модульность, слабая связанность |
| Можно оценить числом/шкалой | Можно только соблюдать или нарушать |

**Почему важно**: Принцип — инструмент для достижения характеристики. Нельзя подменять цель (характеристика) средством (принцип).

**Объект оценки — всегда система, никогда принцип.** Цепочка: Принципы ограничивают проектирование → проектирование порождает систему → система обладает измеряемыми характеристиками → оцениваем характеристики системы. Принцип бинарен (соблюдает / нарушает). Характеристика скалярна (качество системы по шкале). АрхГейт (DP.M.005) оценивает систему по характеристикам, а не принципы напрямую.

**Тест 1**: Можно ли сказать «платформа масштабируема на 85%»? Да → характеристика. «Платформа модульна на 85%» — бессмысленно → принцип.
**Тест 2**: Оценил числом? → характеристика (скалярная, свойство системы). Проверил «соблюдается / нарушается»? → принцип (бинарный, ограничение проектирования).

---

### DP.D.011: Platform-space ≠ User-space

| Platform-space | User-space |
|----------------|------------|
| Общее для всех пользователей | Уникальное для конкретного пользователя |
| Модули CLAUDE.md, шаблоны, правила скилов | Список РП, репо, captures, предпочтения |
| Обновляется разработчиками платформы | Обновляется пользователем и его ИИ-системами |
| Одинаковое поведение у всех | Персонализированное поведение (→ [DP.CONCEPT.003](../02-domain-entities/DP.CONCEPT.003-adaptive-personalization.md)) |

**Почему важно**: Отчуждаемость платформы требует чёткого разделения. Всё, что в platform-space, работает для любого пользователя. Всё, что в user-space, принадлежит только ему.

**Тест**: Изменится ли это, если платформу подключит другой человек? Да → user-space. Нет → platform-space.

---

### DP.D.012: Знание ≠ Информация

| Знание (knowledge) | Информация (information) |
|---------------------|--------------------------|
| Формализовано (ID, frontmatter, структура) | Сырое, неклассифицированное |
| Размещено в Pack | Размещено в inbox, заметках, переписках |
| Прошло экстракцию и валидацию | Не обработано |
| Source-of-truth | Источник для экстракции |

**Почему важно**: Размещение неформализованной информации в Pack разрушает его статус source-of-truth. Информация должна пройти экстракцию прежде чем стать знанием.

**Тест**: Есть ли у записи ID, frontmatter, и она размещена в Pack-директории по правилам SPF? Да → знание. Нет → информация.

---

### DP.D.013: Навигация ≠ Поиск

| Навигация | Поиск |
|-----------|-------|
| Структурный обход по связям | Контентный поиск по тексту |
| Знает структуру репо и связи | Не знает структуру |
| Карты, индексы, кросс-ссылки | Grep, embeddings, семантика |
| Отвечает «где это в системе?» | Отвечает «где это упоминается?» |

**Почему важно**: Навигация показывает место знания в структуре. Поиск находит фрагменты текста. Для работы со знанием нужны оба, но они дополняют друг друга, а не заменяют.

**Тест**: Нужно ли понимать структуру репозиториев для получения результата? Да → навигация. Нет → поиск.

---

### DP.D.014: Оперативная память ≠ Справочник

| Оперативная память (Memory) | Справочник (Reference) |
|-----------------------------|------------------------|
| Меняется по правилам (weekly, on-close) | Стабильное знание |
| Текущие РП, статусы, ссылки | Различения, FPF, правила типов |
| Минимальный объём (≤100 строк) | Любой объём |
| Всегда в контексте | Читается по необходимости |
| Рабочий стол | Библиотека |

**Почему важно**: Перегрузка оперативной памяти снижает эффективность ИИ-ассистента. Справочные знания, нужные раз в 10 сессий, не должны занимать место рядом с блокирующими правилами каждой сессии.

**Тест**: Меняется ли содержимое регулярно по триггерам (weekly/on-close/on-change)? Да → оперативная память. Нет → справочник.

---

### DP.D.015: ИИ-система ≠ ИТ-система

| ИИ-система | ИТ-система |
|------------|------------|
| LLM-зависимая (инференс) | Детерминированная (без LLM) |
| Stateless | Stateful |
| Может галлюцинировать | Предсказуемый результат |
| Слой 3 архитектуры | Слой 2 архитектуры |
| Стратег, Проводник, ДЗ-чекер | CRM, LMS, Биллинг, MCP-серверы |

**Почему важно**: ИИ-системы и ИТ-системы — виды **систем платформы**, но с принципиально разными режимами проектирования, тестирования и мониторинга. Смешение → failure mode DP.FM.002.

**Зонтичный термин**: Когда нужно говорить про оба вида вместе — **система платформы**.

**Тест**: Зависит ли компонент от инференса LLM для выполнения основной функции? Да → ИИ-система (Слой 3). Нет → ИТ-система (Слой 2).

---

### DP.D.016: Capture-to-Pack ≠ Knowledge Extraction

| Capture-to-Pack | Knowledge Extraction |
|-----------------|---------------------|
| Примитив: «заметил → анонсировал → отложил/записал» | Полный pipeline: detect → classify → route → formalize → validate |
| Выполняется человеком или ИИ-ассистентом по ходу работы | Выполняется Knowledge Extractor (AISYS.013) |
| Вход: наблюдение в сессии | Вход: capture, документ, Pack-diff |
| Выход: анонс «Capture: X → Y» | Выход: формализованный файл в Pack с frontmatter и ID |
| Не требует проверки противоречий | Обязательна проверка противоречий |
| Часть протокола Work (CLAUDE.md § 2) | Часть протокола Close + отдельные сценарии |

**Почему важно**: Capture — это обнаружение кандидата на знание. Extraction — это превращение кандидата в формализованное знание. Без Capture нечего экстрагировать. Без Extraction capture остаётся заметкой.

**Тест**: Есть ли у результата ID, frontmatter, проверка противоречий и размещение в Pack? Да → Knowledge Extraction. Нет → Capture-to-Pack.

---

### DP.D.017: Стратегический DDD ≠ Тактический DDD

| Стратегический DDD | Тактический DDD |
|-------------------|----------------|
| Bounded Context, Context Map, UL | Entity, Value Object, Aggregate, Repository |
| Универсален (любой стек, любая архитектура) | ООП-специфика (Java Enterprise, C#) |
| О границах ответственности и языке | О паттернах кода внутри модуля |
| SOTA (2026, подтверждён Khononov) | Часто карго-культ за пределами ООП |

**Почему важно**: Стратегический DDD — метод, тактический — набор ООП-паттернов. Применение тактического DDD без стратегического = реализация паттернов без понимания домена.

**Тест**: Можно ли применить этот паттерн DDD без ООП-языка? Да → стратегический. Нет → тактический.

### DP.D.018: Model ≠ View (3 паттерна)

| Model (модель) | View (представление) |
|----------------|---------------------|
| Изменение семантики, утверждений, границ | Изменение формы, подачи, потребителя |
| Source-of-truth (Pack) | Проекция (Downstream) |
| Одна | Много |

**3 паттерна:** viewOf(model), compositionViewOf(models[]), projectionView(model, concern).

**Почему важно**: Дублирование знаний = рассинхронизация. View проецирует, не копирует.

**Тест**: Требует ли изменение обновления Pack? Да → модель. Достаточно обновить downstream → view.

### DP.D.019: DSL ≠ DSLM

| DSL (Domain-Specific Language) | DSLM (Domain-Specific Language Model) |
|-------------------------------|---------------------------------------|
| Явный язык с синтаксисом | Implicit language в weights модели |
| Deterministic | Probabilistic |
| SQL, Terraform, GraphQL | Fine-tuned LLM на доменном корпусе |
| Стабильный, зрелый | Фронтир (2026) |

**Почему важно**: Принцип DSL ценен, инструментарий бифурцировал.

**Тест**: Можно ли записать правило как формальный синтаксис с парсером? Да → DSL. Нужна обученная модель? → DSLM.

### DP.D.020: Capture During-Work ≠ After-Work

| During-Work (real-time) | After-Work (ретроспективно) |
|------------------------|---------------------------|
| В момент обнаружения | После завершения работы |
| Высокая точность (контекст свежий) | Потери (контекст забыт) |
| Capture-to-Pack | «Documentation sprint» |
| SOTA (KM 2026) | Legacy practice |

**Почему важно**: Знание утрачивается экспоненциально после обнаружения.

**Тест**: Фиксируется ли знание в той же сессии? Да → during-work (SOTA). Нет → after-work.

---

### DP.D.021: Вайб-моделирование ≠ Профессиональное моделирование

| Вайб-моделирование | Профессиональное моделирование |
|--------------------|-------------------------------|
| Без типизации, «навскидку» | Single-meaning slot, типы, инварианты |
| Допустимо на старте (прототип) | Обязательно при масштабировании (команда, обмен данными) |
| Обратная связь — быстрая и локальная | Обратная связь — медленная и распределённая |
| AI-агент ускоряет ошибки | AI-агент усиливает точность |
| Невидимый технический долг | Управляемая сложность |

**Почему важно**: AI-агент без профессионального контроля позволяет «ошибаться быстро, убедительно и массово». Вайб-режим — мультипликатор вреда при переносе из малого масштаба в большой.

**Тест**: Результат будет использоваться другими людьми/системами? Да → профессиональное моделирование обязательно. Нет (pet-project, прототип) → вайб допустим.

> Источник: Левенчук, «Профессиональное кодирование и моделирование против вайб-кодирования», 15 фев 2026

### DP.D.022: Три уровня проверяемости (формальная ≠ семантическая ≠ операционная)

| Формальная | Семантическая | Операционная |
|------------|---------------|-------------|
| Синтаксис, типы, constraints | «Это действительно то, что вы думаете?» | «Работает ли в процессах?» |
| Машинная проверка | Человек + AI-агент | Только интервенция |
| `email` ∈ RFC 5322 | Этот адрес действительно принадлежит контакту? | Письмо на этот адрес доставляется? |
| Дёшево | Средне | Дорого |

**Почему важно**: AI-агент закрывает формальный уровень и частично семантический. Операционный уровень требует интервенций в реальный мир — то, чего AI-агент не может без embodiment.

**Тест**: Можно ли проверить автоматически? Да → формальная. Нужна экспертная оценка? → семантическая. Нужно физическое действие / эксперимент? → операционная.

> Источник: Левенчук, «Профессиональное кодирование и моделирование против вайб-кодирования», 15 фев 2026

### DP.D.023: Роль ≠ Агент; Агент ≠ Инструмент

| Роль (AgentialRole) | Агент | Инструмент |
|---------------------|-------|------------|
| Контекст исполнения | Исполнитель | Средство |
| «Как» и «зачем» действовать | «Кто» действует | «Чем» действует |
| У одного агента — несколько | Выбирает КАК действовать | Следует правилам |
| Стратег, Экстрактор, Кодировщик | Claude (Grade 3-4), Пользователь (Grade 4) | Бот (Grade 1), Синхронизатор (Grade 1) |

**Почему важно**: Смешение приводит к: (1) созданию «агентов», которые просто скрипты (inflation); (2) дублированию логики между ролями; (3) невозможности масштабирования — 14 «агентов» вместо 2 агентов с 13 ролями.

**Тест**: Может ли сущность выбирать, КАК действовать (не только ЧТО)? Да → агент (Grade 2+). Нет → инструмент (Grade 0-1). Контекст, в котором агент действует → роль.

**Три категории исполнителей:** ИИ-агент, Человек, Инструмент. Единый реестр: DP.ROLE.001 § 3.

> Основание: FPF A.13 — Agent = System#AgentialRole:Context. Agency Grade (0-4).

### DP.D.024: Semantic Search ≠ Keyword Search

| | Semantic (Vector) Search | Keyword Search |
|---|---|---|
| Что ищет | Смысл (embedding similarity) | Точную строку / слова |
| Хорош для | Естественный язык, «похожие документы» | Коды (DP.ROLE.001), точные термины |
| Слаб в | Структурированные идентификаторы, acronyms | Переформулировки, синонимы |
| Скорость | ~300ms (embedding + vector scan) | ~5ms (GIN index) |
| Модель | bge-m3 → 1024d cosine distance | pg_trgm ILIKE + tsvector FTS |

**Почему важно**: knowledge-mcp обслуживает и людей (смысловые вопросы), и AI-агентов (tool_use по кодам сущностей). Один тип поиска не покрывает оба случая. Hybrid retrieval — стандарт production RAG 2025 (SOTA: Hybrid Retrieval dense+BM25).

**Тест**: Запрос содержит паттерн `XX.YYY.NNN` (код сущности)? → keyword path. Запрос на естественном языке? → vector path. Непонятно? → оба (RRF).

**Реализация:** knowledge-mcp v3.1 — keyword-first routing + vector fallback. Схема: pg_trgm GIN + tsvector GIN. Без изменения MCP API.

### DP.D.025: Harness (упряжь) ≠ Agent (агент)

| Harness (упряжь/обвязка) | Agent (агент/модель) |
|--------------------------|---------------------|
| Среда, ограничения, контекст, обратная связь | Исполнитель (LLM, человек) |
| Определяет качество результата | Выполняет работу |
| Проектируется инженером | Обучается / масштабируется |
| Улучшение = переделка среды | Улучшение = смена модели / обучение |

**Почему важно**: Изменение только обвязки улучшает результаты 15 LLM на 5-14 п.п. (Boluk 2026). Дефект результата — чаще дефект среды, а не агента. IWE = harness для интеллектуальной работы.

**Тест**: Для улучшения результата — нужно менять агента или достаточно улучшить среду? Если второе эффективнее — harness > agent.

> Подробно: [DP.D.025](DP.D.025-harness-vs-agent.md). Источники: OpenAI (2026), Can Boluk (2026)

### DP.D.026: Хранимый счётчик ≠ Вычисляемая проекция

| Хранимый счётчик (mutable counter) | Вычисляемая проекция (computed view) |
|------------------------------------|--------------------------------------|
| Инкрементируется при событии | Вычисляется из журнала событий |
| Хрупкий: race condition, стейлый кеш, сброс при смене контекста | Всегда актуален: SELECT COUNT(*) |
| Требует синхронизации при изменении условий | Автоматически корректен при любых условиях |
| Ошибка накапливается | Ошибка невозможна (один SQL-запрос) |

**Почему важно**: Мутируемый счётчик `topics_at_current_complexity` в `interns` таблице терял значение при смене уровня сложности (reset=0), при race condition (+1 не применялся), при стейловом кеше (user dict не обновлён). Вычисление `COUNT(*) FROM answers WHERE complexity_level=$1` даёт точное значение всегда — answers = журнал фактов (Event Sourcing, SOTA.012).

**Тест**: Значение зависит от N событий и может «сбиться»? → Вычисляй из событий, не храни.

> Источник: баг бота (@TserenTserenov: 5 theory_answer, counter=0). Фикс: `get_theory_count_at_level()` в `db/queries/answers.py`. Связь: DP.D.005 (производный индикатор), SOTA.008+SOTA.012.

|---------------|--------------------|--------------------|

### DP.D.035: Контуры (L1-L4) ≠ Тиры (T0-T4 + TM/TA/TD)

| Контуры (L) | Тиры (4-осевая модель) |
|-------------|----------|
| ГДЕ в архитектуре | ЧТО доступно пользователю |
| Организационные границы | Конфигурация сервиса |
| 4 значения: L1 Ecosystem, L2 Platform, L3 Template, L4 Personal | 4 оси: T (T0-T4 учащийся), TM (TM1-TM3 наставник), TA (TA1-TA4 администратор), TD (TD1 разработчик) |
| Определяют КТО владеет (мета-роль) | Определяют ЧТО получает (пользователь) |
| Статичны (архитектура системы) | Динамичны (пользователь продвигается по T-оси, назначается на TM/TA/TD) |
| Вложенность: L1 ⊃ L2 ⊃ L3 ⊃ L4 | Прогрессия T-оси: T0 → T1 → T2 → T3 → T4. Оси TM/TA/TD ортогональны |

**Почему важно**: L и T — ортогональные оси. L отвечает «где в системе?» (разработчик шаблона работает на L3). T отвечает «что получает пользователь?» (пользователь на T4 работает в личной IWE на L4). Владелец платформы = T4 + TA4 + TD1 (комбинация осей, не отдельный тир). Смешение → непонятно, кому адресовано изменение.

**Тест**: Вопрос про владение/обновление/границу? → контур (L). Вопрос про набор сервисов/возможностей пользователя? → тир (T).

> Подробно: [DP.IWE.001 §4](../02-domain-entities/DP.IWE.001-intelligent-working-environment.md), [DP.ARCH.002](../02-domain-entities/DP.ARCH.002-service-tiers.md)

### DP.D.036: Method (уровень роли) ≠ Instrument (уровень назначения)

| Method (метод) | Instrument (инструмент) |
|----------------|-------------------------|
| ЧТО делать (подход) | ЧЕМ конкретно (средство) |
| Привязан к роли | Привязан к назначению (роль × исполнитель) |
| Стабилен при смене исполнителя | Меняется при смене исполнителя |
| Пример: «ArchGate (ЭМОГССБ)» | Пример: CLI + memory/sota-reference.md |
| Пример: «Бухгалтерский учёт» | Пример: 1С (или Excel у другого исполнителя) |

**Почему важно**: Документирование инструментов на уровне роли создаёт ложную связанность. Та же роль + другой исполнитель = другие инструменты (бухгалтер в 1С vs бухгалтер в Excel). Тот же исполнитель + другая роль = другие инструменты (Claude в роли Стратега → strategist.sh, Claude в роли Экстрактора → extractor.sh). Инструмент принадлежит **назначению** — паре (роль, исполнитель).

**Тест**: Сменился исполнитель — инструмент сменился? Да → instrument at assignment level. Метод остался тем же? Да → method at role level.

> Основание: FPF A.7 (Method ≠ Tool). Шаблон: DP.D.033 §3 (`instruments` в `current_holders`). Связь: DP.D.025 (Harness ≠ Agent).

### DP.D.037: Кастомизация агента (Harness Engineering) ≠ Дообучение (Fine-Tuning)

| Harness Engineering (кастомизация) | Fine-Tuning (дообучение модели) |
|--------------------------------------|-------------------------------|
| Меняет промпты, инструменты, данные, ограничения | Меняет веса модели |
| Мгновенно, обратимо, дёшево | Долго, необратимо, дорого |
| Пользователь может сам (L4 Personal) | Требует ML-инфраструктуру |
| Подход IWE: L2 → L3 → L4 (DP.D.025) | Не наш подход |
| Результат: тот же Base LLM, другое поведение | Результат: другая модель |

**Почему важно**: «Настроить агента под себя» в архитектуре IWE = harness engineering (DP.D.025), НЕ fine-tuning LLM. Pipeline кастомизации по контурам: Base LLM → +L2 (API config, system prompt) → +L3 (CLAUDE.md, роли, скрипты) → +L4 (personal CLAUDE.md, ЦД, личные Pack). Каждый контур добавляет слой обвязки (harness), не меняя модель.

**Тест**: Меняются веса модели? → Fine-tuning. Меняются промпты, инструменты, контекст, ограничения? → Harness engineering (кастомизация).

> Связь: DP.D.025 (Harness ≠ Agent), DP.D.034 (L2/L3/L4 контуры), DP.ROLE.001 §2.1 (Agent Customization Pipeline).

### DP.D.038: Обучение (Pre-Training) ≠ Онбординг (Context Engineering, НЕ HR-процесс)

| Обучение (Pre-Training) | Онбординг (Context Engineering) |
|-------------------------|--------------------------------|
| Меняет веса модели | Меняет контекст (промпты, знания, инструменты) |
| До «найма» (стадия 0) | После «найма» (стадия 3) |
| Делает изготовитель (Anthropic, OpenAI) | Делает пользователь или инженер среды |
| Месяцы, миллионы долларов | Минуты–часы, бесплатно |
| Результат: описание (артефакт с весами) | Результат: настроенная среда (harness) |
| Необратимо (новая версия модели) | Обратимо (отредактировал промпт) |

**Почему важно**: Люди говорят «обучите мне ИИ» или «ИИ нужно обучить», когда имеют в виду онбординг — ввод в контекст. Обучение уже произошло (в Anthropic/OpenAI). Обычный пользователь не обучает модель — он проводит онбординг через context engineering. Смешение → ложное ожидание, что нужны данные и ML-инфраструктура для настройки агента.

> ⚠️ **ОМОНИМ:** «Онбординг» в этом тексте = context engineering (технический смысл: ввод агента в контекст задачи). НЕ путать с HR-онбордингом (адаптация нового сотрудника в компании). Контекст всегда технический, если речь идёт о настройке ИИ-агента.

**Тест**: Меняются ли веса модели? Да → обучение (pre-training / fine-tuning). Нет, меняется только контекст (промпты, документы, инструменты)? → онбординг (context engineering).

> Связь: DP.D.037 (Harness Engineering ≠ Fine-Tuning), DP.D.025 (Harness ≠ Agent), DP.SOTA.002 (Context Engineering).

### DP.D.039: Обещание (= сценарий использования) ≠ Описание метода ≠ Сервис

**Три понятия + навигатор:**

| Обещание / Сценарий использования (SC) | Описание метода (MethodDescription) | Сервис (accessSpec) |
|---|---|---|
| ЗАЧЕМ и ЧТО получит потребитель | КАК работает (шаги) | ГДЕ точка входа (навигация) |
| U.ServiceClause | U.MethodDescription | accessSpec в MAP.002 |
| Pack DP / 08-service-clauses/ | `<repo>/PROCESSES.md` | MAP.002 (каталог) |
| Не зависит от реализации | Зависит от системы | Зависит от архитектуры |

**Описание метода** имеет два масштаба (не два разных понятия):
- **Внутрисистемное** («процесс») — шаги внутри одной системы → `<repo>/PROCESSES.md`
- **Межсистемное** («сценарий») — управление передаётся между системами → `DS-ecosystem/PROCESSES.md`

**Синонимы:**
- «Сценарий использования» = «обещание» = SC (U.ServiceClause). Взаимозаменяемы.
- «Сценарий» (без «использования») = межсистемное описание метода. НЕ синоним обещания.
- «Процесс» = внутрисистемное описание метода.

> ⚠️ **ОМОНИМ-ЛОВУШКА:** слово «сценарий» без уточнения имеет два несовместимых смысла в этом Pack:
> - «сценарий использования» (=обещание, SC, U.ServiceClause) — в контексте обещаний потребителю
> - «сценарий» (=межсистемный процесс) — в контексте описания методов
>
> Агент или читатель, не зная контекста, может слить эти смыслы (lexical dedupe). Правило: при чтении документа с «сценарий» без уточнения — уточнить у автора или смотреть на раздел (08-service-clauses → обещание; PROCESSES.md → описание метода).

**Почему важно**: Без обещаний разработка начинается с реализации (КАК), минуя понимание потребности (ЗАЧЕМ). Обещание — единственный артефакт, который можно показать новичку или боту без знания внутренней архитектуры.

**Связь**: Обещание (SC) → реализуется через сервисы (MAP.002) → каждый сервис детализируется описанием метода (PROCESSES.md).

**Тесты**:
- Описывает, ЧТО получит потребитель (без КАК)? → Обещание (SC).
- Описывает шаги реализации? → Описание метода (процесс или сценарий).
  - Внутри одной системы? → Процесс.
  - Управление передаётся другой системе? → Сценарий.
- Это точка входа для навигации? → Сервис.

### DP.D.041: Статистическое знание (AI) ≠ Верифицированное знание (Pack)

| Статистическое (AI) | Верифицированное (Pack) |
|---------------------|------------------------|
| Наиболее вероятный ответ | Проверенное экспертом с skin in the game |
| Деградирует на long-tail | Надёжно именно на long-tail (доменная специфика) |
| Масштабируется бесплатно | Требует курирования |
| Устаревает с drift данных | Версионируется осознанно |

**Почему важно**: LLM деградируют на long-tail знаниях (Kandpal, ICML 2023). Доменное знание организации — по определению long-tail. Pack = инфраструктура для context engineering, не дублирование того, что «AI итак знает».

**Тест**: Ответ одинаков для 1000 организаций? → Статистическое (AI справится). Ответ специфичен для этого домена/контекста? → Верифицированное (нужен Pack).

> Источник: Q.001-Q.002 (Strategy.md, 2026-02-20).

### DP.D.042: Генерация паттернов (AI) ≠ Генерация смысла (человек)

| Генерация паттернов (AI) | Генерация смысла (человек) |
|--------------------------|---------------------------|
| Рекомбинация существующих паттернов | Выбор темы (taste/judgment) |
| Скорость и масштаб | Skin in the game (репутация) |
| Нет авторства | Де-компиляция tacit knowledge |

**Почему важно**: AI генерирует паттерны, профессионал генерирует **смысл** (Messeri & Crockett, Nature, 2024). Три вещи, которых нет у AI: (1) выбор что важно сейчас, (2) де-компиляция неявного знания, (3) ответственность репутацией. Это определяет ценность экспертного контента в эпоху AI.

> Источник: Q.003 (Strategy.md, 2026-02-20).

### DP.D.043: Рынок знания (commodity) ≠ Рынок компиляции (растёт)

| Рынок знания | Рынок компиляции |
|--------------|-----------------|
| Знание отчуждаемо (копируется) | Мировоззрение не отчуждаемо |
| AGI обвалит (commodity) | AGI усилит (спрос растёт) |
| Продукт: информация | Продукт: трансформация мышления |
| Конкуренция: кто дешевле | Конкуренция: кто глубже |

**Почему важно**: Principal-agent problem не исчезает при AGI — агенту нужны цели принципала, Pack их кодифицирует (Russell, 2019). Структурированное знание = комплементарный актив к AI (Teece, 1986). Платформа работает на рынке компиляции, не знания.

> Источник: Q.004, Q.008 (Strategy.md, 2026-02-20).

### DP.D.044: Смена роли в диалоге ≠ Расширение промпта

| Смена роли (role switch) | Расширение промпта (prompt bloat) |
|--------------------------|-----------------------------------|
| Новый агент (отдельный Claude API вызов) | Тот же агент, раздутый system prompt |
| Свой контекст, инструменты, инструкции | Всё в одном промпте — конфликтующие инструкции |
| Пользователь видит: кто ответил (attribution) | Пользователь не знает, какая «часть» промпта сработала |
| Масштабируется: N ролей = N промптов | Не масштабируется: промпт растёт → качество падает |

**Почему важно**: Добавление функций Навигатора в промпт Консультанта (R3) → промпт раздувается, инструкции конфликтуют, качество обоих ролей падает. Context isolation (SOTA.006) + tool specialization → каждая роль отвечает в своём контексте. Пользователь видит подпись роли → trust signal.

**Тест**: «Можно ли убрать эту часть промпта в отдельный вызов без потери контекста?» Да → отдельный агент. Нет (нужен тот же диалог/состояние) → оставить в одном.

**Реализация по средам:** IWE (Claude Code) = sub-agent. Бот = отдельный Claude API вызов с другим промптом.

**UX-контракт:** (1) Footer: 🧭 Навигатор, 🎯 Диагност, ✂️ Портной. (2) Переход: *«Подключаю Навигатора»*. Возврат: *«Возвращаю Консультанта»*.

> Правило и UX-контракт: DP.ROLE.001 §3.4. Связь: DP.D.023 (Роль ≠ Агент), DP.D.025 (Harness ≠ Agent), SOTA.006 (context isolation).

### DP.D.045: ЦД-CEO (Executive) ≠ ЦД-Model (Passive Replica)

| ЦД-CEO (Executive) | ЦД-Model (Passive Replica) |
|---------------------|----------------------------|
| ЦД = **OS kernel** между сознанием и реальностью, оркестрирует agent swarms | ЦД = **статическая модель** характеристик, данных, состояний |
| CEO: приоритизирует очередь, делегирует задачи агентам, рендерит выходы | Справочник: хранит информацию, отвечает на запросы |
| Continuous loops: agents 24/7, API-to-API координация между ЦД пользователей | On-demand: обновляется по запросу, не инициирует действий |
| Human = Chairman of the Board: veto authority, утверждает стратегии ЦД | Full control: все действия по явному запросу |
| 4 вектора (Wealth, Bio, Social, Learning) → каждый = swarm of agents | Единая модель данных (характеристики, состояния, история) |

**Почему важно**: Текущий ЦД (v2.x) больше Model, чем CEO. Архитектура Phase 2 (WP-73) движется к CEO-модели: Activity Hub, персональные руководства, agent orchestration. McDonagh: «You are Chairman of the Board, Twin is CEO» — делегирование executive function, не хранение модели.

**Тест**: «ЦД инициирует действия самостоятельно?» Да → CEO. Нет → Model.

**Различие с DP.D.009**: DP.D.009 — ИИ-агент ≠ ИИ-ассистент (общее). DP.D.045 — **внутри** ЦД: executive vs passive (специфическое).

> Источник: McDonagh (Life in the Singularity, 2026). Связь: WP-73, DP.D.009.

### DP.D.046: Экзоскелет (Exoskeleton) ≠ Автопилот (Autopilot)

| Экзоскелет (Exoskeleton) | Автопилот (Autopilot) |
|---------------------------|----------------------|
| Усиливает мышление человека — человек решает, система помогает исполнить | Заменяет действие человека — система решает и исполняет |
| Human gate обязателен: знание, через которое не прошёл — не твоё | Human gate отсутствует: LLM пишет и поддерживает базу, человек редко трогает |
| Цель: глубина понимания. Медленнее на старте, надёжнее при масштабе | Цель: скорость компиляции. Быстрее на старте, хрупче при масштабе |
| Применение: доменное знание, стратегия, Pack (source-of-truth) | Применение: разведка, первичный обзор, черновой слой |

**Почему важно**: Оба режима необходимы в IWE, но на разных слоях. Черновой слой (Scout, auto-compilation) работает в режиме автопилота — LLM собирает, компилирует, линтит без участия человека. Pack и стратегические решения требуют экзоскелетного режима — человек работает с материалом, пропускает через себя, и только осознанное знание фиксируется как source-of-truth. Смешение режимов: автопилот на Pack → некритически принятые знания, потеря калибра. Экзоскелет на черновиках → бутылочное горлышко, человек тонет в рутине.

**Тест 1 (понимание)**: «Человек должен понимать этот материал, чтобы принимать решения на его основе?» Да → экзоскелет. Нет (материал промежуточный, для ориентировки) → автопилот.

**Тест 2 (объяснимость)**: «Можете ли вы объяснить это решение без ссылки на "ИИ подсказал"?» Нет → решение не ваше, экзоскелетный режим нарушен. Финальная ответственность всегда на человеке.

**Визуальная метафора**: Протез заменяет функцию (снимите — человек не может работать). Экзоскелет усиливает функцию (снимите — человек работает, просто медленнее). ИИ предлагает → Инженер решает.

**Связь**: DP.D.025 (Harness ≠ Agent) — harness = экзоскелет для агента. DP.D.045 (CEO ≠ Model) — CEO-режим ЦД использует оба: автопилот для сбора, экзоскелет для утверждения.

> Источники: анализ подхода Karpathy (LLM Knowledge Base, апрель 2026) vs IWE-архитектура. Визуальная метафора: презентация «The Intellectual Exoskeleton» (апрель 2026).

### DP.D.047: Квалификация (стадия развития) ≠ Тир (уровень оснащения)

| Квалификация | Тир |
|-------------|-----|
| Ступень мастерства: Случайный → Практикующий → Систематический → Дисциплинированный → Проактивный (1–5) | Уровень оснащения: T1 Старт → T2 Изучение → T3 Персонализация → T4 Созидание |
| Определяется поведением и активностью (FORM.089); вычисляется автоматически stage_evaluator | Определяется подпиской (T2) и подключённой средой (T3=ЦД/тайный гит; T4=GitHub OAuth/явный гит) |
| Влияет на множитель баллов, дневной cap, рекомендованный поток S0–S4 | Влияет на доступ к сервисам, интерфейсам (Браузер, VS Code), инструментам Портного |
| Привязана к пользователю (переносима при смене платформы) | Привязана к конфигурации среды (не переносима) |

**Официальные имена тиров (mydata.py):** T1=Старт, T2=Изучение, T3=Персонализация, T4=Созидание.
**Детектор (tier_detector.py):** T4 ← GitHub OAuth подключён; T3 ← ЦД подключён (GitHub не нужен); T2 ← подписка БР + LMS активна; T1 ← иначе.

**Три пути пользователя IWE (ортогональны):**
1. **Путь оснащения (T1→T4)** — что система знает и может делать (тиры)
2. **Путь развития (ступени 1→5)** — мастерство созидателя (квалификация)
3. **Программная линейка (S0–S4)** — практикумы как ускорители активности (S0=Марафон, S1–S4 по ступени); НЕ автоматически переводят ступень — только помогают накопить активность для её вычисления

**Почему важно**: Смешение приводит к ошибке в формуле баллов. Участник T4 с квалификацией «Случайный» не должен получать максимальный множитель — он настроил среду, но ещё не развился. Аналогично: прохождение S1 не гарантирует ступень 2 — ступень считается автоматически по activity_log.

**Тест**: «Это про мастерство пользователя или про его доступ к инструментам?» Мастерство → квалификация/ступень. Доступ → тир.

> Источник: WP-121 + WP-165 (4 апр 2026); уточнение tier-matrix + S0-S4 (WP-343, 22 мая 2026). Ранее в DP.SC.105 квалификация ошибочно обозначалась как T0-T4.

### DP.D.048: Скрипт ≠ Агент

| Скрипт | Агент |
|--------|-------|
| **Фиксированный control flow** — автор написал последовательность шагов | **LLM выбирает следующий шаг** на каждой итерации |
| Один вход → одна последовательность действий (результат может отличаться из-за сети/БД) | Один вход → разные последовательности (LLM решает) |
| Вход: аргументы CLI, переменные окружения | Вход: промпт + набор tools |
| Отлаживается как программа (воспроизводимый trace) | Отлаживается как диалог (разные ветвления) |
| Размещение по типу (см. DP.KR.001 §5.6) | `.claude/agents/` или `<repo>/agents/` |

**Почему важно**: Оба — исполнители ролей в IWE, и оба могут выдавать разный результат на одинаковом входе (недетерминизм среды). Разница не в предсказуемости результата, а в том, **кто выбирает следующий шаг**: автор скрипта или LLM в runtime. Путать → хранить агенты там, где место скриптам, или наоборот.

**Тест**: «Если я уберу LLM из runtime — выполнение сломается?» Да → агент. Нет (упадут только реализации вызовов) → скрипт.

> Источник: обсуждение размещения `week-draft-append.sh` и последующая инвентаризация скриптов IWE (17 апреля 2026).

### DP.D.049: Лог ≠ Инцидент ≠ State file

| Лог (operational) | Инцидент (governance) | State file |
|-------------------|----------------------|------------|
| Хронологический поток событий исполнения | Зафиксированный сбой + разбор причин | Текущее состояние (не история) |
| Пишется автоматически исполнителем | Пишется человеком (или агентом под надзором) | Пишется/перезаписывается скриптом |
| Живёт рядом с исполнителем | Живёт в governance-репо (DS-ecosystem-development/.../Incidents/) | Живёт рядом с исполнителем |
| Примеры: `week-draft-append.log`, `payment-worker.log` | Примеры: P10 (DP.FM.010), P11 (DP.FM.011) | Примеры: `sync-manifest.yaml`, `last-check.json` |
| Для отладки конкретного запуска | Для извлечения урока и ретроспективы | Для следующего запуска (idempotency, дифф) |

**Почему важно**: Смешение приводит к (а) логам в governance-репо (засоряют историю решений случайными сообщениями) и (б) инцидентам в `<service>/logs/` (теряются, не разбираются). State-файл путают с логом и либо удаляют (ломая идемпотентность), либо делают append-only (теряя смысл «текущего состояния»).

**Тест**: «Это хронология, вывод или состояние на момент X?» Хронология → лог. Вывод (разбор + решение) → инцидент. Снимок → state file.

> Источник: аудит скриптов IWE (17 апреля 2026) — обнаружено, что правило размещения артефактов исполнения не зафиксировано.

### DP.D.050: Баллы (геймификация) ≠ Бонусы (лояльность) ≠ Ступень (квалификация)

> Три системы учёта одной пользовательской активности. Один источник событий (Activity Hub) — разные правила обработки, разные потребители.

| | Баллы | Бонусы | Ступень |
|--|-------|--------|---------|
| **Что** | earned_total — накопленная сумма начислений | `min(points, Σ(active_days_at_qual_i × daily_cap_i))` | cp-профиль (13 срезов + 7 bh, FORM.089) |
| **Убывает?** | Никогда | Да (при оплате бонусами) | Нет |
| **Кто пишет** | DP.ROLE.034 Rewards Projector | DP.ROLE.051 Points Redeemer | R28 Profiler |
| **Для чего** | Лидерборд, статус, история | Скидка при оплате сервисов | Определяет daily_cap бонусов + функционал IWE |
| **Ограничение** | — | История × дневной cap квалификации | — |

**Формула бонусов** учитывает смену квалификации: `Σ(active_days_at_qualification_i × daily_cap_i)` — суммируется по всем периодам, когда пилот находился на разных ступенях. Источник данных: `rewards.applied_events.qualification_snapshot` (уже содержит снимок).

**Почему важно:** путаница «Баллы = то, что тратится» приводит к ошибке архитектуры: при оплате уменьшается бонусный баланс (`point_balances.points`), а не earned_total. Лидерборд должен показывать earned_total — независимо от истории оплат. Также: ступень влияет на daily_cap, но сама не убывает и не является «баллами».

**Тест:** «не убывает?» → баллы. «Тратится на оплату, ограничено историей дней × cap?» → бонусы. «Определяет мастерство?» → ступень.

> Источник: WP-327 Этап 0-3, 20 мая 2026 — терминологическое различение согласовано при проектировании DP.SC.141 (Зачёт баллов в оплату).

### DP.D.053: Проблема ≠ Задача ≠ Формулировка работы ≠ Работа (4-уровневая шкала)

| Уровень | Состояние | Что требуется |
|---------|-----------|---------------|
| **Проблема** | Не понимаю, что вообще делать. Неопределённость, ступор | Системное моделирование → конвертация в Задачу |
| **Задача** | Понятно, какой метод применить | Выбор метода, планирование |
| **Формулировка работы** | Спецификация: кто, как, когда, какой рабочий продукт | Согласование до начала |
| **Работа** | Реальное исполнение в физическом мире | Среда, инструменты, агенты |

**Почему важно:** ИИ-автопилот ускоряет Задача→ФР→Работа, но не конвертирует Проблему в Задачу. Без этого перехода: либо ступор, либо случайный результат (ИИ ответил на упрощённую версию). Конвертация = системное моделирование + экзоскелет (DP.D.046) + среда (платформа L2 + IWE L4, DP.D.034).

**Тест 1 (уровень):** «Я понимаю, какой метод применить?» Да → Задача. Нет → Проблема (нужно моделирование сначала).

**Тест 2 (ИИ):** «ИИ ответил на мой исходный вопрос или на упрощённую версию?» Упрощённая → Проблема не сконвертирована.

> Подробно: [DP.D.053](DP.D.053-problem-task-workflow.md). Расширяет HD «Задача ≠ ФР ≠ Работа» (практикум РР, 27 апр). Связь: DP.D.046 (Экзоскелет ≠ Автопилот), DP.D.034 (Platform L2 ≠ IWE L4).

### DP.D.054: Context Engineering ≠ Prompt Engineering

| Аспект | Prompt Engineering | Context Engineering |
|--------|-------------------|---------------------|
| **Суть** | Что **сказать** модели | Что **дать** модели |
| **Артефакты** | Instruction text, examples, templates | Tools, memory files, retrieval, constraints |
| **Цель** | Improve output quality | Enable task completion |
| **Пример** | «Think step-by-step» | MEMORY.md + Bash tool + PACK index + RAG |
| **Слой** | Микро (формулировка) | Макро (информационная среда) |

**Почему важно:** PE оптимизирует формулировку запроса; CE проектирует информационную среду вокруг модели. PE без CE = промпт без контекста (галлюцинации, узкое видение). CE без PE = богатая среда без точного запроса (агент тонет в шуме).

**Связь:** DP.SOTA.002 (Context Engineering как дисциплина) описывает *стратегии CE* (Write/Select/Compress/Isolate). DP.D.054 фиксирует *границу с PE*. AS.SOTA.006 Layer 2 описывает *эволюцию контекста* (ACE = self-evolving CE).

**Источник:** Context Engineering framework (Anthropic, 2026); WSCI Framework (Panat, 2026).

### DP.D.083: Persistent TaskTracker (filesystem) ≠ Ephemeral TodoWrite (session memory)

| Аспект | TodoWrite | Filesystem TaskTracker |
|--------|-----------|----------------------|
| **Хранение** | Память процесса (in-process) | Файловая система (`inbox/agent/tasks/TASK-<id>.md`) |
| **Scope** | Текущая сессия | Персистентен между сессиями |
| **При рестарте** | Данные теряются | Задачи выживают |
| **Аудит** | Невозможен после завершения | Файлы доступны для проверки |
| **Применение** | Внутрисессионные чеклисты | Scheduled/periodic агенты, dispatcher |

**Тест выбора:** «Нужно ли возобновить задачу после рестарта агента?»
- Да → filesystem TaskTracker
- Нет → TodoWrite достаточен

**Почему важно:** Headless-агенты, работающие периодически (cron/dispatcher), не могут полагаться на TodoWrite — при каждом запуске `claude -p` начинается новый процесс. Для сохранения прогресса задачи между запусками обязателен файловый трекер.

**Контекст:** Выявлено при проектировании DP.IWE.011 (headless adapter) и Agent Inbox (WP-324). Расширяет DP.D.048 (Script ≠ Agent) — добавляет ось persistence.

### DP.D.084: Workspace-координация peer'ов ≠ Conversational-сессия peer'ов

| Аспект | Workspace-координация (DP.SC.034, DP.SC.035) | Conversational-сессия (DP.SC.154) |
|--------|----------------------------------------------|------------------------------------|
| **Объект работы** | Разные файлы workspace | Одна задача, один отчёт |
| **Режим** | Асинхронный, parallel | Синхронный, turn-taking |
| **Координация** | File lock + peer-status (focus, intent) | Журнал реплик + детектор `ESCALATE_TO_USER` |
| **Транспорт** | Local Gateway (Unix socket) + git | Файловый журнал `agent-conversation/<task-id>/` |
| **Результат** | Каждый peer коммитит своё | Один общий `report.md` от писателя |
| **Метафора** | Команда инженеров делит модули | Команда обсуждает решение и докладывает |
| **Эскалация к пилоту** | По `awaiting_decision` в peer-status | По маркеру в реплике |
| **Pacing** | Долговременный (часы/дни сессии) | Короткий (минуты-десятки минут, ходы по 30-60с) |

**Тест выбора:** «Делят ли агенты workspace (разные файлы) или обсуждают одну задачу (один результат)?» → разные → workspace; один → conversational.

**Почему важно:** В workspace-координации разногласия разрешаются через изоляцию focus (каждый peer работает над своим). В conversational-сессии разногласия — естественная часть процесса, цель — согласованный отчёт через многотуровый обмен аргументами. Смешение двух режимов в одном протоколе ведёт к ложным lock-конфликтам (peer'ы блокируют друг друга на одной задаче) или к unilateral-решениям (один peer молча перезаписывает другого).

### DP.D.086: Дистрибутив-bundle ≠ Дистрибутив-coupling

**Метафора «дистрибутив» несёт два разных смысла, которые путают при обсуждении архитектуры платформ:**

| Смысл | Что фиксирует | Пример | Переносим? |
|-------|--------------|--------|-----------|
| **bundle** | набор согласованных компонентов + единый релиз + предсказуемые интерфейсы | Ubuntu, JVM, POSIX-окружение | Да |
| **coupling** | жёсткая зависимость от одного ядра / провайдера | Ubuntu↔Linux kernel (на BSD не работает) | Нет, специфично |

**Тест:** «работает ли при смене ядра / core-провайдера?»
- Да → **bundle**-смысл.
- Нет → **coupling**-смысл.

**Применение к IWE:** IWE = portable runtime + Pack + host-адаптеры (см. [DP.IWE.011](../02-domain-entities/DP.IWE.011-host-adapter.md)). Bundle есть (согласованный набор скриптов, хуков, скиллов), coupling с одним LLM-ядром нет (Claude / GPT / локальные модели — через адаптер). Ближе к JVM (portable runtime) + POSIX (контракт хоста), чем к Ubuntu.

**Применение в публичных материалах:** при использовании метафоры «дистрибутив» оговаривать, какой смысл имеется в виду. Без оговорки слушатель достраивает Linux-модель и приписывает coupling-семантику host-агностичному продукту. Случай 22 мая 2026: реакция Андрея на отчёт пилота показала это рассогласование (WP-337).

- L3 `.claude/rules/distinctions.md` — авторская формулировка того же различения (более лаконичная)

### DP.D.087: OAuth pending state in-memory ≠ OAuth pending state externalized (БД)

| Аспект | In-memory state | Externalized state (БД) |
|--------|-----------------|-------------------------|
| **Хранение** | Живой объект на инстансе сервера | Запись в общей БД (`oauth_pending_state`) |
| **Инициатор authorize** | Только authorize-сервер | Любой клиент с доступом к БД |
| **Масштабирование** | Требует sticky sessions | Горизонтальное без ограничений |
| **Выживаемость** | Теряется при рестарте | Персистентен (TTL/cron cleanup) |
| **Риск** | Нет race condition на state | Нужна транзакция на callback-match |
| **Пример** | Session cookie на одном инстансе | `oauth_pending_state` в Neon + bot-generated link |

**Тест выбора:** «Может ли OAuth-flow пережить рестарт authorize-сервера между шагами authorize и callback?»
- Да → externalized (БД)
- Нет → in-memory

**Почему важно:** Externalized state позволяет боту инициировать OAuth-flow за пользователя (генерирует запись в БД, отдаёт ссылку в чат) и поддерживает горизонтальное масштабирование authorize-handler. Цена — race conditions при параллельных запросах и требование транзакционности при callback-match.

**Контекст:** Выявлено при реализации LLM Proxy auth (WP-200 Ф7, 2026-05-22). Применимо ко всем multi-server OAuth-провайдерам и serverless-deployments authorize-эндпоинта.

### DP.D.088: `environment.d` (декларативный, persistent) ≠ `systemctl --user set-environment` (императивный, ephemeral)

| Аспект | `~/.config/environment.d/*.conf` | `systemctl --user set-environment KEY=VALUE` |
|--------|----------------------------------|----------------------------------------------|
| **Момент применения** | При старте user-сессии (login/linger=yes) | Немедленно |
| **Персистентность** | Между сессиями (файл на диске) | Теряется при logout/reboot |
| **Существующие unit'ы** | НЕ видят переменную до перезапуска | Видят немедленно |
| **Тип** | Декларативный (конфиг-файл) | Императивный (команда) |
| **Проверка** | `cat /proc/$(pidof <agent>)/environ` | `systemctl --user show-environment` |

**Правильный паттерн для headless-агента:**
1. Записать в `environment.d` (персистентность между reboot)
2. Выполнить `set-environment` (немедленный эффект без рестарта сессии)
3. `daemon-reload + restart` затронутых unit-файлов

**Тест применения:** «Переменная появилась в `systemctl --user show-environment`?» → `set-environment` отработал. «Появилась в `/proc/$(pidof <agent>)/environ`?» → unit перезапущен после загрузки `environment.d`.

**Почему важно:** Только `set-environment` — потеря переменной после reboot. Только `environment.d` — новая переменная не видна до полного session restart. Для headless-агентов с `linger=yes` оба механизма обязательны.

**Контекст:** Выявлено при деплое агентов на tsekh-1 (WP-200 Ф7, 2026-05-22). Применимо ко всем remote-headless deployments через user systemd.

### DP.D.103: In-memory session state (auto-cleanup on redeploy) ≠ Persistent session state без TTL (zombie accumulation)

| Аспект | In-memory state | Persistent без TTL |
|--------|-----------------|-------------------|
| **Поведение при redeploy** | Очищается автоматически | Остаётся навечно |
| **Zombie sessions** | Нет — redeploy = garbage collector | Накапливаются без TTL/cron |
| **Failure mode** | Потеря активных сессий при сбое | Orphan-записи растут бесконечно |
| **Применимость** | Краткоживущие сессии (диалоги, wizard) | Требующие сохранения после сбоя |

**Тест выбора:** «Нужно ли сохранять сессию после сбоя/рестарта сервера?»
- Нет → in-memory (cleanup при redeploy = feature)
- Да → persistent с явным TTL/cleanup job

**Почему важно:** «In-memory с потерей» интуитивно воспринимается как слабость. Но для краткоживущих диалоговых сессий потеря при redeploy = автоматический cleanup zombie-сессий. БД без TTL накапливает orphan-записи. Ключевой критерий — lifecycle объекта, не «надёжность» как абстрактное свойство.

**Контекст:** Выявлено при ArchGate WP-358 Ф10 (2026-05-28), проектирование session tracker в Telegram-боте.

### DP.D.106: Trigger по состоянию ≠ Trigger по счётчику (для архитектурных переключений)

**State-based trigger** — переключение запускается при появлении **первого** объекта out-of-current-scope (первый non-Mac пилот; первый T2+ user; первый клиент в новом geo). Срабатывает до накопления tech-debt'а.

**Counter-based trigger** — переключение запускается, когда счётчик достигает порога («когда users > 20»). К моменту срабатывания accumulated cost от обходных решений обычно превышает migration cost.

| Аспект | State-based | Counter-based |
|--------|-------------|---------------|
| **Trigger** | Появление out-of-scope объекта | Достижение N |
| **Накопление debt'а** | До trigger ≈ 0 | Линейный рост до threshold |
| **Migration cost** | Стабильный | Растёт с каждым добавленным workaround'ом |
| **Подходит для** | Качественных сдвигов (новая платформа, рефакторинг, абстракция) | Инкрементальной стоимости (capacity scaling) |

**Тест выбора:** «Растёт ли debt линейно с N или есть точка качественного сдвига?» Качественный сдвиг → state-based. Линейный рост ёмкости/нагрузки → counter-based.

**Failure mode:** counter-based для качественного сдвига → к trigger N=20 уже написано 3 OS-specific install-скрипта, миграция дороже, чем сделать extension при N=1.

**Применимо к:** решениям о вводе абстракций, замене стека, миграции с PoC на production stack, кросс-платформенным архитектурам.

**Источник:** session-transcript 2026-05-27 (peer-сессия 21 wp358-archgate, Тема 4 — switching B → A).


### DP.D.106: «Обнаружение → действие» контур ≠ «литерал → вычисленное» (диагностика gap-ов в скаффолдах)

**Источник:** peer-session 2026-05-30-07-gap-list-day-open (Тема 2), WP-356.

«Литерал → вычисленное» — поверхностная диагностика gap-а: «текст в шаблоне был placeholder вместо команды → заменить на вызов скрипта». Лечит симптом, не корень.

«Обнаружение → действие» — корневая диагностика: «нет замкнутого контура от detection к blocking action — даже если placeholder заменён, нет proven path от signal к stop the line». Замена литерала на `STATUS: skipped (no data)` не лечит отсутствие источника данных — pipeline молча проходит как «всё OK».

**Тест:** «если источник данных вдруг исчезнет, что произойдёт в pipeline?»
- Тихо `STATUS: skipped` → контур разорван (поверхностный fix).
- Stop the line + actionable error + блокировка → контур замкнут (корневой fix).

**Уровневая декомпозиция:** для каждого gap определить разорванный слой контура — скрипт→документ, подсистема→документ, скаффолд→инцидент, inbox→SLA.

**Применимо:** скаффолды, day-open хуки, build-pipelines, deployment-проверки — везде где «отсутствие данных» не должно молча проходить как «всё OK».

### DP.D.107: Косметический баг ≠ Operational alert

**Тест:** будит ли неверный output оператора?

| Косметический баг | Operational alert |
|------------------|-------------------|
| false-positive в read-only dashboard | false-positive в alert-source (пейджер, on-call) |
| оператор замечает «когда-нибудь» | оператор вызван в 09:00 субботы |
| backlog OK | править в той же сессии |
| severity = cosmetic | severity = operational |

**Почему важно:** распространённая ошибка triage — «неверная цифра / неточный SQL / wrong window» → косметика → backlog. Тест жёстче: если неверный output **порождает action** у оператора (просыпание, проверка, эскалация) — это operational, даже когда code-fix = одна строка.

**Антипаттерн:** alarm fatigue от cosmetic-fixed-as-cosmetic alerts накапливает desensitization к реальным incidents.

**Тест границы:** «если игнорировать этот баг 30 дней — кто-то будет разбужен / отвлечён зря?» Да → operational; нет → cosmetic backlog OK.

**Прецедент:** WP-7 pulse-daily-report (2026-05-30, peer-session 2026-05-30-17): UX Alert SQL-фильтр `activity_date = CURRENT_DATE` вместо 24h окна → false-positive «бот умер 0 DAU» в 09:00 субботы. Изначально классифицирован как «cosmetic», переклассифицирован в operational.


### DP.D.104: content_role ≠ process_position (двухосная модель роли в multi-agent peer-сессии)

**Источник:** WP-367 Ф5, peer-session 2026-05-30-06, DP.SC.154 v4 (commit a65df76).
**Standalone-определение:** см. [DP.SC.154 §3.1, §6.2, §13](../08-service-clauses/DP.SC.154-multi-agent-conversational-session.md).

| Ось | Что задаёт | Возможные значения | Источник |
|-----|-----------|--------------------|----------|
| **content_role** | Домен-контекст (4 аспекта: критерии метода, формат артефакта, критерии качества, связи с другими ролями) | `DP.ROLE.NNN` \| `MIM.R.NNN` \| `ad-hoc:<имя>` | Pack или `meta.yaml.ad_hoc_roles` |
| **process_position** | Координация хода (lock + escalation invariants) | `writer` \| `peer` | Default `initiator = writer`; перенос через `SWAP_WRITER` (ACK/NACK) |

**Default rule:** инициатор сессии = writer по умолчанию, без обсуждения в Opening. Opening обсуждается только для content_role.

**SWAP_WRITER** = explicit маркер передачи writer-позиции с ACK/NACK другой стороны и записью в `meta.yaml.swap_history`. Нужен потому что lock-инвариант требует ровно одного writer; «два writer одновременно» = collision (нелегитимная комбинация).

**ROLE_DRIFT** — смена content_role в середине сессии:
- **Incremental** (тот же домен/семейство) → маркер `ROLE_DRIFT_INCR` в реплике, сессия продолжается.
- **Fundamental** (смена домена) → закрываем сессию + открываем новую с правильным `content_role`.

**Почему не трёхосная модель** (content × process × initiative): initiative — session-invariant (фиксируется в Opening), не per-turn атрибут; дублируется на 10 реплик; 3! комбинаций не оправданы 2² базой.

**Тест границы:** «изменилось ли что — *что* делает участник или *как* координирует ход?» Что → content_role. Как → process_position.

**Применимость:** любой turn-based ролевой протокол (peer-programming, code review, brainstorming), где у участника есть и доменная экспертиза, и процессная функция на ходу.

### DP.D.105: scaffold-инициация ≠ point-capture ≠ онтологическая интеграция (три роли производства Pack-знания)

**Источник:** WP-369, peer-session 2026-05-30-11-creator-orgdev-roles-design.

Производство доменного knowledge (Pack) внутри knowledge-системы распределено по трём существенно разным ролям, путаемым при первом проектировании:

| Роль | Артефакт | Длительность | Контракт |
|------|----------|--------------|----------|
| **Scaffold-инициация** (`/pack-new`) | Новый Pack из шаблона, новый раздел | Секунды-минуты | Структура соответствует шаблону |
| **Point-capture** (`/ke`) | Дополнение существующего файла фактом/различением/правилом | Секунды | Факт идентичен оригиналу + маршрутизация в нужное место |
| **Онтологическая интеграция** (Создатель паков) | Связное покрытие домена (роли, обещания, методы, FM, инварианты) | Часы-недели | Полный SPF-цикл; ≥3 фаз SPF/process 01-11; отсутствие коллизий с другими Pack |

**Объект Создателя** = процесс наполнения Pack по SPF/process, не готовый артефакт. Характеристика качества = глубина SPF-цикла × качество различений × отсутствие коллизий.

**Тест границы:**
- «Появится ли в результате новый файл шаблонной структуры?» Да → scaffold.
- «Дописал ли я существующий файл фактом?» Да → capture.
- «Прошёл ли я ≥3 фаз SPF/process?» Да → онтологическая интеграция.

**Опасности смешения:**
- Scaffold-роль, претендующая на онтологическую интеграцию → создаёт «мёртвые Pack-заготовки» без содержательного покрытия.
- Capture-роль, претендующая на интеграцию → фрагментирует домен (множество разрозненных фактов без связности).

**Применимость:** проектирование knowledge-production каталогов в Pack-системах (Aisystant, Roam, Obsidian-граф, knowledge-pack экосистемы).

### DP.D.125: Стратегическая доменная роль ≠ infrastructure-agent

| Стратегическая доменная роль | infrastructure-agent |

### DP.D.126: Negative definition ≠ Positive definition (для кодификации craft)

Кодификация craft-знания (вкус, стиль, мастерство) допускает два способа определения. Они не равноценны: для воспроизводимости выигрывает negative.

| Negative definition | Positive definition |
|---------------------|---------------------|
| Каталог запретов (антипаттернов) + пара «было/стало» | Абстрактная формула «как делать хорошо» («красивый код — это…») |
| Вкус = отсутствие запахов | Вкус = наличие достоинств |
| Проверяемо на конкретном артефакте без интерпретации | Требует интерпретации, недетерминировано |
| Дополняется новым прецедентом, не переписывается | Переписывается при каждом уточнении |

**Тест:** «Можно ли проверить нарушение правила на конкретном артефакте без интерпретации?» Да → правило сформулировано negative-способом корректно. Нет → переформулировать через запрет + якорь.

**Прецеденты в Pack (кросс-доменный паттерн):**
- DP.SC.050 (`communication-style-base.md`) — речевой craft: 11 правил = запрет + примеры.
- DP.SC.172 (`engineering-code-style-base.md`) — инженерный код-стиль: перечень запахов с «было/стало».

Оба независимо построены по negative definition в разных доменах craft (проза vs код) — это и подтверждает обобщаемость различения, а не один частный случай.

**Граница слоя:** это различение (как определять), не воспроизводимый метод. «Собрать 5 антипаттернов» — эвристика, не алгоритм; место в `01B-distinctions`, не в `03-methods`. Метод-классификация исходного KE-кандидата (DP.M.302) отвергнута, знание зафиксировано как distinction; ID DP.M.302 освобождён.

### DP.D.133: Голос (Voice) ≠ Тон (Tone) агента

**Голос** — стабильная подпись агента: неизменяемые свойства (ритм, лексика, метафоры). Всегда включён; пользователь не конфигурирует. Живёт в base-промпте.

**Тон** — ситуативная настройка 4 осей: формальность, юмор, уважительность, энтузиазм. Выбирается пользователем/пресетом. Только для человеко-регистров; технические и аудит-регистры тон не имеют.

**Тест:** «Меняется ли от ситуации?» Да → тон. «Узнаваемо при смене ситуации?» Да → голос.

**Ошибки смешения:**
- Пользователь может «отключить голос» → агент теряет узнаваемость
- Голос реализован через тон → одно переключение уничтожает оба

### DP.D.134: Logout (Kratos login-сессия) ≠ Отзыв OAuth-grant (Hydra)

**Logout / «Выйти со всех устройств»** (Kratos `settings/logout`) — гасит login-сессии пользователя на платформе. Управляет методами входа, не выданными разрешениями.

**Отзыв OAuth-grant** (Hydra admin API + RFC 7009 revoke) — отзывает refresh-токены/grants, выданные внешним клиентам (напр., claude.ai MCP). Требует предъявить сам токен; у пользователя обычно нет прямого доступа.

**Следствие:** Reconnect MCP-коннектора переиспользует живой grant — окна входа не появляется даже после logout.

**Тест:** «После logout и переподключения показалось окно входа?» Нет → grant жив, сессия не прервалась.

**UI-следствие:** Раздел «Управление доступом» нужно делить на две секции: «Активные сессии входа» (Kratos) и «Разрешения приложений» (Hydra), с разными API для каждой.

**Источник:** WP-411 Ф5, peer-session 2026-06-12-01.

### DP.D.135: Метод входа (authentication method) ≠ LLM-аккаунт (ресурсная подписка)

При проектировании multi-method login возникает соблазн связать «каким методом вошёл» с «какую LLM использует». Это смешение двух ортогональных осей.

| Метод входа | LLM-аккаунт |
|-------------|-------------|
| Какой идентификатор использован для логина (email, Google, Apple, BYOK-код) | Какая подписка или ключи используются для модели (Claude subscription, BYOK-ключи) |
| Ось идентификации: Ory/Kratos anchor | Ось ресурсов: billing, квоты, провайдер модели |
| Несколько методов → одна identity (account linking, стандартный паттерн) | Один billing-аккаунт → одна LLM-квота |
| Управляется identity provider (Ory Kratos) | Управляется billing системой (отдельно от IdP) |
| Смена метода входа не меняет ресурсы | Смена LLM-аккаунта не меняет identity |

**Тест:** «Смена метода входа меняет ли LLM-квоту?» Нет → оси независимы. Если отвечаешь «да» — смешиваешь оси.

**Ложный отказ от account linking:** «Добавить Google-логин = создать второй аккаунт» — ошибочно, если у Ory уже есть identity с этим email. Account linking привязывает новый метод входа к существующей identity, LLM-аккаунт не затрагивается.

**Связи:** DP.D.087 (OAuth state storage — смежно), DP.D.134 (Logout ≠ OAuth-grant revocation — другой аспект Ory sessions)

**Источник:** session-transcript 2026-06-12 + git diff IWE/.claire/rules/distinctions.md (38b1205, WP-411 Ф5)

### DP.D.138: Локализация-как-derived-only ≠ Два параллельных продукта

При выпуске продукта на двух языках (RU/EN) возникают два принципиально разных архитектурных решения:

| Цепочка одного истока | Два параллельных продукта |
|-----------------------|--------------------------|
| Один первоисточник (RU) + автоконвейер в производное (EN) | Две независимые ветки/репо, каждая редактируется вручную |
| Target read-only: iwesys.ru руками не правят — пишет только конвейер | Target может редактироваться напрямую |
| Дрейф невозможен: следующий прогон конвейера стёрт | Двусторонний дрейф (как в FMT/scripts vs scripts/) |
| Масштабирование бесплатно: добавить язык = добавить конвейер | Масштабирование линейно по числу языков × усилие |

**Инвариант:** target-репо защищается branch protection от прямых push'ей.

**Тест:** «Можно ли вручную поправить target, минуя источник?» Да → архитектура двух параллельных продуктов (дрейф неизбежен). Нет → цепочка одного истока работает.

**Обобщение:** это extension паттерна «Source-of-truth ≠ Производный» с внутренних артефактов (scripts, config) на уровень продуктовой локализации (язык, регион, дистрибутив). Принцип тот же — новый контекст применения.

### DP.D.139: JIT provisioning через client-mediated flow ≠ direct-link flow

JIT provisioning (создание аккаунта на лету при первом обращении) реализуется на разных уровнях стека. Ключевое различение — где живёт provisioning-логика:

| Client-mediated flow | Direct-link flow |
|---------------------|-----------------|
| Пользователь приходит через посредника (MCP, OAuth callback, SSO relay) | Пользователь открывает ссылку входа напрямую |
| Посредник вызывает provisioning-endpoint ДО redirect на identity-форму | Провайдер не знает о намерении создать аккаунт — форма появляется сразу |
| Нового пользователя создают автоматически | Нового пользователя форма не создаёт — только authenticate |
| Пример: MCP flow через claude.ai → Ory создаёт аккаунт | Пример: прямая ссылка `/login` → Ory не знает, что аккаунта нет |

**Инвариант:** JIT provisioning работает только там, где стоит interceptor/посредник.

**Тест:** «Выполняется ли provisioning, если пользователь приходит без посредника?» Нет → асимметрия flow'ов (риск DP.FM.159). Требуется либо выносить provisioning на уровень identity-провайдера, либо явное UX-разделение двух entry-point'ов.

### DP.D.141: Источник доставки ≠ Политика-на-место ≠ Физический транспорт

| Источник доставки | Политика-на-место | Физический транспорт |
|-------------------|-------------------|----------------------|
| Производитель сообщения (урок-марафон, нудж, персональное руководство) | Правило для **поверхности** (Telegram-чат): потолок, дедуп, приоритет, предпочтения | Очередь + воркер: marathon_queue, общая очередь class-workers |
| Несколько | Одна на место (source-agnostic) | Один или несколько (вопрос цены миграции) |
| «Что слать» | «Сколько и в каком порядке упадёт пользователю сюда» | «Через какую трубу» |

**Почему важно**: «Доставка уроков/сообщений/руководства — одна или несколько?» расщепляется на 3 оси. Источников несколько; политика доставки одна и привязана к МЕСТУ (не к источнику и не к каналу-Bot-API): один журнал «что ушло пользователю» (`learning.domain_event`) = source-of-truth, на нём потолок/дедуп/приоритет/предпочтения — это **Доставщик** ([DP.SC.177](../08-service-clauses/DP.SC.177.md)). Физических транспортов один-или-несколько — вопрос цены миграции, не правильности. Жёсткий потолок видит только capped (must-deliver обходит); отдельная очередь НЕ обязана консультироваться у Доставщика ради потолка — общее только read-side (журнал).

**Тест**: «потолок „≤N/день" считает по источнику, по каналу или по месту?» По месту (сколько упало человеку в чат), source-agnostic.

**Связано с**: [DP.D.140] (Наблюдатель-сторож ≠ Сервис доставки), DP.SC.177 (Доставщик), Информация (источник) ≠ Канал доставки ≠ Место (поверхность) — WP-417.

### DP.D.142: Тело контента (рендер-в-место) ≠ Уведомление о контенте (сообщение)

| Тело (рендер-в-место) | Уведомление (сообщение) |
|----------------------|-------------------------|
| Артефакт открывается в своём месте | Короткий пинг прилетает в чат |
| Доставка через pull (git-репо, личная страница, `/lesson pull`) | Доставка через push (Telegram-нудж класса `capped`) |
| Полный контент (документ, плейлист, отчёт, персональное руководство) | Триггер открыть контент (CTA: «занятие готово / руководство обновлено») |
| Контракт места рендера | Контракт очереди сообщений |
| Размер не ограничен политикой Доставщика | Учитывается потолком «≤N/день» |

**Почему важно**: Гнать тело руководства через очередь сообщений = спутать рендер-в-место с транспортом сообщений. Поверхности разные: место рендера хранит и отдаёт по запросу; очередь сообщений доставляет push-импульс. Раздельные SLA, разные failure modes, разные политики приватности.

**Тест**: «человек получает это, открыв сам (pull/страница), или ему прилетает в чат (push)?» Тело — открывает сам; уведомление — прилетает.

**Применение**: при проектировании доставки любого крупного артефакта (документ, отчёт, плейлист, персональное руководство) — отделить тело (рендер-в-место) от уведомления (сообщение). Долг (WP-418 Ф4): мёртвый push-путь тела (`engines/tailor/delivery.py:notify_tailor_lesson`, `BotTailorAdapter` — ноль живых вызовов после WP-301) вычистить или явно переподтвердить git-канал в Pack.

**Связано с**: [DP.D.141] (Источник ≠ Политика-на-место ≠ Транспорт), [DP.D.100] (IWE как платформа доказательств ценности ≠ система продуктивности), WP-301 (git-канал персонального руководства).

### DP.D.143: Интеграция как архитектурная конвенция ≠ Интеграция в открытом зонтике

| Конвенция (живёт у владельцев) | Открытый зонтик (живёт фактом контейнера) |
|--------------------------------|--------------------------------------------|
| Кросс-ссылки между живыми РП-владельцами + строка-конвенция в documentation | Связь держится потому, что зонтик-РП открыт |
| Переносимая истина | Inventory (мёртвый координационный капитал) |
| Сохраняется при закрытии зонтика | Растворяется при закрытии зонтика → шов через 2 месяца |
| Audit-able по grep cross-references | Не audit-able вне самого зонтика |

**Почему важно**: Когда зонтик собрал N дочерних РП в единый data-flow (память → наблюдаемость → аналитика), связь между ними не должна держаться фактом «зонтик открыт». При закрытии её фиксируют кросс-ссылками между живыми РП-владельцами (WP-295 ↔ WP-290) + строкой-конвенцией в documentation/manifest целевых сущностей. Иначе через 2 месяца после закрытия зонтика между дочерними появляется шов: ни один РП не «хозяин» связи.

**Тест**: «если закрыть зонтик-контейнер, связь между дочерними РП сохранится явной ссылкой или растворится?» Растворится → шов, конвенция не зафиксирована.

**Применение**: при закрытии любого umbrella WP с дочерними артефактами — перед `status: done` материализовать межартефактные связи как кросс-ссылки + строку-конвенцию в живых РП.

**Связано с**: [DP.D.064] (То же обещание ≠ Другое обещание — scope-дискриминатор при закрытии РП), Inventory ≠ Progress (Goldratt), OwnerIntegrity (один факт — одно место).

### DP.D.144: Пустой output контрольной роли ≠ «нет находок»

| «Нет находок» (ожидаемое) | Пустой output (нарушение обещания) |
|---------------------------|-----------------------------------|
| Роль проверила → нарушений нет → output: «ОК, нарушений нет» | Роль насчитала critical=N, но содержимое excerpt потеряно |
| Получатель может действовать: «всё под контролем» | Получатель не может действовать: есть сигнал, нет содержания |
| Честный ноль | Счётчик > 0 при пустом теле |
| Закрывает ответственность контрольной роли | Нарушает обещание контрольной роли |

**Почему важно:** Контрольная роль обязана выдавать содержательный output — иначе создаёт ложно-зелёный сигнал «что-то есть, но разбираться не с чем». Счётчик > 0 при пустом excerpt → парсинг секции отчёта сломан или передача потеряна. Слепая зона хуже отсутствия алерта: пилот видит «нужно внимание», но не может действовать.

**Тест:** «Может ли получатель отчёта действовать по тому, что ему пришло?» Нет → роль не выполнила обещание — это не «нет находок».

**Применение:** если счётчик > 0 и excerpt пуст → баг форматтера/транспорта, не «нет данных».

**Связано с:** [DP.D.080] (Контрольная роль ≠ Операционная роль), [[Детектор существует ≠ детектор блокирует]].

### DP.D.145: Probe-канал (прямая проверка) ≠ Cascade detection (обнаружение через следствия)

| Probe-канал | Cascade detection |
|-------------|-------------------|
| Напрямую проверяет корневую зависимость | Обнаруживает корень через downstream-эффекты |
| Время обнаружения: ≤ период probe (N мин) | Время обнаружения: время до жалобы или падения метрики |
| Явный сигнал: «LLM отдала != 200» | Пассивный: «ошибки в боте, DAU=0» |
| SLA: предсказуемый | SLA: непредсказуемый |

**Почему важно:** Cascade detection пассивен и отстаёт — каждый downstream-сигнал указывает на следствие, а не корень. Пример: 403 от внешней LLM обнаружился через downstream с задержкой ~1ч. Прямой probe ловит корень за ≤N мин.

**Тест:** «Есть ли канал, который проверяет корневую зависимость напрямую, а не её следствия?» Нет → детектирование сбоя = время до жалобы.

**Применение:** для каждой критической внешней зависимости (LLM, БД, payment-provider, auth) — отдельный прямой probe-check.

**Связано с:** [DP.D.146] (Бизнес-алерт ≠ Технический алерт), [[HTTP status check ≠ keyword check]], [[Внутренний алерт (failure) ≠ Внешний heartbeat (dead-man's switch)]].

**Источник:** peer-session 2026-06-15-23-ke-candidates-review.

### DP.D.146: Бизнес-алерт ≠ Технический алерт

| Бизнес-алерт | Технический алерт |
|--------------|------------------|
| Метрика ценности: DAU, MRR, LDAU, conversion | Здоровье инфры: error-rate, latency, exception |
| Пример: LDAU = 0 (никто не учился 24ч) | Пример: error rate +20%, P95 > 5s |
| Не покрывается стандартными APM-инструментами | Покрывается стандартными APM-инструментами |
| Нужен явный пороговый триггер с push-каналом | Нужен Sentry / PagerDuty |

**Почему важно:** Технические инструменты мониторинга не покрывают бизнес-сигналы автоматически. LDAU=0 — P0-сигнал продуктового класса, который тонет в daily-отчёте без отдельного push-уведомления.

**Тест:** «Если ключевая бизнес-метрика обнулится — узнает ли команда до утра?» Нет → нет отдельного бизнес-алерт-канала.

**Применение:** определить 1-2 ключевых бизнес-метрики и завести явные пороговые триггеры с push-каналом, независимые от технического мониторинга.

**Связано с:** [DP.D.145] (Probe-канал ≠ Cascade detection), [[Сторож, метящий просрочку ≠ сторож, самовосстанавливающий её]].

**Источник:** peer-session 2026-06-15-23-ke-candidates-review.

### DP.D.147: Минимальный содержательный барьер (GREEN скрипта) ≠ Полное качество артефакта

| Минимальный барьер пройден | Артефакт готов к эксплуатации |
|---------------------------|-------------------------------|
| Структурные критерии выполнены (N секций, непустые блоки, обязательные заголовки) | Логика алгоритма проверена, edge cases покрыты, peer-review пройден |
| Автоматический скрипт говорит GREEN | Вертикальный аудит (ВДВ, peer-сессия) подтверждает содержание |
| «Артефакт не сломан структурно» | «Артефакт делает то, что обещает» |
| Нижняя оценка: false-negative невозможен | Полная оценка: false-positive невозможен |

**Почему важно:** Автоматические скрипты проверяют форму (есть ли `## Algorithm`, `### Step N`, непустое содержание). Они не ловят логические дефекты алгоритма, несогласованность с доменными знаниями, пропущенные сценарии. Приравнивание GREEN к «готов» → переоценка фазы. Кейс: content-audit.sh, WP-422 Ф9 — 5 структурных критериев, GREEN для всех скиллов, при этом некоторые алгоритмы содержали логические ошибки.

**Тест:** «Если скрипт выдаёт GREEN — можно ли немедленно деплоить артефакт в продакшен?» Нет → GREEN означает только «минимальный барьер», не «готов».

**Применение:** в отчётах о фазах явно указывать: «прошёл минимальный структурный барьер (content-audit GREEN); логическое качество требует отдельного слоя проверки (ВДВ-аудит, peer-review)». Не суммировать в «фаза закрыта успешно» без второго слоя.

**Связано с:** [[Тесты зелёные ≠ миграция корректна]], [[Детектор существует ≠ детектор блокирует]], [DP.D.148] (Разбор-на-бумаге ≠ Наблюдаемый артефакт), [DP.M.314] (структурный критерий vs символьная эвристика).

**Источник:** session-transcript 2026-06-17, WP-422 Ф8+Ф9, commit 0dbe3b0 (content-audit.sh).

### DP.D.148: Разбор «на бумаге» (walkthrough) ≠ Наблюдаемый артефакт (smoke)

| Walkthrough (разбор «на бумаге») | Smoke (наблюдаемый артефакт) |
|----------------------------------|------------------------------|
| Описательный разбор логики без исполнения | Реальный прогон, оставляющий след в файловой системе |
| Не проверяет код/скрипт — только намерения | Проверяет фактическое поведение кода |
| Нет артефакта для верификатора | Артефакт: новый файл, изменённый файл, git diff |
| Эффективен для обнаружения логических противоречий в плане | Обязателен для закрытия фазы как «протестировано» |
| Может проводиться до имплементации | Требует работающей имплементации |

**Почему важно:** Walkthrough не защищает от регрессий в коде. Если smoke-сценарий не оставил проверяемого следа — регрессия в алгоритме может остаться незамеченной. Кейс: WP-422 Ф8 — 3 из 5 smoke-сценариев предлагалось заменить walkthrough; при этом именно те сценарии (смена уровня, перенос Claude→Kimi, обезличивание путей) покрывают путь через skill-creator, где возможны регрессии.

**Тест:** «Оставил ли smoke-сценарий проверяемый след в файловой системе (новый файл, изменённый файл, git diff)?» Нет → это walkthrough, не smoke.

**Применение:** в DoD фазы: «smoke-тесты пройдены» означает артефакты созданы на диске + верификатор зафиксировал результат. Walkthrough допустим как дополнительный шаг, но не заменяет smoke.

**Связано с:** [DP.D.147] (минимальный барьер ≠ полное качество), [DP.M.088] (Pack-инварианты: defense-in-depth).

**Источник:** session-transcript 2026-06-17, peer-сессия WP-422 Ф8, report.md «Главный инсайт».

### DP.D.151: Распределённая шина захвата следов ≠ Локальная шина (Local Gateway)

Распределённая шина: один логический журнал (read-side SoT) с N физическими адаптерами — облачный (бот/клуб/LMS) и локальный (VS Code/Vault). Каждый адаптер пишет туда, где зарождается след. Локальная шина: все следы централизуются через Local Gateway на Mac — невозможно для облачно-рождённых следов: если Mac выключен, след теряется, граница «платформа ≠ IWE» нарушена.

**Инвариант:** dual-write запрещён. Composition rule: след с приватно-локальными данными в миксе → локальный адаптер; целиком облачный → облачный адаптер. **Тест:** «Может ли след физически доехать до Mac после рождения в облаке без потери?» Нет → шина не может быть только локальной. Уточняет [[суть ≠ интерфейс]] на сторону захвата и [[Local Gateway (DP.IWE.005) ≠ Cloud Gateway (DP.IWE.003)]]. Источник: WP-427 Ф2 peer-session 2026-06-18.

### DP.D.153: ICT-токен (ict_...) ≠ Ory OAuth (claude.ai / VS Code коннектор)

| Аспект | ICT-токен | Ory OAuth (OIDC) |
|--------|-----------|-----------------|
| **Формат** | `ict_...` строка | Ory refresh_token / JWT access_token |
| **Клиент** | Claude Code CLI (`.mcp.json`) | claude.ai, VS Code extension |
| **Получение** | `POST /internal/auth/exchange` + auth-код из бота | OIDC Authorization Code flow через Hydra |
| **Видимость** | Показывается в `/my_clients` бота | НЕ показывается в `/my_clients` |
| **Хранение** | `.mcp.json` в проекте | Ory token store |
| **Без токена** | Claude Code CLI ходит как T0 (базовый набор, без тира) | Нет доступа к gateway |

**Тест различения:** «Виден ли мой коннект в `/my_clients` бота?»
- Да → ICT-токен (Claude Code CLI)
- Нет → Ory OAuth (claude.ai / VS Code)

**Почему важно:** Без `Authorization: Bearer ict_...` в `.mcp.json` Claude Code CLI работает как анонимный T0 — получает базовый набор инструментов без персонализации и тировых возможностей. ICT и Ory — независимые механизмы авторизации, не взаимозаменяемые.

**Дополнение (JWT кэш):** Ory JWT кэшируется ~1 час и может содержать устаревший тир. Когда JWT говорит T1 — gateway обязан делать DB-fallback для актуального тира пользователя.

**Связано с:** [DP.D.087] (OAuth pending state in-memory ≠ externalized), [DP.FM.153] (intermittent 401 static key).

### DP.D.156: Операция агента, воспроизводимая ядром без него ≠ Авторитетная новая суть, закреплённая агентом

Когда агент (Claude, Kimi, Hermes, агент пользователя) задействует свои возможности — вызывает инструмент, генерирует навык, пишет в свою встроенную память — где проходит граница между «интерфейс делает свою работу» и «суть утекла в интерфейс»? Per-операционный тест: **может ли ядро IWE (Aisystant MCP) воспроизвести итоговое состояние без этого агента?**
- Да → операция воспроизводима ядром = легитимная работа интерфейса. Разрешено.
- Нет → агент стал единственным держателем новой авторитетной сути. Запрещено.

Это per-операционная операционализация различения «суть ≠ интерфейс»: то даёт системный тест («новый экземпляр знает IWE с нуля настройки»), это — тест на каждое отдельное действие агента.

**Правило перетока памяти (операционное следствие).** У агента два слоя памяти с разными правилами (опирается на «Персона ≠ Память ≠ Контекст», HD #27):
- **Контекст диалога** (runtime ephemeral; напр. встроенная SQLite Hermes, история сессии) — остаётся локальным у агента, это норма; синхронизация не требуется.
- **Память.Derived** (авторитетные факты о пилоте/мире) — реконсилируется в ядро через обычный capture-процесс: агент только **предлагает** факт, апрув даёт экстрактор / стратег / пилот. Агент не назначает истину сам.

Особый случай — Hermes (Nous Research): у него, в отличие от Claude/Kimi, есть встроенная в рантайм автономная память (диалоги, навыки с self-evolution, подключаемые memory providers). По этому различению она = оперативный слой и генератор кандидатов, НЕ второй источник истины.

**Тест:** «Повторит ли IWE этот итог без данного агента?» Нет → суть закреплена агентом (нарушение). И: «Кто утвердил факт как авторитетный — агент сам или процесс IWE?» Агент сам → нарушение.

**Связано с:** «суть ≠ интерфейс» (это его per-операционная операционализация), [DP.FM.160] (интерфейс без ядра → галлюцинация), «Memory provider (Honcho-style) ≠ Digital Twin», «Персона ≠ Память ≠ Контекст» (HD #27).

**Источник:** peer-session 2026-06-22-03-hermes-agent-iwe-integration (Claude + Kimi).

### DP.D.157: Прокси-на-пути (роутинг/расходы) ≠ Наблюдаемость-сбоку (трассировка/оценка качества)

Два дополняющих (не взаимозаменяемых) слоя LLM-ops, которые легко спутать: оба «про LLM-вызовы» и оба показывают стоимость.

| Аспект | Прокси-на-пути | Наблюдаемость-сбоку |
|--------|----------------|---------------------|
| **Позиция** | НА пути вызова (каждый запрос проходит насквозь) | СБОКУ (пассивно трассирует случившееся) |
| **Делает** | роутинг, единая точка биллинга, кеш, fallback, подмена модели | трассировка spans, разбивка расходов, оценка качества (LLM-as-judge) |
| **Вмешивается в вызов** | да (маршрутизирует / кеширует / подменяет модель) | нет (только наблюдает и оценивает постфактум) |
| **Примеры** | OpenRouter, LiteLLM (WP-400), Helicone, Portkey | LangFuse, LangSmith, Arize Phoenix |

**Корень ошибки:** «у нас уже прокси сводит расходы — зачем ещё observability?» — оба отчитываются о стоимости, поэтому кажутся заменой. Но прокси не оценивает качество и не хранит span-level трассы; observability не маршрутизирует и не кеширует.

**Тест:** «Компонент стоит НА пути вызова (можно роутить / кешировать / подменять модель) или СБОКУ (только наблюдает и оценивает)?»

**Связано с:** [[Замена runtime ≠ Замена модели]] (distinctions.md); [DP.SOTA.015] (3+1 framework, таксономия «AI gateways» vs «AI-native tracing»); WP-400 (LiteLLM proxy), WP-444 (observability).

**Источник:** session-transcript 2026-06-25 (Оперативка ИТ; прокси Ильшата через OpenRouter + LangFuse), WP-444.

### DP.D.158: Основное бизнес-событие ≠ Сторонний best-effort захват (деградация без блокировки)

К основному бизнес-событию (транзакция, начисление, регистрация) часто пристёгивают вторичный сбор данных «на будущее» (телеметрия, обогащение, аналитический след). Правило: вторичный захват — **отдельная best-effort ветка ПОСЛЕ основного события**; его отказ (нет согласия пользователя ИЛИ ошибка записи) не откатывает и не блокирует основное событие.

| Основное бизнес-событие | Сторонний best-effort захват |
|-------------------------|------------------------------|
| Источник ценности (баллы, оплата, чек-ин) | Обогащение для будущего анализа (текст, телеметрия) |
| Должно зарегистрироваться всегда | Может молча отсутствовать |
| Коммит в основной транзакции | try / best-effort после коммита основного |
| Отказ = инцидент | Отказ = деградация без сигнала пользователю |

**Тест:** «Если падает вторичный захват, теряется ли основное событие?» Да → захват не развязан (анти-паттерн); ветки должны быть независимы.

**Связано с:** [[Read-path ≠ Write-path (side effects)]] (distinctions.md); consent-vocab Учётчика (`pending_consent` / `consent_unverified`, WP-427 Ф5); [DP.D.113] (AND ≠ OR семантика multi-storage state).

**Источник:** WP-427 Ф6.2, peer-session 2026-06-25-02, commit event-gateway 985d730 (захват HTML-текста поста клуба после начисления баллов).

### DP.D.159: Последовательная выкатка по направлению зависимости ≠ Параллельная выкатка (аддитивная фича через слои в разных репо)

Когда новая фича добавляется несколькими слоями в РАЗНЫХ репозиториях/ветках (схема БД + код-писатель + пользовательский триггер-текст), атомарный co-deploy невозможен. Выкатывать строго по направлению зависимости: сначала производитель зависимости, затем потребитель, затем инициатор записи.

| Последовательно по зависимости | Параллельно |
|--------------------------------|-------------|
| (1) таблица БД (migration) → (2) код-писатель → (3) пользовательский триггер | все слои разом |
| у каждого слоя при выкатке уже поднята его зависимость | слой стреляет в ещё-не-существующую зависимость |
| безопасно при cross-repo (нет атомарной транзакции деплоя) | код пишет в отсутствующую таблицу; бот собирает согласие на захват, которого ещё нет |

**Тест:** «Если выкатить только этот слой, есть ли у него уже поднятая зависимость?» Нет → не выкатывать первым.

**Граница:** forward/аддитивный комплемент к [DP.M.222] (3-компонентный **атомарный** co-deploy — когда всё умещается в один PR) и к [[Авто-деплойный прокси нельзя пушить раньше нового бэкенда]] (distinctions.md). ### DP.D.160: Типизация (is-a, отнесение к роду) ≠ Синонимия (is-named) — семантика specializes в графе понятий

В онтологическом графе связь `specializes` (ребёнок → родитель) означает **«это ЕСТЬ X»** (типизация, отнесение к роду), а не **«это НАЗЫВАЕТСЯ X»** (синонимия).

| Типизация (is-a) | Синонимия (is-named) |
|-----------------|---------------------|
| «Метод ABC → U.Method» = «ABC есть вид Метода» | «Метод ABC = другое имя для Метода» |
| Имя ребёнка — собственное (ABC) | Имя ребёнка наследуется от родителя |
| Тест: «Этот узел относится к роду X?» | Тест: «Этот узел называется X?» |
| Связь используется для типизации | Связь используется только для истинных синонимов |

**Почему важно.** В данных WP-439: у корня `U.Method` 420 дочерних узлов. Наследование имени по `specializes` → 420 сущностей с одинаковым именем «Method» (имена стёрты). Связь даёт **тип** ребёнка как подсказку системе перевода, но не имя.

**Правило для трансляторов.** При автоматическом переводе/именовании через граф: брать имя из `specializes`-родителя допустимо только для узлов, доказуемо являющихся синонимами (таких в данных < 1%). Для остальных — собственное имя из источника.

**Тест:** «Ребро означает "это ЕСТЬ X" (тип) или "это НАЗЫВАЕТСЯ X" (синоним)?» Тип → имя не наследуется.

**Опровергает дизайн-допущение** «РР-термины наследуют EN-имя по `specializes`» (WP-439 Ф2, сессия 05).

**Источник:** peer-session 2026-06-25-10; WP-439 Ф2 (migration 018); git diff DS-MCP/knowledge-mcp f681001.

### DP.D.161: Выход фазы для машины-потребителя = структура в БД (VIEW) ≠ человекочитаемый отчёт

Выбор формата выхода фазы определяется **типом потребителя**, а не удобством автора.

| Машина-потребитель (следующая стадия конвейера) | Человек-потребитель |
|------------------------------------------------|---------------------|
| Запрашиваемая структура в БД: VIEW, таблица, materialized view | Markdown-отчёт, документ |
| Читается программой напрямую через SQL/API | Читается человеком визуально |
| Отчёт для машины = лишний слой парсинга + не запрашиваемый | Структура для человека = избыточный SQL-overhead |
| Фаза имеет самостоятельный артефакт (VIEW) | Фаза «схлопывается» в отчёт |

**Тест:** «Кто потребитель выхода этой фазы — человек или следующая стадия конвейера?»
- Машина → структура (VIEW/таблица).
- Человек → отчёт.

**Следствие:** если выход потребляет машина, фаза не схлопывается в отчёт — её самостоятельный продукт = витрина в БД. Это меняет DoD фазы.

**Применение в WP-439 Ф2:** выход Ф2 (тип-подсказка для перевода) потребляет Ф3 (машинный конвейер) → созданы два VIEW: `concept_kind_context` (1043 строки) и `concept_translation_orphans` (2710 строк). Без VIEW Ф3 требовала бы парсинга markdown.

**Связано с:** DP.D.018 (Model ≠ View — ортогональное различение, о паттерне проектирования); DP.D.003 (Данные ≠ Представление). Не заменяет их, дополняет по оси «для кого».

**Источник:** peer-session 2026-06-25-10; WP-439 Ф2; git diff DS-MCP/knowledge-mcp f681001.

### DP.D.164: Метрика покрытия N/A (неприменима) ≠ Coverage PASS (критерий выполнен)

При однородном (односложном) трафике метрика вида «N≥порог наблюдений» не применима по существу: все входы идентичны, и N можно накрутить механически. Честный вывод — coverage = N/A («механизм проверен, метрика неприменима»), а не сфабрикованное проходное число.

**Тест различения:** «Можно ли набрать порог N, повторив один и тот же вход?»
- Да → метрика неприменима к данному трафику → объявить N/A.
- Нет (входы реально разнообразны) → метрика работает, проверять N≥порог.

**Почему важно:** Выдавать inapplicable метрику как «зелёную» — вид zero-masking (DP.FM.120): проблема спрятана, а не устранена. Явный N/A сохраняет честность верификации и позволяет заменить метрику, когда трафик станет разнообразным.

**Связано с:** [DP.D.148] (walkthrough ≠ observable smoke), [DP.D.147] (minimum content barrier ≠ full quality), [DP.FM.120] (zero-masking instead of rootfix). Источник: WP-423 Ф6.4, session-close 2026-06-21.

### DP.D.165: SPF (фреймворк вторых/доменных принципов) ≠ Pack (результат применения SPF)

|-----|------|
| Фреймворк: требования + процесс | Результат применения фреймворка |
| Задаёт форму и критерии домена | Наполненный инженерный ядро-учебник домена |

**Связано с:** [DP.D.166] (ось происхождения ≠ ось охвата). Источник: WP-451, семинар Левенчука 28.06.2026.

### DP.D.174: Локальный pre-push хук ≠ серверный branch-protection

**Описание:**
Локальный git-хук (pre-push) и серверный branch-protection — два независимых уровня защиты с разными моделями угроз.

- **Локальный хук** запускается в git-клиенте; защищает от небрежности и случайных ошибок авторизованных агентов; обходится через `--no-verify` или прямой API любым участником.
- **Серверный guard** (CODEOWNERS + branch-protection) применяется на уровне GitHub/GitLab; защищает от целенаправленных действий привилегированного пользователя, включая администратора.

**Следствие:** Оба уровня нужны одновременно; один не заменяет другой. Локальный хук без серверного guard = защита только от рядовых участников. Серверный guard без локального = медленная обратная связь разработчику.

**Тест:** «Администратор репо хочет сделать force-push в main — заблокирует ли локальный хук?» Нет — только серверный guard.

**Источник:** WP-436 Ф-agent-coord, 2026-06-30.
**Смежно:** DP.D.059 (три класса хранения credentials), DP.D.034 (модель контроля доступа).

### DP.D.175: Зона суверенитета данных = машина владельца, не managed cloud

**Описание:**
В суверенном гибриде (sovereign hybrid): алгоритм/метод обработки единый (централизован), исполнение с данными происходит на машине владельца, а не в managed cloud.

- **Managed cloud**: данные уходят в сторонний сервис для обработки → потеря суверенитета
- **Суверенный гибрид**: метод единый, данные остаются в своей зоне (tsekh-1 = личная машина пилота, не shared cloud server)

**Следствия для проектирования:**
1. **Downtime model**: машина может засыпать / уйти офлайн → delivery должна учитывать (snapshots, fallback, async)
2. **Data residency**: личные данные не уходят на сторонний управляемый сервис
3. **Deploy model**: шаблон разворачивается у каждого пользователя локально, нет единого shared processing cloud

**Тест:** «Где физически обрабатываются данные пользователя?» Если ответ — внешний управляемый сервис, это потеря суверенитета данных.

**Источник:** ADR-2026-06-30 (топология персональных руководств, ArchGate PASS).
**Смежно:** DP.D.172 (метод сборки ≠ место исполнения ≠ поверхность — ожидается pending), DP.D.030 (deployment topology), DP.D.059 (хранение credentials).

### DP.D.176: Учебный контент (guide/) ≠ Операционный контент (panel/)

**Описание:**
В контент-системе персонального обучения два независимых типа контента с разными жизненными циклами.

- **Учебный контент (guide/)**: неизменяемый смысл для изучения. Содержит знание, принципы, методы. Актуален независимо от текущего состояния системы. Аналог: учебник.
- **Операционный контент (panel/)**: задания, организационная информация, статистика прогресса. Меняется с изменением состояния системы. Аналог: рабочая тетрадь.

**Следствие для проектирования:**
Смешение в одну директорию guide/ делает её непригодной как учебный артефакт — пилот видит задания вместо знания. Разделение → разные директории, разные артефакты, разные жизненные циклы.

**Тест:** «Изменится ли этот контент при смене статуса пользователя или дедлайна?» Да → panel/. Нет → guide/.

**Источник:** WP-149 Ф-local-assembly-delivery, 2026-06-30.
**Смежно:** DP.D.172 (метод сборки ≠ место исполнения ≠ поверхность — pending), DP.D.073 (внешняя витрина ≠ внутренняя часть).

### DP.D.178: LPF — сквозная классификация фрагментов ≠ физический контейнер (папка, репо)

**LPF (Lifework Personal File)** — не папка и не целый репозиторий, а **сквозной атрибут классификации** фрагментов: фрагмент является LPF тогда и только тогда, когда он теряет смысл при замене конкретного носителя роли на другого носителя той же роли.

Два подслоя:
- **LPF-декларативный** — преимущественно `Lifework/`: «Личный устав», «Моя миссия», «Семейный уклад». Содержание специфично для данного человека, не переиспользуется при смене носителя роли.
- **LPF-оперативный** — фрагменты `current/`, `decisions/`, `sessions/`, `inbox/WP-*/` и их архивы. Представляют траекторию решений конкретного носителя. Один файл может одновременно содержать LPF-оперативный след (траектория) и TPF-контентный выход (итоговый артефакт).

**Тест:** «Теряет ли фрагмент смысл, если носителя роли заменить на другого носителя той же роли?» Да → LPF. Нет → TPF или DPF.

**Связано с:** [DP.D.166] (ось охвата FPF/DPF/LPF по Левенчуку), [DP.METHOD.104] (тест замены носителя). Источник: WP-448 Ф11, session-transcript 2026-07-02-03-wp448-f11-lpf-arch.

### DP.D.185: Разделение прав = сдерживание (containment), ≠ устранение причины

**Описание:**
Разделение прав (per-service роли, минимальные привилегии) ограничивает радиус поражения инцидента, но не устраняет причину, если источник инцидента находится внутри нового периметра.

- **Containment (сдерживание):** мера ограничивает область, в которой проблема может причинить вред. Причина продолжает существовать.
- **Root-cause fix (устранение причины):** мера исключает возникновение проблемы — нечему сдерживать.

**Тест различения:**
«Если причина находится внутри разрешённого периметра — мера всё ещё помогает?» Нет → это containment, не root-cause fix.

**Следствие:** Принять containment как достаточную меру легитимно, если остаточный риск внутри периметра приемлем и явно задокументирован. Продавать containment как «причина устранена» — ошибка коммуникации, скрывающая остаточный риск.

**Источник:** WP-454 Ф5, peer-сессия 2026-07-03.
**Смежно:** DP.FM.188 (per-service роли как containment для shared DB key).

### DP.D.188: Возраст процесса ≠ Зависание процесса

| Возраст процесса | Зависание процесса |
|------------------|--------------------|
| Прошедшее время с запуска | Неспособность обработать запрос |
| «старый» = долго работает | «завис» = перестал реагировать |
| Грубый backstop (порог недели) | Реальный критерий — N неудач health-check |
| Применим к одноразовым скриптам | Неприменим к долгоживущим демонам |

**Почему важно**: Демон-прокси или воркер обязан жить сутками и неделями — это нормальное поведение. Watchdog, использующий возраст как признак зависания, выдаёт ложные тревоги на любой здоровый долгоживущий процесс. - «старый процесс» ≠ «зависший процесс»
- «молодой процесс» ≠ «здоровый процесс»
- Возраст — backstop для аномально долгих процессов (порог: недели), не оперативный индикатор

### DP.D.189: no ≠ conditional-no ≠ defer (три статуса готовности системы к охвату)

При оценке готовности компонента к включению в систему ярлык «нет» скрывает три принципиально разных состояния с разными путями разблокировки:

| Статус | Смысл | Что нужно для разблокировки |
|--------|-------|----------------------------|
| **no** | Нет ни роли, ни моста, ни кода — не планируется | Стратегическое решение начать |
| **conditional-no** | Условие гипотетическое, в работе нет | Конкретное решение о реализации условия |
| **defer** | Работа уже начата, ждёт конкретного блокера | Устранение одного названного блокера |

**Почему важно**: одинаковый ярлык «нет» для разного уровня готовности вводит в заблуждение при планировании бэклога — создаётся иллюзия одинакового расстояния до готовности. `defer` намного ближе к `yes`, чем `no`.

**Тест:** «есть ли уже начатая работа, ведущая к этому состоянию?» Да → defer. «Есть гипотетическое условие, но оно не в работе?» → conditional-no. «Ничего нет и не планируется?» → no.

**Контекст:** WP-457 Ф10 (State-Transition Gate), статусы охвата осей Включённость и Забота (2026-07-05).

### DP.D.198: Вычисляемый статус ≠ характеристика (строка таблицы критериев)

| Вычисляемый статус | Характеристика |
|--------------------|----------------|
| Композиция нескольких атрибутов | Отдельный срез / измерение объекта |
| Нет в строке критериев — выводится из них | Размещается строкой в таблице критериев |
| Пример: «Стажёр» = Х2 AND Х3 | Пример: Х2 (доступ к курсам), Х3 (сдан тест) |

**Почему важно**: Вычисляемый статус, помещённый строкой в таблицу характеристик, выглядит как ещё одно независимое измерение. Читатель теряет различение «атрибут объекта vs логическая композиция атрибутов». Решение: вынести acceptance-критерий на основе вычисляемого статуса отдельным блоком под таблицей характеристик — граница «характеристика vs вычисляемый статус» становится видна визуально. Применимо к любому документу-контракту, где смешиваются атрибуты и производные от них статусы.

**Источник:** session-close 2026-07-05 (WP-406, WP-464, WP-457, FMT issues).

### DP.D.199: RLS-политика ≠ Защита для роли с BYPASSRLS

**Контекст:** PostgreSQL, многопользовательские БД с Row-Level Security.

**Различение:**
- **RLS-политика (декларативная)** — правило фильтрации строк, применяется к ролям, для которых RLS активен.
- **Защита для роли с BYPASSRLS** — для ролей с флагом `BYPASSRLS` политика строк **не применяется**; база игнорирует содержимое политики независимо от того, насколько правильно она написана.

**Следствие:** настройка RLS-политики для служебной роли с BYPASSRLS создаёт видимость защиты без реальной защиты. Защита для таких ролей должна жить в коде приложения как дисциплина фильтрации запроса (L2-PRIVACY-паттерн), а не в декларативной политике базы.

**Тест:** «Применяется ли политика к субъекту — или субъект её обходит по флагу?» Обходит → декларативная политика не работает.

**Источник:** WP-457 Ф10 (2026-07-05), peer-session report.

### DP.D.200: FORCE ROW LEVEL SECURITY ≠ Защита от роли с атрибутом BYPASSRLS

**Контекст:** PostgreSQL, Row-Level Security, управляемые облачные базы (Neon, RDS).

**Различение:**
- **FORCE ROW LEVEL SECURITY** — заставляет RLS применяться к **владельцу таблицы** (который по умолчанию обходит собственные политики). Лечит: «хозяин таблицы видит все строки».
- **Роль с атрибутом BYPASSRLS** — обходит RLS при любых условиях, включая FORCE ROW LEVEL SECURITY. FORCE защищает только от первого механизма и не влияет на второй.

**Следствие:** добавить `FORCE ROW LEVEL SECURITY` недостаточно, если к базе подключается роль с атрибутом `BYPASSRLS` (например, управляемая облаком `neondb_owner`, у которой `ALTER ROLE ... NOBYPASSRLS` недоступен). Два механизма обхода → два разных решения.

**Тест:** «Есть ли `FORCE ROW LEVEL SECURITY` → защита полная?» Нет — если хотя бы одна подключающаяся роль имеет `BYPASSRLS`.

**Фикс для BYPASSRLS-роли:** разделение ролей (отдельная роль без атрибута для приложения) или программная фильтрация данных в коде приложения поверх BYPASSRLS-роли.

**Связано:** DP.D.199 (RLS-политика ≠ защита для роли с BYPASSRLS — общий принцип).

**Источник:** WP-417 Ф6 + WP-457 Ф10 (2026-07-05), peer-session.

### DP.D.201: Защита-в-коде (флаг + тест) ≠ Требование-в-документе

**Контекст:** резервирование места под будущую функциональность; любой guardrail, который должен пережить будущие правки.

**Различение:**
- **Защита-в-коде** — флаг-заглушка (например, `FEATURE_X=False` рядом с уже действующим аналогичным флагом) + тест на существование и значение по умолчанию. Если флаг удалят или переименуют — CI падает немедленно.
- **Требование-в-документе** — фраза «при следующей правке завести флаг». Не ловится автоматической проверкой, забывается при рефакторинге.

**Следствие:** флаг-заглушка с тестом — это код, чьё назначение (зарезервировать место) явно и верифицировано. Отличать от «спящей политики» (DP.D.199): мёртвая конфигурация выглядит как работающая защита, но не работает; заглушка с тестом не претендует на работу — она верифицируемо резервирует место.

**Тест:** «Есть ли автоматическая проверка, которая упадёт, если кто-то уберёт это без замены?» Нет → это документ, а не защита.

**Связано с:** DP.ARCH.008 (наблюдатель вне субъекта: документ = сила памяти ≈ 0, тест = детерминированная проверка), DP.D.022 (формальная проверяемость).

**Источник:** WP-417 Ф6 (2026-07-05), session-transcript 2026-07-05-23-wp417-apply-prod-schema.

### DP.D.202: Логическое «готово» ≠ Операционное «готово»

**Контекст:** приёмка фазы/РП, включающей деплой сервиса; любой признак «работает с даты X».

**Различение:**
- **Логическое «готово»** — код написан, задеплоен, тесты зелёные, фаза отмечена ✅.
- **Операционное «готово»** — инфраструктура сконфигурирована (env, credentials, unit-файлы), сервис реально исполняется, результат виден пользователю.

**Следствие:** фича может быть логически готова и операционно мертва: флаг включён, но сервис без переменных подключения тихо пропускает блок (нет credentials → нет данных → нет вывода). Приёмка фазы обязана включать операционный уровень, не только логический. Прецедент: рендер-сервер числился работающим с середины июня, но systemd-юнит не получал переменных подключения к БД — блок не показывался ни одному пользователю.

**Тест:** «Если потушить и поднять сервис заново — функция работает без ручных вмешательств?» Нет → операционно не готово.

**Связано с:** DP.D.022 (операционная проверяемость — этот уровень и пропускается при приёмке «по коду»), DP.FM.088 (done-фаза со скрытым долгом), DP.FM.096 (конфигурация без эмиттера — невидимый баг).

**Источник:** WP-417 (2026-07-05), session-transcript 2026-07-05-23-wp417-apply-prod-schema.

### DP.D.203: iCloud app container ≠ iCloud Drive — данные iOS-приложений доступны только через API

**iCloud app container** — приватное хранилище данных конкретного iOS/macOS-приложения (Health, Fitness и др.). Данные не доступны как обычные файлы без нативного API (HealthKit, CloudKit). При включённом «Optimize Mac Storage» файл существует по пути (`~/Library/Mobile Documents/...`), но локально занимает 0 KB — заглушка (содержимое только в облаке). Проверка `[ -f ... ]` проходит, а `du -k` показывает 0.

**iCloud Drive** — пользовательское файловое хранилище (`~/iCloud Drive/`, `~/Library/Mobile Documents/com~apple~CloudDocs/`). Читается стандартными POSIX-вызовами после материализации файла.

**Тест:** «Данные iOS-приложения синхронизируются через iCloud?» — не значит «можно прочитать как файл без API». Перед содержательными операциями — `du -k` для проверки локальной материализации.

**Следствие для data-pipeline:** iCloud Drive — не универсальный мост к данным iOS-приложений. Для каждого источника (Health, Garmin, Strava) нужен отдельный экспортёр на устройстве. Эталон архитектуры — трёхслойка IO/calc/store (WP-470, panel_wakatime.py).

**Связано:** облачная заглушка smart-sync проходит проверку существования, но рушит проверку бэкапа (WP-7 BAK1-F2).

### DP.D.219: Compression ≠ Lazy — различения без advance-signal требуют split hot/warm, а не lazy-load

Два разных приёма снижения eager-стоимости каркасного компонента. Выбор определяется наличием детерминированного advance-signal.

| Lazy-load (отложенная загрузка) | Compression (сжатие через split) |
|----------------------------------|----------------------------------|
| Грузит полный контент по триггеру | Держит горячим самое частое + поиск для редкого |
| Требует детерминированный advance-signal (lexical prefix) | Работает без сигнала |
| Применимо: роли, скиллы, формат-правила | Применимо: distinctions (агент не знает заранее, какое понадобится) |
| Полный контент в сессии, где триггер сработал | Hot-часть всегда; warm-часть по `/distinction <термин>` или semantic-search |

**Почему различение важно.** distinctions.md нельзя сделать lazy через prefix: нет advance-signal — агент не знает заранее, какое из ~147 различений понадобится. Решение — не «загрузить когда понадобится», а split: hot-часть (≤150 строк, 15-20 самых горячих) + warm-часть (остальные, доступны через `/distinction <термин>` или semantic-search).

**Тест:** «Есть ли детерминированный advance-signal для этого компонента?»
- Да → lazy-load (DP.METHOD.146).
- Нет → split hot/warm (compression).

**Связано с:** DP.METHOD.146 (activate-on-prefix lazy); DP.FM.235 (eager framework context bloat — общая проблема, которую оба приёма лечат); DP.D.220 (режим отказа lazy-компонента ≠ блокировка).

**Источник:** session-transcript 2026-06-26 (WP-445 Ф3 ArchGate, peer-session 2026-06-26-02); git diff DS-my-strategy 321fa9fa9.

### DP.D.220: Режим отказа lazy-компонента = деградация (capability недоступна в сессии) ≠ блокировка работы

Условно-загружаемый каркасный компонент (скилл, формат-правило, роль, style-guide) может не загрузиться: advance-signal не пришёл, триггер не отработал, хук не вызвался. Контракт отказа: агент **продолжает работу без этого компонента** (деградация изолирована), а не падает.

| Деградация (правильно) | Блокировка (анти-паттерн) |
|------------------------|---------------------------|
| Lazy-компонент не загрузился → capability недоступна в этой сессии | Lazy-компонент не загрузился → работа останавливается |
| Отказ изолирован, основная работа идёт | Отказ каскадирует в остановку |
| Lazy сохраняет смысл (eager-стоимость не возвращается) | Lazy теряет смысл: всё равно надо было грузить eager |

**Тест:** «Если lazy-компонент не загрузился — система падает или продолжает?»
- Падает → lazy сломан по дизайну (надо было грузить eager).
- Продолжает (деградация) → контракт корректен.

**Граница с DP.D.158.** DP.D.158 — про *write-path* (сторонний best-effort захват данных деградирует без отката основной транзакции). DP.D.220 — про *read-path* (загрузка опциональной capability в контекст деградирует без блокировки сессии). Разные стороны различения «Read-path ≠ Write-path (side effects)».

**Связано с:** DP.D.158 (write-path сиблинг: best-effort захват ≠ основное событие); DP.METHOD.146 (activate-on-prefix — режим отказа = этот контракт); DP.FM.235 (eager bloat — проблема, которую lazy лечит при условии этого контракта).

**Источник:** session-transcript 2026-06-26 (WP-445 Ф1 Service Clause, peer-session 2026-06-26-02); git diff DS-my-strategy cffa8a78f.

### DP.D.221: Качественный порог мастерства ≠ Счётчик очков/частоты

| Качественный порог (qualitative threshold) | Счётчик очков (frequency counter) |
|-------------------------------------------|-----------------------------------|
| Смысловое событие (понимание, публикация, связь в графе знаний) | Любое действие × N |
| Рост на осмысленных скачках | Рост полоски за ежедневное открытие |
| Вовлечённость через значимость | Вовлечённость через привычку / anxiety |
| Пауза = нейтральна | Пауза = потеря streak / очков |

**Почему важно**: Частотный счётчик (daily streak, очки за открытие) возвращает Tamagotchi-механику через чёрный ход — скрытый счётчик создаёт тревогу пропуска, пользователь перестаёт ценить содержание. Качественный порог: рост = осмысленное событие, пауза нейтральна.

**Тест**: «За что растёт маскот/индикатор — за факт открытия или за смысловое достижение?» Факт открытия → счётчик (риск Tamagotchi-anxiety). Смысловое достижение → qualitative threshold.

**Связано с:** DP.METHOD.148 (rest state = silence).

**Источник:** session-transcript 2026-06-26-13; WP-292 peer Ф9a mascot spec.

### DP.D.222: Non-blocking аудит (рекомендательный канал) ≠ Слой защиты (blocking-by-default)

| Non-blocking аудит | Слой защиты |
|-------------------|-------------|
| Не блокирует merge по умолчанию | Блокирует merge по умолчанию |
| Ревьюер может игнорировать под давлением дедлайна | Ревьюер не может аппрувнуть без fix |
| Обход попадает в main, живёт до следующего полного аудита | Обход отклоняется при merge |
| «Обязателен для review» = процессная декларация | Blocking-статус = технический инвариант |
| Week-Close аудит — слишком редко для критичного контура | Запуск на каждый push в main |

**Почему важно:** Процессные декларации («должен быть проверен») имеют нулевую силу под давлением дедлайна или при direct push. Настоящий слой защиты: (1) blocking-by-default для PR, затрагивающих файлы запуска; (2) ложные срабатывания решаются audited whitelist + documented break-glass, а не ослаблением гарда; (3) запуск на каждый push в main, иначе direct push и post-merge drift проходят мимо.

**Тест:** «Может ли ревьюер аппрувнуть этот PR без фикса?» Да → это рекомендация, не слой защиты.

**Применение:** при проектировании security-контуров различать, является ли проверка блокирующим шлюзом или рекомендательным каналом. Non-blocking = advisory. Для enforcement нужен blocking + break-glass + out-of-band trigger (push в main).

**Связано с:** DP.D.144 (детектор существует ≠ детектор блокирует), DP.FM.237 (Provenance вне репо), DP.FM.238 (Self-referential exemption), DP.METHOD.154 (bypass-class taxonomy).

### DP.D.223: Видимое узкое место (наглядный дефицит) ≠ Связывающее ограничение (TOC bottleneck)

| Видимое узкое место | Связывающее ограничение |
|--------------------|------------------------|
| Наглядно, шумно, притягивает внимание | Может быть неочевидным, тихим |
| Не обязательно определяет throughput системы | Определяет весь throughput системы |
| Устранение не гарантирует прогресс | Устранение открывает следующую пропускную способность |
| Пример: агрессивная воронка набора (24-28 заявок за 12 дней) | Пример: неготовая программа, без которой набор нельзя запускать |

**Почему важно:** Самый шумный дефицит притягивает ресурсы, но может не быть связывающим ограничением по TOC. Устранение несвязывающего дефицита не увеличивает throughput — система упирается в следующий шаг. Ресурсы потрачены, ограничение осталось.

**Тест:** «Если убрать этот дефицит, система пойдёт — или упрётся в следующий шаг?» Упрётся → это не bottleneck.

**Применение:** перед вложением ресурсов в устранение видимой проблемы — проверить, является ли она связывающим ограничением. Использовать скилл bottleneck-pick (DP.ROLE.054) для диагностики.

**Связано с:** DP.ROLE.054 (Аналитик ограничений — bottleneck-pick).

### DP.D.224: Сужение объёма (scope) как дешёвый рычаг ≠ Сужение объёма, когда объём = носитель сигнала

Сужение объёма (числа участников, размера выборки) обычно считают дешёвым рычагом под дедлайн. Но если сам объём несёт измеряемый сигнал — контрольная группа, минимальный размер для статистической значимости — то урезание разрушает цель: результат из сравнения превращается в анекдот.

**Тест перед урезанием scope:** «Является ли вырезаемая часть носителем измеряемого сигнала или контрольной группой?»
- Да → сужение — не lever, а разрушение цели. Искать другой рычаг (дата, требования).
- Нет (вырезаемое — дополнительное удобство, не носитель) → сужение допустимо.

**Пример:** Эксперимент «команда vs одиночки» при сужении до групп 3-4 человека убирает контрольную группу одиночек — статистический сигнал исчезает. Сужение объёма = обесценивание работы, не экономия.

**Связано с:** «Inventory ≠ Progress» (незавершённый эксперимент = мёртвый капитал), «Целевая система проекта ≠ класс систем». Источник: WP-437 peer-03 2026-06-28.

### DP.D.225: Просроченный шлюз — блокирующее предусловие (сбой) ≠ Восполнимая разведка (задержка)

«Отставание по плану» неоднородно. Просроченные шаги делятся на два класса с разными реакциями:
- **Блокирующее предусловие:** его отсутствие = некорректность следующего шага (запуск пойдёт на неутверждённой модели/решении). Это процессный сбой, требует эскалации и остановки.
- **Восполнимая разведка:** её потеря ухудшает качество решения, но не делает следующий шаг некорректным. Восполнимо прямым действием за 1-2 дня без эскалации.

**Тест классификации:** «Без этого шага следующий шаг системно некорректен — или просто менее информирован?»
- Некорректен → блокирующее предусловие → остановить, эскалировать.
- Менее информирован → восполнимая разведка → нагнать параллельно.

**Пример:** WP-437: просроченная «архитектурная проверка модели» = сбой (запуск без утверждённой модели); просроченный «разведочный опрос» = задержка разведки (можно провести за 1 день позже).

**Связано с:** DP.D.144 (детектор существует ≠ детектор блокирует), DP.FM.239 (решение не зафиксировано). Источник: WP-437 peer-03 2026-06-28.

### DP.D.226: Уровень принципов (степень общности: ZPF/FPF/SPF/TPF) ≠ Слой репозиториев (место хранения: Base/Pack/DS)

Две ортогональные оси, которые слипаются в одну строку и читаются как тождество.

**Ось 1: Уровень принципов** — степень специфичности правила (ZPF самый общий → TPF самый специфичный). Один принцип может «жить» на любой оси 2.

**Ось 2: Слой репозиториев** — место хранения (Base = ZPF+FPF+SPF = платформа → Pack = доменные знания → DS = реализации). Один репо может содержать принципы разных уровней.

| | ZPF/FPF/SPF/TPF (ось 1) | Base/Pack/DS (ось 2) |
|--|--|--|
| **Что описывает** | Степень общности принципа | Место хранения артефакта |
| **Вопрос** | «Насколько специфично это правило?» | «В каком репо это лежит?» |
| **Пример: «правило IWE»** | TPF (самое специфичное) | DS или Pack (зависит от природы) |
| **Пример: «форматирование»** | FPF (универсальный формат) | Base (платформенное хранилище) |

**Тест:** «Это про степень общности правила или про то, в каком репозитории оно лежит?» Разные вопросы → две разные оси.

**Почему слипаются:** цепочка «чем специфичнее принцип, тем ниже по иерархии хранилищ» верна как тенденция, но не как тождество. TPF-принцип может жить в Pack (если он доменный); FPF-принцип может жить в DS (если он реализационный). Смешение ведёт к «TPF — это DS», что бессмысленно.

**Связано с:** DS→Pack→Base Fallback Chain, DP.ARCH.001, CLAUDE.md §1 Архитектура репозиториев.

**Источник:** peer-session 2026-06-28-07-wp448-f2-tpf-ladder, report.md §4; WP-448 Ф2.

### DP.D.227: Singular-ресурс (0..1 на владельца) ≠ Plural-ресурс (0..N на владельца): безопасность confirm-скопом зависит от кардинальности

Операция «confirm/rollback всех резервов по аккаунту» (скоп-по-владельцу) имеет разную безопасность для разных типов ресурсов.

| | Singular-ресурс | Plural-ресурс |
|--|--|--|
| **Кардинальность** | 0..1 резерв на аккаунт | 0..N резервов на аккаунт |
| **Confirm-скоп** | Безопасен (резерв всегда один) | Дефект двухфазного коммита |
| **Пример** | Подписка | Курсы |
| **Риск** | Нет | Confirm A списывает бонусы за ещё неоплаченный B |

**Механизм дефекта для plural:** пользователь покупает курс A (резерв A создан) и параллельно нажимает оплатить курс B. Confirm-скопом захватывает резервы A + B → бонусы списываются за оба, хотя оплата пришла только за один.

**Тест перед переносом аналогии:** «Сколько таких сущностей может быть у одного владельца одновременно — одна или несколько?»
- Одна (singular) → скоп-по-владельцу безопасен.
- Несколько (plural) → нужна привязка к идентификатору конкретного экземпляра.

**Обобщение:** операция, безопасная для singular-ресурса, при механическом переносе на plural-ресурс ломается by design. Проверять кардинальность перед переносом паттерна.

**Связано с:** DP.FM.011 (P1b — провал фиксации).

**Источник:** peer-session 2026-06-28-04-bonus-redemption-course-payment, report.md §4, §2 тема 4; WP-446.

### DP.D.228: Способ исполнения как поле-данные авторитетного каталога ≠ магическая строка/конвенция имени файла в коде

| Поле-данные в каталоге | Магическая строка / конвенция имени |
|------------------------|--------------------------------------|
| Явное поле `exec_kind: none\|script` | Сравнение имени (`if name == 'pass'`) или суффикс (`*.py → скрипт`) |
| Каталог = авторитетный источник способа исполнения | Код = неявная конвенция, скрытая в ветке |
| Заглушка явно помечена как данные | Заглушка скрыта в имени или строке-сравнении |
| Рефакторинг имени не ломает логику диспетчера | Переименование заглушки ломает поведение |
| Новый тип исполнителя = новая запись в каталоге | Новый тип = новая ветка в коде диспетчера |

**Инвариант:** параметр поведения (способ исполнения) должен быть данными в авторитетном источнике, не строкой в коде. Конвенция имени — хрупкий хардкод: если заглушка и скрипт могут называться одинаково (оба `.py`), конвенция ломается молча.

**Тест:** «Диспетчер решает тип исполнения по полю-данным в каталоге или по строке/суффиксу имени в коде?» Строка/суффикс → хрупкий хардкод. Поле в каталоге → авторитетный источник.

**Связано с:** DP.D.025 (Harness ≠ Agent — что определяет результат), DP.D.229 (жёсткий отказ при нарушении каталога — следствие данного принципа).

**Источник:** WP-436 Ф1 (iwe-agent-dispatcher.py, executor-catalog.yaml поле `exec_kind`), peer-session 2026-06-21-30-gate-enforce-headless-impl, commit 43e6fe2d2, 2026-06-21.

### DP.D.229: Жёсткий отказ при отсутствии обещанного исполнителя ≠ тихий fallback в дорогую модель

| Жёсткий отказ (fail-loud) | Тихий fallback в LLM |
|--------------------------|----------------------|
| Каталог объявил `exec_kind: script`, файла нет → явная ошибка | Нет файла → тихо вызвать дорогую модель |
| Баг каталога виден немедленно | Баг каталога скрыт за fallback-ветвью |
| Заслонка (gate) работает как задумано | Заслонка имеет скрытый обход (bypass) |
| Понятный сигнал: «почини каталог» | Скрытая стоимость: неожиданный LLM-вызов |

**Инвариант:** если каталог является авторитетным источником способа исполнения (DP.D.228), отсутствие задекларированного ресурса — баг каталога, не повод для тихого обхода. Тихий fallback в LLM восстанавливает ровно тот обход, который принудительная заслонка должна закрыть, и неожиданно расходует бюджет.

**Тест:** «При `script` без файла — заслонка отказывает явно или молча проваливается в LLM-ветку?» Молча → скрытый bypass. Явно → fail-closed.

**Связано с:** DP.D.228 (способ исполнения как данные каталога), DP.ARCH.008 (enforcement requires external observer).

**Источник:** WP-436 Ф1 (iwe-agent-dispatcher.py), peer-session 2026-06-21-30-gate-enforce-headless-impl, report.md §2 Q3, §4, commit 43e6fe2d2, 2026-06-21.

### DP.D.230: Тест на гард/валидацию обязан падать без фикса ≠ тест декорирует гард (зелёный ≠ гард работает)

| Честный тест гарда | Декоративный тест |
|-------------------|-------------------|
| Подаёт вход, который гард ДОЛЖЕН поймать, но тривиальная проверка пропускает | Проверяет кейс, который гард ловит с самого начала |
| Падает без фикса | Зелёный как до, так и после фикса |
| Доказывает корреляцию: fixer → test passes | Нет доказательства: тест зелёный и без фикса |
| Ассертирует: «опасное действие не произошло» (`mock_read.assert_not_called()`) | Ассертирует только HTTP-статус / код возврата |

**Инвариант:** тест безопасности (гард, валидация пути, permission-check) обязан быть написан так, чтобы без тестируемого фикса он ПАДАЛ. Доказательство «красный без фикса» — обязательная часть приёмки для security-кода.

**Конструкция честного теста гарда:**
1. Подать вход, который гард ДОЛЖЕН отбить, но тривиальная ветка пропускает (пример: `lesson/../../secret`, а не `../../secret`)
2. Ассертировать, что опасное действие не произошло, а не только статус ответа
3. Убедиться, что deny приходит по нужной ветке гарда

**Тест мета-уровня:** «Стал бы этот тест красным, если убрать гард?» Нет → тест декорирует, не тестирует гард.

**Связано с:** DP.D.147 (MIN содержательный барьер GREEN ≠ полное качество), DP.D.148 (walkthrough ≠ наблюдаемый артефакт smoke).

**Источник:** WP-426 Ф6, peer-session 2026-06-21 (path traversal guard mid-path обход `lesson/../../secret`), commit 2ed548837, memory/lessons_security_test_must_fail_without_fix.md, 2026-06-21.

### DP.D.231: Owned узкий контракт enqueue (producer → API/RPC) ≠ raw cross-service SQL write

Производитель публикует НАМЕРЕНИЕ через owned-контракт получателя (`enqueue` — узкий API/RPC, зеркало канало-агностичного `send()`). Он НЕ пишет сырой SQL в БД сервиса-получателя напрямую. Разделение ответственности:
- **Producer (Nudge Engine):** решает ЧТО доставить и КОГДА по смыслу (контент, уместность). `scheduled_at` НЕ входит — это будущая data-driven политика получателя.
- **Consumer (Доставщик):** решает ПРОПУСТИТЬ ли (потолок/дедуп/opt-out) и КОГДА физически.

**Тест:** «Производитель пишет в БД получателя напрямую (INSERT/UPDATE)?» Да → нарушение границы. Должен идти через `enqueue` (API/RPC).

**Связано с:** «Источник доставки ≠ Политика-на-место ≠ Физический транспорт» (уточняет ось «owned-контракт vs raw cross-service write»), «Gateway с одной ответственностью ≠ Gateway с прикладной логикой» (тот про gateway; этот про любую producer-consumer границу).

**Источник:** WP-117 Ф-integration peer-session 2026-06-21 (DP.SC.116 «Контракт enqueue», «Связь с DP.SC.177»).

### DP.D.232: Единый писатель append-only журнала (один writer-модуль) ≠ N независимых писателей

Append-only журнал решений/событий должен иметь РОВНО одного писателя — единую функцию-writer в одном модуле (`classify_and_log(inp, source)`). При N независимых писателях: (1) дрейф формы записи между ними; (2) каждый новый исполнитель, пишущий своим `printf`/`puts`, воспроизводит обход централизованной двери (gate) без изменения кода двери.

**Следствие для gate-enforcement:** поле `source` в каждой записи позволяет различать исполнителей — на нём держится критерий приёмки «хотя бы одна запись от каждого обязательного исполнителя».

**Тест:** «Могу ли я добавить нового исполнителя, не зарегистрировав его через единственную функцию-writer?» Да → писателей N, обход возможен. Нет → единственный writer.

**Связано с:** «Дедуп-гейт отправителя ≠ приватная защёлка» (там — readers журнала; здесь — writers), «Детектор существует ≠ детектор блокирует» (смежный класс: enforcement через единственную точку vs. множество), DP.D.049 (Лог ≠ Инцидент ≠ State file — тип артефакта; данный — целостность через единственного writer). Смежно: DP.FM.186 (Append-only phantom early-writer — другой механизм отказа: не множественность писателей, а неавторизованный ранний писатель).

**Источник:** WP-436 Ф1 peer-sessions 2026-06-21-16 + 2026-06-21-30 (iwe_gate.py classify_and_log, commit 43e6fe2d2).

### DP.D.233: Тихое исключение при деплое (silent-exclude) ≠ Уведомление об устаревании (notify-deprecate)

В системах распространения шаблона два механизма с похожим внешним эффектом «файл не доезжает / считается устаревшим», но разной семантикой:
- **Silent-exclude:** файл игнорируется при деплое, потребитель не уведомлён (тихо).
- **Notify-deprecate:** потребителю явно сигнализируется удалить файл вручную — сигнал повторяется при каждой проверке (`--check`), пока файл не удалён.

**Тест:** «Скрыть файл при деплое или предупредить потребителя, что его нужно удалить?» Скрыть молча → silent-exclude. Явно предупредить с повтором до устранения → notify-deprecate.

**Связано с:** DP.FM.075 (deprecated_files как TODO-tracker — конкретная реализация половины пары «notify-deprecate»).

**Источник:** capture session-close 2026-06-30 (`update-manifest.json`: поля `deprecated_files` vs `excluded_paths`); решение о Pack-маршруте (абстрактно, без привязки к именам полей) — пилот, 2026-07-11.

### DP.D.234: Метод сборки (логика компиляции) ≠ Место исполнения (резидентность данных) ≠ Поверхность отображения (витрина/репо)

**Контекст:** Три оси топологии сервисов с разделением логики и данных по зонам доверия.
При проектировании смешение этих осей приводит к вопросу «одно место или два?» — ложной
дихотомии, игнорирующей три независимые оси.

**Различение:**

- **Метод сборки** — логика компиляции/рендеринга артефакта. Единый, версионируется
  на платформе, раздаётся клиентам. *Не зависит* от того, где хранятся данные.
- **Место исполнения** — где физически запускается логика и обрабатываются данные.
  Может различаться по зоне доверия: платформа / локальная машина пользователя /
  выделенный сервер (tsekh-1). Определяет резидентность данных.
- **Поверхность отображения** — куда поставляется готовый артефакт (публичная витрина,
  личный репо, дашборд). Может быть одна или несколько, независимо от метода и места.

**Суверенный гибрид:** метод единый (платформа); данные обрабатываются в суверенной зоне
пользователя (его машина); результат публикуется на витрине. Три оси — три независимых
решения.

**Тест:** «Нам нужно одно место или два?» — вопрос сформулирован неверно. Правильно:
«Где сборка? Где исполнение? Куда отображение?» — три отдельных вопроса.

**Источник:** ADR-2026-06-30-personal-guide-topology.md (WP-149); peer-session 2026-06-30-04.
**Смежно:** DP.METHOD.165 (витрина подключает только финальный результат).

### DP.D.235: Создание артефакта-руководства (единоразовая работа) ≠ Конвейер его обновления (recurring process)

**Контекст:** При работе с долгоживущими руководствами (guide, playbook, стандарт) легко
смешать акт создания артефакта с его системой поддержки в актуальном состоянии.

**Различение:**

- **Создание артефакта-руководства** — единоразовая работа: написать, структурировать,
  согласовать, опубликовать. Owner = автор/команда. Триггер = один раз. Результат: текстовый
  артефакт в определённый момент времени.
- **Конвейер обновления** — recurring process: мониторить изменения в практиках/требованиях,
  триггерить перегенерацию/ревизию, публиковать обновлённую версию. Owner = отдельный процесс
  (pipeline, cron, responsible role). Триггер = изменение upstream (практики, стандарты, данные).
  Результат: живой артефакт, актуальный в любой момент.

**Почему важно разделить:**

Без явного конвейера обновления руководство деградирует: через N месяцев практики изменятся,
а текст останется прежним. Создать документ ≠ поддерживать его — разные артефакты, разные
owner и lifecycle.

**Прецедент:** WP-362 создал универсальные руководства ЛР. Процесс их обновления при
изменении FMT-практик не был специфицирован → WP-453 явно закрыл этот gap (конвейер:
FMT-практика изменилась → раздел 7 guide.system-school.ru обновляется).

**Тест:** «Если FMT-практика изменится завтра — когда и кто обновит руководство?»
Нет ответа → конвейер обновления не описан.

**Источник:** session-transcript 2026-06-30 + git diff (WP-452.md, WP-453.md ef66b893e).
**Смежно:** DP.METHOD.166 (canonical source для данных — другой аспект актуальности).

### DP.D.236: Доставка обучения к рабочему контексту ≠ Производственное действие как шаг развития

**Доставка обучения к работе** — обучение размещается рядом с рабочим контекстом пользователя:

задача в системе) является шагом в траектории развития пользователя. Работа и развитие
тождественны, не смежны.

**Тест:** «Если убрать учебный компонент (урок / коуч / тренажёр) — работа остаётся работой?»
- Да → смежность (доставка обучения к работе)
- Нет → тождество (работа = развитие)

**Практическое следствие для платформы:** по состоянию на 2026 конкуренты доставляют обучение
В МЕСТО работы, но ни у кого само производственное действие не является шагом развития.
Это незанятая архитектурная позиция.

### DP.D.237: Уникальный элемент связки ≠ Уникальная связка как целое (Bundle Moat)

**Уникальный элемент** — один компонент продукта или системы, который конкурент не может
скопировать немедленно. При коммодитизации рынка таких элементов становится всё меньше.

**Уникальная связка (bundle moat)** — комбинация компонентов, каждый из которых по
отдельности скопируем, но вместе они создают защищённую позицию, которую сложно
воспроизвести одновременно.

**Тест:** «Какой ОДИН элемент связки уникален?»
- Есть однозначный ответ → защита через элемент (уязвима при коммодитизации).
- Ни один элемент не уникален → искать защиту в связке: насколько сложно скопировать
  именно комбинацию целиком?

**Практическое следствие:** конкурентный анализ недостаточно проводить по компонентам —
нужно проверять, существует ли связка. Даже если каждый компонент платформы имеет аналог
у конкурента, связка «методология + данные работы + модель ступени + владение данными»
может быть уникальна как целое.

**Источник:** competitive-analysis §1 п.3, commit ce91c2ee2, 2026-07-02.
**Смежно:** [DP.SOTA.033] (коммодитизация AI Learning Platform), [DP.D.236] (доставка обучения ≠ работа как развитие).

### DP.D.238: Смещённый прокси ≠ честное «не знаем»

**Описание:**
- **Прокси со случайной погрешностью (шум с запасом)** — измерение косвенное, но ошибка случайна и предсказуема. Пример: bytes/5 как прокси токенов (погрешность ±20%, не систематична). Консервативен — защищает от ошибки.
- **Прокси со систематическим смещением** — ошибка системна из-за структурного отличия прокси от оригинала. Пример: tiktoken (OpenAI BPE) как прокси Claude-токенов на смеси кириллицы/markdown/путей: токенайзер чужой, смещение непредсказуемо по знаку и величине. Маскирует ошибку под измерение — опаснее явного «не знаем».

**Ключевое следствие:**
Случайный шум с запасом → консервативен. Систематическое смещение → создаёт ложную уверенность без защиты.

**Тест:** «Может ли ошибка прокси быть систематической (всегда в одну сторону) из-за структурного отличия прокси от оригинала?» Да → прокси со смещением → использовать честное «не измерено» или калибровать отдельно перед использованием.

**Правило:** Прокси с неизвестной/систематической погрешностью нельзя выдавать за измерение.

**Источник:** session-close 2026-07-02 (WP-450 Ф3, снятие тезиса про tiktoken как прокси Claude-токенайзера).
**Смежно:** DP.M.368 (пофайловая калибровка), DP.FM.248 (подмена единицы метрики).

### DP.D.239: Pack-тип ≠ DB-таблица ≠ DB-строка

**Описание:**
- **Pack-тип** — описание класса (type-level, Episteme): онтологический тип домена. Определяет, что существует как сущность в домене. Не имеет строк, первичных ключей, индексов, NULL-ограничений.
- **DB-таблица** — schema реализации: техническая структура хранения данных. Может соответствовать Pack-типу, но не обязана (денормализация, шардинг, полиморфные таблицы — всё допустимо).
- **DB-строка** — token: конкретный экземпляр типа в конкретный момент времени.

**Ключевое следствие:**
Связь между Pack-типом и DB-таблицей — только явный маппинг (`ECO.MAP.BIND.*`), не совпадение имён. Ожидание 1:1 Pack↔схема = ошибка проектирования.

**Тест:** «Нужно добавить FK или индекс — это идёт в Pack?» Нет → реализационное решение → DS docs. «Это описание класса сущностей домена?» → Да → Pack-тип.

**Правило:** Не тащить FK, индексы, NULL-constraints в Pack. Не ожидать, что каждый Pack-тип соответствует ровно одной таблице.

**Источник:** WP-251 Ф3, session-close 2026-07-11 (git commit 3246d99). FPF A.7 (Type-level ≠ Token-level).
**Смежно:** [DP.D.001] (Объект ≠ Модель), [DP.D.002] (Модель ≠ Данные), [DP.KR.001] §6 (маршрутизация знаний), HD #29 (Pack-знание ≠ реализационное решение).

### DP.D.241: Реестр (registry) ≠ Продовое состояние (production state)

| Реестр | Продовое состояние |
|--------|-------------------|
| Декларативная запись о намерении/факте | Фактически задеплоенное и работающее |
| Обновляется вручную или CI-pipeline | Меняется при каждом deploy/config |
| Может отставать от реальности | Всегда текущее (даже если нет записи) |
| Источник: команда/агент | Источник: production environment |

**Почему важно:** механизм может быть задеплоен в production (работает, отвечает) без записи в реестр. Перед реализацией «нового» механизма — проверить production-baseline (live e2e тест, grep по деплоям), не только реестр. Ошибка: ArchGate и двойная реализация, основанная на устаревшем реестре.

**Тест:** «Если реестр говорит — не существует, проверял ли ты production?» Нет → drift-риск.

**Источник:** WP-5 MCP tool discovery, session-close 2026-07-07. Инструмент динамического discovery задеплоен с мая — реестр (executor-catalog.yaml / MAP.002) не знал.

**Смежно:** [DP.FM.202] (multiple-registries-one-entity-drift), [DP.FM.246] (stale-active-wp-in-memory-table).

### DP.D.242: Событие перехода (per-transition) ≠ Событие состояния (per-state)

| Per-transition event | Per-state event |
|---------------------|-----------------|
| Эмитируется при изменении (old → new) | Эмитируется при каждом наблюдении/проверке |
| Есть только при реальном изменении | Есть всегда, даже если состояние не изменилось |
| Event log: только реальные переходы | Event log: дубли при повторных read/observe |
| Replay корректно считает переходы | Replay завышает количество «переходов» |

**Почему важно:** в event sourcing / CQRS системах с состояниями пользователя — эмиссия per-state засоряет event log дублями и делает replay некорректным. Read-model хранит текущее состояние (fast-read), event log содержит только реальные переходы.

**Тест:** «Есть ли observable change в системе?» Да → event; нет (проверка без изменения) → тишина.

**Источник:** WP-457 Ф10 belonging/engagement, session-close 2026-07-07. `user_axis_transitioned` генерируется при ИЗМЕНЕНИИ оси, не при каждом read `user_axis_state`.

**Смежно:** [DP.D.002] (Модель ≠ Данные), [DP.FM.028] (event-coverage-gap).
