# DP.D.208 — Проверка, читающая всегда-пустое поле = тавтологический pass

**Различение:** data-blocker (входные данные равномерно пусты → проверка никогда не срабатывает) ≠ algorithmic-pass (код проверки отработал корректно, нарушений нет).

| Аспект | Тавтологический pass (data-blocker) | Корректный pass |
|--------|-------------------------------------|-----------------|
| Откуда «нарушений нет» | Поле пусто в 100% записей — читать нечего | Поле заполнено, проверка отработала |
| Сигнал «всё чисто» | Ложный (нарушения могли быть, но не детектированы) | Достоверный |
| Как воспроизвести | Mock с заполненным полем → проверка должна найти нарушение | Mock не меняет результат |
| Что чинить | Источник данных (заполнить поле) или метод вывода (выводить из надёжного сигнала) | Ничего |

**Тест:** «Если заполнить поле тестовым значением — начнёт ли проверка обнаруживать нарушения?»
- Нет → data-blocker: проверка читает правильно, но данных нет. Тавтологический pass.
- Да → код проверки работает, поле было пусто → устранить data-blocker.

**Решение:** выводить свойство из надёжного сигнала, недоступного для пустоты (например, путь файла: `PACK-*/` → платформенный тир), а не из поля каталога. Тестировать детектор на mock-fixtures с непустыми значениями — реально-пустой каталог подтверждает что угодно.

**Семья различений false-green:**
- «Детектор существует ≠ детектор блокирует» — код проверки есть, но exit-код игнорируется.
- «HTTP status check ≠ keyword check» — HTTP 200 + пустой ответ = false-green по форме.
- **Данное** — равномерно пустые входные данные = false-green по содержимому.
Корень разный: здесь проблема в источнике данных, а не в коде или интерпретации ответа.

**Источник:** WP-429 Ф4 (layer-3 детектор реестров): поле `tir` пусто в 55 из 55 записей каталога — проверка тира никогда не срабатывала.
