# DP.SC.059 «Сторож разрывов данных (data-gap watchdog)»

> Источник домена: `DS-my-strategy/inbox/WP-476/CONCEPT-data-pipelines.md` §2 П5 (АрхГейт 14.07 — self-test обязателен И обязан подтверждать canary-факт, конъюнкция, не альтернатива), §9 (триада С7 «Актуализация» — data-gap-сторож). WP-476 Ф4б.

## Правило (инвариант)

> Что ВСЕГДА должно выполняться для данного сервиса. Нарушение = провал SC.

- [ ] Детектор проверяет **содержимое** дома данных (timestamp последней записи), а не живость процесса-производителя — это отдельный слой от `date-watchdog.sh`/`day-open-pipeline-watchdog.sh` (те следят, запустился ли producer по расписанию; этот следит, дошли ли реальные данные). Процесс может успешно отработать и не записать ни одной актуальной строки — ровно так был пропущен разрыв 45ч в WP-470.
- [ ] Self-test обязателен **И** обязан подтверждать детерминированный canary-факт (искусственно внесённый разрыв, который no-op-чекер физически не может пройти зелёным) — присутствие self-test без проверки содержания не засчитывается (прецедент `day-open-checks`, no-op с момента создания).
- [ ] Детектор различает «источник молчит» (infrastructure error: невалидный WakaTime-ключ, недоступна health.db) от «реально ноль активности» — не пишет ложный ноль вместо алерта (паттерн уже есть в `panel_wakatime.py`: транзиентный сбой → `None`, не 0).
- [ ] Числовой порог разрыва — атрибут конкретного потока, регистрируется в реестре конвейеров (WP-476 Ф3), не хардкодится в детекторе.

## Обещание

**Кому:** R14 Заказчик (пилот)

**Зачем:** три известных прецедента дошли до пилота только через ручное наблюдение месяцами позже: разрыв health.db 20ч→45ч (WP-470, обнаружен пилотом вручную при разборе), 2-месячный провал `engagement_collector`, умерший WakaTime-ключ (виден только в логах). Существующие сторожа (`date-watchdog`, dead-man's switch, alerter heartbeat) следят за живостью процессов, ни один не следит за содержимым данных.

**Что получит:** Telegram-алерт при первом скане после превышения числового порога разрыва для зарегистрированного потока (health.db, WakaTime — стартовый набор Ф4б) + еженедельное подтверждение (Week Close), что сам детектор жив и реально ловит разрыв (self-test на canary-факте), а не молча деградировал в no-op.

**Триггер:** периодический скан по расписанию (аналог Контура B WP-429 — периодический батч, не write-time gate; интервал = наименьший SLA среди зарегистрированных потоков) + явный self-test-флаг на Week Close.

**Время отклика:** алерт о реальном разрыве — на первом скане после превышения порога (не мгновенно, ограничено интервалом скана). Self-test verdict — синхронно при запуске на Week Close.

**Режим отказа:** если сам сторож не запустился (упал cron/launchd) — это зона ответственности process-watchdog (`date-watchdog.sh`), не дублируется здесь. Если self-test не поймал canary-факт на Week Close — **блокирующий инцидент**, не warning (аналог `registry-checker` WP-429: детектор без подтверждённого self-test не считается работающим).

## Сценарии использования (минимум 3, разные потребители)

### UC-1: Периодический скан ловит реальный разрыв health.db (потребитель — R14 Заказчик)

Инициатор — сам сторож по расписанию, без участия пилота. Разрыв в потоке `health.db` (receiver-путь телефон→Railway) превышает порог реестра → Telegram-алерт пилоту с указанием потока и длительности разрыва. Предотвращает повтор WP-470 (пилот узнаёт за интервал скана, не за 45ч ручного наблюдения).

### UC-2: Self-test с canary-фактом на Week Close (потребители — R14 Заказчик + R24 Аудитор)

Инициатор — ритуал Week Close (`/run-protocol week-close`). Сторож вносит детерминированный искусственный разрыв (canary) и проверяет, что сам его ловит. PASS → запись в лог, ничего не показывается пилоту (штатно). FAIL → блокирующий инцидент в Week Close отчёте (аналог Security Audit Cadence) — детектор без подтверждённого self-test не считается работающим, по образцу `registry-checker` WP-429.

### UC-3: Регистрация нового потока данных (потребитель — инженер/Кодировщик, регистрирующий конвейер в Ф3)

Инженер добавляет запись в реестр конвейеров WP-476 Ф3 (новый тип данных, `freshness_sla`, canary-схема). Сторож подхватывает новый поток при следующем запуске без правки собственного кода — по аналогии с `DP.SC.146` («новый секрет → сканер подхватит при следующем запуске, если добавлен в inventory»). Разделяет ответственность: инженер решает *что* мониторить (реестр), сторож решает *как* (скан + self-test).
