# [DP.SC.173] Реестр языковых стилей

## Правило (инвариант)
- [x] Стиль хранится как **данные** (значения осей поле/отношение/канал, голос, тон, регистры, жанры, пресеты), не как захардкоженный текст в хуках.
- [x] **Детерминизм:** один и тот же полный композитный ключ → один и тот же фрагмент промпта. Навсегда, без временных оговорок.
- [x] Полный ключ = `(context_key, user_override_hash, platform_layer_hash)`. `context_key` = (мета-класс читателя, роль, канал, домен). Хэши вычисляются от **нормализованных/отсортированных** значений осей (эквивалентные состояния каскада → один хэш).
- [x] **Каноническая нормализация хэша (часть контракта, не реализации).** `platform_layer_hash = sha256(canonical_json({"slot_version": <хэш source-слота>, "overlays": <отсортированный список имён применённых наложений>}))`. `canonical_json` = JSON с `sort_keys=true`, разделители `(",",":")`, null опущены, без пробелов. Без фиксации формы две реализации компилятора (Python в Ф5, возможный Go в Ф6) дадут разный хэш → детерминизм сломается на уровне контракта. `user_override_hash` нормализуется тем же `canonical_json`.
- [x] Реестр — read-path: вызов не имеет побочных эффектов (запись оверрайдов идёт через DP.SC.175, не здесь). **Derived-кэш (`compiled/`) и его пересборка по `manifest_hash` — допустимая идемпотентная мемоизация read-path, не побочный эффект:** один и тот же вход всегда даёт один выход, кэш лишь избавляет от повторной материализации.

## Обещание
- **Кому:** primary — Диспетчер стилей (DP.ROLE.074); secondary — агент-исполнитель (получает фрагмент через инъекцию, в реестр сам не ходит).
- **Зачем:** стиль перестаёт дублироваться в каждом хуке; новый регистр = запись данных, не новый хук с копией структуры.
- **Что получит:** фрагмент системного промпта (правила стиля как текст) по полному ключу.
- **Триггер:** Диспетчеру нужен фрагмент стиля для сборки промпта хода.
- **Вход:** полный композитный ключ `(context_key, user_override_hash, platform_layer_hash)`. На практике Диспетчер передаёт плоские рантайм-факты (`context_key` + активные наложения + ссылка на user-оверрайд); `platform_layer_hash` вычисляет сам реестр (DP.ROLE.073) — граница «маршрутизация ≠ данные» цела.
- **Выход:** структура `{fragment, applied_layers, key_hash, fallback_used, source_refs}`. `fragment` — текст правил стиля. `source_refs: [{source_id, source_hash}]` — список разыменованных указателей (слот + владелец контента + наложения) с их отпечатками: audit-trail для отладки «почему фрагмент такой» и опора для cross-repo guard свежести.
- **Время отклика:** синхронно, в процессе сборки промпта (in-process lookup, без отдельного сетевого вызова; до генерации ответа).
- **Режим отказа:** нет правила для ключа → базовый регистр (fallback) + лог промаха ключа.

## Свидетельства (4 компонента семиозиса)
- **Данные:** реестр-yaml (индекс слотов, наложения) + слот-файлы с указателем `content_source` на владельца правил; компилятор «данные → фрагмент». Двухслойная модель source/compiled (вариант A′, peer-session 2026-06-11-31): *source* — слот + указатель (OwnerIntegrity, правила у владельца); *compiled* — материализованный фрагмент в derived-кэше (`compiled/`, в `.gitignore`), разыменование указателя один раз при сборке (freeze-at-assignment), а не на каждом lookup — так держатся и OwnerIntegrity, и детерминизм.
- **Контекст:** Диспетчер вычислил ключ и запросил фрагмент при сборке промпта.
- **Полномочия:** владелец данных реестра — DP.ROLE.073 Хранитель реестра стилей.
- **Свидетельства:** лог промахов ключа (fallback на базовый регистр); тест детерминизма «два вызова с одним полным ключом → один фрагмент»; `registry-manifest.lock` (коммитится, мелкий) с отпечатками всех источников из **обоих репо** (слоты + владельцы контента + наложения) — guard свежести (`verify`) ловит cross-repo дрейф указателя; кэш инвалидируется по `manifest_hash`, поэтому дрейф структурно невозможен, а не «виден на ревью». Облачная резолюция пути к владельцу (когда соседнего пака нет на диске) вынесена за скоуп Ф5 → Ф10 (split платформа/IWE).

## Сценарии использования (≥3)
1. **Агент собирает ответ пилоту в IDE** — Диспетчер вычисляет ключ (мета-класс «человек», роль «пилот», канал «IDE», домен текущий) → реестр отдаёт фрагмент разговорного регистра (A1-A11) → инъекция.
2. **Kimi пишет коммит-сообщение** — ключ (мета-класс «агент», роль «исполнитель», канал «git», жанр «коммит») → реестр отдаёт плотный технический регистр без тона.
3. **Новичок в боте задаёт вопрос** — ключ (роль «новичок», канал «Telegram») → реестр отдаёт бытовой регистр с заменами терминов (онбординг-таблица DP.SC.050).
