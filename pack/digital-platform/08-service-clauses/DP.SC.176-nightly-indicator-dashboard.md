# [DP.SC.176] Ночное табло показателей пилота

> **Границы (IntegrationGate).** Это фазы 1-2 (обещание + сценарии). Роль (DP.ROLE) и реализация (ночной воркер, схема хранилища, эндпоинты доставки, watchdog) — последующие фазы/РП. Документ описывает КОНТРАКТ, не КАК.

## Правило (инвариант)
- [x] **Расчёт вне критического пути.** Показатели считаются после закрытия суток и до открытия дня, отдельным процессом. Закрытие дня (Day Close) и открытие дня (Day Open) расчётом НЕ нагружаются.
- [x] **Одна авторитетная панель дня.** Публикуемый артефакт за день D — панель показателей как зафиксированный факт (аналог «закрытого баланса дня»). Сырьё расчёта может храниться рядом для аудита и воспроизводимости, но контракт его не обещает и потребители его не читают. Один источник истины для потребителей.
- [x] **Потребители только читают.** Day Open, личная страница и фоновые роли НЕ пересчитывают панель (read-path без side effects). Формула расчёта — интерпретация, принадлежит воркеру, за дверью контракта.
- [x] **Статус свежести вместо гарантии часа.** Панель имеет статус `предварительная` или `финальная`. Финальная — неизменна (immutable). Контракт не обещает финальность к фиксированному часу (входные данные — WakaTime, реестр решений — могут до-синхронизироваться поздно).
- [x] **Стабильная структура панели** для всех потребителей, не зависящая от схемы хранилища (потребитель не лезет в суть).

## Обещание
- **Кому:** пилот (через открытие дня и через личную страницу); фоновые роли сопровождения.
- **Зачем:** видеть основные показатели прошлого дня (не только мультипликатор) без утяжеления закрытия и открытия дня; калибровать ритм работы.
- **Что получит:** одну авторитетную панель из 5 показателей (рычаг с числом агентов · поток · переделка · точность оценки · когнитивная нагрузка — метод РП414) за прошедший день, со статусом свежести.
- **Триггер:** ежедневно после закрытия суток и до открытия дня.
- **Вход:** данные за прошедший день — коммиты и сессии репозиториев, бюджеты закрытых РП (заморожены на WP Gate), физическое время (WakaTime), реестр решений (веса нагрузки), история по классам верификации (калибровка/bootstrap).
- **Выход:** одна авторитетная панель показателей за день D + статус свежести, доступная всем потребителям через стабильную структуру.
- **Время отклика:** целевой SLA — панель за D готова к началу открытия дня; чтение потребителем <1с. (Это целевой SLA, не гарантия финальности — см. инвариант о статусе.)
- **Режим отказа:** панель не готова или расчёт не прошёл → потребители показывают последнюю успешную версию + маркер «данные устарели/предварительные»; открытие дня НЕ блокируется; пилот уведомлён.

## Свидетельства (4 компонента семиозиса)
- **Данные:** панель дня D (5 тайлов + статус); сырьё расчёта (для аудита, вне контракта); история панелей по дням.
- **Контекст:** сутки D закрыты; запущен ночной расчёт.
- **Полномочия:** считает воркер (не агент-исполнитель, не потребитель — trusted reference из метода РП414 §6); потребители только читают; владелец механизма — будущая роль (DP.ROLE, фаза 3).
- **Свидетельства:** аудит-трейл панели до первички (список РП с бюджетами и коммитами, лог сессий, выгрузка WakaTime — РП414 §6.2); статус и время финализации; лог отказов/пересчётов.

## Сценарии использования (≥3, разные потребители)
1. **Пилот утром на открытии дня (активный потребитель, VS Code).** Открывает день, видит готовое табло за вчера (рычаг с числом агентов · поток · переделка · точность · нагрузка). Нагрузка была у порога → решает сегодня меньше параллельных сессий или уйти в простые задачи. Что делает с результатом: калибрует ритм дня.
2. **Пилот днём на личной странице (пассивный/мобильный потребитель, браузер).** Заходит с телефона между делами на guide.system-school.ru, видит то же табло без открытия рабочего окружения. Гайд тянет панель через платформенный шлюз (не лезет в хранилище), по стабильной структуре. Что делает: быстрый взгляд на тренд.
3. **Контролёр развития (фоновая роль R46, аналитический потребитель).** Читает накопленные панели за неделю для тренда; при перегрузе (нагрузка ≥ порога несколько дней) формирует сигнал/нудж пилоту. Что делает: еженедельная сверка + проактивный нудж.

## Открытый выбор для фазы реализации
- **Финализация данных за вчера:** лаг в один день (показывать финальную панель за позавчера) ИЛИ строгий data-ready gate (расчёт по сигналу «данные готовы» или по таймауту). Оба варианта укладываются в контракт; выбор — на фазе реализации, решает пилот.
