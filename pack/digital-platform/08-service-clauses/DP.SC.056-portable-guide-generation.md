# DP.SC.056 «Портативная сборка персонального руководства без серверов»

<!-- carrier-specific обещание портативного носителя роли R27; см. WP-483 Ф1/Ф1.5 -->

## Обещание

**Кому:** человеку, чья база уже размечена по типам 2.1-2.4 (выход DP.SC.055), с любым ИИ-помощником (свой ключ или локальная модель) — регистрация в IWE или на платформе НЕ требуется.

**Зачем:** обещание роли (собрать руководство) само по себе не говорит, ГДЕ роль исполняется и чем она за это платит. Портативный носитель даёт две гарантии, которых нет и не может быть у серверного: независимость от чужой инфраструктуры и проверяемость каждого факта на месте, в файлах пользователя.

**Что получит потребитель:**
1. **Ноль обязательных серверов.** Полное по форме руководство собирается на машине пользователя из его размеченной базы: без Neon, без Telegram, без нашей инфраструктуры. Сетевые вызовы — только к LLM-провайдеру пользователя (его выбор: свой ключ или локальная модель) и, опционально при подписке, к источнику свежего контента. Недоступные подписочные источники помечаются, не имитируются.
2. **Честный provenance.** Каждый факт руководства атрибутирован источником в журнале решений (decision_log: слот → файл-источник → поле → метод извлечения → confidence → время). Обязательные слоты без подтверждённой атрибуции → отказ всего прогона с диагностическим отчётом (какие слоты, почему), НЕ руководство с выдуманными фактами и НЕ молчаливый пустой результат.

**Триггер:** пользователь (через своего ИИ-помощника как MCP-инструмент `generate_guide` или headless CLI) запускает сборку, указав `profile.yaml`.

## Инвариант

- [x] **И1 (no-invented-facts).** Ни один факт о пользователе не появляется в руководстве без записи в decision_log с непустым источником. Проверяется по журналу, не по тексту: эксперт-ревьюер верифицирует «ни один факт не угадан» чтением лога (сценарий 3 концепции WP-289 §4). *Реализовано в Ф1: `adapter.py` build_decision_log + apply_hard_fail_gate.*
- [x] **И2 (policy, не хардкод).** Список обязательных слотов — декларативная политика (`required_attribution_slots`), не константа в коде; порог confidence для llm-assisted записей задаёт автор политики, не сама LLM (самооценка уверенности LLM не принимается — найдено пир-сессией 13.07, ход 3). *Реализовано в Ф1: `policies/default.yaml`, отсутствие политики = отказ запуска.*
- [x] **И3 (hard-fail вместо имитации).** Инструмент данных не подведён / профиль обязателен, но пуст по required-слотам → отказ с диагностикой (`DP.FM.160`), никогда — правдоподобный текст без данных. *Реализовано в Ф1: все отказы через диагностический отчёт, сетевые ошибки всех трёх LLM-бэкендов и пустой ответ LLM ловятся отдельно.*
- [x] **И4 (zero-upload).** Сборка не отправляет содержимое базы пользователя ни на какой наш сервер. Единственный исходящий трафик с содержимым — BYOK-вызов LLM самого пользователя (его провайдер, его выбор). *Реализовано в Ф1; CI-тест — Ф5 WP-483.*
- [ ] **И5 (один код роли) — ЦЕЛЕВОЕ СОСТОЯНИЕ, вступает в силу после WP-483 Ф1.5.** Портативный носитель — тот же код ядра (planner/horizons/prompt), что использует платформа через свой переходник: гарантии И1-И3 не могут разойтись между «локально» и «на платформе», потому что реализованы одним ядром. *Факт на 14.07.2026: платформа работает на собственной, отдельной копии ядра (`render-pilot-guides.py` + `agents/tailor/`) — см. `DP.ROLE.001` R27 current_holders; миграция = Ф1.5, план согласован пир-сессией 2026-07-14-05.*

## Режим отказа

- **Пустой профиль** → корректное холодное состояние (`stage=0`), руководство стартового уровня с честными пробелами — НЕ ошибка и НЕ выдумка биографии.
- **LLM-провайдер недоступен / сетевая ошибка** → диагностический отчёт с причиной (не трейсбек и не пустой файл) — все сетевые ошибки бэкендов превращаются в диагностику (закрыто код-ревью Ф1).
- **LLM вернул валидный, но пустой ответ** → отказ «руководство с пустым разделом не публикуется» (отдельная проверка после гейта атрибуции — найдено независимой проверкой Ф1).
- **Не атрибутирован required-слот** → отказ с перечислением слотов и причин, руководство не генерируется.

## Сценарии использования

> Те же пять сценариев, что у DP.SC.055 (концепция WP-289 §4) — этот SC покрывает генерационную половину цепочки: Марина (пустая история → честные пробелы), Дэвид (богатая база → каждый факт в логе), эксперт-ревьюер (проверяет decision_log, не текст), пилот-гибрид (одинаковое поведение при любом происхождении профиля), интегратор (headless CLI, 20 профилей циклом).
