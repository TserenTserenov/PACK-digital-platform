# [DP.SC.160] Артефактор-Постановщик задач IWE

## Правило (инвариант)

> Нарушение любого = провал SC.

- **Артефактор возвращает structured request, не вызывает исполнителя.** Выход Артефактора — всегда routing-тег + описание РП; передаётся обратно в Маршрутизатор (DP.ROLE.059), а не напрямую в скилл/скрипт.
- **Класс РП = routing-ключ.** Классификация `{trivial, closed-loop, open-loop, problem-framing}` — по критериям WP Gate Ritual (CLAUDE.md §2). Артефактор не вводит новые классы.
- **Один выход — один routing-tag.** Артефактор не производит несколько вариантов РП; если неоднозначность — фиксирует наиболее широкий класс (например, open-loop вместо closed-loop при сомнении).
- **Не блокирует пилота уточняющими вопросами.** При недостаточном входе — делает наилучшее предположение и передаёт результат с флагом `confidence: low` для последующего уточнения.

---

## Обещание

**Кому:**
- **Маршрутизатор (DP.ROLE.059)** — «неструктурированный вход превращён в routing-tag + артефакт; loop ограничен 1 итерацией»
- **Пилот IWE** — «не нужно вручную формулировать тип задачи; система определяет сама по содержанию»

**Зачем:**
- Opening-протокол обнаруживает задачу без routing-tag → нет исполнителя → зависание
- WP Gate Ritual существует как протокол, но требует ручного применения; Артефактор-Постановщик автоматизирует структурирование

**Что получит:**

```json
{
  "task_type": "role_design | bot_fix | day_open | agent_fault | ...",
  "class": "trivial | closed-loop | open-loop | problem-framing",
  "artifact": "краткое описание ожидаемого артефакта",
  "budget_estimate": "~Xh | ?",
  "confidence": "high | low",
  "routing_tag": "{class, task_type}",
  "resolution_path": "keyword | llm"
}
```

Поле `budget_estimate: "?"` — маркер «не определено» (потребитель запрашивает у пилота отдельно).
Поле `resolution_path` — путь классификации: `"keyword"` = статический lookup (< 200 мс), `"llm"` = Haiku-вызов (< 60 сек).

**Время отклика (два SLA):**

| Путь | SLA | Условие |
|------|-----|---------|
| `keyword` | < 200 мс | task_type однозначно определён по ключевым словам |
| `llm` | < 60 сек | Haiku-fallback при неоднозначности; потребитель видит `resolution_path: "llm"` |

Потребитель, ожидающий < 5 сек, должен проверять `resolution_path` перед синхронным ожиданием.

## Основной flow

```
Сырой запрос (нет routing-tag)
  │
  ├─ task_type очевиден по ключевым словам? (статический lookup)
  │   └─ да → построить routing-tag напрямую (без LLM)
  │   └─ нет → Haiku: «Определи task_type и class из описания: <вход>»
  │
  ├─ Артефактор строит structured request:
  │   {task_type, class, artifact, budget_estimate, confidence}
  │
  └─ Вернуть structured request → Маршрутизатор (DP.ROLE.059) для lookup
```

## Сценарии использования (Ф2)

### Сц-1: Пилот пишет «нужно разобраться почему упал бот»

- **Потребитель:** Маршрутизатор, получил запрос без тега
- **Что делает Артефактор:** ключевые слова «бот», «упал» → `task_type=bot_error_diagnosis, class=closed-loop, artifact=«диагноз причины падения», budget_estimate=~1h, confidence=high`
- **Результат:** Маршрутизатор lookup → скилл диагностики бота. Пилот ничего не формулировал вручную.

### Сц-2: Пилот пишет «надо что-то придумать с подписками»

- **Потребитель:** Маршрутизатор, нет ключевых слов для статического lookup
- **Что делает Артефактор:** Haiku классифицирует → `task_type=subscription_design, class=problem-framing, artifact=«концепция или дизайн подписок», budget_estimate=~3h, confidence=low`
- **Результат:** `confidence=low` — Маршрутизатор передаёт routing-tag + сигнал неопределённости; исполнитель (LLM Opus) получает артефакт для уточнения.

### Сц-3: Opening обнаруживает задачу без РП (WP Gate не сработал)

- **Потребитель:** Opening-протокол, напрямую без Маршрутизатора
- **Что делает Артефактор:** получает неформальное описание задачи → строит routing-tag → возвращает в Opening для продолжения WP Gate Ritual (регистрация РП в 4 местах)
- **Результат:** WP Gate получает уже структурированный вход; пилоту не нужно повторно описывать задачу.

### Сц-4: Маршрутизатор вызвал Артефактора, тот вернул некорректный тег

- **Потребитель:** Маршрутизатор (второй вызов loop)
- **Что делает Артефактор:** повторная попытка → нет routing-tag (техническая ошибка LLM-вызова)
- **Результат:** Маршрутизатор фиксирует `STRUCTURE_FAILED` (loop = 1 итерация максимум); Артефактор не вызывается третий раз.

## Режим отказа

| Сценарий | Поведение |
|---------|-----------|
| Haiku не может определить task_type | Вернуть `{class: open-loop, task_type: unknown, confidence: low}` — не блокировать |
| Вход пустой или < 5 слов | Вернуть `INSUFFICIENT_INPUT` → Маршрутизатор логирует, не вызывает исполнителя |
| LLM Haiku недоступен | Статический lookup по ключевым словам; при отсутствии совпадения → `{class: open-loop, task_type: unclassified}` |
| Результат возвращён без routing-tag (технический сбой) | `STRUCTURE_FAILED` — Маршрутизатор прерывает loop |
