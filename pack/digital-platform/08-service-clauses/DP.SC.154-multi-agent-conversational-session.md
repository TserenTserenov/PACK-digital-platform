# [DP.SC.154] Мульти-агентная диалоговая сессия

## Правило (инвариант)

- [ ] Write-доступ к файлам workspace во время диалога — только у писателя (writer). Напарник (peer) пишет только в свою реплику `<NN>-peer.md` в журнале.
- [ ] Любой участник может прервать цикл эскалацией к пилоту через маркер `ESCALATE_TO_USER: <причина>` в своей реплике.
- [ ] Финальный отчёт `report.md` собирается из журнала реплик, не «по памяти писателя».
- [ ] Журнал реплик `agent-conversation/<task-id>/` сохраняется до явной архивации (для аудита и pattern mining).
- [ ] Лимит ходов в одной сессии — не больше 10 (защита от расходящихся обсуждений). При исчерпании без консенсуса итог = «не сошлись», отчёт включает обе позиции.

## Обещание

**Кому:** DP.ROLE.001 Создатель IWE (пилот) — заказчик задачи, которая выигрывает от двух точек зрения.

**Зачем:** В задачах с высокой ценой ошибки (архитектурное решение, code review, аудит документа) один взгляд недостаточен. Два peer-агента разных вендоров с разными сильными сторонами через многотуровый обмен дают более качественный анализ, чем суммирование двух независимых отчётов: они видят аргументы друг друга и реагируют на них.

**Что получит:**
1. Один общий `agent-conversation/<task-id>/report.md` от писателя — синтез обсуждения с явно отмеченными согласиями, разногласиями и итоговой позицией.
2. Журнал реплик `00-writer.md`, `01-peer.md`, `02-writer.md`, ... — полная стенограмма для аудита.
3. При срабатывании эскалации — прямой вопрос пилоту до того, как писатель проигнорирует возражение напарника.

**Триггер:**
- Команда пилота «обсуди X с напарником» в живой сессии писателя.
- Запуск `scripts/peer-conversation.sh <task-id>` с подготовленной начальной репликой.
- Явное создание `agent-conversation/<task-id>/00-writer.md` в репозитории.

**Время отклика:**
- Один ход напарника ≤90 секунд (запуск `claude -p` headless + reasoning).
- Полная сессия ≤30 минут (типично 4-6 ходов до консенсуса).
- Эскалация — писатель прерывается на следующем ходе после обнаружения маркера.

**Режим отказа:**
- Напарник не ответил за 5 минут → ход считается пропущенным; писатель решает: продолжить без него или эскалировать пилоту факт отказа.
- Лимит ходов исчерпан без консенсуса → отчёт фиксирует «не сошлись», обе позиции с обоснованиями, эскалация пилоту на финальное решение.
- Маркер `ESCALATE_TO_USER` без обоснования причины → ход отклоняется, писатель просит напарника переписать или фиксирует отказ.
- Напарник попытался `write_file` в workspace вне своей реплики → Local Gateway отклонит (lock не у него); писатель записывает нарушение в журнал.
- Журнал недоступен (диск/сеть) → сессия не стартует; пилот получает уведомление об инфраструктурной ошибке.

## Сценарии использования (минимум 3)

### Сценарий 1. Архитектурное решение

**Контекст:** Пилот разрабатывает новый компонент IWE и хочет проверить дизайн до начала реализации.

**Поток:**
1. Писатель (Claude в живой сессии) формулирует архитектурную заявку в `00-writer.md`: проблема, предлагаемый дизайн, альтернативы, обоснование выбора.
2. Напарник (Kimi через `claude -p` или альтернативу) в `01-peer.md`: критика дизайна, поиск незамеченных рисков, контр-предложение если есть.
3. Писатель в `02-writer.md`: реакция на критику — соглашается, оспаривает, дорабатывает.
4. Цикл до консенсуса (обычно 4-6 ходов).
5. Финал — `report.md` с решением, ключевыми рисками и зафиксированными разногласиями.

**Польза:** Дизайн проверен с двух точек зрения до коммита. Сэкономлены часы переделок.

### Сценарий 2. Code review двумя агентами

**Контекст:** Писатель набросал реализацию, нужен review до merge.

**Поток:**
1. Писатель в `00-writer.md`: ссылка на diff, контекст задачи, специфические опасения автора.
2. Напарник в `01-peer.md`: разбор по категориям — стиль, ошибки, edge-cases, безопасность.
3. Писатель в `02-writer.md`: соглашается / спорит / спрашивает уточнения по конкретным пунктам.
4. Напарник в `03-peer.md`: уточнения, доп. находки, итоговый чек-лист правок.
5. `report.md` — согласованный список правок с приоритетами.

**Польза:** Code review более глубокий, чем у одного агента. Расхождения позиций видны явно.

### Сценарий 3. Аудит документа

**Контекст:** Пилот хочет проверить документ (Pack-формализация, договор, спецификация) у двух независимых ревизоров до публикации.

**Поток:**
1. Писатель в `00-writer.md`: документ + критерии аудита (полнота, согласованность, отсутствие галлюцинаций).
2. Напарник в `01-peer.md`: свои находки по тем же критериям.
3. Писатель в `02-writer.md`: пересечение находок, добавление пропущенного.
4. Напарник в `03-peer.md`: подтверждение или несогласие с интерпретацией пересечений.
5. `report.md` — объединённый список находок с уровнями уверенности (оба видят / только один / спорное).

**Польза:** Расхождения находок — сигнал для глубокой проверки. Согласованные находки — сигнал для гарантированного исправления.

| 2 | Создать `agent-conversation/<id>/00-writer.md` со своим ходом + инструкцией для напарника | DP.ROLE.039 (писатель) | git Write |

## Открытые вопросы (для первой реализации, WP-337-З-Ф2)

1. **Headless-канал напарника:** `claude -p` с альтернативным провайдером (другой `ANTHROPIC_BASE_URL`) или отдельный CLI вендора (например, `ki` для Kimi)? Уточнить с пилотом — записано в [project_peer_agents.md](../../../memory/project_peer_agents.md).
2. **Лимит ходов:** фиксированный 10 или адаптивный (детектор сходимости аргументов)? Стартовое значение — 10 фиксированных, адаптивный — в WP-337-З-Ф4 при наличии метрик из smoke.
3. **Расположение журналов:** `~/IWE/.iwe-runtime/agent-conversation/` (эфемерно, не в git) или `inbox/WP-NNN/agent-conversation/<id>/` (под WP в git)? Рекомендация — под WP, для аудита и pattern mining.
4. **Persistence журналов:** хранить после сессии (pattern miner) или удалять? Рекомендация — хранить, архивировать через 30 дней по правилу Agent Inbox.
5. **Identity напарника в журнале:** имя файла `01-peer.md` или `01-peer-kimi.md`? Рекомендация — короткое, идентификатор в frontmatter реплики.
