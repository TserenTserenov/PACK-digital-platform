# [DP.SC.154] Мульти-агентная диалоговая сессия

## Правило (инвариант)

- [ ] Write-доступ к файлам workspace во время диалога — только у писателя (writer). Напарник (peer) пишет только в свою реплику `<NN>-peer.md` в журнале.
- [ ] Любой участник может прервать цикл эскалацией к пилоту через маркер `ESCALATE_TO_USER: <причина>` в своей реплике. Маркер без обоснования причины → ход отклоняется.
- [ ] Напарник может сигнализировать о консенсусе через маркер `CONSENSUS: <резюме>` (опциональный, машинно-парсируемый). Писатель читает маркер и самостоятельно решает: выйти досрочно или продолжить. Формат фиксированный, case-sensitive.
- [ ] Финальный отчёт `report.md` собирается из журнала реплик, не «по памяти писателя».
- [ ] Журнал реплик `sessions/conversations/<YYYY-MM-DD>-<NN>-<slug>/` сохраняется до явной архивации (для аудита и pattern mining). Нумерация `NN` ежедневная, начинается с `01`.
- [ ] Лимит ходов в одной сессии — не больше 10 (защита от расходящихся обсуждений). **Лимит применяется к содержательной части после согласования ролей.** Ходы sequential role-discovery (см. раздел «Opening сессии») в лимит **не входят** (max 3 discovery-хода до эскалации). При исчерпании содержательного лимита без консенсуса итог = «не сошлись», отчёт включает обе позиции, эскалация к пилоту.

## Двухосная модель ролей (WP-367 Ф5, v4)

> **Источник:** peer-session `2026-05-30-06-wp367-content-role-primacy` (CONSENSUS turn 5). Уточняет N-мерную ортогональность (v3) до конкретной двухосной модели с явными default- и swap-правилами.

Каждый агент в peer-сессии характеризуется по двум независимым осям:

| Ось | Поле в frontmatter реплики | Что задаёт | Источник значения |
|-----|----------------------------|------------|-------------------|
| **Содержательная роль** (`content_role`) | `content_role: DP.ROLE.NNN \| MIM.R.NNN \| ad-hoc:<имя>` | **Полный домен-контекст**: критерии выбора метода + формат артефакта + критерии качества + связи с другими ролями. Онтологическая линза, не маршрутизатор. | Pack (`DP.ROLE`/`MIM.R`) или ad-hoc snapshot в `meta.yaml.ad_hoc_roles` |
| **Процессная позиция** (`process_position`) | `process_position: writer \| peer` | Координация: writer держит workspace lock, peer имеет право эскалации. **Не определяет экспертизу.** | Default rule (см. ниже) или explicit swap |

**Session context** (в `meta.yaml`, не в реплике):
- `initiator_agent: <id>` — invariant сессии, кто открыл.
- `swap_history: []` — журнал перестановок `process_position` (если были).
- `ad_hoc_roles: {role_name: {agent_id, rationale, first_used_turn}}` — реестр ad-hoc ролей, использованных в сессии.

### Default rule для process-position

- [ ] **Initiator = writer, respondent = peer.** Без обсуждения в Opening. Process-position derived автоматически из `meta.yaml.initiator_agent`.

Это **не** делает process-position derived от content-role — обе оси независимы. Default — это **координационное правило по умолчанию**, не логический вывод.

**Граница автоматизма:** автоматизация касается ТОЛЬКО `process_position` (writer/peer). `content_role` всё равно обсуждается в Opening (Sequential role-discovery, см. ниже) — это содержательное согласование «кто чем занимается по существу», обязательный разговор. Уточнение v4 убирает из Opening одну техническую тему («кто пишет»), не доменное согласование.

### SWAP_WRITER explicit маркер

Для смены writer-позиции в течение сессии — explicit-маркер в реплике:

```
REQUEST_SWAP_WRITER: <reason>
```

Протокол:
1. Любой агент пишет `REQUEST_SWAP_WRITER: <reason>` в своей реплике.
2. Партнёр в следующей реплике отвечает: `SWAP_ACK` (согласен) или `SWAP_NACK: <reason>` (отказ).
3. При `SWAP_ACK` — мета-реплика `<NN>-swap.md` фиксирует переход:
   ```yaml
   ---
   turn: <NN>
   type: swap_writer
   from_writer: <old_agent_id>
   to_writer: <new_agent_id>
   reason: "<...>"
   ---
   ```
4. Обновляется `meta.yaml.swap_history: [{turn, from, to, reason}]`.
5. При `SWAP_NACK` — сохраняется текущий writer, сессия продолжается. `swap_history` не меняется. Эскалация к пилоту — опционально (если NACK блокирует прогресс).

**Запрет:** implicit swap (изменение поведения без маркера) — нарушение lock-инварианта.

### ROLE_DRIFT маркер

Для смены `content_role` в течение сессии — explicit-маркер:

```
ROLE_DRIFT: <old_role> → <new_role> — reason: <...>
```

Различение:
- **Инкрементальный drift** (новая роль из того же семейства, e.g. Стратег → Стратег-кризисный, Архитектор → Архитектор-данных) — маркер + `meta.yaml.roles` update, сессия продолжается.
- **Фундаментальный drift** (смена домена, e.g. Архитектор → Аудитор кода, или смена класса задачи open-loop → trivial) — закрытие сессии (`CONSENSUS: none, drift fundamental`) и открытие новой с правильным framing.

Граница субъективная: «новый методический инструментарий из того же семейства?» Если да — incremental, если нет — fundamental.

### Constraints (нелегитимные комбинации)

- [ ] **Ровно 1 writer per session.** Lock-инвариант. Два агента с `process_position: writer` одновременно = коллизия.
- [ ] **Content-role валидируется** через Pack (`DP.ROLE`/`MIM.R`/`VR.R`) ИЛИ через snapshot в `meta.yaml.ad_hoc_roles` (с rationale).
- [ ] **Swap process-position только explicit-маркером.** Implicit — нарушение.
- [ ] **Принцип:** содержательные роли разных агентов взаимодополняющие (см. Правило 2 ниже). Одинаковые = эхо-камера.

## Правила совмещения ролей

В peer-сессии каждый агент играет одну или несколько **ролей**. Роли бывают двух типов:
- **Протокольные позиции** — `writer` (писатель) / `peer` (напарник). Фиксированы DP.SC.154. Определяют write-доступ к workspace и порядок реплик.
- **Содержательные роли** — каталог Pack (`DP.ROLE.NNN`, `VR.R.NNN`). Определяют экспертизу, метод, домен внимания.

**Все роли ортогональны друг другу** — N независимых измерений, не одна ось «протокольная × доменная» (см. [DP.ROLE.039 §13](../02-domain-entities/DP.ROLE.039-peer-agent.md#13-n-мерная-ортогональность-ролей)). С v4 (WP-367 Ф5) — конкретизировано до двухосной модели выше.

### Правило 1. Внутри одного агента

- [ ] Агент может играть **несколько ортогональных ролей одновременно** в одной сессии. Пример: писатель (протокольная) + Стратег (DP.ROLE.012) + Декомпозитор (DP.ROLE.053).
- [ ] **Запрет:** совмещение контрольной и операционной роли на одном артефакте (DP.D.080 «Контрольная роль ≠ Операционная»). Аудитор, правящий аудитуемый артефакт, теряет независимость.

### Правило 2. Между двумя агентами в peer-сессии

- [ ] **Содержательные роли двух агентов должны быть взаимодополняющими** — создавать полезное напряжение (Стратег ↔ Аудитор, Инженер ↔ Методолог, Менеджер ↔ Стратег, Постановщик ↔ Верификатор).
- [ ] **Антипаттерн:** одинаковые содержательные роли у обоих агентов (Стратег + Стратег) = эхо-камера, не критика. Если detected → ESCALATE_TO_USER на role mismatch.

## Opening сессии: Sequential role-discovery

Если пилот назначил роли явно при запуске сессии (через параметр `roles` или поле в инвокации) → агенты играют как назначено, discovery пропускается.

Иначе — **sequential протокол с правом несогласия**:

### Ход 0 (initiator)

Агент, в **чьём окне запущена peer-сессия** (writer/инициатор), первым:
1. Анализирует задачу
2. Определяет свою роль (с проверкой Pack: какая роль уместна для domain задачи)
3. Предлагает напарнику роль (взаимодополняющую по Правилу 2)
4. Записывает в frontmatter `00-writer.md`: `proposed_roles: {agent_id: [DP.ROLE.NNN, ...]}`

Формат предложения в теле реплики: «Беру роль X (DP.ROLE.NNN) — потому что [причина]. Тебе предлагаю Y (взаимодополняющую) — потому что [причина]».

### Ход 1 (respondent)

Напарник в `01-peer.md`:
- **(a)** согласиться: играет предложенную роль
- **(b)** подсказать initiator'у поменять его роль (с обоснованием)
- **(c)** взять другую роль для себя (с обоснованием)
- **(d)** комбинация (b)+(c)

Фиксирует выбор в frontmatter:
```yaml
chosen_role: VR.R.001 | <DP.ROLE.NNN> | <ad-hoc:имя>
suggested_initiator_role: keep | change-to-<DP.ROLE.NNN>
```

### Ход 2 (initiator response)

Initiator в `02-writer.md`:
- согласиться с предложениями respondent
- **не согласиться** (право initiator'а): «Останусь X — потому что [причина]»
- предложить компромисс (двойные роли, иной набор)

Фиксирует в frontmatter `agreed_roles: {agent_id: [DP.ROLE.NNN, ...]}`.

### Эскалация

Если не согласовано за 3 хода (0, 1, 2) → `ESCALATE_TO_USER: ambiguous role choice — initiator предлагает X, respondent — Y, компромисс не найден`. Пилот решает.

### Завершение discovery

После согласования (или прямого назначения пилотом):
- initiator обновляет `meta.yaml` поле `roles: {agent_id: [DP.ROLE.NNN, ...]}`
- **Содержательная сессия начинается с хода 3** (или сразу с хода 1 если назначено пилотом)
- Discovery-ходы (0, 1, 2) не учитываются в лимит 10 содержательных ходов

### Pack-first с gap-toleration

> **Источник gap-toleration:** peer-session `2026-05-29-25-wp367-pack-roles-implementation` ход 1 (VR.R.001 Верификатор отметил: при текущем недонаполненном каталоге `03-methods/` формальный «deviate с обоснованием» сделает Pack-first нарушаемым в 90% случаев). Решение записать gap-toleration принято initiator'ом в ходе 2.
>
> **Уточнение v4 (WP-367 Ф5):** содержательная роль из Pack даёт **полный домен-контекст** (критерии выбора метода + формат артефакта + критерии качества + связи), не только метод. Метод подбирается **внутри линзы**, не определяется ей 1:1. Pack — каталог онтологических линз, не маршрутизатор «роль→единственный метод».

При определении роли:
- **Default:** использовать **домен-контекст роли из Pack** (`DP.ROLE.NNN` / `MIM.R.NNN`): критерии выбора метода (passport), формат артефакта (templates), сценарии (relations). Метод подбирается внутри линзы — может быть `DP.M.NNN` / `MIM.M.NNN`, может быть ad-hoc если задача уникальна.
- **При gap (нет роли или метода в Pack):** допустим ad-hoc подход с явной фиксацией в реплике («Pack-gap: для X нет в каталоге, использую ad-hoc Y») И в `meta.yaml.ad_hoc_roles`.
- **Систематический gap:** 3+ ad-hoc для одной роли (по разным сессиям, не по упоминаниям в одной) → флаг для расширения Pack (создать `DP.ROLE.NNN`/`DP.M.NNN`).

### Каскад Pack-расширения (in-session signal + Week Close audit)

> **Источник:** peer-session `2026-05-30-06-wp367-content-role-primacy` turn 3-5 + уточнение пилота 2026-05-30 (после deploy v4): in-session сигнал — primary, скрипт audit — secondary back-up.

**Pipeline (двухуровневый):**

**Уровень 1 — In-session signal (primary).** В момент использования ad-hoc роли агент **обязан сразу** объявить пилоту:

```
Беру ad-hoc роль «<имя>». В каталоге такой нет.
Обязанности: <…>. Метод: <…>.
Предлагаю создать РП на формализацию (~30 мин: passport + scenarios + templates).
Выбери: создать сейчас / отложить (сторож напомнит при Week Close).
```

Это choice-question для пилота. Сигнал работает БЕЗ скрипта-сторожа — каскад замыкается прямо в диалоге. Запись в `meta.yaml.ad_hoc_roles` происходит независимо от выбора пилота (для уровня 2).

**Уровень 2 — Week Close audit (secondary).** Скрипт `audit-ad-hoc-roles.py` — back-up для случаев когда in-session сигнал был пропущен или пилот выбрал «отложить»:
1. Скрипт проходит по `sessions/YYYY-MM/`, агрегирует частоту по имени ad-hoc роли.
2. При частоте ≥3 сессий И отсутствии открытого `WP-NNN-pack-gap-<role-name>` в `inbox/` (проверка через `WP-REGISTRY.md` grep + `inbox/` glob) — выводит **напоминание** пилоту со списком частых ad-hoc ролей и предложением создать WP.
3. Создание WP — по согласованию с пилотом. Флаг `--auto` для автогенерации без согласования (default = напоминание).

> **Порог `≥3` сессий** (а не `≥2`, упомянутый в CONSENSUS peer-сессии 2026-05-30-06): консервативный выбор, унаследованный от v3 (Pack-first §«Систематический gap: 3+ ad-hoc»). Обоснование: при threshold=2 две случайные ad-hoc в течение недели уже триггерят напоминание, что создаёт шум. Threshold=3 — устойчивый паттерн. Пересмотр — при наблюдении проблемы.

**Принцип:** owner = пилот через in-session сигнал (уровень 1) + WP-механика (уровень 2). Backlog не накапливается «где-то там» — материализуется в системе РП по согласованию с пилотом.

Это честнее, чем формальный «deviate с обоснованием» при пустом каталоге методов.

### Ad-hoc роль

Если в Pack нет подходящей роли (DP.ROLE.NNN) — агент в Opening предлагает **ad-hoc роль** (вне каталога):
- Объявить явно: «играю ad-hoc роль X с обязанностями Y» (как у Pack-ролей)
- Ожидать подтверждения пилота (отдельный ход или явное согласие в чате)

**Обратная связь:** ad-hoc роль использована 2+ раз → формализовать как `DP.ROLE.NNN` в Pack. Без обратной связи каталог не растёт.

## Расширение до N агентов (v5, WP-509)

> **Источник:** peer-сессии `2026-07-30-04-wp509-triadic-protocol-design` (тройной консенсус Claude/Kimi/Codex, 3 хода, 0 эскалаций) и `2026-07-30-09-wp509-protocol-skill-params` (формализация текста, Claude + Kimi). Триггер — WP-367 Ф4 прямо откладывала это расширение до «появления 3-го агента в сессии»; пилот запросил расширение 2026-07-30.

Всё, что описано в разделах выше (Двухосная модель ролей, Правила совмещения, Opening: Sequential role-discovery, инвариант «ровно 1 writer»), остаётся в силе без изменений при N>2. Ниже — только то, что специфично для 3 и более участников.

### Write token ≠ process_position

`process_position` (кто держит lock/оркестрацию, writer/peer) не меняется при N>2 — `SWAP_WRITER` работает как описано в «Двухосная модель ролей», без изменений.

При N>2 появляется вторая, независимая сущность — **write token**: чьё предложение сейчас в работе (кого писатель сейчас реализует через Edit). Держатель write token не обязан совпадать с держателем `process_position=writer` — единственный технический оркестратор сессии применяет правки Edit/Write, но может реализовывать предложение любого участника, у кого сейчас write token.

**Handoff write token:**
- [ ] Держатель token передаёт его только явным действием: `OFFER_HANDOFF: <агенту> — <причина>` в своей реплике → адресат подтверждает `ACCEPT_HANDOFF` в следующей.
- [ ] Любой участник может попросить передачу: `REQUEST_HANDOFF: <причина>` — это **необязывающая просьба**, держатель вправе отказать (кратко указав причину) без передачи.
- [ ] Инициировать `OFFER_HANDOFF` может только текущий держатель, не любой участник. Отвергнутая альтернатива — «любой может инициировать передачу»: даёт двум участникам сговориться и забрать token у третьего без его согласия (найдено на ходе 1 сессии `2026-07-30-04-...`).

**Практический эффект при текущей архитектуре peer-conversation** (единственный технический оркестратор — см. `.claude/skills/peer-conversation/SKILL.md` §«Архитектура»): handoff не меняет физического держателя Bash/Edit — он меняет то, чьё предложение сейчас реализуется. Полный симметричный handoff (второй участник сам ведёт оркестрацию своей сессией) возможен только когда у него тоже есть своя оркестрирующая сессия — сегодня это отдельный скилл `kimi-peer-writer` для двух участников, вне рамок N-агентного расширения.

### Раунды вместо бесконечного круга

- [ ] Содержательная часть сессии при N>2 идёт **раундами**: в каждом раунде высказывается каждый участник по одному разу, в порядке, зафиксированном при открытии сессии.
- [ ] Явное право промолчать в своём раунде — маркер `PASS` в начале реплики (пустая содержательная позиция, не ошибка протокола).
- [ ] Участник не ответил в отведённое время → раунд не блокируется, очередь двигается дальше, пропуск фиксируется в `meta.yaml`.
- [ ] Отвергнутая альтернатива — жёсткий бесконечный круг говорящих без раундов: застревает при недоступном участнике (найдено на ходе 1 сессии `2026-07-30-04-...`).

**Лимит.** Для N=2 семантика не меняется — `turns_limit: 10` считает реплики, как в v4. Для N>2 вводится отдельное поле `rounds_limit` (`meta.yaml`, default 6 раундов) — не переопределяет `turns_limit`, независимое поле, применимое только при N>2. Разделение намеренное: молчаливая замена смысла существующего `turns_limit` с реплик на раунды удвоила бы длину сессий при N=2 без отдельного решения об этом.

### Разрешение спора между 3+ позициями

Новое понятие, отсутствовавшее в v4 (там только двусторонний `ESCALATE_TO_USER`). Критерий — **обратимость решения**, не то, на чьей стороне большинство само по себе:

- [ ] **Решение обратимо и в пределах полномочий участников** → достаточно согласия 2 из 3 (или большинства при N>3). Несогласие меньшинства фиксируется рядом (в реплике или в `report.md` §3 «Отвергнутые альтернативы»), не блокирует продолжение.
- [ ] **Решение необратимо ИЛИ выходит за рамки полномочий участников сессии** → нужно либо согласие всех участников, либо решение передаётся пилоту (`ESCALATE_TO_USER`).
- [ ] **Сам вопрос «обратимо ли это решение» вызывает разногласие** → автоматически применяется строгий режим (единогласие или пилот) — спор о критерии не решается тем же критерием, который оспаривается.

Отвергнутая альтернатива: критерий «есть ли у меньшинства новый довод» — отклонён как субъективный (см. `2026-07-30-04-wp509-triadic-protocol-design/report.md` §3).

### Role-discovery для N>2

Sequential-протокол (см. «Opening сессии» выше) обобщается заменой хода на раунд — той же заменой единицы, что и в разделе «Раунды» выше, без нового числа:

- [ ] **Раунд 0 (инициатор):** предлагает содержательную роль себе и каждому из N-1 участников (было — только одному напарнику).
- [ ] **Раунд 1 (все остальные):** каждый участник — согласие / встречное предложение своей роли / встречное предложение роли другого участника, в фиксированном порядке раунда.
- [ ] **Раунд 2 (финал инициатора):** инициатор фиксирует итог — согласие с правками раунда 1 или обоснованный отказ (то же право, что и в паре).
- [ ] Не согласовано за 3 раунда → `ESCALATE_TO_USER: ambiguous role choice at N>2` — тот же порог (3), что и для пары, применённый к раундам вместо ходов.
- [ ] Discovery-раунды не входят в `rounds_limit`/`turns_limit` — так же, как для пары.

### Constraints (дополнение к N=2)

- [ ] **Ровно 1 держатель write token одновременно** — тот же lock-инвариант, что у `process_position=writer`, но для отдельной сущности.
- [ ] **Content-role по-прежнему валидируется через Pack или `ad_hoc_roles`** — правило не меняется с ростом N.
- [ ] **Взаимодополняемость (Правило 2) — для каждой пары участников**, не только писатель↔напарник. Несколько одинаковых содержательных ролей (например, два Аудитора при N=3) — та же эхо-камера, что и у пары.

## Обещание

**Кому:** DP.ROLE.001 Создатель IWE (пилот) — заказчик задачи, которая выигрывает от двух точек зрения.

**Зачем:** В задачах с высокой ценой ошибки (архитектурное решение, code review, аудит документа) один взгляд недостаточен. Два peer-агента разных вендоров с разными сильными сторонами через многотуровый обмен дают более качественный анализ, чем суммирование двух независимых отчётов: они видят аргументы друг друга и реагируют на них.

**Что получит:**
1. Один общий `report.md` от писателя в папке сессии — синтез обсуждения с явно отмеченными согласиями, разногласиями и итоговой позицией. При наличии `result_path` в `meta.yaml` — скопирован туда (в конкретный WP/Pack/DS).
2. Журнал реплик `00-writer.md`, `01-peer.md`, `02-writer.md`, ... — полная стенограмма для аудита в `sessions/conversations/<YYYY-MM-DD>-<NN>-<slug>/`.
3. При срабатывании эскалации — прямой вопрос пилоту до того, как писатель проигнорирует возражение напарника.

**Триггер:**
- Команда пилота «обсуди X с напарником» в живой сессии писателя.
- Запуск `scripts/peer-conversation.sh <slug>` с подготовленной начальной репликой.
- Явное создание `sessions/conversations/<YYYY-MM-DD>-<NN>-<slug>/00-writer.md`.

**Время отклика:**
- Один ход напарника ≤90 секунд (запуск `claude -p` headless + reasoning).
- Полная сессия ≤30 минут (типично 4-6 ходов до консенсуса).
- Эскалация — писатель прерывается на следующем ходе после обнаружения маркера.

**Режим отказа:**
- Напарник не ответил за 5 минут → ход считается пропущенным; писатель решает: продолжить без него или эскалировать пилоту факт отказа.
- Лимит ходов исчерпан без консенсуса → отчёт фиксирует «не сошлись», обе позиции с обоснованиями, эскалация пилоту на финальное решение.
- Маркер `ESCALATE_TO_USER` без обоснования причины → ход отклоняется, писатель просит напарника переписать или фиксирует отказ.
- Напарник попытался `write_file` в workspace вне своей реплики → Local Gateway отклонит (lock не у него); писатель записывает нарушение в журнал.
- Журнал недоступен (диск/сеть) → сессия не стартует; пилот получает уведомление об инфраструктурной ошибке.

## Сценарии использования (минимум 3)

### Сценарий 1. Архитектурное решение

**Контекст:** Пилот разрабатывает новый компонент IWE и хочет проверить дизайн до начала реализации.

**Поток:**
1. Писатель (Claude в живой сессии) формулирует архитектурную заявку в `00-writer.md`: проблема, предлагаемый дизайн, альтернативы, обоснование выбора.
2. Напарник (Kimi через `claude -p` или альтернативу) в `01-peer.md`: критика дизайна, поиск незамеченных рисков, контр-предложение если есть.
3. Писатель в `02-writer.md`: реакция на критику — соглашается, оспаривает, дорабатывает.
4. Цикл до консенсуса (обычно 4-6 ходов).
5. Финал — `report.md` с решением, ключевыми рисками и зафиксированными разногласиями.

**Польза:** Дизайн проверен с двух точек зрения до коммита. Сэкономлены часы переделок.

### Сценарий 2. Code review двумя агентами

**Контекст:** Писатель набросал реализацию, нужен review до merge.

**Поток:**
1. Писатель в `00-writer.md`: ссылка на diff, контекст задачи, специфические опасения автора.
2. Напарник в `01-peer.md`: разбор по категориям — стиль, ошибки, edge-cases, безопасность.
3. Писатель в `02-writer.md`: соглашается / спорит / спрашивает уточнения по конкретным пунктам.
4. Напарник в `03-peer.md`: уточнения, доп. находки, итоговый чек-лист правок.
5. `report.md` — согласованный список правок с приоритетами.

**Польза:** Code review более глубокий, чем у одного агента. Расхождения позиций видны явно.

### Сценарий 3. Аудит документа

**Контекст:** Пилот хочет проверить документ (Pack-формализация, договор, спецификация) у двух независимых ревизоров до публикации.

**Поток:**
1. Писатель в `00-writer.md`: документ + критерии аудита (полнота, согласованность, отсутствие галлюцинаций).
2. Напарник в `01-peer.md`: свои находки по тем же критериям.
3. Писатель в `02-writer.md`: пересечение находок, добавление пропущенного.
4. Напарник в `03-peer.md`: подтверждение или несогласие с интерпретацией пересечений.
5. `report.md` — объединённый список находок с уровнями уверенности (оба видят / только один / спорное).

**Польза:** Расхождения находок — сигнал для глубокой проверки. Согласованные находки — сигнал для гарантированного исправления.

## Edge-case: Peer-unavailable unilateral CONSENSUS

**Триггер:** peer-агент физически недоступен (content filter, API down, ключ истёк, network failure).

**Процедура:**

1. **2 попытки вызова peer** через адаптер (`claude-peer-adapter.sh` / `kimi-peer-adapter.sh`).
2. При стойком отказе — запись в peer.md и meta.yaml:
   - `peer.md`: `consensus: unavailable, status: blocked`.
   - `meta.yaml`: `peer_blocked: true, escalations_count: 1`.
3. Writer оценивает наличие реальных альтернатив для решения:
   - Альтернативы отсутствуют (декомпозиция очевидна, спецификация диктует выбор) → **unilateral CONSENSUS легитимен**.
   - Альтернативы есть → **эскалация пилоту**, не unilateral.

**Тест границы:**

«Существует ли альтернатива, по которой peer мог бы возразить?»
- Да → эскалация пилоту (writer не решает без peer-критика).
- Нет → unilateral CONSENSUS, audit trail в meta.yaml.

**Когда применимо:**

- Переадресация к другому peer (claude-headless вместо Kimi) невозможна или не быстрее, чем продолжить unilateral.
- Технический выбор без content-trade-off (декомпозиция фаз, переименование артефакта).

**Failure mode без этого правила:**

Writer либо стопает прогресс и просит пилота решать (мелкие технические выборы → bottleneck на пилоте), либо тихо принимает решение без записи о peer-блокировке (теряется audit trail).
