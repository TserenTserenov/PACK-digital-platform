# DP.SC.055 «Разметка пользовательской базы знаний по типам данных»

<!-- see WP-483 Ф0, родитель-концепция inbox/WP-289/CONCEPT-portable-guide-generator.md -->

## Обещание

**Кому:** человеку с произвольной базой заметок (файлы, Obsidian, Notion-экспорт, своя SQL/vector-БД), который хочет получить персональное руководство развития (DP.SC.055 → потребляется DP.ROLE.001 Портной), но чья база никогда не размечалась по нашей оси типов. Не требует регистрации в IWE или на платформе.

**Зачем:** без разметки Генератор не может отличить устойчивый факт о человеке от потока событий или чужого секрета — либо соберёт руководство вслепую (риск утечки чужих PII в генерацию), либо не соберёт вовсе. Разметчик — единственный шаг, который делает произвольную базу пригодной для генерации, без изменения самих файлов пользователя.

**Что получит потребитель:**
- `type-index.json` — путь → `{type: 2.1-2.4, subtype, mode: index|pointer|external, freshness, confidence, source}` для каждого файла базы.
- `profile.yaml` (частично заполненный, секция 2.1-declared) — переносимый формат, потребляемый Генератором напрямую.
- `residency.yaml` — карта согласия/резидентности данных.
- Явный карантинный список «вне оси» — файлы, требующие решения пользователя, НЕ подаваемые в генерацию по умолчанию.
- Поднятый локальный MCP `search()`-endpoint над размеченной базой (для дальнейших запросов Генератора).

**Триггер:** пользователь (через свой ИИ-помощник — Claude/ChatGPT/Cursor/локальная модель — или headless CLI) указывает путь к базе (или существующий MCP `search()`-backend) и вызывает `structure_base`.

## Инвариант

- [ ] **И1 (обязательный карантин).** Любой файл с признаками чужого PII, секретов, платёжных данных или третьих лиц попадает в bucket «вне оси» и НЕ индексируется для генерации без явного решения пользователя. Не опция — блокирующее требование (см. концепция §9 «Риски»).
- [ ] **И2 (не форсировать 2.4).** Материал без структурных признаков типов 2.1-2.3 остаётся в 2.4 «остаток» — Разметчик НЕ пытается насильно разложить его по другим типам. Генератор получает его как материал для рефлексивных вопросов, не как структурированное знание (решение пилота, концепция §11.1 п.5).
- [ ] **И3 (frontmatter побеждает эвристику).** Явный frontmatter-override в файле пользователя (`type: 2.3`) имеет приоритет над классификацией «по месту» (`homes.yaml`) и над per-file эвристикой.
- [ ] **И4 (ядро-в-центре).** Базовая разметка (по месту + структурные эвристики) работает БЕЗ LLM — детерминированный классификатор. LLM (локальный/BYOK) вызывается ТОЛЬКО для явно неоднозначных файлов, не участвует в решении о карантине «вне оси» (И1 — детерминированная проверка, не LLM-решение).
- [ ] **И5 (zero-upload).** Разметка не отправляет содержимое файлов пользователя ни на один внешний сервер, кроме опционального BYOK-вызова LLM для неоднозначных файлов (явно управляется пользователем).

## Режим отказа

- **Пустая или только что созданная база** → пустой `type-index.json` + пустой `profile.yaml` — корректное холодное состояние (`stage=0`), НЕ ошибка.
- **Файл не читается** (битый формат, permission denied, бинарный не по расширению) → пропуск с явной записью в лог структуратора, не молчаливый скип и не остановка всего прогона.
- **Неоднозначный файл** (не подходит ни под одну эвristику по месту/структуре) → тип 2.4 с низким `confidence`, явно помечен — НЕ попытка LLM-угадывания без пометки уверенности.
- **MCP `search()`-backend недоступен при повторном вызове** → hard-fail с явным сообщением (`DP.FM.160`: интерфейс без подведённого источника данных не имитирует работу).

## Сценарии использования

> Источник — концепция WP-289 §4 (уже прошла проверку с пилотом), проекция на действия именно Разметчика.

### Сценарий 1 — Марина: незарегистрированный пользователь, локальный Obsidian vault
Продакт-менеджер без аккаунта IWE. Разметчик проходит по vault: `Journal/`→2.2 (поток), `Profile/`→2.1-declared, `Concepts/`→2.3, `Sessions/`→2.4; всё непонятное и чужие PII/секреты — в карантинный bucket «вне оси». Поднимает локальный MCP `search()` (SQLite+vec0) над vault. **Показывает:** работу с нуля, без единого нашего сервера.

### Сценарий 2 — Дэвид: незарегистрированный, своя Postgres-база, с подпиской на контент
Разметчик работает НАД Supabase pgvector — сама разметка не зависит от наличия подписки (подписка нужна ниже по цепочке, для Родника). `search()`-endpoint проходит Knowledge Gate KG-01..07. **Показывает:** разметка одинакова вне зависимости от платного статуса пользователя (И5 держится всегда).

### Сценарий 3 — Доменный эксперт с Notion/Obsidian, крупный собственный пак
Разметчик классифицирует структурированный пак как 2.3 (FPF-подобная форма), регистрирует его `search()`-endpoint через тонкий MCP-слой. **Показывает:** работу с богатой, уже структурированной базой — не только с плоскими заметками.

### Сценарий 4 — Зарегистрированный пилот IWE, гибридный режим
Разметчик размечает ТОЛЬКО локальную базу (РП, рефлексии, captures) — платформенные derived-данные подключаются отдельным каналом (`dt_read_digital_twin`, download-only), Разметчик их не трогает и не конфликтует с DP.SC.053. **Показывает:** границу ответственности — Разметчик не знает о существовании платформы, платформенные данные приходят поверх его выхода.

### Сценарий 5 — Интегратор/наставник когорты, headless batch-режим
Наставник запускает Разметчик в цикле по 20 профилям учеников через headless CLI (`stdin JSON → stdout JSON`), для каждого — своя база, свой storage-adapter. **Показывает:** повторяемость и переносимость роли между носителями (не завязана на конкретный рантайм-хост).

## Открытые задачи (handoff, не входят в этот SC)

- Точный формат `homes.yaml` и структурных эвristик per-file классификатора — реализационная деталь Ф2 РП483, не часть обещания.
- Трактовка типа 2.4 (выразимость vs переносимость) — открытый вопрос, см. РП449 Ф2, концепция §9. Ось `2.4` помечена `provisional` до разрешения.
- ArchGate на storage-абстракцию (read/write/find), которую Разметчик использует для доступа к базе — отдельный документ, см. WP-483 Ф0 (совместно с WP-449 Ф2).
