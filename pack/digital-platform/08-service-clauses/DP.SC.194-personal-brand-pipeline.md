# [DP.SC.194] Конвейер личного бренда

<!-- see WP-472 Ф1, DP.ROLE.087, DS-my-strategy/inbox/WP-472/research-self-description-brand.md -->

## Правило (инвариант)

> Что ВСЕГДА должно выполняться для данного сервиса. Нарушение = провал SC.

- [ ] **Решение за живым владельцем.** Каждый кандидат (тема, факт профиля, обновление)
      останавливается на `status: proposed`; accept/reject/defer принимает сам человек —
      по контракту apply-captures (`decision_source: pilot`, `defer_until` обязателен).
      Агенты и пир-сессии не подменяют решение владельца бренда (DP.SC.040).
- [ ] **Без выдуманных фактов (honesty rule).** Пустое поле профиля — легальное состояние
      (`{ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ}`). Агент не дозаполняет биографию, цифры, имена, цитаты.
      Косвенные выводы маркируются источником и пометой «проверь перед использованием»
      (паттерн labeled inferences из ai-job-search `/setup`).
- [ ] **Read-before-write, идемпотентность.** Перед любым мержом в профиль агент читает
      текущее содержимое; повторный запуск не дублирует и не затирает. Противоречия
      (conflicting changes) предъявляются по одному с вариантами keep / replace / manual.
- [ ] **Личное ≠ доменное ≠ продуктовое.** Материал бренда (истории, факты, голос, темы)
      живёт в личном репо владельца (`DS-{name}-Brand`); в Pack уходит только обобщённый
      метод. Граница «личное vs продуктовое» проверяется тестом positioning (OwnerIntegrity).
- [ ] **Мерж никогда не молчит («тест интервью-отката»).** Каждое противоречие между
      источниками (биография vs соцсети vs посты) предъявляется владельцу нумерованным
      списком до продолжения; у владельца всегда есть выход «manual — сделаю сам».

## Обещание

**Кому:** Пользователю ступени Мастер+ (по реестру нормативов WP-151: семейство
«Публичность» включается с Мастера; ось `mastery` — `gate_ready`, WP-457).

**Зачем:** Норматив публичности (публикации, выступления, регулярность контент-конвейера)
измеряется со ступени Мастер, но платформенного механизма «завести и вести личный бренд»
не было — единственный пример (WP-442) решался вручную. Без конвейера норматив висит
на силе воли человека; мировая литература (Schaefer «Known», Kleon «Show Your Work!»)
сходится: бренд умирает не от плохого исполнения, а от отсутствия системы пополнения.

**Что получит:**

1. **Репо бренда из шаблона** — структура `profile/` (кто я, позиционирование, ключевые
   идеи, голос, истории, проекты, видение, темы, границы), `content/` (темы, черновики,
   topic-log.yaml), `style/`, `funnel/` — по образцу DS-Tseren-Brand, без контента донора.
2. **Setup-сессию самоописания** — document-intake (папка `intake/` с постами, биографией,
   экспортами соцсетей) или интервью; идемпотентный мерж в профиль с cross-reference
   проверкой; точечные обновления `--section` по мере эволюции.
3. **Регулярный сбор кандидатов** — движок тем (по образцу шага 7c WP-442 Ф9): темы дня
   из платформенного следа (коммиты, заметки, captures) и, где применимо, из публичного
   следа в сети; статусная модель `proposed → accepted/rejected → written → published/archived`,
   автоархив >14 дней.
4. **Процедуру разбора** — accept/reject/defer живым владельцем по аналогии с
   apply-captures, с дедуп-проверкой перед предложением темы.
5. **Теорию и задания по публичности** в персональном руководстве Мастер+ (интеграция
   WP-149, DP.SC.020): конвейер — SOTA-метод рычага «регулярность» семейства F.

**Триггер:** достижение ступени Мастер (рекомендация руководства) ИЛИ явный запрос
пользователя Мастер+ («завести бренд», «дай темы»).

**Время отклика:** setup-сессия — один сеанс 30-60 минут до первого заполненного профиля;
кандидаты на темы — в ритме Day Open (ежедневно) или по запросу в той же сессии.

**Режим отказа:** нет платформенного следа (новый пользователь) → только интервью-путь
setup, движок тем стартует после первых недель следа; web-scan недоступен → кандидаты
только из платформенного следа, пометка `public_trace: skipped`; репо бренда не создан →
движок не предлагает темы, а предлагает пройти setup. Падение сбора не блокирует
Day Open (деградация с пометой, не сбой ритуала).

## Свидетельства (критерий приёмки)

**Данные** (что фактически существует):

| Критерий | Как проверить |
|----------|--------------|
| Шаблон репо существует и разворачивается без контента донора | `gh repo create` из template; grep по `profile/` не находит «Церен» |
| topic-log ведётся, темы проходят статусную модель | `topic-log.yaml`: записи со статусами proposed/accepted/published/archived |
| Решения по кандидатам имеют `decision_source: pilot` | grep по журналу разборов; решений без поля нет |
| Ни один факт профиля не выдуман | выборочная сверка 5 фактов профиля с первоисточниками владельца |

**Контекст** (при каких условиях обещание действует):

| Условие | Проверка |
|---------|---------|
| Пользователь — ступени Мастер+ | запись реестра нормативов / ЦД пользователя |
| У пользователя есть IWE-контур (след существует) ИЛИ он прошёл интервью-путь | наличие platform trace / заполненный intake |

**Полномочия** (кто уполномочен подтвердить):

| Роль | Что подтверждает |
|------|-----------------|
| Владелец бренда (сам пользователь) | принятие/отклонение каждого кандидата; факты своей биографии |
| DP.ROLE.087 Куратор личного бренда | корректность сбора, дедуп, маркировку инференсов |
| Реестр нормативов (WP-151, stage_evaluator) | факт публикаций как измерение характеристики «публичность» |

**Свидетельства** (как узнать, что обещание выполнено):

| Свидетельство | Источник |
|--------------|---------|
| Конвейер работает минимум на двух живых людях (критерий зонтика WP-472) | два независимых `DS-{name}-Brand` с историей accepted-тем |
| Темы дня появляются в DayPlan пользователя | блок «Контент — тема дня» в DayPlan |
| Публикации фиксируются как события | `domain_event: post_published` |

## Сценарии использования

### С1. Церен — донор паттерна (уже работает, WP-442)

Мастер, основатель МИМ. Репо DS-Tseren-Brand заведён вручную пир-сессиями. Движок тем
(шаг 7c) ежедневно предлагает тему дня из следа последних 36 часов; Церен принимает или
отклоняет в Day Open; принятые темы идут в черновики (WP-167). **Что сценарий доказывает:**
механика жизнеспособна на одном человеке ≥2 недель (темы C-001…C-039+, принятые →
публикации C-015, C-032, C-033). **Чего не хватает:** всё собрано руками, перенос на
другого человека = пересборка с нуля.

### С2. Инженер-менеджер Анна, свежий Мастер — заведение с нуля

Анна получила ступень Мастера (защита в МИМ), руководство рекомендовало семейство
«Публичность». Платформенный след есть (полгода в IWE: заметки, captures, коммиты),
бренд-репо нет. Запускает конвейер: разворачивает шаблон `DS-Anna-Brand`, проходит
setup-сессию — intake пуст, поэтому интервью-путь (45 минут): кто я, для кого, против
чего, ключевые идеи, границы приватности. Через неделю движок начинает предлагать темы
из её следа; раз в несколько дней она разбирает кандидатов (accept/reject/defer).
**Что доказывает:** путь «есть след, нет материалов» — интервью + отложенный старт движка.

### С3. Реформатор Борис с публичным следом — document-intake + web-scan

Борис (Реформатор) годами пишет в Telegram и LinkedIn, выступает, но без структуры:
биография расходится между площадками, темы повторяются. Складывает экспорты и лучшие
посты в `intake/`, запускает setup: document-intake читает папку, cross-reference check
показывает 4 несостыковки (даты, названия ролей) — Борис разрешает каждую keep/replace/manual.
Web-scan добавляет публичный след: конференции, упоминания. Мерж идемпотентен: повторный
запуск через месяц предлагает только additive-обновления. Движок тем получает второй
источник — «что уже резонирует у аудитории».
**Что доказывает:** путь «много материалов, нет структуры» — intake + откат-разрешение
конфликтов + публичный след.

### С4. Наставник МИМ — потребитель чужого бренд-репо (вторичный)

Наставник сопровождает двух Мастеров. Их бренд-репо (структура из шаблона) дают ему
готовые факты, формулировки и голос подопечных: он рекомендует площадки и темы, не дёргая
их за биографиями, и видит разобранные/отклонённые темы. **Что доказывает:** репо бренда —
консумер-готовый артефакт не только для владельца (как README DS-Tseren-Brand «для команды»).
