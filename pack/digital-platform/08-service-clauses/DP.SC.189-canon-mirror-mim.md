# DP.SC.189 — Зеркалирование методического контента aisystant в МИМ

## Обещание

**Кому:** русскоязычным читателям методического контента, которые заходят через организацию МИМ; авторам, которые продолжают писать материалы в приватных репозиториях `aisystant`, не меняя свой процесс.

**Зачем:** 11 методических репозиториев (`docs`, `guides`, `main-docs`, `ssm2025`, `DS-principles-curriculum`, `PACK-personal`, `metadata`, `forms`, `aist_bot`, `personal-knowledge`, `simulator-lab`) закрываются (становятся приватными) в `aisystant`, но русскоязычный читатель должен продолжать видеть контент — не в `aisystant`, а в организации МИМ, без ручного переноса и без штатного fork/transfer, который оставил бы публичный git-след связи между организациями.

**Что получит потребитель:**
- Публикацию изменённого содержимого (как есть, без перевода) в парный репозиторий МИМ при каждом push в `aisystant`.
- Публикацию без публичного git-родства (fork/transfer) и без отображения связи в UI репозитория — связь остаётся видна только во внутренних метаданных исполнителя (audit log GitHub App), не в интерфейсе для стороннего наблюдателя.
- Явный сигнал (не тихий сбой), если публикация не удалась.
- Защиту ветки в МИМ от прямой записи людьми — иначе двусторонняя запись создаёт дивергенцию, которую зеркалирование не умеет разрешать.
- Авторство коммита в МИМ-репозитории отражает исходного человека-автора (не только исполнителя-бота) — см. раздел «Авторство коммитов» ниже.

## Критерий приёмки

1. Push в `main` одного из 11 репозиториев `aisystant` → в течение одного прогона автоматики парный репозиторий МИМ содержит идентичное (побитово) содержимое, включая переименования и удаления файлов.
2. При первом подключении конвейера к репозиторию, где в МИМ уже есть непустая история — публикация не идёт тихим форс-пушем; требуется явное подтверждение пилота, что история МИМ будет перезаписана источником.
3. Ветка МИМ-репозитория защищена от прямой записи людьми (branch protection): пуш разрешён только исполнителю (`canon-sync[bot]`) + обязательная проверка (`required status check`, имя `canon-sync/validated`) выставляется исполнителем после успешной публикации — merge/push без этой проверки невозможен (fail-closed).
4. Если целевой репозиторий МИМ недоступен или не существует — сохраняется чёткое предупреждение в логе прогона, публикация не завершается тихим пропуском.
5. Коммит в МИМ-репозитории имеет `author` = человек, внёсший исходное изменение в `aisystant` (взято из `git log` исходного коммита, email в формате `id+login@users.noreply.github.com`), и `committer` = `canon-sync[bot]`. Сообщение коммита — нейтральная форма, не копирующая дословно внутренние детали исходного коммита (номера РП, пути, названия внутренних систем).

## Авторство коммитов (решение пилота, 2026-07-09)

> Источник: пир-сессия `2026-07-09-06-wp415-dpsc189-commit-authorship`, по фидбэку ИТ-встречи 2026-07-09 (записи Zoom «Оперативка ИТ») о доверии к коммитам в публичных/МИМ-репозиториях.

- **Автор ≠ Коммитер.** GitHub различает поля `author` (кто внёс изменение) и `committer` (кто выполнил технический коммит). Исполнитель конвейера ставит `--author` из исходного коммита, оставаясь `committer`. Это стандартный, узнаваемый паттерн (используется ботами backport/cherry-pick) — не создаёт впечатления анонимности или подмены.
- **Согласие авторов не требуется отдельной процедурой.** Пилот решил: авторы — участники команды/проекта, публикация вклада под своим именем — ожидаемая часть рабочего контекста (как в open-source), отдельного opt-in не нужно.
- **Не раскрывать связь с приватным источником.** Раскрывается только имя автора-человека (уже публичная GitHub-идентичность) — не факт существования приватного RU-репозитория-источника. Сообщение коммита формируется отдельно от исходного (не копия), чтобы не протекли внутренние маркеры (пути, номера РП, названия систем).

## Не гарантирует

- Невидимость связи между организациями в принципе — GitHub App, установленный в обеих организациях, оставляет след в audit log и в installation-метаданных. Обещание — только отсутствие публичного git-родства (fork/transfer) и отсутствие отображения связи в UI, не полное отсутствие всех следов.
- Атомарность между 11 репозиториями — каждый репозиторий синхронизируется независимо, не единой транзакцией.
- Перевод или адаптацию контента — публикация зеркалирует содержимое как есть, на том же языке.

## Связь с другими обещаниями

- Реализуется той же ролью, что и DP.SC.188 — **DP.ROLE.081 Ретранслятор канона** — но отдельным контрактом: перевод (DP.SC.188) и зеркалирование (DP.SC.189) имеют разные критерии успеха (качество перевода vs побитовое совпадение) и разные режимы отказа (деградация качества vs дивергенция историй), поэтому не объединяются в одно обещание.
- НЕ покрывает Конвейер 1 (личный RU ↔ aisystant приватные RU) — решение по варианту (pull-only / push-only / двусторонний) остаётся за пилотом, не спроектировано здесь.

## Архитектура реализации (уточнено 2026-07-09)

> GitHub Actions триггеры — per-repository по своей природе (нельзя одним workflow-файлом слушать push в 11 разных репозиториев). Декомпозиция: логика живёт в одном месте, в каждом из 11 репозиториев — только тонкий вызов.

- **Reusable workflow** (`workflow_call`) — один файл в центральном репозитории (`iwesys/iwe-translation-engine`), содержит всю логику зеркалирования (git author mapping, публикация, commit status).
- **11 caller-файлов** — по одному тонкому workflow (~10 строк) в каждом из 11 исходных репозиториев `aisystant`, вызывающих reusable workflow с параметрами (`target_repo`, ...).
- **Pin по SHA, не `@main`** — caller ссылается на конкретный коммит reusable workflow (`uses: iwesys/iwe-translation-engine/.github/workflows/mirror-to-mim.yml@<sha>`), обновление — через dependabot PR в каждом caller'е. Даёт контролируемый rollout вместо мгновенного эффекта на все 11 репозиториев при правке центральной логики.
- Реализация репозиториев-целей (создание 11 репозиториев в МИМ, применение branch protection) — отдельный шаг, требует решения пилота по именам репозиториев и подтверждения первого подключения (см. критерий приёмки №2); код reusable workflow и caller-шаблона можно подготовить заранее.
