# DP.SC.142 — Текстовый анализ косвенных характеристик

## Правило (инвариант)

> **Scope Guard (Вариант А):** Honcho / memory-провайдер вправе влиять ТОЛЬКО на cp.wld, cp.agt, bh.awr.
> Запрещено: прямое или косвенное влияние на cp.rhy, cp.skl, cp.iwe, cp.int, stage, certificate.
>
> **Parliament Model:** `cognitive`-схема изолирована. Аттестатор и Зачётчик баллов не имеют доступа к `cognitive`.
> Только `cognitive_proxy_reader` — read-only для shared profile.

- [ ] Текстовый анализ влияет ТОЛЬКО на cp.wld, cp.agt, bh.awr — никакие другие характеристики через этот канал не меняются.
- [ ] Значения из текстового анализа НЕ входят в расчёт stage и certificate. Используются ТОЛЬКО для рекомендаций (Портной, Диагност).
- [ ] До подтверждения PII Gate (B7.3): только синтетические данные. Реальные W-рефлексии, captures, переписка — запрещены.
- [ ] PII Gate (B7.3) закрыт при подтверждении всех 5 пунктов: регион хранения, DPA + политика удержания, GDPR Art.17 API, качество скрабера на русском тексте, опция self-host.
- [ ] Результаты пишутся в `learning.cognitive` (схема изолирована) — доступны внешним агентам только через `cognitive_proxy_reader`.
- [ ] Каждое обновление характеристики имеет `source: text_analysis` + `provider: <name>` в записи.

## Обещание

**Кому:** Портной (MIM.R.008), Диагност (MIM.R.009) — для персонализации рекомендаций. Аттестатор НЕ потребляет эти значения для расчёта stage.

**Зачем:** Детерминированные характеристики (cp.rhy, cp.skl и др.) хорошо измеряются через activity_log, но cp.wld (мировоззрение) и cp.agt (деятельность) слабо сигнализируют через бихевиоральные прокси. Текстовые инференции из рефлексий и captures — единственный практичный источник сигнала для этих характеристик.

**Что получит:**
1. Значения cp.wld, cp.agt, bh.awr в `learning.cognitive` (изолированная схема), доступные через `cognitive_proxy_reader`.
2. Источник записи маркирован `source: text_analysis` — отличим от детерминированного activity-канала.
3. Портной использует значения для персонализации руководства; Диагност — для уточнения профиля при диагностике. В формальный расчёт ступени (min(cp.*) → stage) и в certificate НЕ входят.

**Триггер:**
- Новая W-рефлексия зафиксирована в базе (`w_reflection_submitted`).
- Новый capture обработан (DP.SC.004).
- Пакетная задача из Agent Inbox (DP.SC.135) с интервалом ≤ 1 неделя.

**Время отклика:** ≤24ч после триггера.

**Режим отказа:**
- Honcho / провайдер недоступен → характеристики не обновляются, но не обнуляются (последнее известное значение сохраняется с `stale: true`).
- PII Gate не закрыт → анализ выполняется только на синтетических данных; реальный контент блокируется на уровне пайплайна.
- Скрабер не подтверждён → сырой текст рефлексий не отправляется провайдеру; анализ не запускается.

## Сценарии использования

> Подробно: `DP.SC.142-scenarios.md`

**Сценарий 1 (Диагност, первичный срез).** Пилот проходит диагностику впервые. cp.wld детерминировано = 0 (нет activity). Honcho-инференция из 3 w-рефлексий даёт cp.wld = 2. Диагност видит ступень 2, а не ступень 1 — более точный результат.

**Сценарий 2 (Портной, персональное руководство).** Портной формирует руководство под пилота. cp.agt из activity = 1 (мало событий). Honcho из captures и переписки даёт cp.agt = 3. Портной адаптирует руководство под деятельного пилота, не под начинающего.

**Сценарий 3 (PII Gate не закрыт — fallback).** Провайдер не предоставил DPA. Анализ выполняется только на синтетических тестовых данных, реальные рефлексии не передаются. cp.wld/cp.agt/bh.awr не обновляются из реального контента — остаются детерминированными значениями из activity.
