# DP.SC.061 «Каденция аудита базы знаний (knowledge-audit)»

> Источник домена: `DS-my-strategy/inbox/WP-476/f0-map-mechanisms-stages.md:165` («knowledge-audit ручной без расписания и владельца»), `CONCEPT-data-pipelines.md` С7 (Актуализация). WP-476 Ф5.

## Правило (инвариант)

> Что ВСЕГДА должно выполняться для данного сервиса. Нарушение = провал SC.

- [ ] Промпт `DS-ai-systems/extractor/prompts/knowledge-audit.md` (уже существует, реализует Шаги 1-5) запускается не реже раза в месяц без ручного напоминания пилоту себе — по прецеденту `data-gap-watchdog` (DP.SC.059): расписание, не «рекомендуется периодически».
- [ ] Отчёт («Knowledge Audit Report», формат уже определён в промпте Шаг 4) доставляется пилоту через тот же канал, что и остальные периодические отчёты платформы (Telegram, `iwe-tg`), не остаётся в файле, который никто не открывает.
- [ ] Scope ротируется по Pack'ам (не «все Pack'и каждый месяц» — дорого; по аналогии с Security Audit Cadence per-ArchGate/Week/Month) — конкретная ротация фиксируется в реализующем скрипте, не хардкодится в этом SC.
- [ ] Критичные находки (🔴 общая оценка) — не тихая запись в лог, а явный сигнал пилоту с готовым текстом исправления (промпт Шаг 5 уже это делает) — SC добавляет только каденцию запуска, не меняет уже спроектированную логику самого аудита.

## Обещание

**Кому:** R14 Заказчик (пилот)

**Зачем:** промпт аудита базы знаний спроектирован полностью (структурная + контентная проверка, готовый формат отчёта), но не имеет расписания и владельца — по факту ни разу не запускался автоматически с момента создания. Дыра того же класса, что уже была у `data-gap-watchdog` до WP-476 Ф4б: спецификация без исполнения (П1 модели конвейеров — декларация без запуска легализует дыру вместо её устранения).

**Что получит:** ежемесячный отчёт о здоровье Pack-репозиториев (структурные проблемы, пробелы, дубликаты) без необходимости самому вспоминать и запускать аудит вручную.

**Триггер:** периодический запуск по расписанию (launchd, ежемесячно) — Экстрактор (R2) вызывается в режиме `knowledge-audit` с заранее определённым scope (ротация Pack'ов).

**Время отклика:** отчёт доставляется в тот же день, когда запущен скан (LLM-вызов, не мгновенно — минуты).

**Режим отказа:** если сам запуск не состоялся (launchd не сработал) — зона ответственности process-watchdog слоя (`date-watchdog.sh`), не дублируется здесь. Если LLM-вызов упал (rate limit, API error) — исполняющий скрипт логирует ошибку и не выдаёт ложный «здоровый» отчёт молча.

## Сценарии использования (минимум 3, разные потребители)

### UC-1: Ежемесячный автоматический скан (потребитель — R14 Заказчик)

Инициатор — launchd по расписанию, без участия пилота. Экстрактор проверяет ротационный scope (например, один Pack за раз, полный цикл — раз в квартал по числу Pack'ов) → формирует Audit Report → присылает сводку в Telegram. Пилот видит критичные проблемы без ручного запуска.

### UC-2: Ручной запуск вне расписания (потребитель — пилот)

Пилот говорит «аудит PACK-digital-platform» вне расписания (уже поддержано промптом, Шаг «Как тестировать») — SC не меняет этот путь, только добавляет автоматическую каденцию поверх него.

### UC-3: Регистрация нового Pack в ротацию (потребитель — инженер/Кодировщик)

При создании нового Pack (`/pack-new`) новый репозиторий должен попасть в ротационный scope knowledge-audit без правки кода самого сторожа — аналогично UC-3 `data-gap-watchdog` (реестр решает *что*, сторож решает *как*). Точный механизм регистрации — реализуется вместе с чеклистом онбординга пака (WP-476 Ф5, соседний пункт).
