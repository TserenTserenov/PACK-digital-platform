# DP.SC.195 — DRR (Design Rational Record) как обязательный вход в пополнение Pack по теме

## Обещание

Пополнение Pack/DPF по теме фиксирует принятые решения как набор типизированных DR-записей (YAML-frontmatter: context, drivers, options, decision, consequences, basis, maps_to) ДО генерации текста разделов — вместо перехода «выбрали домен → сразу заполнили структуру». Ревью и приёмка идут по компактным DR-записям, а не по диффу всего Pack; связь «решение → в какой раздел/паттерн оно легло» переживает генерацию.

## Триггер

Старт пополнения Pack по теме: `/pack-creator` (перед фазами SPF 02-11 по новой теме), РП на обновление существующего Pack, массовый захват знания по теме через `/ke`. НЕ триггер: точечная правка (опечатка, одно различение) — порог «тема», не «любая правка».

## Входы

- Тема пополнения и целевой Pack (`PACK-<slug>`)
- Материалы Intake: что уже в Pack по теме, источники, противоречия/напряжения
- Шаблоны: `.claude/skills/pack-creator/templates/DRR-index-template.md`, `DR-record-template.md`

## Выходы

- `inbox/WP-NNN/drr/DRR.md` — индекс: Intake-итог + реестр решений + чеклист покрытия
- `inbox/WP-NNN/drr/DR-NN.md` — по одной записи на решение, с `maps_to` (раздел SPF-структуры или id паттерна) и опциональным `confidence_tier` (черновик/достаточно/проверено — информационное поле, не влияет на гейт Шага 1.7)
- Гейт: генерация раздела Pack разрешена только при наличии ≥1 DR-записи со `status: accepted` и `maps_to` на этот раздел (pack-creator SKILL.md, Шаг 1.7)
- Провенанс: DRR архивируется вместе с WP-context (`archive/wp-contexts/`) — по вопросу «почему в Pack так» агент находит DR-запись

## Время отклика

Формирование DRR — часть работы автора/агента по теме (не отдельный сервисный вызов): типично 15-40 мин на Intake + 5-10 мин на DR-запись. Дешевле ревью диффа по 11 разделам SPF постфактум.

## Инвариант

1. **Owner vs производная.** DR-запись — owner решения (source-of-truth); текст раздела Pack — производная расфасовка. Правка решения начинается с DR-записи, не с текста Pack (различение `DRR-запись ≠ Pack-текст`, distinctions Tier-B).
2. **Одна запись = одно решение**, отвергнутые альтернативы фиксируются в Options — иначе следующий агент/автор предложит их заново.
3. **Гейт декларативный** (precondition в SKILL.md, дух CGUS), не блокирующий скрипт: нарушение = повод для ревью, не отказ операции. Запрещён элемент `generic/other` в maps_to — утечка в «решение вообще».
4. **ArchGate не дублируется:** для решений архитектурного характера DR-запись ссылается на профиль ЭМОГССБ (поле `archgate_profile`), а не повторяет оценку — ArchGate оценивает, DRR хранит и линкует.

## Режим отказа

- DRR отсутствует при старте пополнения темы → скилл предлагает сформировать (Шаг 1.7), не блокирует молча; малое пополнение автор может явно подтвердить как «тема не требует DRR» — фиксируется в WP-context, не молчаливый пропуск.
- DR-запись без `maps_to` → не считается покрытием раздела (гейт не пройден для этого раздела).
- Решение изменилось после расфасовки → старая запись получает `status: superseded-by DR-MM`, новая записывается отдельно; перезапись accepted-записи задним числом запрещена (теряется провенанс).

## Сценарии использования

1. **Пополнение Pack новой темой.** WP открыт на добавление методов в `03-methods/` → Intake (что уже есть, 2 противоречия) → 3 DR-записи (accepted) → генерация раздела покрыта DR-02; ревью пилотом — по трём записям, не по диффу раздела.
2. **Провенанс-вопрос.** Через месяц вопрос «почему в Pack написано так?» → агент по `maps_to` находит DR-запись в `archive/wp-contexts/WP-NNN-*/drr/` → ответ с основанием (basis: наблюдение) и отвергнутыми альтернативами.
3. **Смена решения.** Новая практика опровергла допущение → DR-04 `superseded-by DR-07` → текст раздела перегенерируется из DR-07; цепочка решений сохранена, не переписана задним числом.

## Ограничения

- Гейт декларативный, не enforced детерминированным хуком (deterministic enforcement — сознательно отложено, WP-481 Ф2 «Сознательно отложено»).
- Validation двусторонней полноты (каждый затронутый раздел покрыт DR-записью и каждая accepted-запись ушла в текст) — ручной чеклист в DRR.md; субагент-автомат по мотивам AgenticAKM отложен (связка с WP-481 Ф3, экзекьютор-ревьюер).
- Intake как явная фаза SPF-процесса (перед roadmap 01-11) не встроена в upstream `SPF/process/` — правка SPF = отдельное governance-решение, не этот контракт.
- Промоушен шаблонов в FMT-exocortex-template (template-sync) — отдельный шаг, не выполнен на 15.07.2026.
