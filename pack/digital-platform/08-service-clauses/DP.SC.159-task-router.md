# [DP.SC.159] Маршрутизатор задач IWE

## Правило (инвариант)

> Нарушение любого = провал SC.

- **Маршрутизатор всегда первый.** Любой запрос через Opening проходит через Маршрутизатор — до вызова конкретного скилла, скрипта или LLM.
- **Routing-tag обязателен перед lookup.** Если тег отсутствует — вызвать Артефактора-Постановщика (DP.ROLE.058) для структурирования. Loop ограничен 1 итерацией.
- **Единственный исполнитель.** Маршрутизатор выбирает ровно одного исполнителя из executor-catalog.yaml. Параллельный routing запрещён.
- **Нет автоматического retry.** При отказе исполнителя — зафиксировать EXEC_FAILED, вернуть ошибку вызывающему контексту.
- **AGENT_FAULT → iwe_checklist_memory.py record.** Задачи типа AGENT_FAULT маршрутизируются в систему учёта косяков WP-316, не в LLM.

---

## Обещание

**Кому:**
- **Пилот IWE** — «любая задача дойдёт до правильного исполнителя; токены не тратятся там, где достаточно скрипта»
- **WP Gate (протокол ОРЗ)** — «routing-решение, принятое при открытии РП (класс задачи), исполняется, а не переопределяется»
- **Диспетчер (DP.ROLE.045)** — «задача, поднятая из очереди agent inbox, получает исполнителя через единую точку lookup»

**Зачем:**
- Routing-логика размазана по скиллам → каждый скилл тащит инструкции в контекст, LLM вызывается там, где достаточно `grep`
- Нет единой точки аудита: невозможно понять, какой тип задач идёт через LLM, а какой — через скрипты
- AGENT_FAULT попадает в LLM вместо SQLite → косяки не учитываются

**Что получит:**

```
{
  "executor": "имя исполнителя из каталога",
  "routing_path": "tag → executor (для метрики routing-path-distribution)",
  "exec_result": "результат исполнителя или EXEC_FAILED/STRUCTURE_FAILED/NO_MATCH"
}
```

**Время отклика:**
- Lookup в executor-catalog.yaml — O(1), < 1 мс для каталога до 1000 записей
- Haiku для разрешения неоднозначности (несколько исполнителей с одним тегом) — < 2 сек

## Основной flow

```
Запрос (любой)
  │
  ├─ нет routing-tag?
  │   └─ Артефактор-Постановщик (DP.ROLE.058) → structured request с тегом
  │       └─ нет тега после Артефактора → STRUCTURE_FAILED
  │
  ├─ tag = AGENT_FAULT → iwe_checklist_memory.py record
  ├─ tag = trivial     → скрипт из $IWE_SCRIPTS/
  ├─ tag = closed-loop → скилл (/.claude/skills/) или MCP-tool
  ├─ tag = open-loop   → LLM Sonnet / скилл с рассуждением
  └─ tag = problem-framing → LLM Opus
       │
       └─ нет исполнителя в каталоге? → NO_MATCH + тип задачи для регистрации
```

**Метрика:** при каждом routing записывается `routing-path-distribution` (tag → executor → success/fail).

## Сценарии использования (Ф2, ≥3)

### Сц-1: Пилот даёт задачу без явного типа («проверь состояние бота»)

- **Потребитель:** Пилот, открывает сессию через Opening
- **Контекст:** задача не оформлена как РП, нет routing-tag
- **Что делает Маршрутизатор:** обнаруживает отсутствие тега → вызывает Артефактора → Артефактор возвращает `{task_type: "bot_status_check", tag: "trivial"}` → lookup в каталоге → `route-bot-status.sh`
- **Результат:** скрипт проверяет Railway + Neon, выдаёт статус. LLM не вызывался.

### Сц-2: WP Gate классифицировал РП как open-loop («дизайн новой роли»)

- **Потребитель:** WP Gate в протоколе ОРЗ Opening
- **Контекст:** пилот открывает РП, WP Gate проставляет класс `open-loop` и тип `role_design`
- **Что делает Маршрутизатор:** получает routing-tag `{class: open-loop, type: role_design}` → lookup → скилл `/artifactor` (Декомпозитор) для разбивки на этапы, затем LLM Sonnet для содержательной работы
- **Результат:** задача идёт в правильный инструмент без дополнительной классификации.

### Сц-3: Пилот говорит «зафиксируй косяк — агент пропустил чеклист»

- **Потребитель:** Пилот, прямо в сессии
- **Контекст:** Артефактор структурирует как `{task_type: "AGENT_FAULT", severity: "major"}`
- **Что делает Маршрутизатор:** видит tag `AGENT_FAULT` → routing в `iwe_checklist_memory.py record` (без LLM)
- **Результат:** косяк записан в SQLite (WP-316 L1), markdown audit trail сгенерирован автоматически.

### Сц-4: Диспетчер поднимает задачу из agent inbox

- **Потребитель:** Диспетчер (DP.ROLE.045), background execution
- **Контекст:** задача в inbox имеет `task_type: "dt_collect"` и routing-tag `trivial`
- **Что делает Маршрутизатор:** lookup → `dt-collect.sh`, передаёт параметры из task-файла
- **Результат:** детерминированный скрипт выполняется без LLM; Диспетчер получает exit code.

## Режим отказа

| Сценарий | Поведение |
|---------|-----------|
| Нет routing-tag и Артефактор не смог структурировать | `STRUCTURE_FAILED` + тип входа → вернуть в вызывающий контекст |
| Исполнитель завершился с ошибкой (exit ≠ 0 / timeout) | `EXEC_FAILED` + тип задачи + код ошибки → `routing-errors.log`; retry запрещён |
| Тип задачи не найден в executor-catalog.yaml | `NO_MATCH` + тип задачи → логировать для пополнения каталога |
| Несколько исполнителей с одним тегом | Haiku disambiguates → выбирает одного; при fail Haiku → первый по алфавиту (детерминированный fallback) |
| Loop Маршрутизатор ↔ Артефактор сработал дважды | `STRUCTURE_FAILED` на второй итерации — не зацикливаться |
