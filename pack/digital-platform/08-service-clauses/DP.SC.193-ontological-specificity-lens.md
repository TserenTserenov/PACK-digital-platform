# DP.SC.193 — Приёмочная линза специфичности для сгенерированного доменного контента

## Обещание

Сгенерированный Pack/DPF-раздел или персональное руководство, прошедший приёмку через режим `ontological` верификатора (VR.R.001), даёт явный specificity-скор и список пустых (лексических/generic) claim'ов — вместо того чтобы полагаться на глазомерный контроль автора.

## Триггер

Явный вызов `/verify ontological <путь>`, либо предложение агента после генерации Pack/DPF-раздела или руководства (автоопределение — `verify` SKILL.md, Шаг 0).

## Входы

- Путь к сгенерированному артефакту (Pack-раздел, руководство, capture-кандидат)
- Опционально: список известных проблем домена (для recall-проверки) — из WP-контекста или gap-анализа Pack'а

## Выходы

- Verdict PASS/CONDITIONAL/FAIL со specificity-скором
- Таблица claim'ов с классификацией по двум осям (О: онтологическое/лексическое, П: реальная проблема/generic)
- Список непокрытых известных проблем домена (если проводилась recall-проверка)

## Время отклика

Один прогон sub-agent'а (Sonnet, context isolation) — типично 1-3 мин на артефакт среднего размера (аналог `pack`-проверки).

## Инвариант

1. Верификатор не участвовал в создании проверяемого артефакта (context isolation, VR.SOTA.002) — промпт не получает историю генерации.
2. Verdict FAIL только при missing по ОБЕИМ осям на ключевом утверждении текста — одной лексической или одной generic-оси недостаточно для FAIL.
3. Пороги PASS/CONDITIONAL/FAIL помечены `seed` до калибровки на размеченной пилотом выборке — до калибровки CONDITIONAL приоритетнее точной границы PASS/FAIL.

## Режим отказа

- Эталон (список известных проблем домена) не передан → recall-проверка пропускается, не считается FAIL по умолчанию (у sub-agent'а нет внешнего знания, что «должно было быть»).
- Артефакт слишком мал для декомпозиции (<3 claim'ов) → verdict CONDITIONAL с пометкой «недостаточно claim'ов для статистики», не автоматический PASS/FAIL.
- Расхождение между двумя независимыми прогонами → эскалация на Opus (Model Tiering, по аналогии с набором критиков WP-481 Ф3).

## Сценарии использования

1. **Приёмка нового Pack-раздела.** pack-creator сгенерировал `01B-distinctions.md` → `/verify ontological` находит 3 из 8 различений лексическими («важно учитывать контекст» без привязки к kind) → автор переписывает три, PASS со второго прогона.
2. **Ревью персонального руководства.** Сгенерированный подраздел проходит `verify subsection` (структура+нарратив) PASS, но `ontological` находит specificity 35% — сигнал, что раздел структурно корректен, но содержательно пуст; переписывается до генерации следующего.
3. **Recall-проверка при наличии gap-анализа.** WP-474 передаёт список из 5 известных gap'ов Pack'а → линза подтверждает 4 покрытых, 1 непокрытый — попадает в отчёт отдельным пунктом, не блокирует PASS.

## Ограничения

- Пороги (70%/40%) не откалиброваны — рабочая гипотеза, не эмпирический результат (WP-481 Ф9 шаг 6, требует разметки пилотом, не проведено на 14.07.2026).
- Не встроена как обязательный гейт в pack-creator/verify-pack/verify-fpf-subsection — только явный вызов. Глубокая интеграция сознательно отложена (выше риск регрессии живых скиллов, WP-481 систематическое ранжирование 14.07.2026).
- Recall-ось требует явно переданного списка известных проблем — без него линза видит только precision (отсутствие generic), не recall (охват реальных проблем).
