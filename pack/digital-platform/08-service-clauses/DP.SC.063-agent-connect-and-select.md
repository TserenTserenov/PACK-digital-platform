# [DP.SC.063] Простое подключение и выбор агента IWE

> **Различение:** это не DP.SC.035 (Peer-agent choreography). DP.SC.035 регулирует, как уже подключённые peer-агенты не мешают друг другу файлом одновременно (turn-taking, lock). Этот SC — на шаг раньше: как агент вообще становится «подключённым», и как пилот (или агент) решает, кому из уже подключённых поручить задачу, ещё до того, как встал вопрос о файловых блокировках.

## Правило (инвариант)

> Что ВСЕГДА должно выполняться. Нарушение = провал SC.

- [ ] Новый файловый агент не считается подключённым, пока не прочитал общее ядро правил (`AGENTS.md`) — без этого шага остальные пункты чеклиста не имеют смысла.
- [ ] Агент, который параллельно с другими правит файлы репозитория, обязан подключиться к локальному шлюзу (DP.SC.034) под собственным `IWE_AGENT_ID` — иначе он не «подключён», а работает в обход координации.
- [ ] Выбор агента под конкретную задачу не блокирует работу: если в таблице «какой агент для какой задачи» нет прямого указания, пилот (или агент) решает разово; решение не откладывается в ожидании нового инструмента.
- [ ] Механизированный способ выбора (агент сам предлагает, кому передать) не вводится заранее «на всякий случай» — только если практика покажет, что таблицы недостаточно (IntegrationGate: обещание → сценарии → роль → реализация, в этом порядке).

## Обещание

**Кому:** Пилот, владеющий персональным инстансом IWE и использующий несколько агентных систем одновременно (сейчас: Claude Code, Kimi, Гермес; на подходе: Codex).

**Зачем:** Число агентов растёт быстрее, чем описание того, как их подключать и как между ними распределять работу. Без этого SC каждое новое подключение агента — импровизация с нуля (WP-337, май 2026, явно отложил эту работу на «отдельный РП после Ф8 executor-catalog» — см. WP-499).

**Что получит:**
- Чеклист подключения нового файлового агента из 4 шагов, применимый к любому следующему агенту, не только к Codex.
- Табличный (не инструментальный) способ решить, кому из подключённых агентов отдать задачу — обновляется правкой одной строки, без нового скрипта.
- Явную границу: когда табличного способа недостаточно и стоит рассмотреть механизацию (поле в `executor-catalog.yaml`) — вместо неявного накопления самодельных решений.

**Триггер:**
- Пилот решает подключить нового агента-вендора.
- Пилот (или агент перед стартом задачи) не уверен, кому её поручить.

**Время отклика:**
- Подключение нового агента — разовое, по чеклисту (часы, не минуты; зависит от того, поддерживает ли агент MCP/skill-discovery).
- Выбор агента под задачу — мгновенно (сверка с таблицей).

**Режим отказа:**
- Агент не умеет читать локальные файлы (только MCP) → этот SC не покрывает подключение такого агента: используется паттерн Гермеса (Cloud Gateway / `get_instructions`), не этот чеклист.
- В таблице нет подходящей строки под новый тип задачи → пилот решает разово; при повторении вопроса — таблица дополняется (не создаётся новый процесс).

## Свидетельства (критерий приёмки)

**Данные** (что фактически существует):

| Критерий | Как проверить |
|----------|--------------|
| `AGENTS.md` в корне существует и актуален | `sync-agent-instructions.sh --check` → exit 0 |
| Новый агент коммитит с собственной строкой атрибуции | `git log --grep="Co-Authored-By: <agent>"` находит коммиты |
| Таблица «какой агент для какой задачи» покрывает всех подключённых агентов | `project_peer_agents.md` содержит строку на каждого |

**Контекст** (при каких условиях обещание действует):

| Условие | Проверка |
|---------|---------|
| Агент — файловый (работает в репозитории), не MCP-only клиент | Тип определён на старте подключения (Сценарий А ниже vs паттерн Гермеса — вне scope) |
| Пилот использует ≥2 агентов параллельно | `~/.iwe/peer-status/*.json` содержит ≥2 файла (условие для DP.SC.035, не для этого SC — здесь достаточно и 1) |

**Полномочия** (кто уполномочен подтвердить):

| Роль | Что подтверждает |
|------|-----------------|
| Пилот | Что подключение агента завершено и агент допущен к работе |
| DP.ROLE.039 Peer Agent (сам подключаемый агент) | Что прочитал `AGENTS.md` и соблюдает file-lock (если применимо) |

**Свидетельства** (как узнать, что обещание выполнено):

| Свидетельство | Источник |
|--------------|---------|
| Smoke-тест: агент выполнил реальную задачу и закоммитил с атрибуцией | `git log` по конкретному агенту |
| Таблица выбора агента обновлена в момент подключения нового агента | `git diff` на `project_peer_agents.md` |

## Сценарии использования (минимум 3)

### Сценарий 1: Подключение нового файлового агента (Codex)

Пилот хочет добавить Codex как ещё одного агента, работающего прямо в репозитории, наравне с Claude Code и Kimi. Идёт по чеклисту из 4 шагов (Правило выше): проверяет, что Codex прочитал `AGENTS.md`, заводит его в Local Gateway под `IWE_AGENT_ID=codex`, добавляет строку атрибуции, дополняет таблицу выбора агента. Не пишет новый скрипт-адаптер с нуля — переиспользует паттерн, уже отработанный на Kimi (WP-150).

### Сценарий 2: Пилот вручную выбирает агента под задачу

Пилоту нужно быстро отрефакторить код в нескольких файлах параллельно. Он открывает `project_peer_agents.md`, видит строку «Multi-file edit параллельно с Клодом → Kimi/Codex», открывает нужный инструмент. Никакого промежуточного шага «спросить систему, кого использовать» — решение принимается за секунды по табличке, без обращения к какому-либо инструменту выбора.

### Сценарий 3: Агент перед стартом задачи сверяется с таблицей сам

Claude Code, получив задачу, которая по описанию больше подходит для параллельной обработки многих файлов, читает `project_peer_agents.md`, видит рекомендацию передать это Kimi/Codex, и явно предлагает пилоту переключиться — вместо того чтобы молча делать задачу медленнее своими силами. Обещание SC работает не только для пилота, но и для агента, принимающего решение о делегировании.

### Сценарий 4 (пограничный, режим отказа): таблицы недостаточно

Пилот подключает пятого агента, и распределение задач по типам перестаёт укладываться в простую табличку (пересекающиеся зоны компетенций, частые споры «кому это поручить»). Табличный способ (Правило выше) явно признаётся недостаточным на практике — это триггер для Сценария В из WP-499 (минимальное поле в `executor-catalog.yaml`), а не повод молча городить самодельный скрипт в обход этого SC.

## Связь с другими обещаниями

- Использует: **DP.SC.034** (Local MCP Gateway — транспорт для file-lock при подключении файлового агента)
- Передаёт эстафету: **DP.SC.035** (Peer-agent choreography) — после того как агент подключён, дальнейшая координация его параллельной работы с другими регулируется уже DP.SC.035, не этим SC
- Не пересекается с: паттерном подключения Гермеса (Cloud Gateway / `get_instructions`) — тот вне scope, у него нет локального файлового доступа
- Носитель роли (агент-сторона): **DP.ROLE.039** Peer Agent — новая роль не создаётся (см. WP-499 Ф3)

## Открытые вопросы (для реализации, не блокируют спецификацию)

1. **Кто именно выбирает агента, когда табличка не даёт однозначного ответа?** — рекомендация: пилот решает разово, агент не блокируется в ожидании; при повторении — таблица дополняется.
2. **Нужна ли отдельная координационная роль (по аналогии с Маршрутизатором DP.ROLE.059), если таблица вырастет?** — не создавать заранее; пересмотреть при срабатывании Сценария 4.
3. **MAP.002 registration:** сервисы этого SC пока не заведены строгими `S??`-кодами в `DP.MAP.002` — сделать при переходе от draft к подтверждённому статусу, не блокирует Ф1/Ф2 WP-499.
