# DP.METHOD.113 — ACL как companion-артефакт схемы, не ручная операция в проде

## Описание

Права доступа к новому объекту хранилища (таблице, представлению, функции) — ревьюируемый артефакт того же пайплайна, что и схема; ручные GRANT в проде недопустимы.

## IPO

**Input:** новый объект хранилища (таблица, view, sequence) + список сервисов/ролей, которым нужен доступ

**Process:**
1. Проверить: существует ли устоявшийся паттерн выдачи прав в репо? (grep по файлам миграций/schema на GRANT/REVOKE)
2. Если паттерн есть → обязательный companion-файл с правами в той же PR/batch, что и DDL-изменение
3. Companion-файл проходит code review как любой другой артефакт схемы
4. Обнаружена `permission denied` в проде → диагностика: (а) в DDL-миграции нет GRANT? → пропущен шаг паттерна; (б) SECURITY DEFINER функция → выполняется с правами дефайнера, не вызывающего

**Output:** companion-файл с правами в репо ИЛИ диагноз «пропущен companion при создании объекта»

## Пример

WP-455: `permission denied` у воркера после новой миграции. В репо 43 из 140 файлов содержат GRANT — паттерн устоявшийся. Значит, пропущен шаг. Фикс: новый файл 275-...-grant.sql на review, не ручной GRANT в продакшн.

## Тест применимости

«В репо есть файлы с GRANT/REVOKE рядом с DDL?» Да → companion обязателен при каждом новом объекте.

## Антипаттерн

Разовый ручной GRANT в проде как «быстрый фикс» — не ревьюируется, исчезает из истории, повторяется при следующем деплое схемы в новую среду.

## Связи

DP.M.303 (production DDL через gated-шаг, отдельный .sql файл вне application code) — тот же принцип «схемное изменение не проходит вручную», применённый к DDL в целом; этот метод — специализация для ACL/GRANT конкретно.
