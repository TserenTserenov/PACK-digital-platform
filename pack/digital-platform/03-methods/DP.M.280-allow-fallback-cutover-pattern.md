# DP.M.280 — Allow-Fallback Cutover Pattern

**Назначение:** безопасная миграция потока при наличии живых пользователей в старом состоянии (deprecated SM).

## Проблема

При переключении с machine state M (старый) на поток N (новый) существующие пользователи без записи в N оказываются в тупике: старый путь закрыт, новый не начат.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Переход на новый поток ↔ доверие существующих пользователей | Форсированный старт нового потока может запутать пользователей; fallback сохраняет доставку контента, но откладывает миграцию |
| Явная миграция ↔ автоматический fallback | Намеренный вход должен спрашивать согласие, чтобы не запускать поток без ведома; автоматический push/scheduler должен доставлять что-то, чтобы не сломать привычку |
| Чистота кода ↔ безопасность пользователей | Быстрое удаление deprecated пути упрощает код, но оставляет пользователей без состояния; fallback-ветка временно усложняет код, но спасает пользователей |
| Надёжность push-доставки ↔ уважение к user intent | Push-сообщения не могут полагаться на согласие пользователя; но если они автоматически запускают новый поток, пользователь теряет контроль |

## Паттерн

Центральный гейт `try_deliver_new_flow(allow_fallback: bool)` проверяет наличие прогресса пользователя в новом потоке:

**`allow_fallback=False` (основные входы — намеренное действие пользователя):**
- Нет прогресса → показать подсказку `/start_new_flow`, без автостарта.
- Пользователь сам инициирует начало нового потока.

**`allow_fallback=True` (автоматические входы — push-доставка планировщика):**
- Нет прогресса в новом потоке → доставить контент из deprecated потока.
- Гарантирует: пользователь получает что-то (доверие сохраняется), не получает ошибку.

## Разделение по типу входа

| Тип входа | allow_fallback | Обоснование |
|-----------|----------------|-------------|
| Намеренный (кнопка, команда) | False | Пользователь готов к новому флоу |
| Автоматический (push, scheduler) | True | Контент должен приехать |

## Lifecycle deprecated пути

После периода deprecated:
1. Всем оставшимся SM-пользователям — auto-migrate или explicit migration prompt
2. Убрать `allow_fallback=True` ветку в той же уборке кода
3. Удалить deprecated SM

## Тест завершения миграции

`count(users WITH old_sm_state AND NOT new_flow_progress) == 0` → deprecated путь можно удалять.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| «Новый поток лучше — все должны перейти сразу» | Практикующий форсирует новый поток для всех пользователей, игнорируя тех, у кого нет прогресса; теряется доверие и появляются застревания |
| «Fallback — временная костыль, убрать как можно скорее» | Allow-fallback ветка удаляется до завершения миграции; пользователи со старым состоянием остаются без контента и ошибок |
| «Намеренный и автоматический входы можно вести через один гейт» | Не различается `allow_fallback=False/True`; push/scheduler автоматически запускает новый поток без согласия пользователя |
| «Deprecated SM можно удалить, как только код готов» | Путаница готовности кода и готовности пользователей; удаление происходит до выполнения условия `count(users...) == 0` |
| «Подсказка `/start_new_flow` достаточна, пользователи прочитают» | Надеются на явный выбор пользователя при намеренном входе; в реальности часть пользователей не реагирует и остаётся в тупике |
