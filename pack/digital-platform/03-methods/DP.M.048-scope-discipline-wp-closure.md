# Дисциплина scope-решений при закрытии РП (DP.M.048)

## 1. Контекст

При реализации или закрытии РП обнаруживается смежная работа. Возникает соблазн «доделаю заодно» → бюджет уходит, DoD размывается, РП тянется 7+ фаз без точки закрытия.

## 2. Правило

При обнаружении новой работы во время текущего РП — применить дискриминатор обещания (DP.D.064):

1. Затронут ли исходный Service Clause (или эквивалент обещания текущего РП)?
2. Если **да** — это фаза в текущем РП (даже после deploy, даже после `status: done`).
3. Если **нет** — это другое обещание → новый РП через `wp-new`, не phase creep.

## 3. Условия применимости

- Текущий РП имеет чёткое обещание (Service Clause или эквивалент).
- Новая область может быть отложена без блокировки текущего обещания.
- Применимо ко всем РП ≥3h. Для тривиальных РП (≤30 мин) формальный тест избыточен.

## 4. Симптом нарушения

РП с историей 7+ фаз и неясной точкой закрытия → ретроспективно: на какой фазе нарушен дискриминатор, какая фаза должна была стать самостоятельным РП.

## 5. Признаки явного применения дискриминатора

В секции «Осталось» WP-context файла зафиксированы оба решения рядом:
- «Пост-деплой баги ✅ DONE» — то же обещание, фаза текущего РП.
- «Ф{N} {название} — отдельный РП, не в бюджете текущего» — другое обещание, вынесено.

Каждое решение сопровождается короткой fail-mode-formulation (что именно случилось бы при противоположном выборе).

## 6. Альтернативы и их анти-паттерны

| Альтернатива | Анти-паттерн |
|--------------|--------------|
| «Доделаю заодно — всё равно открыт» при другом обещании | Budget overrun + размывание DoD |
| «Закрою как есть, потом отдельно» при том же обещании | `status: done` при невыполненном DoD (`feedback_fixes_as_phases_not_separate_wp.md`) |
| «Открою новый РП на каждый шаг» | Раздробление бюджета, потеря контекста |

## 7. Связь с DP.M.010

DP.M.010 описывает жизненный цикл РП (статусы, хранилища, drift). DP.M.048 описывает дисциплину scope-решений на этапе Closure (один из переходов жизненного цикла). DP.M.010 §5 «Закрытие РП» — момент применения дискриминатора DP.D.064.

## 8. Пример (WP-320, 16 мая 2026)

При закрытии WP-320 (Notification Dispatcher: Ф0-Ф3 + пост-деплой баги) обнаружена смежная область — calendar integration. Применён дискриминатор:

- **Пост-деплой баги (tz-mismatch + bot_id isolation):** затронут исходный Service Clause WP-320 (Notification Dispatcher) → фаза текущего РП, добавлена «### Пост-деплой баги ✅ DONE 2026-05-16».
- **Ф4 calendar integration:** другое обещание (интеграция календаря, не доставка уведомлений) → отдельный РП, в той же сессии записано «Ф4 calendar → отдельный РП».
