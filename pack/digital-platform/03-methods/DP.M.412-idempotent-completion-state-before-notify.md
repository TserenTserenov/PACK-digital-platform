# DP.M.412 Состояние перед уведомлением: идемпотентный порядок завершения

## Описание

При завершении многошагового процесса, где один из шагов — внешнее уведомление (Telegram, email, push), порядок операций обязан быть: сначала все изменения внутреннего состояния, уведомление — строго последним шагом. Если процесс завершения повторяется (ретрай после сбоя сети, повторный вызов обработчика), обратный порядок даёт один из двух отказов: повторное уведомление о том, что уже было сообщено, либо ещё хуже — уведомление о результате, который не был записан.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Скорость обратной связи пользователю ↔ гарантия согласованности состояния | Отправить уведомление сразу после первого успешного шага даёт пользователю быстрый отклик, но если следующие шаги упадут — уведомление окажется ложью о состоянии, которого ещё нет |
| Простота линейного кода ↔ устойчивость к частичному сбою | Писать шаги в естественном порядке повествования (сначала сообщить, потом убрать за собой) читается проще, но именно естественный порядок чаще всего ставит внешний вызов не последним — потому что "рассказать" интуитивно кажется завершением истории |

## IPO

**Вход:** многошаговый процесс завершения, среди шагов — минимум одна внутренняя запись состояния и один внешний вызов уведомления
**Процесс:**
1. Выполнить все шаги записи внутреннего состояния (обновление прогресса, изменение статуса сущности) — в порядке, где более общее состояние (например статус целиком) пишется после частного (прогресс), если между ними есть зависимость чтения
2. Только после того, как все внутренние записи подтверждены — вызвать внешнее уведомление
3. При ретрае после сбоя: если внутреннее состояние уже отражает завершение — внешний вызов можно повторить безопасно (получатель увидит то же сообщение ещё раз, не хуже); если внутреннее состояние ещё не отражает завершение — процесс с шага 1, уведомление не отправлялось и не отправляется, пока состояние не будет записано

**Выход:** при любом количестве повторов — внутреннее состояние никогда не расходится с фактом отправленного уведомления; худший видимый эффект ретрая — дублирующееся сообщение о СОСТОЯВШЕМСЯ факте, не сообщение о несостоявшемся

## Правило

**Проверка на конкретном случае (источник находки):** порядок для завершения марафона — `update_progress(completed)` → `update_intern(marathon_status='completed')` → `send_message`. Если внешний вызов Telegram API упадёт до синхронизации статуса — при ретрае поздравление придёт повторно, но это не критично (дубль поздравления безобиден); критично было бы обратное — если бы `send_message` стоял до записи статуса, ретрай после сбоя записи статуса привёл бы к сообщению «поздравляем» без реально завершённого состояния.

## Тест

«Если внешний вызов упадёт ПОСЛЕ записи состояния, но ДО подтверждения — что увидит пользователь при ретрае?» Дубль уведомления о факте, который уже произошёл — метод соблюдён. Уведомление о факте, которого ещё нет — метод нарушен, поменять порядок.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| Естественный порядок повествования тянет уведомление вперёд | Когда пишешь код "как рассказываешь историю" — "сделали шаг, значит сообщим" — внимание непроизвольно ставит коммуникацию сразу после первого успеха, а не после ПОСЛЕДНЕГО внутреннего шага; чем длиннее цепочка внутренних шагов после этой точки, тем незаметнее становится нарушение |
| Внимание к happy path заслоняет вопрос "а что при ретрае" | Код пишется и читается для случая без сбоев, где порядок не имеет значения (все шаги проходят один раз); вопрос идемпотентности всплывает только при явном мысленном прогоне сценария повтора — если такой прогон не сделан, нарушение порядка не будет замечено до первого реального сбоя в проде |
