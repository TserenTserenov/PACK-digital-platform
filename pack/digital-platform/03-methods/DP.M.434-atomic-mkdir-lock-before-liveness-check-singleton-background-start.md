# DP.M.434 — Атомарный `mkdir`-замок до любой проверки состояния при идемпотентном старте фонового процесса

## Определение

Гарантия «не больше одного экземпляра» фонового процесса обеспечивается атомарным примитивом ОС (`mkdir` каталога-замка; эквиваленты — `flock`, `ln`), захватываемым ПЕРВЫМ шагом, до чтения PID-файла и любой другой проверки состояния. Проигравший конкурент выходит сразу; `trap` снимает замок на любом выходе победителя.

## Проблема

Идемпотентность старта фонового маяка проверялась схемой «прочитать PID-файл → `kill -0` → если процесс мёртв, запускать новый». Между чтением и запуском есть окно: два почти одновременных `SessionStart` (например, после сжатия контекста в двух параллельных агентах) оба видят «процесса нет» и оба стартуют. Второй экземпляр становится осиротевшим — его PID никто не записал, и ни одна последующая проверка того же PID-файла его не увидит. Схема check-then-act на PID-файле не атомарна по построению и не закрывается «более аккуратной» проверкой.

## Структура

Схематично (порядок шагов — суть метода):

```bash
LOCK_DIR="${TMPDIR:-/tmp}/my-beacon.lock"
if ! mkdir "$LOCK_DIR" 2>/dev/null; then
  exit 0            # конкурент уже внутри критической секции — молча уступаем
fi
trap 'rmdir "$LOCK_DIR" 2>/dev/null' EXIT   # снять замок на любом выходе (DP.M.413)

# --- только теперь: проверка состояния и запуск ---
if [ -f "$PID_FILE" ] && kill -0 "$(cat "$PID_FILE")" 2>/dev/null; then
  exit 0            # предыдущий экземпляр жив
fi
start_beacon &      # запуск; PID пишется под тем же замком
echo $! > "$PID_FILE"
```

## Ключевые свойства

1. **Атомарность — свойство примитива ОС, не логики скрипта.** `mkdir` на POSIX либо создаёт каталог, либо отказывает — только один из двух конкурирующих вызовов может его создать. Никакая последовательность «прочитать → проверить → записать» этого не даёт.
2. **Замок — до чтения состояния, не после.** Проверка «жив ли предыдущий» остаётся, но выполняется уже внутри критической секции; иначе она сама и есть окно гонки.
3. **Проигравший уступает молча, не ждёт.** Для идемпотентного старта «кто-то уже занимается» эквивалентно «уже запущено»; ожидание или повторная попытка не нужны.
4. **Замок короткоживущий, отдельный от PID-файла.** Каталог-замок защищает только критическую секцию старта и снимается `trap`'ом; долгоживущая идентичность процесса живёт в PID-файле. Смешение двух ролей возвращает проблемы stale-PID (DP.FM.143, DP.FM.217).
5. **`mkdir` не требует утилиты `flock(1)`**, которой может не быть в базовой поставке платформы (примечание экстрактора; в источнике `mkdir`/`flock`/`ln` названы равноправными атомарными примитивами).

## Когда применять

**Тест:** «Старт фонового процесса может быть инициирован двумя независимыми событиями почти одновременно (два хука, два таймера, два агента)? Гарантия единственности опирается на чтение файла состояния перед запуском?» Да на оба → check-then-act недостаточен, нужен атомарный примитив первым шагом.

## Отличие от смежного

- **DP.M.413 (файловая блокировка: освобождение через `trap` на любом выходе):** там — надёжность СНЯТИЯ замка; здесь — атомарность ЗАХВАТА и его место в последовательности (до любой проверки состояния). Ортогональные аспекты одного примитива; `trap` из DP.M.413 используется здесь как есть.
- **DP.M.372 (`flock`: гранулярность замка):** там — на каком уровне держать замок при обходе ресурсов; здесь — зачем замок вообще нужен там, где раньше была «проверка живости».
- **DP.FM.143 (stale PID → PPID-fallback) и DP.FM.217 (PID оболочки ≠ PID сессии):** оба — о неверном содержимом PID-файла; этот метод — о гонке при его чтении, которая воспроизводится и при верном содержимом.

## Применимо к

Любой идемпотентный старт «не больше одного экземпляра» фонового процесса из хуков, таймеров или параллельных агентов: маяки сессий, watcher'ы, локальные демоны синхронизации, фоновые очереди.
