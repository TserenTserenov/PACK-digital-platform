# DP.METHOD.054 — Метод кодирования и классификации IWE

> **Статус draft:** метод не применяется к production до приёмки (прогон чеклиста на 3 реальных кейсах + 1 новом) и ревью на ИТ-встрече (схемы 0.OPS — командный канон, 4 владельца). Основания — `WP-419-f1-principle-draft.md`; отбор SOTA — `WP-419-f3-sota-mapping.md`.

## 1. Зачем метод

В экосистеме ~65 реестров/нумераций/префиксов, каждый кодирует по своей ad-hoc схеме. Без метода новые коды и списки размножаются и рассинхронизируются (8 зафиксированных коллизий, треть реестров отстала от факта). Метод задаёт: **как завести, вести, версионировать и отменить** код или схему, чтобы она была одновременно **правильной** (дизайн) и **живучей** (принуждение).

**Эпистемная оговорка:** кодирование и классификация — деятельность (как мы концептуализируем и называем), её результат — *метод* или *схема*, а не «система». Не «система кодирования».

## 2. Две дорожки (обе обязательны)

| Дорожка | Вопрос | Предиктор |
|---------|--------|-----------|
| **Дизайн** | схема *правильная*? (оси ортогональны, нет коллизий, есть владелец) | качество проектирования осей |
| **Принуждение** | схема *выживет*? (нарушение дорого/невозможно) | стоимость нарушения, не качество дизайна |

> **Инвариант:** выживание ≠ корректность. Хорошо принуждённая плохая схема остаётся плохой; хорошо спроектированная схема без принуждения отмирает. Регистрация требует ответа по обеим дорожкам.

## 3. Дорожка дизайна — правила проектирования схемы

1. **Владелец (обязателен).** У каждой схемы — явный owner (= Registration Authority, ISO/IEC 11179). Отсутствие владельца namespace — корень коллизий.
2. **Фасетная дисциплина осей** (Ранганатан). Ось: имеет имя; ортогональна другим; внутри взаимоисключающа. Не overload одного числового диапазона между разными фасетами (источник коллизии транспонированных матриц).
3. **Bounded context = namespace** (DDD). Реестр объявляет свой контекст (owner + scope). Cross-context ссылка обязана квалифицировать код: `P5 (DP.SC.172)` ≠ `P5-block (AR.NNN)`. Это **допустимое дублирование**, а не коллизия, если контекст всегда разграничивает.
4. **ID стабилен, классификация — в поле.** Не вшивать изменчивую классификацию в идентификатор. IWE использует смысловые ID (данность) — дрейф митигируется (§5), но новые схемы держат ID стабильным, а меняющуюся категорию выносят в отдельное поле.

## 4. Дорожка принуждения — ось механизмов E0-E3

| Уровень | Механизм | Покрытие |
|---------|----------|----------|
| **E0** | Физическая структура (папки) | 100% — нарушить невозможно |
| **E1-hard** | Код ПАДАЕТ без поля/записи | путь чтения; запись нарушенного возможна |
| **E2** | Gate блокирует при нарушении (policy-as-code: git-хук/CI) | git-flow; не out-of-band |
| **E1-soft** | Код использует поле если есть | не покрывает absent-case |
| **E3** | Только конвенция/документ | ничего |

> Эмпирика выживаемости: E0 ~100% → E3 ~5-15%. E2 = policy-as-code (концептуальный референс OPA/Conftest; реализация через наши хуки, без нового инструмента).

## 5. Чеклист «заводишь новый код / список»

При создании реестра/нумерации/префикса ответить:

```yaml
schema_registration:
  name: "..."
  owner: "..."                       # ОБЯЗАТЕЛЕН (Registration Authority)
  bounded_context: "..."             # namespace + scope
  axis_facet: "..."                  # имя оси; ортогональна? взаимоисключающа?
  enforcement_mechanism: E0 | E1-hard | E2 | E1-soft | E3
  enforcement_surface:
    covered_paths: []                # git-commit, agent-write, api-write...
    uncovered_paths: []              # что НЕ покрыто
    uncovered_is_nonstandard: true|false
  # Два НЕЗАВИСИМЫХ контрольных вопроса (НЕ «два слоя одного контракта»):
  structural_check: E0 | E1-hard | E2          # «схема присутствует»
  semantic_check: E0 | E1-hard | E2            # «значение корректно»
    # ИЛИ для semantic:
  semantic_e3_acknowledged: "что не проверяется и почему допустимо"
  validator: "..."                   # путь/имя или «нет»
  generator: "..."                   # markdown-вид или «нет»
  schema_version: 1                  # semver: breaking = major
```

> **Поправка аудита (условие в):** structural и semantic — **два независимых вопроса**, не «два слоя одного контракта» (последнее не отраслевой термин). Пустой `semantic_check` без `semantic_e3_acknowledged` = решение не принято → регистрация не выполнена.
>
> **Если механизм E1-soft или E3** → `enforcement: weak` + еженедельный coverage-сторож. E3-«при одном пользователе» как исключение НЕ принимается (будущий факт, тихая бомба).

## 6. Жизненный цикл кода

```
proposed → active → deprecated → retired
```

- **proposed:** заведён, чеклист §5 заполнен, не используется в production.
- **active:** прошёл приёмку; механизм принуждения работает.
- **deprecated:** объявлен устаревшим, дата; tombstone-пометка; не заводить новое.
- **retired:** удалён из активного использования; запись о коде сохраняется (история).

**Отменённые коды (зафиксировать при активации метода):** Trust Calculus (`F:`/`G:`/`R:`/`trust:`/`epistemic_stage:`) → deprecated (мёртвые); `C.` entity-prefix → deprecated (вытеснён буквой-ядром `C`).

## 7. Рецепт миграции / переименования токена

1. **grep-аудит:** найти все употребления (`grep -r` по `~/IWE/`).
2. **tombstone:** старый код помечается deprecated с датой и ссылкой на новый.
3. **alias:** старый код → новый как синоним на переходный период (SKOS altLabel).
4. **переходный период:** оба работают; по истечении — старый retired.
5. **валидатор** ловит новые употребления retired-кода.

## 8. Правило реестра

> **Новый реестр = (а) запись в каталоге реестров `registry-catalog.yaml` + (б) namespace в реестре нумераций.**

Каталог реестров сам подвержён дрейфу (ср. мёртвый `repo_inventory.tsv`). MVP принуждения каталога: **E1-hard** (генератор падает на битом каталоге) + еженедельный heartbeat. **Target:** E2-drift-guard (commit-блок «отредактировал реестр → забыл каталог», паттерн WP-REGISTRY ↔ inbox).

## 9. Доставка агентам (условие непустоты метода)

> Метод в Pack без хука мёртв при рождении. Поэтому при активации:

- **AR-правило** (PACK-agent-rules): при заведении нового кода/реестра в WP Gate / `wp-new` / Routing Gate — обязательны поля чеклиста §5 (минимум: owner, enforcement_mechanism, bounded_context).
- **Триггер:** Routing Gate (DP.KR.001 §5) проверяет наличие записи в каталоге реестров.

## 10. Что НЕ входит (scope-guard / target-state)

- Полный ISO/IEC 11179, SKOS/RDF-тристор, SHACL, внешний OPA-движок — берём только идеи (lifecycle, owner, alias, policy-as-code-модель), без новых инструментов.
- Непрозрачные (opaque) ID вместо смысловых — meta-РП уровня экосистемы, вне scope.
- E2-drift-guard каталога — target, не MVP.
- **Governance самого метода** (кто и как меняет E0-E3 / AR-правила / условия приёмки) — target-state; без него метод дрейфует, как реестры. Отдельный РП/версия.
