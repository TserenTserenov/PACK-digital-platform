# DP.M.281 — Диагноз повторяющихся ошибок: 4 режима отказа + 2 порождающих ограничения

## Описание

Двухслойный метод диагностики причин, по которым ошибки системы повторяются после «починки». Ключевое наблюдение: большинство повторов происходит из-за лечения симптома вместо порождающей структуры.

## Слой 1 — 4 режима отказа

| Режим | Признак | Описание |
|-------|---------|----------|
| R1 — Повтор симптома без петли возврата | Bug появляется снова после fix | Нет механизма возврата сигнала ops→проект |
| R2 — Orphan-артефакт | Состояние вне кода | Объект без явного владельца и петли возврата |
| R3 — Переклейка мониторинга | Внешний мониторинг принят за code bug | Метрика → код, а причина в инфраструктуре |
| R4 — Слепой mock-only гейт | Тесты зелёные, production падает | Гейт не покрывает production-контракт |

## Слой 2 — 2 порождающих ограничения

| Ограничение | Признак |
|-------------|---------|
| КО-1: Когнитивная перегрузка единственного разработчика | Починка симптома быстрее разбора причины — рациональный выбор под давлением |
| КО-2: Ownership-gap | Орфанный артефакт без петли возврата ops→проект; никто не несёт ответственности за рецидив |

## Алгоритм применения

1. При диагнозе «баг повторяется» — определить режим отказа (R1-R4)
2. Определить активное ограничение (КО-1 или КО-2)
3. Лечить ограничение, не симптом:
   - R1 → создать петлю возврата (ops alert → issue → backlog ownership)
   - R2 → назначить владельца + петлю возврата
   - R3 → разделить мониторинговые алерты и code-level bugs
   - R4 → добавить production-smoke тест к гейту

## Тест

«Есть ли явный владелец + петля возврата для этого артефакта?» — Нет → режим R2.
