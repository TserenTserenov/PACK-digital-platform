# DP.M.281 — Диагноз повторяющихся ошибок: 4 режима отказа + 2 порождающих ограничения

## Описание

Двухслойный метод диагностики причин, по которым ошибки системы повторяются после «починки». Ключевое наблюдение: большинство повторов происходит из-за лечения симптома вместо порождающей структуры.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Лечение симптома ↔ устранение порождающего ограничения | Починка симптома быстра и видна; лечение КО-1/КО-2 требует изменения процесса/ownership, но предотвращает рецидив |
| Ops-обратная связь ↔ dev backlog | Создание петли возврата ops→проект замедляет релиз и добавляет процесс; отсутствие петли позволяет повторы оставаться невидимыми до следующего инцидента |
| Краткость fix ↔ документированность | Короткий patch без anchor закрывает задачу; но при следующем изменении теряется источник и невозможно найти потребителей |
| Разделение мониторинга и code-bugs ↔ скорость диагноза | Чёткое разделение R3 требует анализа; быстрая диагностика в code приводит к лечению не той системы |
| Мгновенное давление ↔ долгосрочная стоимость повторов | Под давлением разработчик выбирает симптом; накопленные повторы превосходят первоначальную экономию |

## Слой 1 — 4 режима отказа

| Режим | Признак | Описание |
|-------|---------|----------|
| R1 — Повтор симптома без петли возврата | Bug появляется снова после fix | Нет механизма возврата сигнала ops→проект |
| R2 — Orphan-артефакт | Состояние вне кода | Объект без явного владельца и петли возврата |
| R3 — Переклейка мониторинга | Внешний мониторинг принят за code bug | Метрика → код, а причина в инфраструктуре |
| R4 — Слепой mock-only гейт | Тесты зелёные, production падает | Гейт не покрывает production-контракт |

## Слой 2 — 2 порождающих ограничения

| Ограничение | Признак |
|-------------|---------|
| КО-1: Когнитивная перегрузка единственного разработчика | Починка симптома быстрее разбора причины — рациональный выбор под давлением |
| КО-2: Ownership-gap | Орфанный артефакт без петли возврата ops→проект; никто не несёт ответственности за рецидив |

## Алгоритм применения

1. При диагнозе «баг повторяется» — определить режим отказа (R1-R4)
2. Определить активное ограничение (КО-1 или КО-2)
3. Лечить ограничение, не симптом:
   - R1 → создать петлю возврата (ops alert → issue → backlog ownership)
   - R2 → назначить владельца + петлю возврата
   - R3 → разделить мониторинговые алерты и code-level bugs
   - R4 → добавить production-smoke тест к гейту

## Тест

«Есть ли явный владелец + петля возврата для этого артефакта?» — Нет → режим R2.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| «Баг уже чинили, почему повторился?» | Практикующий считает symptom-fix достаточным и не переходит к режиму отказа R2-R4, леча симптом вновь |
| «Root cause analysis занимает слишком много времени» | Давление заставляет чинить симптом; накопленные повторы и инциденты превышают первоначальную экономию времени |
| «Добавим тест — и закроем» | R4 (слепой mock-only гейт) воспринимается как достаточный; production-контракт остаётся непокрытым, и продолжает падать |
| «Ops alert — не наш баг» | Мониторинговый алерт (R3) классифицируется как code-bug, и лечение уходит в код, а не в инфраструктуру |
| «Владельца назначим позже» | Orphan-артефакт (R2) остаётся без owner и петли возврата, потому что назначение ownership кажется формальностью |
