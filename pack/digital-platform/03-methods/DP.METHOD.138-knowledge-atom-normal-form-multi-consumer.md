# DP.METHOD.138 — Нормальная форма атома знания: механизм + граница + источник

## Описание

Оформление результата верификационной или аналитической работы в атомарную структуру из трёх компонентов: механизм (что делает), граница применимости (когда работает / не работает), первоисточник (откуда). Атом в такой форме без переделки ложится в N разных потребителей — контент-конвейер, реестр нормативов, каталог мемов — потому что все они потребляют одно и то же.

## IPO

**Input:** результат SOTA-верификации, аналитической работы или peer-сессии в произвольной форме

**Process:**
Переформулировать каждый вывод по шаблону:
```
Механизм: [что именно работает / происходит]
Граница применимости: [условие, при котором верно; контрусловие]
Первоисточник: [автор, год, DOI или ссылка на наблюдение]
```
Зафиксировать в extraction-report один раз. При маршрутизации — добавить целевой контекст потребителя, не переписывать ядро атома.

**Output:** атом в нормальной форме, готовый для N потребителей без дублирования

## Когда применять

- SOTA-верификация перед публикацией (нужен список источников + механизмы для нескольких систем)
- Анализ инцидентов или peer-сессии (вывод нужен и в Pack, и в отчёт, и в контент)
- Любая работа, где результат пойдёт более чем в одно место

## Антипаттерн

Оформлять результат сразу в форме конечного потребителя (пост, Pack-файл, реестр) — тогда при втором потребителе нужно переписывать. «Разводка по N системам = маршрутизация, не переписывание» — только если атом оформлен в нормальной форме.

## Связь с OwnerIntegrity

Расширение принципа «один факт — одно место» на этап ДО записи в Pack: атом оформляется один раз в extraction-report, потребители читают из одного места.
