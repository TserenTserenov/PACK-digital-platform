# DP.METHOD.108 — Масштаб счётчика ошибок как диагностика масштаба причины

## Описание

Размер счётчика отброшенных / ошибочных объектов коррелирует с масштабом корневой причины. Малый счётчик исключает гипотезы массового сбоя; большой — исключает гипотезы единичного сбоя.

## IPO

**Input:** счётчик отброшенных / пропущенных объектов в pipeline + список гипотез о причинах

**Process:**
1. Для каждой гипотезы оценить: какой счётчик она предполагает? (массовый PermissionError → счётчик > 100; phantom writer → счётчик ≤ 10)
2. Сравнить ожидаемый масштаб счётчика с наблюдаемым
3. Исключить гипотезы, предполагающие масштаб ≫ наблюдаемого
4. Сфокусировать расследование на совместимых гипотезах

**Output:** суженный список гипотез без проверки исключённых

## Пример

WP-454: `dropped_sessions = 3` при тысячах активных сессий за период. Гипотеза «массовый PermissionError (нет Full Disk Access у launchd)» предполагала `dropped > 1000`. Счётчик 3 → гипотеза исключена без дальнейшей проверки. Направление переключено на phantom early-writer (единичная аномалия) → верно.

## Тест применимости

«Есть ли в pipeline счётчик отброшенных объектов?» Нет → добавить в pipeline до следующей диагностики — без него метод неприменим.

## Антипаттерн

Проверять все гипотезы по очереди, игнорируя счётчик отброшенных, — тратит время на уже исключённые гипотезы.
