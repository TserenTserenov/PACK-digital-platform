# DP.M.464 — SECURITY DEFINER для не-читателя, не ослабление RLS

## Проблема

RLS-политика (`stream_reader_access`) спроектирована вокруг личности конкретного читателя (per-user reader). Фоновая/периодическая задача (например, планировщик в боте) не действует от имени одного читателя: ей структурно нужны ВСЕ активные строки сразу (все `stream_chat` всех читателей), и она не пройдёт эту политику ни при каком точечном исправлении данных или ролей. Соблазн — ослабить/расширить саму политику под этот edge case, что снижает защиту и для обычного per-user пути.

## Метод

Запрос такого вызывающего выносится в `SECURITY DEFINER` функцию с доступом, суженным до роли фоновой задачи; политика остаётся прежней.

**Вход:** вызывающий без естественной RLS-совместимой личности (не баг политики, а структурное несоответствие «кто спрашивает» и «под кого спроектирована защита») и запрос, которому нужен доступ шире одного читателя. **Выход:** фоновая задача получает нужные строки через узкую функцию, политика для per-user пути не изменена.

1. Обернуть нужный запрос в `SECURITY DEFINER` функцию.
2. Выдать `REVOKE ALL FROM PUBLIC` и `GRANT EXECUTE` только конкретной роли фоновой задачи.
3. Явно закрепить `search_path` внутри функции, не полагаться на `search_path` вызывающего.
4. НЕ ослаблять и не расширять RLS-политику ради этого вызывающего.

Пример из источника:

```sql
CREATE FUNCTION list_active_stream_chats() RETURNS SETOF stream_chat
LANGUAGE sql SECURITY DEFINER
SET search_path = public
AS $$ SELECT * FROM stream_chat WHERE status = 'active' $$;
REVOKE ALL ON FUNCTION list_active_stream_chats() FROM PUBLIC;
GRANT EXECUTE ON FUNCTION list_active_stream_chats() TO scheduler_role;
```

## Тест метода

«У вызывающего нет естественной для этой RLS-политики личности читателя (фоновый планировщик, кросс-пользовательская агрегация), и ему нужен доступ шире одного читателя?» Да → `SECURITY DEFINER` функция с явным `REVOKE`/`GRANT` и закреплённым `search_path`, а не расширенная RLS-политика.

## Forces

| Force | Tension |
|-------|---------|
| Доступ фоновой задачи ко всем активным строкам ↔ защита RLS, рассчитанная на одного читателя | Фоновая задача структурно не проходит политику, рассчитанную на одного читателя; запрос оборачивается в `SECURITY DEFINER` функцию, саму политику не ослабляют и не расширяют |
| Обход RLS внутри функции ↔ минимальные права вызывающего | Функция обходит RLS, поэтому доступ к ней сужается: `REVOKE ALL FROM PUBLIC` и `GRANT EXECUTE` только конкретной роли фоновой задачи |
| Исполнение функции с правами владельца ↔ предсказуемое разрешение имён | Права владельца требуют предсказуемого разрешения имён: `search_path` закрепляется явно внутри функции, без опоры на `search_path` вызывающего |

## Применимо

Когда у вызывающего нет естественной для политики личности читателя (фоновый планировщик, кросс-пользовательская агрегация) и ему нужен доступ шире одного читателя. Если функция-обёртка операции уже есть и вопрос только в минимизации прав вызывающего, — это `DP.M.342`, а не данный метод.

## Связи

- `DP.M.342` (EXECUTE на SECURITY DEFINER функцию вместо прямых прав на таблицу) — тот же механизм (SECURITY DEFINER + сужение GRANT), другой триггер: DP.M.342 решает «есть готовая функция-обёртка операции — как минимизировать права вызывающего»; этот метод решает «у вызывающего нет RLS-совместимой личности вообще — как не ослаблять политику ради него». Смежные, не дубли.
