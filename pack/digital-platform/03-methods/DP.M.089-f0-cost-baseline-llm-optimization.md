# DP.M.089 — Ф0-исследование cost baseline перед LLM-оптимизацией

> Сначала измерь, потом оптимизируй.

## Обещание

Перед принятием решений об оптимизации стоимости LLM (tiering, downgrade модели, proxy-слой) необходима Ф0 research-фаза: сбор актуального cost baseline на реальных сессиях.

## Вход

- Доступ к логам/billing API реальных LLM-сессий (N ≥ 100 сессий)
- Гипотезы об оптимизации (места «потери денег»)

## Выход

- Распределение стоимости по тирам модели (Opus/Sonnet/Haiku)
- Доля cached vs uncached токенов
- Текущее распределение задач по моделям
- «Direction readiness» метрика (% потенциала, который реализован без изменений)

## Алгоритм (IPO)

1. **Собрать данные** — billing API или session logs (N ≥ 100 реальных сессий, не синтетика)
2. **Рассчитать baseline** — медиана/P95 стоимости по модели, доля cached токенов, распределение задач
3. **Проверить гипотезы** — для каждой потенциальной оптимизации:
   - Рассчитать ожидаемую экономию при гипотетическом изменении
   - Сравнить с текущим baseline: «уже оптимально?»
4. **Оценить Direction Readiness** — % потенциала оптимизации, уже реализованного без вмешательства

## Инвариант

Baseline должен быть на реальных сессиях, не на синтетических бенчмарках. Синтетические данные могут дать противоположный вывод о направлении оптимизации.

## Failure mode без Ф0

Оптимизировать то, что уже оптимально — тратить ×3-4 бюджета на изменения, которые дадут <5% экономии. Пример: гипотеза «caching недооптимизировано» оказалась неверна (95.5% уже cached) → реальный bottleneck в другом.

## Применимость

- Решения по model tiering (Opus→Sonnet→Haiku)
- Решения по batch vs realtime processing
- Решения по model downgrade или proxy-слою
- Любая LLM-стоимость оптимизация с бюджетом >$10/мес
