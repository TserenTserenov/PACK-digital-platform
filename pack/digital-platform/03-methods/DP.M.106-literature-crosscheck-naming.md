# DP.M.106 — Literature crosscheck при именовании Pack-сущностей

> **see DP.METHOD.030 (term-translation), DP.METHOD.031 (concept-mapping)**

## Триггер

Создание новой сущности в Pack:
- Роль (DP.ROLE / PD.ROLE / MIM.R)
- Различение (DP.D / PD.D)
- Метод (DP.M / PD.METHOD)
- Формализация (DP.FORM / PD.FORM)
- Service Clause (DP.SC)

## Алгоритм

1. **Идентифицировать дисциплину сущности.** Из какого тела знаний эта концепция: TOC, DDD, FPF, SRE, evidence-based learning, …?
2. **Подобрать 3-4 канонических источника** этой дисциплины. Канонический = автор-классик + 2-3 его комментатора/продолжателя.
3. **Для каждого источника выписать**, как он именует эту сущность. Если автор не именует — пропустить (не натягивать).
4. **Оценить каждое имя** по двум осям:
   - **Семантическая точность.** Покрывает ли имя ровно ту функцию, которая нужна Pack? (Goldratt «Jonah» = наставник, шире чем «аналитик» — отклонить.)
   - **Operational vs analytical scope.** Управляет процессом или анализирует ограничения? (Dettmer «Constraint Manager» — operational, отклонить если в Pack нужен аналитик.)
5. **Выбрать имя closest-to-canon.** Если есть один доминирующий источник — взять его. Если 2-3 равно валидны — выбрать тот, у которого русский перевод понятен без объяснений.
6. **Сохранить решение в Pack-файле сущности** в секции «Источник имени»: 4 источника + причина выбора финального варианта.

## Польза

1. **Сопротивление re-naming через 6 месяцев.** Имя уже валидировано литературой — переименовать = опровергнуть классика, высокий барьер.
2. **Лёгкое onboarding** для новых членов команды или внешних читателей: термин знаком из книг.
3. **Переносимость в внешнюю коммуникацию** (статьи, презентации, конференции).

## Применимость

Все Pack-сущности с собственным именем: DP.ROLE / DP.D / DP.M / DP.FORM / DP.SC и их аналоги в других Pack'ах.

**Исключения** (метод НЕ нужен):
- Implementation-name в DS docs/ (системы, скрипты, миграции) — там работает другая логика.
- Pack-internal служебные ID (нумерация, индексы).
- Имя обещано пользователю / клиенту-внешнему стейкхолдеру (там их канон, не дисциплинарный).

## Тест ретроспективы

«Откуда взялось это имя?»
- Ответ «из книги/автора N» → устойчиво.
- Ответ «придумал на коленке / звучало норм» → высокий риск re-naming через 3-6 месяцев.

## Прецедент

**DP.ROLE.054 «Аналитик ограничений»** (PACK-digital-platform commit f6797ce, WP-313 Ф11, 2026-05-20). Рассмотрены 4 источника TOC:

| Источник | Имя | Оценка | Решение |
|----------|-----|--------|---------|
| Goldratt | Jonah | Наставник, шире чем аналитик | Отклонить |
| Dettmer | Constraint Manager | Operational, не analytical | Отклонить |
| Schragenheim | TOC Analyst | Функционально точно | **Принять** |
| Tendon (TameFlow) | distributed (модификатор) | Не самостоятельное имя | Отклонить |

Финальное имя: «Аналитик ограничений» — русский калькирующий перевод формулировки Schragenheim.

## Связи

- **DP.METHOD.030 (term-translation):** этот метод определяет ENGLISH-имя из литературы; DP.METHOD.030 переводит его в RU-канон с EN-pivot. Последовательность: сначала DP.M.106 (выбор имени), затем DP.METHOD.030 (RU/EN-пара).
- **DP.METHOD.031 (concept-mapping):** этот метод даёт имя; DP.METHOD.031 привязывает имя к FPF-корню (U.*) для онтологической связности.
