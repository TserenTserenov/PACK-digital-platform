# DP.M.040 — Progress Counter N/M для batch-операций CLI

## Суть метода

Длинный batch-цикл (скачивание N файлов, проверка N детекторов, ~30 сек) без вывода создаёт **иллюзию зависания**: пользователь не знает, выполняется ли процесс или завис.

Решение: вывод прогресс-строки `(N/M) описание...` в теле цикла.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Порог принятия решения «нужен ли счётчик» (>10 итераций ИЛИ >5 сек) ↔ момент этого решения — до того, как реальное время выполнения известно | «Когда применять» формулирует порог как измеримое условие, но решение добавлять ли `printf`-строку в цикл принимается на этапе написания скрипта, когда фактическая длительность batch-операции ещё не измерена |
| Единообразие простого shell-паттерна (N/M counter) через весь IWE (update.sh, validator.sh, FMT/DS) ↔ специализированные инструменты по контексту (tqdm, Rich progress bar, asyncio.gather с callback из «Альтернативы по контексту») | Один и тот же простой паттерн переиспользуется ради консистентности между скриптами, хотя в Python/async-контекстах существуют более информативные альтернативы |

## Реализация (shell)

```bash
TOTAL=${#FILES[@]}
CURRENT=0

for file in "${FILES[@]}"; do
    CURRENT=$((CURRENT + 1))
    printf "(%d/%d) downloading %s...\n" "$CURRENT" "$TOTAL" "$file"
    # ... операция ...
done
printf "\n"
```

## Когда применять

**Порог:** >10 итераций ИЛИ >5 сек суммарного времени.

| Операция | Применять? |
|----------|-----------|
| Скачивание N файлов (~30 сек) | ✅ |
| Проверка N детекторов в validator.sh | ✅ |
| Создание 2-3 файлов | ❌ — нет смысла |
| pip install (уже есть встроенный прогресс) | ❌ — дублирование |

## Альтернативы по контексту

| Контекст | Метод |
|---------|-------|
| Python | tqdm |
| Long-running async | asyncio.gather с callback |
| Многострочный вывод | Rich progress bar |
| Shell, простота важна | N/M counter (этот метод) |
