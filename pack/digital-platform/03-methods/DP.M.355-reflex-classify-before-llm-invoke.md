# DP.M.355 — Рефлекс-routing: classify() обязан предшествовать invoke_claude()

## Описание

В двухконтурном диспетчере (рефлекс + LLM) существует критический инвариант исполнения: `classify()` (lookup по executor_catalog.yaml по сигнатуре признаков) должна вызываться **до** `invoke_claude()`.

Если classify() внутри LLM-обработчика или после него — рефлекс-маршрут не экономит токены и не снижает latency. Смысл двухконтурной архитектуры теряется.

Дополнительный инвариант: LLM-путь получает `confidence=0.0` (неопределённая уверенность), а не `confidence=1.0` хардкодом.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Гибкость обработчика ↔ жёсткий порядок вызова | Разместить classify() внутри универсального обработчика запросов кажется гибче (один вход для всех случаев), но именно эта гибкость размывает обязательный порядок «сначала рефлекс, потом LLM» |
| Экономия токенов/latency ↔ простота единого пути обработки | Двухконтурная архитектура экономит ресурсы на частых паттернах, но требует поддерживать два разных пути кода вместо одного универсального — сложнее читать и рефакторить |
| Честная неопределённость (confidence=0.0) ↔ удобство downstream-потребителя метрик | `confidence=0.0` точнее отражает природу LLM-ответа, но downstream-код, ожидающий «уверенность», может неверно интерпретировать ноль как «низкая уверенность вообще», а не как «метрика неприменима к этому пути» |
| Быстрый рефакторинг ↔ сохранение инварианта | При рефакторинге дispatcher-кода легко переместить строку classify() «для читаемости», не осознавая, что перестановка ломает архитектурный инвариант, а не просто меняет стиль |

## Algorithm

### Step 1: Classify first

```python
def dispatch(request: AgentRequest) -> AgentResponse:
    # ОБЯЗАТЕЛЬНО ПЕРВЫМ — до любого LLM-вызова
    match = classify(request, executor_catalog)
    
    if match.is_reflex:
        return execute_reflex(match.handler, request)
    
    # Только если рефлекс не сработал — LLM
    return invoke_claude(request, confidence=0.0)
```

### Step 2: Проверь confidence для LLM-пути

LLM имеет неопределённую уверенность по определению:
```python
# Правильно
return AgentResponse(result=llm_result, confidence=0.0)

# Неправильно (хардкод)
return AgentResponse(result=llm_result, confidence=1.0)
```

### Step 3: Smoke-test инварианта

```python
def test_reflex_classify_before_invoke():
    """При рефлекс-match — invoke_claude НЕ должен вызываться."""
    with mock.patch('dispatcher.invoke_claude') as mock_llm:
        dispatch(reflex_request)
        mock_llm.assert_not_called()  # Инвариант держится
```

## When to use

- Реализация/рефакторинг диспетчера агентов с двумя контурами
- Code review dispatcher-кода: проверить порядок classify → invoke
- Дизайн нового типа агентского маршрута

## Тест применимости

«При рефлекс-match — вызывается ли LLM?»
- **Нет** → classify() работает до invoke_claude(), инвариант держится
- **Да** → classify() вызывается после или внутри LLM-пути, рефлекс не работает

## Anti-patterns

- **classify() внутри LLM-хендлера**: рефлекс-логика недоступна до старта LLM — токены тратятся всегда
- **confidence=1.0 для LLM-пути**: LLM по определению не знает уверенности, хардкод 1.0 вводит в заблуждение downstream-потребителей метрик
- **Отсутствие smoke-test**: инвариант нарушается при рефакторинге без теста

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| «Диспетчер работает правильно — значит, порядок вызова тоже правильный» | Внимание фиксируется на корректности итогового ответа (пользователь получил результат), а не на том, каким путём — рефлексом или LLM — он был получен и сколько это стоило |
| «LLM всё равно почти всегда срабатывает — рефлекс редкое исключение» | При проектировании/код-ревью двухконтурного диспетчера рефлекс-путь воспринимается как второстепенная оптимизация, а не как равноправная ветка с собственным инвариантом порядка |
| «Рефакторинг не трогает логику классификации — порядок не изменится» | При код-ревью diff читается по затронутым строкам, а не по итоговому порядку вызовов; перестановка classify()/invoke_claude может произойти как побочный эффект несвязанного изменения (вынос общего блока, объединение обработчиков) и остаться незамеченной, если ревьюер не проверяет инвариант явно на каждом diff |
| «Инвариант же описан в этой самой карточке метода — все и так знают» | Знание о правиле, зафиксированное в документации метода, воспринимается как достаточная защита сама по себе; без исполняемой проверки (smoke-test) документированный инвариант ничем не отличается от неписаного — он не мешает регрессии до тех пор, пока кто-то не решит написать тест специально |
