# DP.METHOD.147: Cashback-модель при интеграции с API со строгой суммой-валидацией

## Контекст

Некоторые API (Aisystant, marketplace SKU-validation, subscription billing systems) проверяют переданную сумму на соответствие своему каталогу цен. Передача дисконтированной суммы → HTTP 403. YooKassa и аналогичные платёжные шлюзы принимают любую сумму (там дисконт допустим).

## Развилка

| Вариант А: дисконтированная сумма провайдеру | Вариант Б: cashback-модель |
|----------------------------------------------|---------------------------|
| Передаём (цена − бонусы) провайдеру | Передаём полную цену провайдеру |
| Провайдер видит неверную сумму → 403 | Провайдер видит каталожную цену → 200 |
| Нарушает контракт API | Соответствует контракту |
| — | Бонусы списываются через lazy-confirm после подтверждения |

## Правило выбора

**Если** провайдер проверяет сумму по своему каталогу → **Вариант Б (cashback)**.

## UI-правило

Формулировка «скидка N ₽» создаёт expectation mismatch при cashback-модели: пользователь ожидает уменьшенную итоговую сумму к оплате. Правильно: «спишем N баллов после подтверждения оплаты».

## Тест

«Провайдер вернул 403 при передаче дисконтированной суммы?» → применить cashback-модель.

## Применимость

- Subscription APIs, проверяющие сумму по тарифной сетке
- Marketplace SKU-validation (фиксированные цены SKU)
- Любая система billing с catalog-enforced pricing

## Связи

- Смежная FM: DP.FM.236 (premature cache invalidation — другой домен, тот же принцип "порядок операций важен")
- Платёжный шлюз без catalog-check (YooKassa): дисконт там допустим — используй Вариант А
