# DP.M.156 — Upgrade-Markers в Service Contract

## Суть

Паттерн включения явных маркеров готовности к upgrade в service contract. Вместо ad-hoc логики «пользователь долго сидит → предложи апгрейд» — формализованные условия по группам с детерминированными триггерами.

## IPO

| | |
|---|---|
| **Вход** | Service contract для freemium/tier-based продукта; поведенческие данные пользователя |
| **Процесс** | Определить группы upgrade-готовности (B-low/B-high/C/E или аналог) → для каждой группы формализовать условия достаточности → включить как секцию UPGRADE_MARKERS в SC |
| **Выход** | SC содержит явные, тестируемые условия для предложения upgrade каждой группе |

## Шаги

1. Выявить сегменты пользователей, для которых upgrade-нудж уместен (минимум 2 группы по уровню активности)
2. Для каждого сегмента определить: триггер (условие), текст нуджа, канал (push/inline), cooldown
3. Записать как `UPGRADE_MARKERS: [B-low, B-high, C, E]` в frontmatter SC + секцию с описанием каждого маркера
4. Зафиксировать инвариант: «нулевая активность = никаких нуджей» (ложно-положительные нуджи дороже молчания)

## Тест применимости

«Может ли новый разработчик по SC понять, при каком условии пользователю предложат перейти?» Нет → маркеры не формализованы → применить метод.

## Почему важно

- Исключает false-positive нуджи (предложение upgrade при нулевой активности)
- A/B-тестируемо (разные маркеры меняются независимо)
- Изменение логики нуджа = изменение SC → аудитируемо

## Применимость

Любые freemium/tier-based SaaS-продукты с upgrade-нуджами: мобильные приложения, API-продукты, образовательные платформы.
