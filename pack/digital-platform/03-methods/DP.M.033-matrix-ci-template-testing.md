# Matrix-CI по конфигурационному параметру шаблона (DP.M.033)

## Суть метода

Для шаблонов (FMT) с конфигурационными параметрами-заменителями: запускать CI не с одним значением, а с **матрицей** значений ключевого параметра.

**Пример (WP-5 Ф-CI, 2026-05-12):**

```yaml
strategy:
  matrix:
    governance_repo: [DS-strategy, DS-my-governance, DS-governance]
```

Тест выявил два hardcoded `"DS-strategy"` в `dt-collect.sh` и `repair-pass` в `update.sh` — баги, незаметные у автора (у него репо = DS-strategy = совпадает с дефолтом).

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Полнота матрицы значений (≥2 нестандартных значения на параметр, шаг 2) ↔ время выполнения CI | Каждое добавленное значение матрицы (`governance_repo: [DS-strategy, DS-my-governance, DS-governance]`) умножает число CI-job'ов на количество ключевых параметров — рост стоимости прогона ради обнаружения дефектов, которые могли бы и не проявиться |
| Дефолтное значение автора (`DS-strategy`, совпадающее с его реальным репо) ↔ обнаруживаемость hardcoded-констант | Именно потому что дефолт совпадает с личной средой автора, баг в `dt-collect.sh` и `repair-pass` (update.sh) невидим локально — метод специально требует нестандартных значений в матрице, а не только дефолтного, чтобы вскрыть это несоответствие |

## Алгоритм

1. Определить ключевые параметры шаблона: `GOVERNANCE_REPO`, `WORKSPACE_DIR`, `USER_NAME`, `PACK_REPO`
2. Для каждого параметра добавить ≥2 нестандартных значения в matrix
3. CI должен проходить со всеми значениями матрицы
4. При failure: `grep -r "<hardcoded_value>" .` — найти и заменить на `params.yaml`-переменную

## Применимость

- FMT (шаблоны экзокортекса) с `{{PLACEHOLDER}}` → конкретное значение при инсталляции
- Dockerfile / Helm-чарты с параметрами `namespace`, `prefix`, `org`
- Bash-скрипты с заменяемыми конфигурационными значениями

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| Выбор параметров матрицы стагнирует на исторически проблемных | При выборе ключевых параметров для матрицы (шаг 1: `GOVERNANCE_REPO`, `WORKSPACE_DIR`, `USER_NAME`, `PACK_REPO`) внимание практикующего съезжает к параметрам, которые уже когда-то ломались, и недооценивает новые/недавно добавленные конфигурационные точки шаблона — покрытие матрицы не растёт вместе с шаблоном |
| Grep останавливается на первом найденном файле | После обнаружения failure (шаг 4: `grep -r "<hardcoded_value>"`) внимание фокусируется на конкретном найденном файле (`dt-collect.sh`, `repair-pass` в `update.sh`) и останавливается там же — практикующий недооценивает необходимость повторного прогона grep по всему репо на предмет других вхождений того же hardcoded-значения за пределами первого найденного файла |
