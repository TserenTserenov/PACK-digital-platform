# DP.M.276 — ADD-not-RENAME при распаковке tool/role/SC

## Описание

При распаковке функциональности (роль split, SC decomposes, tool разделяется на два или более) — сохранять исходное имя tool/endpoint/SC и добавлять новые параллельно. Не переименовывать.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Backward compatibility ↔ ясность новых имён | ADD сохраняет старые ссылки, но оставляет два имени; RENAME делает имена чётче, но ломает клиентов, скрипты и кэшированные ссылки |
| Чистая миграция ↔ постепенный переход | RENAME требует одномоментного cutover; ADD позволяет клиентам перейти в своём темпе, но увеличивает поверхность для поддержки |
| Чистота кода ↔ операционная безопасность | Переименование endpoint выглядит аккуратнее в коде, но рискует инцидентом в проде; ADD многословен, но не ломает внешние контракты |
| Discoverability новой фичи ↔ стабильность старой | Новое имя делает фичу заметнее, но заставляет всех потребителей обновляться немедленно; ADD скрывает новое имя среди старых ссылок |

## Принцип

| Вариант | Действие | Риск |
|---------|----------|------|
| RENAME (анти-паттерн) | Переименовать исходный + добавить второй | Ломает прод: внешние клиенты, скрипты, кэшированные ссылки, прежние сессии |
| **ADD-not-RENAME** | Сохранить исходный + добавить новый параллельно | Migration ответственность — на стороне клиента, постепенный переход |

## Пример

При распаковке роли «Стратег» (DP.ROLE.012) на discovery (DP.ROLE.012-strategist) + planning (DP.ROLE.066-planner) на серверной стороне:

- ❌ Переименовать `run_strategist` → `run_discovery_strategist`, добавить `run_planner`.
- ✅ Сохранить `run_strategist` (как есть, частью зонтика), добавить `run_planner` параллельно.

## Применение

Паттерн применим к:
- MCP tools (`run_strategist` / `run_planner`)
- CLI subcommands
- REST endpoints
- SC-имена (DP.SC.011 не переименовывается даже после превращения в зонтик)
- Role-имена в каталогах

## Тест применимости

«Есть ли активные внешние ссылки на старое имя?» (клиенты, скрипты пилота, кэш, сессии). Да → ADD, не RENAME. Нет → можно RENAME без риска.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| «Переименовать сразу выглядит чище» | RENAME кажется более решительным и эстетичным в коде; недооценивается blast radius на внешних клиентах, скриптах, кэшах и предыдущих сессиях |
| «Новый метод/endpoint должен иметь правильное имя сразу» | Желание получить «правильную» архитектуру здесь и сейчас перевешивает сохранение существующего контракта; приводит к rename под видом улучшения |
| «Я обновил внутренние ссылки, значит всё в порядке» | Внимание ограничивается собственным кодом; забывают кэшированные ссылки, документацию, третьесторонних потребителей и сохранённые сессии пилотов |
| «Добавление лишней сущности — мусор» | ADD воспринимается как оставление tech debt, а не как явный backward-compat контракт; соблазн убрать старое имя до завершения миграции |

## Антипаттерн «связка распаковки и deprecation»

«Зачищаем legacy сразу, заодно с распаковкой» — соединение двух разных решений (распаковка vs deprecation) в один шаг = риск отказа без необходимости. Deprecation — отдельное решение со своим расписанием, после того как ADD прошло period soak.
