# DP.M.170: Router-роль как рычаг разделения «что вызвать» от «как вызвать»

## Проблема

Routing-логика встроена в каждый скилл → LLM обрабатывает детерминированные dispatch-решения → токены тратятся на reasoning там, где достаточно скрипта.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Экономия токенов на детерминированном dispatch ↔ гибкость LLM-суждения в неоднозначных случаях | Вынос routing-решения из скиллов убирает reasoning там, где достаточно скрипта, но экономический тест («Нужен ли LLM для этого dispatch?») удерживает LLM-Маршрутизатор для решений, требующих суждения — метод не обнуляет LLM, а концентрирует его в одной роли |
| Централизация routing-решения в одной роли ↔ простота самодостаточного скилла | Скилл со встроенной routing-логикой проще написать и не требует нового звена в цепочке, но размножает dispatch-решения по исполнителям; Router-роль собирает их в одну точку (Артефактор → Маршрутизатор → Исполнитель) ценой дополнительного звена и контракта |

## Метод

Выделить единую Router-роль (Маршрутизатор), которая принимает решение «кто исполнит» ДО передачи задачи исполнителю.

## Цепочка ролей

```
Артефактор (сырой запрос → оформленный РП)
→ Маршрутизатор (routing-решение: скрипт / агент / peer)
→ Исполнитель
```

## Экономический тест

> «Нужен ли LLM для этого dispatch?»
>
> - **Нет** → детерминированный скрипт (без LLM)
> - **Да** (неоднозначное решение, требует суждения) → LLM-Маршрутизатор

## Применимость

Любая система с несколькими типами исполнителей (скрипт / агент / peer / MCP-инструмент). Принцип: сначала выбор типа исполнения, потом передача.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| Сэкономленные токены затмевают стоимость нового звена | Внимание приковано к убранному из скиллов reasoning, а накладные расходы самого Маршрутизатора — отдельный вызов, отдельный контракт, новая точка отказа в цепочке Артефактор → Маршрутизатор → Исполнитель — в экономический расчёт не попадают |
| Ясные кейсы затмевают пограничную зону | Экономический тест проверяется на очевидных примерах («точно скрипт» / «точно суждение»), а неоднозначные dispatch-решения, где сам ответ «нужен ли LLM» требует суждения, остаются непомеченными и дрейфуют между скриптом и LLM от вызова к вызову |
