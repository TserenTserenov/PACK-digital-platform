# DP.METHOD.175 — Взаимозависимые изменения БД: наблюдаемый промежуток

## Определение

Два технически связанных изменения (Изменение A требует Изменение B для полной функциональности) деплоятся **раздельно** с наблюдаемым промежутком между ними. Переход ко второму изменению — только после явного подтверждения в журнале, что первое работает штатно.

## IPO

- **Вход:** два взаимозависимых изменения (A и B) к деплою
- **Процесс:** деплой A → ≥1 штатный цикл системы → проверка журнала → деплой B
- **Выход:** каждое изменение валидировано изолированно; журнал содержит явное подтверждение

## Свойства метода

1. **Изолированная диагностика:** если после деплоя A что-то сломалось — причина однозначно A, не смесь A+B.
2. **Machine-readable подтверждение:** переход к B требует явной строки в log-файле расчётчика («no anomalies in cycle X»), читаемой агентами без доступа к БД.
3. **Event-based gap:** промежуток — не «подождать час», а конкретный триггер (≥1 полный штатный цикл системы без аномалий).

## Когда применять

- Изменения БД с технической зависимостью (новая роль → row-level security; новая таблица → foreign key)
- Любые пары изменений инфраструктуры, где одновременный деплой скрывает диагностику
- Миграции данных + изменения схемы

## Тест

«Если после одновременного деплоя A+B что-то сломалось — сможем ли мы определить виновника без rollback обоих?»
- Нет → разнести во времени, применить метод
- Да (изменения независимы) → метод не нужен

## Инвариант

Подтверждение между шагами **обязано быть читаемым из файлов** (log, check-файл) без интерактивного доступа к БД — агент и пилот проверяют статус без подключения к runtime.

## Источник

WP-454: новая роль БД (Ф1) + row-level security из WP-417 (Ф2) технически связаны. Одновременный деплой скрывал диагностику. Решение: Ф1 → ≥1 ночной прогон без аномалий → Ф2.
