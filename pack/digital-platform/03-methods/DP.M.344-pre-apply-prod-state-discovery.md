# DP.M.344 — Pre-apply discovery: узнать фактический delta прода до «применения схемы»

## Решение

Перед любым «применить схему к проду» — сначала запросить фактическое состояние (`\dt schema.*`, `\d tablename`, `information_schema`), чтобы знать реальный delta: что действительно добавится. Не предполагать, что состояние прода совпадает с ожидаемым по документу.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Скорость применения ↔ время на discovery-запрос | Применить миграцию сразу по документу быстрее; запрос фактического состояния прода добавляет шаг перед действием |
| Доверие к плану/документу ↔ доверие к реальному состоянию базы | Документ описывает намерение на момент написания; фоновые процессы (bootstrap-функции воркеров) могли изменить прод уже после этого момента |
| Идемпотентность миграции ↔ знание delta заранее | Идемпотентная миграция технически безопасна при повторном применении; но без знания delta нельзя оценить объём реального изменения и риск для существующих данных |
| Единый предсказуемый прогон ↔ разное поведение на разных объектах | Применение «как по документу» подразумевает одинаковую обработку всех объектов схемы; реальный delta может требовать создать одни объекты и не трогать другие с данными |
| Уверенность после единичной проверки ↔ повторение discovery на каждый apply | Проверить состояние один раз кажется достаточным; но каждый новый «применить схему» требует своего discovery-шага, потому что фоновые компоненты продолжают менять прод |

## Почему документу верить нельзя

Фоновые компоненты с bootstrap-функциями (`ensure_schema()` воркера на каждый запуск) создают объекты схемы задолго до «официального» применения. Прецедент WP-417 Ф6.2: планировали «применить три таблицы к боевому Neon» — все три уже существовали с реальными данными (25 строк), потому что ночной сборщик создавал их с середины июня. Реальный delta свёлся к одной guard-функции с триггером неизменяемости.

## Шаги

1. Список ожидаемых объектов из документа/миграции.
2. Запрос фактического состояния прода (information_schema / метакоманды).
3. Вычислить delta: что существует (и с какими данными), что реально добавится.
4. Применять только delta; существующие объекты с данными — не пересоздавать.

## Тест

«Есть ли в системе другой компонент, который мог уже создать эти объекты?» Да → проверить состояние прода первым шагом.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| «Мы же сами писали этот документ — состояние прода нам известно» | Авторство плана создаёт ложную уверенность в актуальности знания о проде; между написанием и применением прошло время, за которое прод мог измениться |
| «Схема ещё не применялась официально — значит, объектов там нет» | Внимание фиксируется на «официальном» статусе применения, игнорируя возможность, что фоновые bootstrap-процессы создали объекты неофициально |
| «Информация из information_schema — это лишний шаг ради проверки очевидного» | Discovery-запрос воспринимается как формальность, а не как источник реальной информации, способной изменить план действий |
| «Раз миграция идемпотентна, можно не думать о delta» | Идемпотентность подменяет собой знание фактического delta; внимание смещается с «что реально добавится» на «применение технически безопасно» |
| «Прошлый apply прошёл гладко — этот тоже пройдёт» | Успешный precedent снижает бдительность к discovery-шагу для новой миграции, хотя состояние прода с прошлого раза уже изменилось |
