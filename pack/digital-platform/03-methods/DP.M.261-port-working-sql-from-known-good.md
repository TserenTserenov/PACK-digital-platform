# DP.M.261 Port working SQL из known-good источника

## Описание

Когда нужно восстановить функциональность (метрики/отчёт/aggregate query) над теми же таблицами, которые уже использует другой **рабочий** компонент продукта — порт SQL из known-good источника предпочтительнее реимплементации с нуля.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Скорость реимплементации ↔ точность known-good | Написать новый SQL быстро, но теряешь edge-cases; порт из working компонента точнее, но требует поиска и адаптации connection layer |
| Независимость ↔ coupling | Собственный SQL снижает зависимость, но создаёт расхождение в регрессиях; порт даёт симметричные регрессии, но неявная зависимость на эволюцию SQL |
| Краткость patch ↔ документированность | Короткий patch без anchor-комментария быстрее, но при schema change теряется источник и невозможно найти потребителей |

## IPO

**Вход:** нерабочий / отсутствующий код выборки над таблицами T1..Tn; рабочий компонент в проде использует те же таблицы для эквивалентных агрегатов.
**Процесс:**
1. `grep -r '<table_name>' <other-services>/` — найти working SQL.
2. Скопировать query + adapt connection layer (env vars, async/sync driver, DSN).
3. Добавить anchor-комментарий над портированным блоком: `# ported from <repo>/<file>:<line> 2026-05-30`.
4. Smoke-тест на проде / staging — сравнить вывод с baseline working компонента.

**Выход:** восстановленная функция использует тот же SQL, что working компонент → регрессии симметричны.

## Аргументация

1. **Acceptance уже есть** — query работает в проде, edge-cases вычищены историей инцидентов.
2. **Короткий patch** — копировать + адаптировать connection, не проектировать заново.
3. **Coupling-выигрыш** — две системы (источник + потребитель) читают идентичный SQL → регрессии симметричны.

## Минусы и митигация

Создаётся неявная зависимость на эволюцию SQL в обоих местах. Митигация: comment-якорь в порте + review при крупных schema changes.

## Тест применимости

«Есть ли в проде другой сервис, который читает те же таблицы для тех же агрегатов?» Да → попробовать порт сначала.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| «Напишу новый SQL — будет чище» | Практикующий недооценивает edge-case логику, уже вычищенную в working компоненте, и предпочитает реимплементацию порту |
| Игнорирование anchor-комментария | Порт без `# ported from ...` выполняется быстрее, но при schema change невозможно найти потребителей и источник |
| Поиск по своему сервису вместо всех сервисов | Ограничиваем поиск `<table_name>` только текущим repo, пропуская working query в других сервисах продукта |

## Антипаттерн

«У меня есть только pulse, напишу новый SQL» при существовании working query в боте → потеря edge-case логики, регрессии через 1-2 спринта.

## Применимо к

- Восстановление dashboards
- Новые отчёты по существующим event-streams
- Миграция metrics между сервисами
