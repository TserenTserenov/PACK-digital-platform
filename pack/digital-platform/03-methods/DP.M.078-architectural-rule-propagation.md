# DP.M.078 — Многоточечная propagation нового архитектурного правила

## Описание

Метод введения нового **блокирующего** архитектурного правила (Pack-as-SoT, type-strict, security-блокер, новый верификатор). Зафиксировать правило «где-то одном» недостаточно — оно либо не enforce'ится, либо проявляется только в части кейсов. Минимальный набор обязательных точек enforcement — **4**. Пропуск любой точки = отдельный failure-mode.

Не применяется к: bugfix без изменения внешнего поведения, рефакторинг без функциональных изменений, экспериментальные правила «на одну проверку».

## Входы

- Формулировка нового архитектурного правила (что запрещено / что обязательно)
- Тип правила (`structural` priority ≤5 / `behavioural` priority 6+)
- Сценарии применимости (когда срабатывает)

## Выходы

- Запись правила в 4 точках enforcement (см. Алгоритм)
- Propagation checklist с отметкой каждой точки
- Возможно: migration window (flag default WARN → FAIL) для (2) и (3)

## Алгоритм

### Точка 1 — Метод/процесс (formalization)

Создать спецификацию «как делать» в формате-носителе:
- Формат: `PD.FORM.NNN`, `METHOD.NNN`, `DP.M.NNN`, etc.
- Содержание: новая проверка как отдельный этап с входом, действием, выходом
- Без точки 1 — нет онбординг-материала, правило умирает с автором

### Точка 2 — Чек-лист/валидатор (mechanical check)

Добавить правило в валидатор/чек-лист с явным severity:
- Default: `FAIL` (блокирует commit/merge)
- Миграционный режим: флаг `--strict-X` default `WARN` с дедлайном перехода в FAIL
- Без точки 2 — правило существует «на бумаге», не enforce'ится

### Точка 3 — CI/CD инвариант (pipeline gate)

Зафиксировать gate в CI/CD pipeline:
- Формулировка: «no merges without check-N»
- Локальная проверка обходится `--no-verify`/`git push --force`/амнезией; CI — нет
- Без точки 3 — правило обходимо локально

### Точка 4 — Реестр правил агента (proactive recall)

Добавить entry в `PACK-agent-rules/rules/AR.NNN.md` с frontmatter:
- `priority` (структурное 1-5, поведенческое 6-10)
- `triggers` (когда правило применимо — фразы/контексты)
- `hook` (как агент его поднимает в контекст)
- Без точки 4 — агент молчит, правило вспоминается только когда упирается в (2) или (3)

### Финал

Propagation checklist с отметкой 4 точек. Commit-сообщение содержит ссылки на все 4 артефакта (например: `feat: introduce <rule> propagation — PD.FORM.103 / CHECKLIST-v4-lint / CD-PIPELINE invariant / AR.206`).

## Failure-modes (если точка пропущена)

| Пропущенная точка | Что ломается |
|-------------------|--------------|
| (1) Метод/процесс | Нет онбординг-материала; правило умирает с автором |
| (2) Чек-лист/валидатор | Правило не enforce'ится — существует только в спецификации |
| (3) CI/CD инвариант | Обходимо локально через `--no-verify` или забывается |
| (4) Реестр правил агента | Агент молчит — не поднимает правило проактивно |

## Тест применимости

«Вводится новое блокирующее правило, не bugfix?» Да → пройти 4 точки.

**Контр-pattern:** «запишу в [одно место], применю по мере надобности» — правило умирает в течение 1-2 циклов разработки.
