# DP.M.439 — Сравнение веток по patch-id, не по числу уникальных SHA

## Проблема
Наивный подсчёт «сколько коммитов есть в одной ветке и нет в другой» по SHA систематически завышает расхождение между pilot/production ветками, когда практикуется cherry-pick/rebase-перенос: у каждой стороны появляются свои SHA для семантически одного и того же патча. Живой прогон показал 21 SHA-уникальный коммит с одной стороны и 22 с другой при всего ОДНОМ реальном отличии по существу.

## IPO
- **Вход:** две ветки (pilot/production и аналоги), обменивающиеся патчами через cherry-pick/ручной перенос, а не только через общий merge base
- **Процесс:** `git cherry -v` сравнивает по patch-id (хэш нормализованного диффа, не хэш коммита) — схлопывает перенесённые патчи в «уже есть на другой стороне» независимо от SHA. Дополнительно: пометка дельт по чувствительным путям/словам (privacy/auth/gdpr/payment), явная фиксация уже одобренных обходов (`[incident-ok]`/`[cherry-pick-ok]`), append-only журнал соответствий с `first_seen_unmatched_at`, переживающим повторные запуски, алерт только на дельту старше 24ч
- **Выход:** метрика реального расхождения = количество уникальных СОДЕРЖАНИЙ патча, не количество уникальных commit SHA

## Применимо
Две ветки/копии одного дерева, обменивающиеся патчами через cherry-pick или ручной перенос (не через общий merge base) — подсчёт по SHA систематически завышает разрыв на порядок именно там, где перенос практикуется штатно.

## Связи
