# DP.M.430 — Распознавать «республикацию» сравнением итогового содержимого, не патча

## Определение

Скрипту, которому нужно распознать «этот коммит — просто республикация уже применённого в другом месте» (проверка на no-op/эквивалентность патча), нельзя доверять сравнению сырого патча с эталоном: его представление зависит от контекста. Сравнивается итоговое состояние в пределах договора публикации: пути, типы узлов, содержимое и учитываемые права. Для Git сюда входит executable-mode; одинаковые байты при изменённом режиме исполнения ещё не означают отсутствие изменения.

Перед переносом коммита между разошедшимися копиями сравнить его итоговое изменение со свежим опубликованным состоянием в изолированной копии. Совпадение или расхождение номеров секций не заменяет сравнения содержимого. Исключать различия меток можно только по явно заданному правилу нормализации. Дополнительная фраза или другое содержательное изменение рассматриваются отдельно и не объявляются дублем автоматически.

## Отдельная находка: «простое» не значит «безопасное»

Сама функция выглядела «псевдо-простой» (короткий shell-сниппет), но шесть независимых раундов ревью нашли по реальному дефекту в каждом: сохранение прав доступа (mode), проброс exit status, обработка смены типа (файл→symlink), glob-инъекция через неэкранированный pathspec, недостаточное различение ошибок, инъекция через кавычку в обработчике trap.

Для скриптов, меняющих файловую систему, отдельно проверить ссылки в цепочке пути, чувствительность к регистру, коллизии с существующими узлами, состояние блокировок без PID и сбои после частичного изменения. Ожидаемое поведение задаётся для каждого класса заранее. В исходном дополнительном разборе переход отслеживаемый файл↔директория разрешался при предусмотренных условиях; он не обосновывает общий запрет таких переходов. Число раундов ревью само по себе не подтверждает покрытие: каждый раунд оставляет проверяемый результат по рассмотренным условиям.

## Переносимый принцип

1. Проверка идемпотентности/no-op должна идти по конечному состоянию (пути, типы, содержимое, учитываемые права), а не по синтаксическому диффу.
2. Короткие shell-сниппеты, трогающие git plumbing, trap или pathspec, заслуживают нескольких состязательных раундов ревью — «простое» не значит «безопасное».

## Тест обнаружения

«Скрипт определяет no-op/республикацию сравнением сырого патча/диффа коммита?» Да → сравнить конечное состояние по договору публикации. Контрпример: изменение только executable-mode при прежних байтах должно оставаться реальным изменением. Отдельно проверяется смена типа узла.

Дополнительная проверка использует два заранее подготовленных состояния: уже присутствующее содержание с допустимой перенумерацией распознаётся как повтор, реальное добавление сохраняется для рассмотрения. Ожидаемое решение задаётся независимо от сравнивающего скрипта. В синтетических каталогах сравниваются ожидаемые состояния до/после и сообщённый исход, включая отказ после частичного изменения.

## Forces

- Быстрое распознавание повтора ↔ полнота сравнения: нормализация допустима только для заранее определённых различий представления, иначе она скрывает новое содержание.
- Простота короткого скрипта ↔ число состояний файловой системы: проверять нужные классы переходов, не использовать число раундов как замену покрытия.

## Bias-Annotation

- Привязка к меткам и номерам секций смещает решение в сторону ложного повтора или ложного нового изменения; эталон — итоговое содержание.
- Впечатление простоты shell-фрагмента уменьшает внимание к типам узлов, ссылкам и частичному отказу; эти случаи задаются до проверки.

## Применимо к
Любой скрипт межмашинной/межрепозиторной публикации, определяющий «нужно ли вообще коммитить/пушить это изменение».
