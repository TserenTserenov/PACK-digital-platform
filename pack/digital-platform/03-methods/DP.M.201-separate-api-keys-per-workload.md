# DP.M.201: Separate API Keys per Workload

## Назначение

Изолировать rate-limit квоты между независимыми workload-ами через отдельные API credentials вместо reactive spend-alert мониторинга.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Изоляция квот между workload ↔ операционная сложность ключей | Отдельные ключи решают cross-workload exhaust, но каждый новый ключ требует rotation, fallback-логики, раздельного billing'а и мониторинга — избыточная изоляция может стать дороже инцидента |
| Proactive защита (архитектурная превентивность) ↔ reactive spend-alert (лёгкость настройки) | Изоляция предотвращает исчерпание квоты заранее, но spend-alert настраивается за минуты и выглядит «достаточным» до первого инцидента; метод балансирует лёгкость мониторинга с реальной защитой |
| Безопасность (blast radius одного ключа) ↔ удобство единого credential | Меньше ключей — проще ротация и меньше поверхность ошибки, но один shared key превращает любой runaway workload в единую точку отказа для всех потребителей |

## Входы

- Несколько процессов, использующих один внешний rate-limited API
- Симптом: фоновый runner истощает квоту интерактивных сессий (или наоборот)

## Шаги

1. Идентифицировать workload-ы с конкурирующим потреблением квоты
2. Создать отдельный workspace/проект у провайдера для каждого workload
3. Ввести переменные `API_KEY_{WORKLOAD}` (напр. `ANTHROPIC_API_KEY_MARATHON`, `ANTHROPIC_API_KEY_SESSION`) с fallback к дефолтному ключу
4. Spend-мониторинг оставить как вторичный инструмент (не замена изоляции)

## Выходы

- Квоты изолированы: один workload не блокирует другой
- Раздельный billing и мониторинг по workload

## Применимость

Любые rate-limited API: Anthropic, OpenAI, Google, Stripe, Twilio и др.

**Тест:** «Могут ли два независимых процесса исчерпать квоту друг друга?» Да → разделить ключи.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| Spend-alert кажется «достаточной защитой» | Практикующий инвестирует в настройку алертов, потому что они видимы и быстро реализуемы, и откладывает или ослабляет реальную изоляцию ключей |
| Создание отдельных ключей без устранения fallback | Внимание уходит на формальное наличие `API_KEY_{WORKLOAD}`, но fallback на дефолтный ключ оставляет shared путь и сохраняет cross-workload риск |
| Фокус на billing-visibility, а не на quota-isolation | Практикующий разделяет ключи, чтобы видеть расходы по workload, но при этом не проверяет, что provider-level квота тоже изолирована или что алармы настроены на уровне каждого ключа |

## Антипаттерн

Spend-alert monitoring как замена изоляции: алертит постфактум (квота уже исчерпана), не изолирует заранее. Парсинг dashboard = хрупкое решение.
