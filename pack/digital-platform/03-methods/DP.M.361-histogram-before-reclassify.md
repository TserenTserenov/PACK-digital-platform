# DP.M.361 — Снять распределение (histogram) до изменения порога/категории мониторинга

## Описание

Метод предотвращает преждевременную оптимизацию мониторинга: изменение порога алерта или переклассификацию команды/эндпоинта в другую категорию делать только после сбора распределения латентности, а не по единичному алерту.

**Принцип:** единичный алерт = выборка из 1. По одному инциденту нельзя отличить системный мисматч (команда в неверной категории порогов) от транзиентного шума (холодный pooler после ночного простоя).

## Вход → Действие → Выход

- **Вход:** сигнал «команда/эндпоинт срабатывает алертом» (например, `/train` в категории `nav` с порогом red 3000ms, но реально делает несколько запросов к БД).
- **Действие:**
  1. Собрать распределение латентности за N дней (рекомендуется ≥7).
  2. Вычислить P50/P90/P99 по команде/эндпоинту.
  3. Отделить транзиентные причины (холодный старт, разовый сбой) от системных (неверная категория/порог).
  4. Менять порог/категорию только при системном паттерне.
- **Выход:** обоснованное решение reclassify/изменить-порог (или «оставить, причина транзиентная»), подкреплённое распределением.

## Тест применимости

«Есть ли у нас распределение (P50/P90/P99 за N дней), или только один инцидент?»
- Только инцидент → собрать histogram, решение отложить.
- Есть распределение → решение обосновано данными.

## Когда использовать

- Утренние/единичные алерты латентности (вероятный холодный pooler, не системный баг).
- Предложение переклассифицировать команду в другую категорию порогов.
- Любое изменение threshold/SLO по единичному наблюдению.
