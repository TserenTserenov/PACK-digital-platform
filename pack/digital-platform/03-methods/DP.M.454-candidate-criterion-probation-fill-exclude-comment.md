# DP.M.454 — Онбординг нового кандидатского критерия рубрики: заполнять всегда, исключать из вердикта, комментировать худшую оценку

## Проблема

Живой прогон рубрики приёмки на реальных материалах вскрыл два расхождения, не покрытых существующими шкалами (агент оценивал мягче пилота; старые шкалы не ловили «шаблонность» текста) — родились два новых критерия-кандидата. Назначить им порог «на глаз» без калибровки нарушает уже принятый для первых пяти шкал принцип (пороги — решение пилота по данным, не побочный продукт одной выборки). Но оставить критерий «просто наблюдением» без обязательного заполнения — значит, что уже подтверждённый живым разбором дефект перестаёт быть виден вообще: следующий оценщик пропустит необязательную шкалу, и сигнал потеряется ровно тогда, когда он появился.

## IPO

| Элемент | Описание |
|---|---|
| **Вход** | Действующая рубрика с откалиброванными критериями + вновь найденный, ещё не откалиброванный кандидат-критерий |
| **Обработка** | Три независимых переключателя одновременно: обязательность заполнения, участие в итоговом вердикте, требование комментария при экстремальной оценке |
| **Выход** | Кандидат-критерий заполняется на каждой оценке, не влияет на годно/не годно, но при самой низкой оценке оставляет конкретную запись для будущей калибровки |

## Приём

1. **Обязательное заполнение.** Кандидат-критерий заполняется на КАЖДОЙ оценке наравне с откалиброванными — не пропускается как необязательный. Данные для будущей калибровки накапливаются с первого дня существования критерия.
2. **Исключение из вердикта.** Кандидат-критерий НЕ участвует в определении итогового годно/не годно, пока порог не откалиброван на достаточном числе материалов (решение пилота, не автоматический счётчик). Порог «на глаз» на одной выборке не назначается.
3. **Обязательный комментарий при худшей оценке.** Если по кандидат-критерию ставится самая низкая оценка — рядом обязательна конкретная запись, что именно поправить. Это не даёт наблюдению без порога превратиться в наблюдение без последствий.

## Правило области

Применяется в момент, когда живой прогон системы оценки на реальных материалах вскрывает дефект, не покрытый существующими критериями — до того, как для нового критерия есть достаточно данных для порога. Три переключателя разрешают одновременно два конкурирующих риска: полное исключение критерия до калибровки теряет данные, которые могли бы ускорить калибровку; немедленное включение с порогом «на глаз» рискует ложным вердиктом на непроверенном пороге.

## Тест применимости

«Найден ли живым прогоном системы оценки дефект, для которого нет существующего критерия, и достаточно ли уже данных, чтобы прямо сейчас назначить порог?» Дефект есть, данных для порога недостаточно → три переключателя этого метода. Данных достаточно → калибровать порог сразу, не держать в «кандидатском» статусе дольше необходимого.

## Отличие от смежного

- **DP.M.005 §9-10 (ArchGate: L2-характеристики «на обкатке»)** — ближайший прецедент того же общего метода на другом субстрате (архитектурная характеристика, не критерий контентной рубрики): «характеристика на обкатке = информативная [не блокирует], после ≥5 оценок → решение о переводе в блокирующую». Отличия: (а) там триггер условный (по затронутым компонентам), здесь — безусловное заполнение на каждой оценке; (б) там продвижение — счётчик оценок, здесь — калибровочные объекты + отдельное решение пилота о порогах; (в) здесь добавлен ингредиент, которого в §9-10 нет — обязательный комментарий-ремедиация именно при самой низкой оценке.
- **DP.METHOD.218 (CONDITIONAL надёжнее до калибровки порогов)** — про то, как ЧИТАТЬ вердикт уже существующего, но неоткалиброванного порога. Этот метод — про то, как ДОБАВИТЬ новый критерий в живую систему ДО того, как у него вообще есть порог.
- **DP.METHOD.252 (Hypotheses Log Weekly LPF Calibration)** — систематический учёт гипотез о системе с еженедельной сверкой; смежная дисциплина «не доверять непроверенному», но про гипотезы о системе в целом на регулярном ретро, не про добавление одного критерия в рубрику в момент обнаружения дефекта.
- **DP.MAP.003 §В (`rubric_history`, запись 2026-09-13, state: v1.1)** — конкретный экземпляр применения этого метода к RUB.GUIDE-OUTPUT-01; этот метод — обобщённая, переносимая на любую рубрику процедура, извлечённая из того же эпизода.
- **DP.D.314 (этот же отчёт, кандидат #1)** — различение ПОЧЕМУ один критерий вообще не должен попадать на градиентную шкалу (бинарная природа риска); этот метод — ЧТО ДЕЛАТЬ с критерием, который на шкалу попасть МОЖЕТ, но ещё не готов участвовать в вердикте (вопрос калибровки, не природы критерия).

## Применимость

Любая система оценки/рубрика с процессом добавления новых критериев по мере обнаружения дефектов в живой эксплуатации: приёмочные рубрики AI-генерируемого контента, LLM-judge критерии, ArchGate L2-доменные расширения (DP.M.005 §10 — тот же жест «заполнять и наблюдать до решения о статусе», другой субстрат).
