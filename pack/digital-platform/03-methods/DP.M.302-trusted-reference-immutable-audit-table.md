# DP.M.302 — Trusted-reference хранилище: immutable контракт + audit-таблица рядом

## 1. Проблема

Когда обещание сервиса — «trusted reference» (одна каноническая запись на сущность, фиксирующая факт), нужно гарантировать: финальная запись не изменяется после финализации, а сырьё расчёта сохраняется для аудита вне контракта.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Простота одной таблицы ↔ гарантия immutable | Одна mutable-таблица проще в схеме и запросах, но не может гарантировать «финальная запись не изменится» — только дисциплина разработчика, которая рано или поздно нарушается |
| Полнота аудита ↔ чистота контракта | Хранить сырьё расчёта нужно для верификации, но включение его в контрактную таблицу размывает обещание «одна каноническая запись»; разделение на две таблицы держит контракт узким |
| App-level защита ↔ DB-trigger защита | Проверка в `write_panel()` достаточна для штатного пути, но не защищает от прямого UPDATE в БД; двойная защита дороже в поддержке, но закрывает оба канала записи |
| Скорость записи воркера ↔ строгость финальности | Отказ при попытке перезаписи финальной записи замедляет воркер при ошибках расчёта (нужен новый цикл), но именно это не даёт тихо испортить историю |

## 2. Паттерн

Хранилище разбивается на **две таблицы**:

| Таблица | Роль | Контракт |
|---------|------|----------|
| `<entity>_daily` | Контрактная (trusted reference) | `предварительная` → `финальная`; финальная immutable (двойная защита) |
| `<entity>_audit` | Аудитная (вне контракта) | Сырьё расчёта; только для верификации/отладки |

**Доступ потребителей:** только `read_panel(<entity>)` — без side effects.
**Запись:** только воркер через `write_panel(<entity>)`, который отказывает при перезаписи финальной записи.

## 3. Двойная защита финальности

1. **App-level:** `write_panel()` проверяет `status == 'финальная'` → исключение.
2. **DB-trigger:** `BEFORE UPDATE` отклоняет изменение строки с `status = 'финальная'` на уровне БД.

## 4. Различение от CQRS

| CQRS | Этот паттерн |
|------|-------------|
| Read model из event log | Read model = контракт (финальная запись) |
| Event store = воспроизведение | Audit = «follow-the-money», не event sourcing |
| Write ≠ read | Write path — воркер; read path — read_panel |

## 5. Применимость

- Ночные сводки, дайджесты, сертификаты
- Материализованные факты с обязательной историей
- Любой вывод, который «не должен течь» после финализации

## 6. Антипаттерн

Одна mutable таблица → финальный результат перезаписывается рефакторингом → ретроспектива ненадёжна.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| «У нас нет времени на DB-trigger, app-level проверки хватит» | Практикующий считает достаточной защиту в коде и откладывает БД-уровень «на потом»; в проде появляется путь прямого UPDATE (миграция, ручной фикс), который обходит app-level |
| «Аудитная таблица — это на будущее, сейчас не нужна» | Внимание фокусируется на контрактной таблице как единственно важной; audit-таблица создаётся позже, когда уже нет истории для ретроспективы первых записей |
| «Read model = контракт, значит это CQRS» | Практикующий примеряет знакомый паттерн CQRS целиком, упускает, что здесь audit — не event store, и read path не воспроизводим из event log |
| «Раз таблица называется `_daily`, статус всегда обновляется по расписанию» | Внимание уходит от того, что переход `предварительная` → `финальная` — это отдельное бизнес-событие, а не побочный эффект cron-задачи |
