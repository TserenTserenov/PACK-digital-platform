# DP.M.213 UPSERT + xmax=0: атомарное определение INSERT vs UPDATE

## Описание

PostgreSQL idiom для атомарного определения того, была ли строка только что создана (INSERT) или уже существовала (UPDATE), за один roundtrip без гонки состояний (TOCTOU).

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Атомарность определения INSERT vs UPDATE ↔ переносимость SQL | `xmax = 0` даёт корректный ответ в одном roundtrip, но привязывает решение к PostgreSQL MVCC; переход на другую СУБД требует другого механизма |
| Простота одного запроса ↔ явная двухфазная логика | Один `RETURNING (xmax = 0) AS is_new` элегантен, но скрывает семантику системного поля и делает поведение менее очевидным для читателя кода |
| Надёжность против гонки состояний ↔ зависимость от внутренних деталей PostgreSQL | Корректность метода опирается на внутреннее поведение `xmax`; практикующий должен понимать MVCC, иначе решение выглядит как «магическая» проверка |

## IPO

**Вход:** данные для upsert + уникальный ключ конфликта
**Процесс:** `INSERT ... ON CONFLICT DO UPDATE SET ... RETURNING (xmax = 0) AS is_new`
**Выход:** `bool` — True = INSERT (новая строка), False = UPDATE (строка существовала)

## Механизм

`xmax = 0` в PostgreSQL означает, что строка не имеет активной блокирующей транзакции и была только что INSERT, а не UPDATE. После UPDATE xmax содержит ID транзакции, которая изменила строку.

## Тест применимости

«Нужно ли знать INSERT vs UPDATE без гонки (TOCTOU)?» — Да → применять DP.M.213.

## Пример (Python/asyncpg)

```sql
INSERT INTO checkins (user_id, date, data)
VALUES ($1, $2, $3)
ON CONFLICT (user_id, date) DO UPDATE
  SET data = EXCLUDED.data
RETURNING (xmax = 0) AS is_new;
```

## Применение

- Идемпотентный чек-ин (marathon, daily activity)
- Дедупликация webhook-событий
- Любой сценарий: «нужно знать, первый ли раз»

## Bias-Annotation

_Куда систематически съезжает внимание практикующего. Epistemic stage карточки — `empirical`._

| Bias | Direction of distortion |
|------|--------------------------|
| Увлечение «один запрос» | Практикующий применяет идиому `xmax = 0` даже там, где бизнес-логика требует явного конечного автомата или где СУБД не поддерживает `xmax`; внимание смещается к элегантности решения, а не к его области применимости |
| Игнорирование транзакционного контекста | Фокус на `RETURNING` отвлекает от анализа одновременных транзакций, уровней изоляции и видимости строк; поведение `xmax` интерпретируется упрощённо |
| Переоценка универсальности | Идиома воспринимается как переносимый SQL-паттерн, хотя она специфична для PostgreSQL; при миграции на другую базу проверка INSERT/UPDATE может молча изменить семантику |
