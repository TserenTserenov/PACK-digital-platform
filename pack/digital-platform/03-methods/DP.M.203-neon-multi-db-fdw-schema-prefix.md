# DP.M.203 — Neon multi-DB FDW cross-schema prefix rules

## Метод

Правила именования схем при кросс-DB запросах в Neon multi-DB архитектуре с FDW (DP.ARCH.004):

| Контекст запроса | Правильный префикс |
|---|---|
| Внутри БД-хозяина | `public.` или без префикса |
| Из другой БД через FDW | `_foreign_<source_db>.имя_таблицы` |
| Никогда | `<source_db>.` напрямую |

Схема с именем `<source_db>` не создаётся автоматически в FDW-хосте. FDW-схема всегда имеет префикс `_foreign_`.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Портативность SQL-запроса между БД ↔ явность cross-DB идентификатора | Запрос без префикса читается естественно внутри хозяйской БД, но при переносе в FDW-контекст ломается; `_foreign_`-префикс делает зависимость видимой, но ухудшает краткость SQL |
| Безопасность миграции (pre-apply gate) ↔ скорость разработки | Gate ловит отсутствие FDW-схем до деплоя, но добавляет шаг, который хочется пропустить, когда запрос «уже работает локально» |
| Консистентность repo ↔ production-reality | Жёсткое требование префикса в репозитории предотвращает post-deploy drift, но production может уже содержать неформальные правки; приведение их в repo требует миграции и аудита |

## Pre-apply gate

Перед запуском миграции с кросс-DB join'ами:

```sql
-- В target DB
\dn
\dt _foreign_*.*
```

Проверить наличие нужных FDW-схем. Если `_foreign_<source_db>` не найден → FDW не настроен или имеет другое имя.

## Паттерн дрейфа

SQL-файл в репо написан с `reference.` (неверно), в production функция использует `_foreign_reference.` (верно, но исправлено post-deploy неформально). Это создаёт undocumented correction, невидимую при code review.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| Привычка к `source_db.table` в SQL | Практикующий пишет запросы в привычной нотации без префикса, потому что так «естественно читается», и не доходит до проверки FDW-контракта |
| Доверие к production-правкам post-deploy | Неформальное исправление в production кажется быстрым решением и отвлекает внимание от необходимости привести repo в соответствие; со временем накапливается незадокументированный drift |
| Пропуск pre-apply gate при «очевидной» корректности | Запрос выполняется в локальной БД, и практикующий пренебрегает проверкой `\dn _foreign_*`, недооценивая, что FDW-схема может отсутствовать в target БД |
