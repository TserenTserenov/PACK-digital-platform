# DP.M.333 — Матрица режимов отказа по типам событий

## Описание

Режим отказа (fail-closed / fail-open / fail-queue) назначается per-тип события, а не единым дефолтом для всей системы. Событие, фиксирующее волю пользователя (согласие, подпись), при инфра-сбое обязано приниматься в очередь и дозаписываться — блокировка потеряет юридически значимое действие. Событие-привилегия (расширение доступа) может честно ждать.

«Нужна отдельная таблица режимов отказа по типам состояний — для согласия: принять и дозаписать позже.»

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Простота единого дефолта ↔ корректность per-тип | Один режим для всей системы легче реализовать и объяснить, но игнорирует разницу между «можно потерять» и «нельзя потерять» |
| Скорость разработки gateway ↔ юридическая безопасность | Быстрее сделать один fail-strategy сразу; классификация типов событий требует времени до кодирования |
| Единообразие инфраструктуры ↔ разнородность обещаний потребителю | Инфраслой хочет одинаковый путь отказа для всех событий; Service Clause обещает разное для согласия и для метрики |
| Экономия очереди (fail-open) ↔ полнота записи (fail-queue) | Durable-очередь для каждого типа дороже по ресурсам, чем drop; но drop юридически значимого события — потеря воли пользователя |
| Ранняя фиксация таблицы ↔ гибкость поздней доработки | Таблица режимов ДО реализации фиксирует решение рано, когда типы событий ещё могут меняться |

## Algorithm

### Step 1: Классифицировать типы событий по criticality

| Тип | Пример | Обещание потребителю |
|-----|--------|---------------------|
| Юридически значимое | Согласие пользователя, подпись | «Зафиксировано при возникновении» |
| Бизнес-критическое | Платёж, milestone | «Зафиксировано в течение X сек» |
| Информационное | Аналитика, метрики | «Зафиксировано eventually» |
| Привилегия | Выдача доступа, роли | «Зафиксировано только при успехе gateway» |

### Step 2: Назначить режим отказа per-тип

| Тип | Режим при сбое gateway |
|-----|------------------------|
| Юридически значимое | fail-queue: принять + durable очередь + дозапись |
| Бизнес-критическое | fail-queue с TTL: очередь не более X мин, потом alert |
| Информационное | fail-open: drop + metric |
| Привилегия | fail-closed: не принимать до восстановления |

### Step 3: Зафиксировать таблицу как артефакт ДО реализации

Таблица режимов создаётся в архитектурном документе или Service Clause ДО написания кода. При изменении типа события — пересмотреть режим явно.

## When to Use

- Проектирование систем записи событий с разнородными типами
- ArchGate для систем с юридически значимыми данными (consent, signature, payment)
- Любой gateway с единым fail-strategy для всех типов

## Тест применимости

«Одна недоступность gateway блокирует в том числе согласие пользователя?» Да → нужна матрица. «Каждый тип события имеет явный режим отказа в документе?» Нет → матрица отсутствует, единый дефолт опасен.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| «Gateway один, значит и стратегия отказа одна» | Внимание фиксируется на инфраструктурном слое (единый механизм), а не на разнородности бизнес-обещаний за ним |
| «Согласие — просто ещё одна запись в базе» | Юридическая значимость события недооценивается, пока явно не спросить «что теряет пользователь при потере этой записи» |
| «Разберём режимы отказа, когда столкнёмся со сбоем» | Классификация откладывается до инцидента вместо design-time решения; постфактум решение принимается в панике, не по методу |
| «Информационные события тоже жалко терять» | Симметричное внимание ко всем типам событий вместо явного ранжирования по criticality; fail-queue применяется избыточно широко |
| «Таблица создана один раз — этого достаточно» | Внимание не возвращается к таблице при добавлении нового типа события; новый тип наследует дефолт вместо явного назначения режима |
