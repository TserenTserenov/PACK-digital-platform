# DP.M.331 — Журнал действий агента — дозаписываемый sidecar-файл

## Описание

Машиночитаемый audit-trail агента — это отдельный append-only файл (`audit-<id>.jsonl`), расположенный рядом с файлами сессии, а не встроенный в человекочитаемый тред (отчёт/transcript). Журнал записывает события, которые не попадают в тред: вызовы инструментов, чтение и запись файлов, git-коммиты.

## Forces

| Force | Tension |
|-------|---------|
| Единый тред как источник правды ↔ разделение читаемого и машинного слоя | Хранить всё в одном report.md проще для пилота, но структурированные события (tool calls) плохо парсятся из нарратива — sidecar разделяет аудитории ценой лишнего файла |
| Дешёвое ведение в памяти ↔ долговечность сохранённой истории | Запись в памяти пропадает с процессом; для восстановления файлов после сброса ветки нужен коммит, достижимый через сохраняемую ссылку или подтверждённую публикацию |
| Полнота записи каждого действия ↔ объём и шум в jsonl | Записывать каждый tool call даёт полную реконструируемость, но раздувает файл событиями низкой ценности — метод предполагает фильтр «только то, чего нет в треде» |
| Ограничение раскрытия ↔ полезность структурированных данных | Контракт разрешённых значений сохраняет нужные для аудита факты; имя поля само по себе не позволяет считать значение безопасным |

## Algorithm

### Step 1: Создать sidecar-файл при открытии сессии

Создать `sessions/<date>/<session-id>/audit-<session-id>.jsonl` рядом с `report.md` и `transcript.md`. Файл создаётся пустым, дозаписывается в ходе работы.

### Step 2: Записывать только действия, отсутствующие в треде

```jsonl
{"ts": "2026-06-21T10:05:00Z", "event": "tool_call", "tool": "Read", "path_category": "wp-context", "path_match": true}
{"ts": "2026-06-21T10:05:03Z", "event": "tool_call", "tool": "Edit", "path_category": "wp-context", "path_match": true}
{"ts": "2026-06-21T10:07:00Z", "event": "commit", "sha": "a7ea6eb4", "reason_code": "wp-context-update"}
```

Тред (report.md) содержит нарратив и решения. Sidecar содержит машиночитаемую хронологию действий.

### Step 3: Включить sidecar в коммит хода

```bash
git add sessions/<date>/<session-id>/audit-<session-id>.jsonl
git commit -m "step(wp-NNN): <описание>"
```

Локальный коммит фиксирует содержимое, но сам по себе не гарантирует его сохранение в рабочей ветке после `git reset --hard origin/main`. До сброса коммит должен оставаться достижимым через сохраняемую ссылку или подтверждённую публикацию. Восстановление по reflog зависит от срока хранения и очистки объектов, поэтому не заменяет эту гарантию. Проверка восстановления читает ожидаемый журнал из сохранённой истории после синтетического сброса ветки.

### Step 4: Проверять происхождение значений и контракт вывода

Безопасность поля определяется происхождением значения и контрактом журнала, а не названием поля. Путь может включать пользовательский заголовок, а reason — цитату; их нельзя безусловно считать безопасными идентификаторами. Даже значение подходящего формата допускается только из предусмотренного контрактом источника.

Для журнала с запретом исходного текста отдельный сериализатор принимает явную схему разрешённых полей и значений. Причина представляется закрытым кодом; конкретные пути сравниваются до журналирования, в журнал передаются разрешённая категория и результат сравнения. Неизвестные поля и свободный текст ошибок не копируются. Иной контракт может разрешать конкретные значения после проверки происхождения и прав доступа, но универсального исключения для всех путей нет.

Отсутствие совпадений длиной 12 символов и короткий обычный хеш пути не доказывают запрет исходного текста. Проверка подставляет короткие, длинные, Unicode- и экранированные строки в reason, path и неизвестные вложенные поля, затем сравнивает полный выход с независимым разрешённым объектом. В матрицу включаются ошибочные ветви и все точки записи. Само наличие такой схемы в проекте не является доказательством её выполнения реализацией.

## When to use

- При проектировании audit-trail для агентских сессий, требующих воспроизводимости и постмортема
- Когда нужно восстановить хронологию действий агента после `git reset --hard` или инцидента
- Когда тред сессии читается пилотом, но машинная обработка (паттерн-майнинг, replay) требует структурированных данных

## Тест применимости

«Может ли хронология действий агента потребоваться для воспроизведения после hard reset?»
- Да → sidecar включить в коммит и обеспечить сохранность ссылки на него по договору восстановления
- Нет → можно оставить in-memory или не вести

## Отличие от DP.ROLE.047 (Trace Recorder)

DP.ROLE.047 записывает **рассуждения** LLM (гипотезы, выбор, обоснование) — что агент думает. DP.M.331 записывает **действия** агента (инструменты, файлы, коммиты) — что агент делает. Первое — semantic trace, второе — operational audit trail.

## Bias-Annotation

| Bias | Direction of distortion |
|------|--------------------------|
| «Тред и так всё содержит» | Внимание при проектировании сессии останавливается на нарративном отчёте, недооценивая, сколько машиночитаемых событий (tool calls, файловые операции) в него не попадает |
| «Закоммичу sidecar в конце сессии» | Откладывание `git add` до финала создаёт окно, в котором `git reset --hard` или сбой уничтожает журнал раньше, чем он попал в git-историю |
| «Это же просто лог, PII там не бывает» | Названия path/reason или формат идентификатора создают ложное ощущение безопасности; пользовательский текст и ошибки могут попасть в значения структурированных полей |
| «Раз пишем действия — рассуждения тоже стоит сюда» | Смешение operational audit trail (что делал) с semantic trace (что думал) в одном файле — граница с DP.ROLE.047 стирается при поспешном проектировании |
