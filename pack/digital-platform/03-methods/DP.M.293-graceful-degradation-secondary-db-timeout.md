# DP.M.293 — Graceful degradation чтения вторичной БД: таймаут + null-fallback

## Описание

Метод устойчивого чтения из вторичного источника данных внутри обработчика основного запроса: операция ограничена явным таймаутом, при отказе возвращает null-значения без прерывания основного ответа.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Полнота ответа ↔ доступность ответа | Обогащение из secondary делает ответ богаче; но если secondary недоступен, ожидание полноты не должно блокировать выдачу основного ответа |
| Явный таймаут ↔ простота кода | `await secondary_read()` без ограничений — на одну строку короче; явный timeout/AbortController добавляет код ради устойчивости |
| Быстрый ответ ↔ актуальность вторичных данных | Короткий таймаут ускоряет деградацию к null, но может отсечь медленный, но валидный ответ secondary; длинный таймаут рискует общей latency |
| Изоляция сбоя ↔ единая обработка ошибок | Обработка ошибок secondary отдельно от primary усложняет код обработчика, но не даёт сбою вторичного источника «утечь» в основной путь |

## Шаги

1. Запустить чтение вторичной БД с явным таймаутом (AbortController / asyncio.wait_for / Promise.race / любой механизм прерывания).
2. При таймауте или ошибке — вернуть null/default-значения без raise/throw.
3. Основной запрос завершается в любом случае.
4. **Опционально:** если primary поле ещё null — подставить из secondary (дешёвое обогащение ответа).

## Тест применимости

«Вторичный источник данных может быть недоступен независимо от основного?» + «Основной ответ должен выдаваться даже при отказе вторичного?» → применить метод.

## Антипаттерн

`await secondary_read()` без таймаута = основной запрос падает вместе с вторичным.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| «Secondary почти всегда отвечает быстро» | Таймаут выбирается по happy-path latency в разработке, а не по худшему сценарию в проде под нагрузкой; в момент реального отказа выбранный порог оказывается либо слишком долгим (замедляет основной запрос), либо не откалиброван вовсе |
| «Раз есть try/except — деградация уже покрыта» | Внимание фокусируется на факте наличия обработки ошибок, а не на том, ограничена ли операция по времени; зависание без исключения (не error, а hang) остаётся невидимым для этой проверки |
| «Опциональное обогащение — не critical path» | Secondary воспринимается как второстепенный код, которому уделяется меньше ревью-внимания; именно там чаще пропускается явный timeout, потому что «это же просто плюс к ответу» |
| «Null-fallback — это уже готово, тестировать не нужно» | Путь отказа (secondary недоступен) реже покрывается тестами, чем happy-path; проверяется, что метод работает, но не то, что он действительно не блокирует основной ответ при реальном таймауте |
