# DP.METHOD.196 — ArchGate: прецедент инцидента в том же артефакте весомее общего правила

## Определение

При оценке архитектурного варианта на ArchGate **первым делом** проверяется история инцидентов именно этого РП/подсистемы. Локальный прецедент «этот класс решения уже ломал именно эту систему» — самый сильный аргумент отклонения, сильнее общеотраслевого правила.

## IPO

- **Вход:** архитектурный вариант + история РП/подсистемы
- **Процесс:** поиск инцидентов того же класса решений в истории артефакта → оценка весомости
- **Выход:** решение об отклонении/принятии с явным указанием прецедента

## Алгоритм

1. Запросить incident-историю РП/подсистемы (archive/wp-contexts/, bug-файлы, комментарии).
2. Найти инциденты с тем же классом архитектурного решения.
3. Если найдены — вес аргумента «максимальный» (не advisory).
4. Применить к ArchGate: «этот класс решения уже дважды ломал эту систему → отклоняем без оговорок».

## Ключевое различение

**Общее правило** (отраслевое): «двусторонняя синхронизация — источник гонок» → advisory signal.

**Локальный прецедент**: «тот же класс решений ломал THIS конкретный конвейер 2 раза (гонки payment/chargeoff, 62-дневный простой)» → максимальный вес, отклонение без оговорок.

## Когда применять

- ArchGate с несколькими вариантами
- Предлагаемый вариант принадлежит классу, который «технически рискован» по общему правилу
- Есть доступная история РП/системы

## Источник

WP-183 ArchGate Directus: вариант A (MERGE-sync) отклонён на основании 2 прецедентов в истории этого РП. Напарник не принял абстрактное «синхронизация опасна» — потребовал факты из этой системы.
