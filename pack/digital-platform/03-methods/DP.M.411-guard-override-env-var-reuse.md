# DP.M.411 — Override env-var для переиспользования guard

## Суть метода

Скрипт с встроенным guard (условие, блокирующее выполнение в определённых обстоятельствах) переиспользуется в новом, соседнем контексте, где guard мешает — без изменения дефолтного поведения основного скрипта добавляется явный override-флаг через переменную окружения.

## Проблема

Guard в скрипте предназначен для основного, штатного контекста запуска. Когда тот же генератор нужен в другом контексте, где инвариант guard'а не должен применяться, есть два плохих варианта: (а) скопировать скрипт без guard — приводит к дрейфу дублирующегося кода; (б) вшить дополнительный параметр в саму логику guard — хрупко при последующих изменениях guard.

## Алгоритм

1. Определить guard, который блокирует нужное переиспользование в новом контексте
2. Добавить env-var флаг с явным именем (`FORCE_*` или аналог), который отключает именно этот guard для конкретного вызывающего контекста
3. Не менять поведение по умолчанию — флаг активен только при явной установке переменной

## Пример

`DAY_OPEN_FORCE_STRATEGY_DAY=1` обходит guard, блокирующий запуск на strategy_day, без изменения дефолтного поведения при штатном запуске. Используется в `week-open-day-section-patch.sh`, переиспользующем тот же генератор для секции «Открытие дня» внутри WeekPlan по понедельникам.

## Тест

«Один и тот же генератор нужен в двух контекстах, но один из них нарушает инвариант guard?» Да → добавить явный override-флаг с говорящим именем, задокументировать условия использования.

## Связи

- Альтернативы, которых стоит избегать: копия скрипта без guard (дрейф), параметр внутри логики guard (хрупкость)
