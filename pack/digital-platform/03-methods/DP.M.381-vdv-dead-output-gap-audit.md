# DP.M.381 — ВДВ-аудит конвейера: поиск стадий без потребителя Выхода

## Суть метода

ВДВ-анализ (Вход-Действие-Выход) применяется как диагностический метод поиска «мёртвых Выходов» — стадий конвейера, которые производят артефакт, но у него нет потребителя внутри обещанного контура.

**Мёртвый Выход = потенциальный gap observability.**

Стадия с мёртвым Выходом производит артефакт (пишет в файл, обновляет статус), который никто не читает автоматически в рамках контура. Это означает: если эта стадия сработала неправильно — ошибка не проявится до ручной проверки.

## Алгоритм

1. Для каждой стадии конвейера составить ВДВ-карточку: Вход → Действие → Выход.
2. Для каждого Выхода: проверить, есть ли следующий шаг внутри контура, который его потребляет (читает, валидирует, передаёт дальше).
3. Если потребителя нет → стадия имеет мёртвый Выход.
4. Для каждого мёртвого Выхода: решить (а) добавить потребителя или (б) признать, что стадия обслуживает другой контур → вынести её за пределы текущего конвейера.

## Пример

WP-5: `/vdv audit` на `day-open-pipeline.sh` выявил две стадии с мёртвыми Выходами:
1. Opportunistic snapshot refresh → Выход: обновлённый снимок. Потребитель: другой контур (не day-open). Решение: признать обслуживающей другой контур.
2. Черновик дневного отчёта → Выход: `checklist-status.yaml`. Потребитель в контуре: **отсутствует** — никто не читает автоматически. Именно этот gap скрыл баг Block DOF: чеклист писался, но не верифицировался.

## Когда применять

- При диагностике: «почему баг прошёл незамеченным через автоматизированный конвейер?»
- При проектировании нового pipeline: проверка полноты observability.
- При реструктуризации agent-протоколов (Day Open, CI, launchd-цепочка).

## Тест мёртвого Выхода

«Если эта стадия напишет мусор вместо корректного артефакта — когда конвейер это обнаружит?»
- Немедленно → Выход потребляется, не мёртвый.
- Никогда / только при ручной проверке → **мёртвый Выход**.
