# DP.M.341 — Верификация реального механизма защиты перед реализацией схемы доступа

## Описание

Перед реализацией схемы доступа/безопасности по абстрактному эталону — сначала прочитать 5-10 существующих миграций или примеров того же класса в репозитории, чтобы извлечь фактически применяемый механизм защиты. Проектировать поверх него.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Скорость старта реализации ↔ время на чтение существующих примеров | Начать кодировать по эталону сразу быстрее; чтение 5-10 миграций отнимает время до первой строки кода |
| Авторитет учебной документации ↔ авторитет действующего кода | Эталон из обучения/договорённости прошлой сессии выглядит как надёжный источник; но именно репозиторий содержит то, что реально исполняется в проде |
| Единообразие с абстрактным паттерном ↔ совместимость с унаследованным механизмом | Реализация «по книге» красивее и единообразнее; реализация «поверх реального» совместима с тем, что уже защищает данные, даже если это не идеальный паттерн |
| Разовая проверка ↔ повторяемость метода на каждой новой задаче | Соблазн проверить один раз и считать паттерн репозитория известным навсегда; механизм защиты может меняться между задачами |
| Явное признание legacy ↔ молчаливое наследование | Метод требует документировать решение «проектировать поверх legacy» явно, а не тихо повторить прежний механизм без оценки его качества |

## IPO

**Input:** новая задача на реализацию схемы доступа + абстрактный правильный паттерн (из документации, обучения, договорённостей прошлой сессии)

**Process:**
1. Найти 5-10 существующих миграций / примеров того же класса в репо (`ls migrations/` + чтение)
2. Извлечь фактически применяемый механизм защиты: роли, флаги, дисциплины кода, GRANT-паттерны
3. Сверить с абстрактным паттерном — совпадает или отличается?
4. Если отличается → проектировать поверх реального механизма, не поверх учебной абстракции

**Output:** реализация, совместимая с действующим механизмом защиты репо

## Ограничения (обязательны к учёту)

1. Существующий механизм может быть унаследованным / неоптимальным — документировать решение «проектировать поверх него» явно
2. Метод не заменяет архитектурный ревью при смене механизма защиты

## Тест применимости

«Изучал ли я, как реально защищаются данные в этом репо — или проектирую по абстрактному эталону?» По эталону → применить метод сначала.

## Антипаттерн

Реализация схемы доступа по договорённости из прошлой сессии или учебной документации без сверки с реальным кодом → появление «декоративной защиты» (код выглядит правильно, но механизм не применяется к субъекту).

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| «Прочитал 2-3 миграции — уже понятно, как тут устроено» | Внимание останавливается раньше нижней границы (5-10), потому что первые примеры кажутся достаточным паттерном |
| «Нашёл похожий механизм — значит, это и есть стандарт репо» | Один найденный пример принимается за общий механизм без проверки, применяется ли он последовательно во всех похожих местах |
| «Механизм отличается от эталона, но не будем это фиксировать письменно» | Решение «проектировать поверх legacy» принимается молча в голове разработчика вместо явной документации, требуемой Ограничением 1 |
| «Раз старый механизм неоптимален, стоит заодно его улучшить по пути» | Внимание смещается от задачи «встроиться в существующее» к незапрошенному архитектурному ревью механизма защиты, выходящему за рамки текущей задачи |
| «Я уже проверял этот репо на прошлой неделе» | Актуальность найденного паттерна не переспрашивается для новой задачи; механизм защиты мог измениться, а проверка не повторяется |
