# DP.M.414 — Общий шлюз координации публикации: fetch + cherry-pick + retry вместо точного совпадения SHA

## Проблема

Изолированная worktree-сессия отказывалась коммитить/публиковать, если её HEAD расходился с общей веткой хоть на один коммит (точное совпадение версии как предусловие публикации). При параллельных сессиях общая ветка почти всегда успевала уйти вперёд за время анализа одной сессии — штатная гонка параллельной работы систематически превращалась в постоянный отказ публикации.

## IPO

- **Вход:** изолированная (worktree) сессия с готовым к публикации коммитом; общая ветка могла продвинуться вперёд за время работы сессии
- **Процесс:** публикация идёт через единый шлюз координации (уже использовавшийся открытием/закрытием дня для той же гонки) — забрать свежую общую ветку → перенести подготовленный коммит поверх неё → опубликовать с ограниченным числом повторов
- **Выход:** коммит публикуется, несмотря на то что общая ветка продвинулась за время работы сессии; проверка точного совпадения версии убрана как предусловие

## Паттерн

```bash
git fetch origin main
git cherry-pick <prepared-commit-sha>   # поверх свежего origin/main
for attempt in 1 2 3; do
  git push origin HEAD:main && break
  git fetch origin main   # ретрай: подтянуть то, что успело уйти вперёд, и повторить
done
```
Конкретная реализация — общий шлюз координации, уже используемый открытием/закрытием дня для той же гонки (не новый отдельный механизм).

## Применимо

Множественные параллельные (изолированные worktree) агентские сессии, публикующие в одну общую ветку, где предусловие «точное совпадение версии перед публикацией» превращает нормальную гонку параллельной работы в систематический отказ.
