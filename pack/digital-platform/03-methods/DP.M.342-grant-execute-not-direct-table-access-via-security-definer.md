# DP.M.342 — EXECUTE на SECURITY DEFINER функцию вместо прямых прав на таблицу

## Описание

Если операция инкапсулирована в функцию с правами определяющего (SECURITY DEFINER), потребителю выдаётся только `GRANT EXECUTE` на функцию — таблица остаётся закрытой, право сужено до конкретной операции.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Удобство широких прав ↔ принцип наименьших привилегий | `GRANT SELECT`/`GRANT ALL` сразу закрывает любые будущие потребности воркера; `GRANT EXECUTE` требует точно знать, какая операция нужна, и обновлять GRANT при её изменении |
| Скорость выдачи прав ↔ проверка наличия функции-обёртки | Выдать SELECT сразу быстрее, чем сначала искать (grep/`\df+`), есть ли уже готовая SECURITY DEFINER функция для нужной операции |
| Гибкость воркера для будущих запросов ↔ закрытость таблицы | Прямой доступ к таблице даёт воркеру свободу для незапланированных запросов; EXECUTE на функцию ограничивает его ровно тем, что предусмотрено |
| Простота отладки (видно SQL) ↔ инкапсуляция логики | При SELECT/DELETE напрямую воркер видит и контролирует SQL; при EXECUTE вся валидация и логика скрыта внутри функции — отладка требует смотреть внутрь функции |
| Стабильность контракта ↔ поддержка при изменении сигнатуры функции | GRANT EXECUTE на функцию с фиксированной сигнатурой стабилен, но каждое изменение сигнатуры требует явного обновления прав — а не «работает само» как с широким SELECT |

## IPO

**Input:** воркер/роль, которому нужно выполнить операцию (например, удаление данных по праву на забвение), при наличии существующей SECURITY DEFINER функции для этой операции

**Process:**
1. Проверить: существует ли функция-обёртка для нужной операции? (grep по миграциям / `\df+`)
2. Если да — выдать `GRANT EXECUTE ON FUNCTION func_name(...) TO worker_role`
3. Не выдавать прямые права на таблицу (SELECT/DELETE/UPDATE)

**Output:** минимально необходимый набор прав; таблица закрыта, операция доступна только через функцию

## PostgreSQL-пример

```sql
-- Функция уже существует (SECURITY DEFINER)
-- GRANT EXECUTE, не GRANT SELECT:
GRANT EXECUTE ON FUNCTION delete_user_data_on_erasure_request(uuid)
    TO erasure_worker_role;

-- НЕ делать:
-- GRANT SELECT, DELETE ON domain_event TO erasure_worker_role;
```

## Ограничения (обязательны к учёту)

1. Функция должна сама валидировать параметры — потребитель не видит таблицу напрямую
2. Изменение сигнатуры функции требует обновления GRANT

## Тест применимости

«Есть ли уже функция-обёртка для этой операции?» Да → выдать EXECUTE, не прямые права на таблицу.

## Антипаттерн

Выдать `GRANT SELECT` (или широкий `GRANT ALL`) на таблицу воркеру, которому нужна одна конкретная операция, уже инкапсулированная в функцию.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| «Проверю наличие функции-обёртки потом, сейчас важнее не заблокировать воркера» | Внимание смещается к срочности разблокировки задачи, шаг «grep по миграциям / `\df+`» откладывается или пропускается под давлением времени |
| «Функция валидирует параметры — значит, о безопасности можно больше не думать» | Доверие к тому, что SECURITY DEFINER функция «сама разберётся», снижает внимание к тому, что именно она валидирует и какие граничные случаи пропускает |
| «Сигнатура функции не менялась давно — GRANT точно ещё актуален» | Внимание не возвращается к синхронизации GRANT при рефакторинге функции; молчаливое предположение о неизменности сигнатуры |
| «Раз функция уже SECURITY DEFINER, дополнительные права ей не нужны — не важно, что выдаём» | Фокус смещается с прав потребителя (воркера) на права самой функции, хотя именно GRANT EXECUTE потребителю — предмет метода |
| «В этом репо и так все всё видят, какая разница» | Локальная культура репозитория с широкими правами снижает бдительность к конкретному случаю, где инкапсуляция уже доступна и должна быть использована |
