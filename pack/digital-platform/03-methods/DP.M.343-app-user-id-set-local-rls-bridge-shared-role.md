# DP.M.343 — app.user_id через SET LOCAL для построчной защиты при одной служебной роли

## Описание

Реализация RLS-политики по user_id, когда все сервисы (бот, воркеры, аналитика) подключаются под одной служебной ролью — без JWT-моста к базе и без разделения ролей.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Простота одной служебной роли ↔ построчная (per-row) изоляция | Одна роль для всего трафика проще администрировать; SET LOCAL восстанавливает per-row защиту поверх этой простоты без разделения ролей |
| Совместимость с пулингом соединений ↔ строгость проверки переменной | `SET LOCAL` корректно работает с pgBouncer/transaction-mode; но `CURRENT_SETTING(..., true)` мягко проходит при отсутствии переменной, жертвуя строгостью ради совместимости с пулом |
| Скорость внедрения (переиспользовать паттерн) ↔ риск слепого копирования | Найти существующий пример `SET LOCAL app.user_id` в репо быстрее, чем проектировать заново; но бездумное копирование на новую таблицу без проверки контекста может создать несоответствие |
| Универсальность правила «на каждый запрос» ↔ исключение для BYPASSRLS-ролей | Единообразие требует оборачивать каждый запрос в `SET LOCAL`; аналитические роли с BYPASSRLS явно исключены — единого правила без исключений не получится |
| Soft fallback (`true`) ↔ защита от «тихого» отсутствия контекста | Мягкий режим не бросает исключение при отсутствии переменной, что удобно для миграции; но именно это делает возможным непреднамеренный полный доступ, если `SET LOCAL` забыт |

## Условие применимости

| Условие | Применять? |
|---------|-----------|
| Одна служебная роль для всего трафика приложения | Да |
| pgBouncer или transaction-mode pooling | Да |
| Нет JWT → Postgres моста | Да |
| Аналитические роли с BYPASSRLS | Нет (они видят все строки по атрибуту) |

## Механизм

```sql
-- Приложение выставляет в начале каждой транзакции:
SET LOCAL app.user_id = '<user_id>';

-- RLS-политика читает:
USING (user_id = CURRENT_SETTING('app.user_id', true)::uuid)
```

`SET LOCAL` сбрасывается автоматически при `COMMIT`/`ROLLBACK` — переменная не утекает между транзакциями в пуле соединений.

`true` как второй аргумент `CURRENT_SETTING` не бросает исключение при отсутствии переменной (soft fallback). Для строгой защиты нужен отдельный guard.

## Как применять

1. Найти существующий пример `SET LOCAL app.user_id` в репо (паттерн мог уже использоваться для других таблиц).
2. Задеплоить RLS-политику на целевую таблицу с условием через `CURRENT_SETTING`.
3. Обернуть каждый запрос к таблице в транзакцию с `SET LOCAL` перед ним.
4. Аналитические воркеры с BYPASSRLS — оставить без SET LOCAL (они видят все строки по атрибуту).

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| «Раз soft fallback не бросает исключение — значит, всё в порядке» | Внимание принимает отсутствие ошибки за подтверждение корректности, хотя `true`-режим `CURRENT_SETTING` молчит именно тогда, когда `SET LOCAL` забыт |
| «SET LOCAL уже стоит на других таблицах — на этой можно не проверять отдельно» | Наличие паттерна в репо создаёт ложную уверенность, что он применён именно к текущему запросу, без явной проверки на месте |
| «Транзакция короткая, забыть SET LOCAL — не страшно» | Восприятие риска смещается в сторону «маловероятно», хотя отсутствие явного guard-слоя означает, что забытый SET LOCAL даёт доступ ко всем строкам без предупреждения |
| «pgBouncer прозрачен для приложения — SET LOCAL сработает как обычно» | Внимание к деталям пулинга (transaction-mode vs session-mode) снижается; поведение `SET LOCAL` зависит именно от режима пула, а не одинаково в любой конфигурации |
| «Аналитическая роль — она особая, про неё думать не нужно» | Исключение BYPASSRLS-ролей из правила воспринимается как «эта категория вне зоны внимания», хотя именно у неё нужно явно подтвердить отсутствие построчной защиты, а не молчаливо предположить его |
