# DP.M.207 Explicit choice до stateful default при первом входе

## Решение

Если первый вход пользователя в систему создаёт необратимый или малообратимый ресурс с дефолтными параметрами (репозиторий, аккаунт, контейнер для данных, организационная сущность) — показывать explicit-choice экран ДО создания. Не использовать «удобный» auto-default с возможностью переключиться потом.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Снижение onboarding-friction (auto-default) ↔ обратимость выбора | Auto-default убирает один клик, но при создании репозитория/БД/организации откат может стоить дней миграции и конфликтов owner; explicit choice переносит небольшое трение на момент, когда пользователь готов к настройке |
| Руководство пользователя (продукт задаёт опции) ↔ автономия пользователя | Setup-страница с явным выбором даёт контроль, но плохо спроектированная страница перекладывает архитектурное решение на пользователя, который не готов его оценить |
| Скорость time-to-value ↔ корректность создаваемого state | Чем раньше ресурс создан, тем быстрее пользователь видит результат; но неверный дефолт рождает legacy state, который будет дороже исправлять, чем секунда выбора на входе |

## Аргумент

1. **Момент первого входа — единственная точка осознанного выбора.** Пользователь сосредоточен, готов к onboarding-friction, ожидает настройки. Любой выбор позже воспринимается как «зачем меня дёргают, я уже работаю».
2. **Auto-default = неявное согласие.** GDPR-аналогия: галочка-по-умолчанию для согласия запрещена именно потому, что пассивное согласие ≠ информированное согласие.
3. **Cost asymmetry.** Стоимость setup-страницы — секунды + одна-две кнопки. Стоимость неверного дефолта — недели миграции, конфликты owner, legacy state, в худшем случае data loss.

## Граница применимости

| Тип дефолта | Auto-default OK? | Explicit choice? |
|-------------|------------------|------------------|
| Тема UI (dark/light) | ✅ да | нет |
| Язык интерфейса (по локали браузера) | ✅ да | нет |
| Создание репозитория / аккаунта / БД-схемы | ❌ нет | обязательно |
| Создание organization / workspace | ❌ нет | обязательно |
| Выбор канала доставки данных (managed vs personal storage) | ❌ нет | обязательно |
| Подписка на план тарифа | ❌ нет | обязательно |

**Тест:** «Если пользователь решит откатить дефолт через неделю, сколько это стоит?» Минуты → auto-default OK. Дни/недели миграции → explicit choice.

## Реализация

```
[Первый вход в систему]
       ↓
[Setup-страница с явным выбором]
       ↓                    ↓
[Option A: managed]    [Option B: personal]
       ↓                    ↓
[Создание ресурса под выбранную опцию]
```

Setup-страница содержит:
- Короткое объяснение различий между опциями (1-2 предложения каждая)
- Кнопки выбора без «default»-предпочтения визуально
- Возможность пропустить (если применимо) — но не auto-pick

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| Default кажется обратимым | Практикующий недооценивает стоимость отката: миграция данных, конфликты owner, downstream-интеграции кажутся «потом разберёмся», пока state не создан |
| Сокращение onboarding-friction побеждает reversibility | Внимание фиксируется на метрике конверсии первого входа и снижении трения, а долгосрочная цена legacy state остаётся невидимой |
| Explicit choice применяется только к «большим» ресурсам | Практикующий требует выбор для репозитория или организации, но авто-дефолтит канал доставки данных или план хранения, которые позже оказываются малообратимыми |

## Анти-применение

- Pre-existing user без миграции на новую опцию (legacy default остаётся)
- Internal-tooling с одним типом ресурса (без выбора)
- Trial / sandbox с обратимыми ресурсами
