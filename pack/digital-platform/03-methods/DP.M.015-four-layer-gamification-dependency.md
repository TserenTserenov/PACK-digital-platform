# DP.M.015 Четырёхслойная каскадная зависимость в activity-based геймификации

## Определение

Архитектурный паттерн организации вычислений в activity-based системах геймификации как линейной каскадной зависимости четырёх слоёв.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Строгая линейная блокировка (Инвариант: «Слой N не может работать без выхода Слоя N-1») ↔ параллелизация работы команды | Метод жертвует возможностью вести несколько слоёв одновременно ради предотвращения ситуации из «Типичная ловушка» («начинаем Слой 4, а Слой 3 ещё не реализован»), требуя строгого снизу-вверх порядка (Правило реализации) |
| Общность паттерна (Применимость: «любая система прогресс-трекинга с баллами/рангами») ↔ привязка к конкретным сервисам текущей платформы (таблица Слои: Profiler / Evaluator Worker / Rewards handler) | Таблица слоёв называет реальные имена сервисов, из-за чего заявленная общность паттерна проверена пока только на одной реализации (WP-121, WP-298, «Связи») |

## Слои

| Слой | Функция | Сервис / Worker |
|------|---------|----------------|
| 1. Сбор событий | Capture domain_events | Event collector / projection-worker |
| 2. Вычисление индикаторов | M-индексы, составные метрики | Profiler |
| 3. Классификация ступени | Stage transition | Evaluator Worker (DP.M.014) |
| 4. Начисление наград | Points с multiplier | Rewards handler |

## Инвариант

Блокировка линейная: Слой N не может работать без выхода Слоя N-1.

## Правило реализации

Реализовывать строго послойно снизу вверх. Прежде чем браться за Слой N — убедиться, что Слой N-1 уже реализован и работает.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего. Статус карточки — `draft`: пометка `tentative` по прецеденту SA.METHOD.001 (WP-448 Ф12)._

| Bias | Direction of distortion |
|------|--------------------------|
| _(tentative)_ Внимание планирования смещается к верхним слоям | При планировании внимание команды смещается на верхние слои (Слой 4 — награды, самый «видимый» пользователю результат) и недооценивает готовность нижних (Слои 1-2 — сбор событий, индикаторы), хотя именно нижние слои определяют, когда верхние вообще могут стартовать (Инвариант) |
| _(tentative)_ Готовность слоя проверяется по деплою, а не по выходу | При проверке готовности Слоя N-1 практик проверяет факт «сервис задеплоен», а не факт «выход Слоя N-1 согласован по формату/семантике с тем, что ожидает Слой N» — Инвариант формулирует блокировку через «выход», а не через «наличие сервиса», и внимание систематически съезжает на второе как более простое для проверки |

## Типичная ловушка

«Начинаем Слой 4 (награды)», но оказывается Слой 3 (классификация) ещё не реализован → незапланированный WP и задержка.

## Применимость

Любая система прогресс-трекинга с баллами/рангами: обучение, геймификация, квалификационные системы.
