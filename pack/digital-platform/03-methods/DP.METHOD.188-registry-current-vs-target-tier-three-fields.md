# DP.METHOD.188 — Три поля реестра: tier / target_tier / migration_trigger

## Определение

При ведении реестра/каталога артефактов, проходящих институционализацию (переход personal → platform), использовать три поля вместо одного:

- `tier` — **фактическое текущее состояние** (personal / shared / platform)
- `target_tier` — **целевое состояние** (к чему движемся)
- `migration_trigger` — **условие смены статуса** (событие, которое совершает переход)

## IPO

- **Вход:** реестр/каталог с артефактами в процессе институционализации
- **Процесс:** при заполнении статуса — фиксировать фактическое состояние (не желаемое), явно указывать целевое и триггер смены
- **Выход:** реестр с различёнными фактическим и целевым состоянием + явное условие перехода

## Проблема одного поля

Одно поле `tier: platform` для артефакта, который ещё наполняется единолично, превращает реестр в wishlist: статус отражает желание, а не факт. При планировании capacity/ownership это вводит в заблуждение.

## Пример

```yaml
# Банк персон-скептиков
tier: personal          # фактически: наполняет Церен единолично
target_tier: platform   # цель: передать Алёне как domain owner
migration_trigger: "Ф4 WP-251"  # условие: завершение фазы передачи
```

## Применимость

Любой реестр/каталог, который отслеживает артефакты в процессе институционализации: реестры ролей, реестры Pack'ов, каталоги сервисов, регистры инструментов, реестры реестров.

## Источник

WP-251 Ф0 (2026-07-10): при заполнении `registry-catalog.md` и YAML-черновика `WP-419-registry-catalog-draft.yaml` напарник отверг `tier: platform` для банка персон-скептиков — факт (личное наполнение Цереном) ≠ цель (передача Алёне). Паттерн обобщён до трёх полей.
