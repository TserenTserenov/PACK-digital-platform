# DP.M.214 Silent OAuth Token Provisioning

## Описание

UX-паттерн для браузерных расширений и десктоп-клиентов: автоматическое получение API-токена при наличии активной web-сессии пользователя без ручных шагов (копировать/вставить токен).

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Плавный UX без ручных шагов ↔ безопасность токена | Silent provisioning убирает friction, но требует one-time/TTL токена; долгоживущий токен в расширении повышает риск компрометации при утечке локального хранилища |
| Доверие к существующей web-сессии ↔ изоляция расширения | Расширение использует cookie сессии платформы, что размывает границу между web-приложением и сторонним клиентом; удобство достигается за счёт переиспользования доверия |
| Простота установки ↔ прозрачность для пользователя | Пользователь не видит токен и не выполняет явных действий, поэтому может не осознавать, какие разрешения получает расширение |

## IPO

**Вход:** пользователь залогинен в платформе (есть Ory session cookie); расширение только что установлено
**Процесс:** `GET /api/<service>/token` с session cookie → платформа верифицирует через Ory → возвращает `{token, endpoint}`
**Выход:** токен сохранён локально в расширении; ноль ручных действий от пользователя

## Технические требования

- CORS `Allow-Origin: chrome-extension://*` на `GET /api/<service>/token`
- Endpoint верифицирует Ory-сессию через `X-Session-Token` или cookie
- Токен — одноразовый или с TTL (не long-lived)

## Bias-Annotation

_Куда систематически съезжает внимание практикующего. Epistemic stage карточки — `empirical`._

| Bias | Direction of distortion |
|------|--------------------------|
| Пренебрежение CORS/Origin constraints | Практикующий склонен расширить `Allow-Origin: chrome-extension://*` или снять проверку сессии, чтобы интеграция «просто заработала»; внимание смещается от минимизации поверхности атаки к ускорению setup |
| Склонность к long-lived токенам | Фокус на удобстве (не беспокоить пользователя повторной авторизацией) отодвигает требование one-time или TTL токена; в локальном хранилище остаётся долгоживущий секрет |
| Игнорирование отзыва | Предполагается, что отзыв сессионного cookie автоматически аннулирует и токен расширения; внимание не доходит до явного механизма отзыва выданных токенов |

## Антипаттерн

Показывать токен в боте/UI с просьбой скопировать вручную → нереалистичный UX, пользователь не понимает зачем.

## Тест применимости

«Пользователь уже авторизован в web-сессии платформы?» Да → применять DP.M.214.

## Применение

- IWE browser extension получает токен для Local Gateway
- Десктоп-клиент получает API-ключ после OAuth login
- Любое расширение, интегрированное с OAuth-платформой
