# DP.M.231 Диагностика: одновременное восстановление всех domain-rules = main loop block

## Решение

В multi-domain projection worker паттерн одновременного падения/восстановления всех N domain rules — диагностический маркер блокировки главного корутина, а не изолированного domain-фейла.

## Таблица диагностики

| Наблюдение в логах | Диагноз |
|---|---|
| Все N rules упали и восстановились одновременно | Блок в main coroutine: `pool.acquire()` без timeout, бесконечный `wait_for` |
| Один домен упал, остальные живы | Domain-специфичная ошибка (SQL, schema, etc.) |

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Простота диагноза ↔ точность диагноза | По одновременному падению всех доменов легко выявить блок main loop, но такой сигнал грубый — он не говорит, где именно блок; domain-специфичный сигнал точнее, но требует больше времени на анализ |
| Лог-ориентированность ↔ live-debug | Метод работает по логам и не требует подключения отладчика, но требует, чтобы логи фиксировали восстановление каждого домена с timestamp'ами |
| Domain-изоляция ↔ общий event loop | Домены должны быть независимы, чтобы падение одного не ложило остальные, но общий loop даёт сигнал «всё замерло» при main-loop block |

## Механизм

При блокировке main event loop все domains «замерзают» вместе. Восстановление происходит одновременно когда OS закрывает zombie TCP (OS keepalive ~7-10 мин). При изолированном domain-фейле восстанавливается только один домен.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| Один упавший домень кажется причиной | Практикующий видит domain-специфичную ошибку и сразу копает вниз, не замечая, что все домены упали одновременно — главная причина в main loop, а не в SQL |
| Одновременное падение всех доменов воспринимается как «внешний сбой» | Все правила упали и восстановились разом — практикующий списывает это на сетевой глюк или перезапуск, не анализируя как блок main loop |
| Блокировка main loop не замечается | Симптомы выглядят как «все домены временно недоступны», а не как «главный корутин заблокирован»; нужно явно смотреть на корреляцию времени восстановления |

## Применимость

- asyncio worker с несколькими независимыми доменами на общем event loop
- Работает по логам (не требует live-debug)
- Типичный период блокировки до OS keepalive: 7-10 мин
