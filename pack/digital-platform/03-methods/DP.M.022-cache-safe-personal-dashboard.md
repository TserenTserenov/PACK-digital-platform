# DP.M.022 — Cache-safe личный дашборд (снапшот + daily sync)

## Проблема

Личный дашборд с прямыми запросами к Neon при каждом обращении: недоступность БД → HTTP 500 → пользователь видит ошибку вместо данных. Real-time запрос дорог по latency.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Доступность данных всегда (инвариант 1) ↔ актуальность в реальном времени | Метод жертвует real-time точностью ради гарантии «данные всегда доступны, даже при недоступности БД» — таблица Применимость явно исключает операционные данные (сообщения, платёжный статус) именно по этой причине |
| Простота daily sync (раз в сутки, §Алгоритм п.1) ↔ свежесть при частых изменениях | Фиксированный daily sync (напр. 04:45 МСК) прост в эксплуатации, но событие сразу после sync станет видно пользователю только примерно через 24 часа |
| Прозрачность через дату (инвариант 4) ↔ доверие пользователя к данным | Явный показ даты снапшота честно раскрывает staleness, но перекладывает интерпретацию «это нормально или проблема» на самого пользователя вместо скрытия сложности |

## Метод

Данные читаются из кэша-снапшота. Снапшот обновляется по расписанию (daily sync). При недоступности источника — отдавать устаревший снапшот без ошибки, с указанием даты актуальности.

## Инварианты

1. Данные всегда доступны (даже при недоступности БД).
2. Кэш ≠ ошибка — при недоступности sync снапшот не сбрасывается.
3. Данные актуальны на момент последнего daily sync (не real-time).
4. Дата последнего обновления показывается пользователю явно.

## Алгоритм

1. **Daily sync** (напр. 04:45 МСК): запрос к Neon → запись в снапшот-файл/кэш.
2. **Дашборд** читает снапшот, не Neon напрямую.
3. **При сбое sync:** снапшот сохраняется без обновления → UI показывает «данные от {дата}».
4. **HTTP-ответ при недоступности Neon:** не 500 — отдавать кэш с пометкой даты.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| Фокус на happy-path daily sync (Алгоритм п.1) | Реализация концентрируется на успешном обновлении снапшота, а п.3 «при сбое sync снапшот сохраняется без обновления» часто не реализуется явно, потому что тестируется обычно только штатный прогон |
| Граница применимости (таблица) съезжает со временем | Метод изначально предназначен для аналитики (WakaTime, stage indicators), но по мере роста дашборда новые виды данных добавляются в тот же cache-safe путь без повторной проверки по критерию «допустима задержка?», смещаясь в сторону операционных данных, для которых метод помечен ❌ |

## Применимость

| Тип данных | Применять | Почему |
|------------|-----------|--------|
| WakaTime stats, activity streaks | ✅ | Аналитика, допустимо несколько часов задержки |
| Stage indicators (M1, M3, M4) | ✅ | Аналитика, daily sync достаточно |
| Текущие сообщения, платёжный статус | ❌ | Операционные данные, нужен real-time |
