# DP.M.263 — Каскад Pack-расширения

## Назначение

Метод governance-расширения каталога формализованных сущностей (роли, методы, паттерны) **с допуском ad-hoc-использования** до формализации. Решает дилемму throughput vs inventory: жёсткое требование Pack-formalization до использования блокирует throughput; отсутствие требования копит inventory из несформализованных ad-hoc'ов.

**Корневая ошибка предшественников:** ожидание от Pack-coupling «детерминированной маршрутизации роль → метод», как у DI-контейнера. Реальный Pack даёт **онтологическую линзу** — портфолио критериев + 4 аспекта домен-контекста (критерии метода, формат артефакта, критерии качества, связи с другими ролями). Метод выбирается **внутри линзы** контекстуально, не алгоритмически.

## IPO

**Input:** ad-hoc-использование сущности (роли/метода/паттерна) в работе/сессии, не зафиксированной в Pack как формализованная.

**Process:** трёхуровневый каскад:

1. **In-session snapshot** (per-occurrence, секунды).
   - Фиксация: `meta.yaml.ad_hoc_<entity>: {name: {agent_id, rationale, first_used_turn}}`.
   - Без блокировки работы. Throughput сохраняется.
2. **Week Close audit** (periodic, минуты).
   - Скрипт `audit-ad-hoc-<entity>.py` обходит `meta.yaml`-снимки всех сессий недели.
   - Агрегирует по имени ad-hoc-сущности; считает частоту.
3. **Автогенерация candidate WP** (по порогу, рывком).
   - При freq ≥ N (опытно: 3) по одному ad-hoc-имени — генерируется candidate WP «формализовать `DP.<TYPE>.NNN`».
   - Пилот при триаже подтверждает или отклоняет.

**Output:** новая формализованная сущность в Pack (DP.ROLE.NNN, DP.M.NNN, DP.D.NNN) с обоснованием через накопленную частоту использования.

## Параметры

| Параметр | Дефолт | Комментарий |
|----------|--------|-------------|
| `threshold_frequency` | 3 | Минимальная частота ad-hoc-использования для генерации WP. Уточняется опытно. |
| `audit_period` | Week Close | Может быть Day/Month Close для других ритмов. |
| `meta_yaml_key` | `ad_hoc_<entity>` | Унифицированный ключ по типу сущности. |

## Свидетельства результата

- Файл `meta.yaml` с записями `ad_hoc_<entity>`.
- Лог `audit-ad-hoc-<entity>.py` с частотами и сгенерированными WP-кандидатами.
- WP-NNN-pack-gap-<entity>-<имя> при срабатывании порога.

## Когда применять

- Каталог формализованных сущностей (роли, методы, паттерны, распознавания) с допуском ad-hoc-расширений.
- Когерентный ритм закрытий (Week/Month Close) есть.
- Нарушения консистентности накапливаются как drift, не блокируют работу в realtime.

## Когда НЕ применять

- Realtime-блокирующее нарушение (нужен синхронный gate, не каскад).
- Каталог < 5 сущностей того же типа (нет prior для эвристики «то же семейство»).
- Аудит-цикл отсутствует (некому собирать снимки).
