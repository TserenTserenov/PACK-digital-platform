# DP.M.168 — Post-deploy регрессия как гипотеза №1 в RCA

## Суть

Когда новые ошибки появляются в окне после деплоя — первой гипотезой выдвигать сами фиксы, ДО внешних причин (API партнёра, БД, сеть). Иначе анти-паттерн «фиксы отработали — ищем снаружи».

## IPO

| | |
|---|---|
| **Вход** | Окно ошибок ≥1 новая запись + история деплоев за окно |
| **Процесс** | Сравнить timestamp каждого деплоя с первой ошибкой → gap ≤ N мин → деплой = приоритетная гипотеза |
| **Выход** | Ранжированный список гипотез: post-deploy регрессия выше внешних |

## Шаги

1. Собрать timestamps всех деплоев за окно ошибок.
2. Зафиксировать timestamp первой новой ошибки.
3. Вычислить gap. Если ≤ 30 мин (порог настраиваемый) → регрессия = главная гипотеза.
4. Проверить регрессию ДО внешних причин: какие классы изменений в этом деплое могут давать наблюдаемые симптомы?
5. Только при опровержении регрессии (диф-анализ + тест отката) переходить к внешним гипотезам.

## Известные классы post-deploy регрессий

- Новый probe-вызов бросает exception в нетипичных контекстах.
- Canary паузирует scheduler так, что retry молча пропускается.
- Double-count в health_check (см. DP.FM.081).
- Изменение payload schema у клиента, не у сервера.

## Тест применимости

Любая incident-response процедура с историей деплоев.
