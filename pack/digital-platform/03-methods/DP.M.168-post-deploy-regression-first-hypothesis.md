# DP.M.168 — Post-deploy регрессия как гипотеза №1 в RCA

## Суть

Когда новые ошибки появляются в окне после деплоя — первой гипотезой выдвигать сами фиксы, ДО внешних причин (API партнёра, БД, сеть). Иначе анти-паттерн «фиксы отработали — ищем снаружи».

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Скорость локализации (начать с самой вероятной причины) ↔ полнота рассмотрения внешних гипотез | Метод намеренно смещает приоритет на собственный свежий деплой (gap ≤ 30 мин → регрессия = главная гипотеза), рискуя задержать диагностику, если причина всё же снаружи; баланс удерживается шагом 5 — переход к внешним причинам только после опровержения регрессии (диф-анализ + тест отката) |
| Доверие к только что прошедшему ревью/CI деплою ↔ дисциплина повторной проверки своих изменений | Свежий деплой воспринимается как уже проверенный («фиксы отработали»), и перепроверять его — значит платить временем за то, что формально «сдано»; метод заставляет считать его подозреваемым №1 именно потому, что известные классы регрессий (probe-вызов, canary-пауза, double-count, schema mismatch) проходят ревью незамеченными |

## IPO

| | |
|---|---|
| **Вход** | Окно ошибок ≥1 новая запись + история деплоев за окно |
| **Процесс** | Сравнить timestamp каждого деплоя с первой ошибкой → gap ≤ N мин → деплой = приоритетная гипотеза |
| **Выход** | Ранжированный список гипотез: post-deploy регрессия выше внешних |

## Шаги

1. Собрать timestamps всех деплоев за окно ошибок.
2. Зафиксировать timestamp первой новой ошибки.
3. Вычислить gap. Если ≤ 30 мин (порог настраиваемый) → регрессия = главная гипотеза.
4. Проверить регрессию ДО внешних причин: какие классы изменений в этом деплое могут давать наблюдаемые симптомы?
5. Только при опровержении регрессии (диф-анализ + тест отката) переходить к внешним гипотезам.

## Известные классы post-deploy регрессий

- Новый probe-вызов бросает exception в нетипичных контекстах.
- Canary паузирует scheduler так, что retry молча пропускается.
- Double-count в health_check (см. DP.FM.081).
- Изменение payload schema у клиента, не у сервера.

## Тест применимости

Любая incident-response процедура с историей деплоев.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| Симптом ошибки затмевает её положение на таймлайне | Практик классифицирует ошибку по виду (exception, timeout, 5xx) и идёт в код по классу симптома, вместо того чтобы начать с дешёвого вопроса «что деплоилось за N минут до первой записи»; история деплоев остаётся вне поля зрения, пока направление по симптому не исчерпано |
| Ненахождение регрессии принимается за её опровержение | Внимание приковано к поиску подтверждения в дифе, и при первом неудачном просмотре («в дифе ничего такого») практик переходит к внешним причинам; шаг 5 требует именно опровержения (диф-анализ + тест отката), а не отсутствия находки при беглом чтении |
