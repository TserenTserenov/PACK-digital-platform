# DP.METHOD.056 — Pre-deploy аудит потребителей перед сменой имён MCP-инструментов

> **Применяется:** перед любым деплоем gateway или MCP-сервера с переименованием / удалением инструментов.

## §0 Назначение

При переименовании MCP-инструментов клиенты с хардкодом старого имени падают после деплоя. Метод предотвращает breaking change в проде через обязательную pre-deploy проверку.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Полнота grep-покрытия по всем клиентским репо (§1 п.2) ↔ скорость pre-deploy проверки | Проверка каждого репо из явного списка (`aist_me_bot`, `aist_pilot_bot`, `hermes-runtime`) добавляет шаг перед каждым переименованием инструмента, но пропуск хотя бы одного репо превращает «чистый деплой» в ложный вывод — breaking change ловится только после деплоя в проде |
| Атомарность co-deploy (§2 инвариант «gateway и клиенты — co-deploy единица») ↔ независимость релизных циклов потребителей | Требование обновить всех потребителей одновременно с деплоем gateway конфликтует с обычным независимым темпом деплоя каждого клиентского репо — координационная нагрузка растёт с числом клиентов, что и мотивирует расширение §3 при >3 клиентах |

## §1 Алгоритм

1. **Определить изменения контракта:** список переименованных / удалённых инструментов из diff
2. **Grep по всем клиентским репо:**
   ```bash
   for repo in aist_me_bot aist_pilot_bot hermes-runtime; do
     echo "=== $repo ===" && grep -rn "старое_имя_инструмента" ~/IWE/$repo/ 2>/dev/null
   done
   ```
3. **Если есть совпадения** — обновить до деплоя шлюза (атомарный PR или одновременный деплой)
4. **Если совпадений нет** — деплой чистый, продолжать

## §2 Инвариант

**Deploy нового контракта без одновременного обновления потребителей = breaking change в проде.**

Правило: gateway и его клиенты — co-deploy единица при изменении имён.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| Ложное чувство полноты после zero-match grep | Внимание переоценивает нулевой результат grep (§1 п.2) как доказательство отсутствия зависимости, хотя grep ловит только литеральные строки — динамически собранные имена инструментов (шаблоны, конфиги) остаются невидимыми, и проверка тихо проходит мимо реального риска |
| Фиксация на статичном списке репо | Внимание закрепляется на трёх repos, явно перечисленных в for-цикле §1 п.2 (`aist_me_bot`, `aist_pilot_bot`, `hermes-runtime`), и не доходит до вопроса «появился ли новый клиент с тех пор, как список был написан» — расширение §3 (`consumers.yaml`) сформулировано именно как реакция на этот дрейф |

## §3 Расширение

При масштабировании (>3 клиентов): завести `consumers.yaml` с полным списком → grep автоматизировать через `scripts/pre-deploy-consumer-check.sh`.
