# DP.METHOD.116 Позиционирование user_id в хэш-цепочке при праве на забвение

## Контекст

Система обещает и неизменяемость (hash-chain integrity), и право на забвение (GDPR Art.17). Конфликт:
- user_id **внутри** хэшируемого содержимого → обезличивание мутирует строку → цепочка ломается.
- user_id **снаружи** хэша → привязка события к человеку ничем не защищена.

Выбор обязан быть зафиксирован в классификации данных таблицы **до** реализации. Иначе одно из двух обещаний окажется ложным.

## Развилка дизайна

### Вариант А: Crypto-shredding

PII шифруется отдельным ключом, специфичным для пользователя. В строке журнала хранится зашифрованное значение или pseudonymous handle. Забвение = удаление ключа шифрования. Хэш-цепочка остаётся целой.

**Ограничение:** нужен HSM / secure key-lifecycle management.

### Вариант Б: Разрыв цепочки (epoch)

Обезличивание легитимно рвёт цепочку. Новый отрезок открывается с явной пометкой эпохи (`anonymization_epoch: N, reason: gdpr_erasure`). Верификация целостности — внутри каждой эпохи; разрывы задокументированы и приняты.

**Ограничение:** сложнее для непрерывного аудита.

## Алгоритм выбора

1. Нужна непрерывная chain-of-custody (финансовый / регуляторный аудит)? → **Вариант А**.
2. Можно реализовать надёжный key-lifecycle? → **Вариант А**.
3. Малый объём событий, аудит не требует непрерывности? → **Вариант Б** проще.

## Тест при проектировании

> «Что произойдёт с хэш-цепочкой при исполнении запроса на удаление данных конкретного пользователя?»

Нет ответа → развилка не принята → СТОП, решить до реализации.
