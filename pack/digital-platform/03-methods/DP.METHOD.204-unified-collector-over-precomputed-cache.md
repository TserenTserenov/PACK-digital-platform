# DP.METHOD.204: Единый сборщик live+historical вместо предкомпьютинга

## Контекст

При построении data pipeline возникает соблазн «оптимизировать»: вычислять агрегаты один раз при закрытии записи (Close-протокол), сохранять в индекс, и читать из него. Это работает для historical-данных. Но live-данные (незавершённые записи, открытые сессии) всё равно требуют разбора сырых данных в реальном времени.

## Правило

**Если live-путь и historical-путь требуют одинакового парсинга → единый читатель сырых данных.**

**Вопрос-тест:** «Нужна ли та же логика парсинга для live-данных?»
- **Да** → не кэшируй при записи, читай при запросе через единый сборщик
- **Нет** → предкомпьютинг оправдан (live-данных нет или они принципиально иные)

## Антипаттерн (что НЕ делать)

```
close_protocol() → вычислить + сохранить в index   # дублирует логику сборщика
sborshchik() → читать из index (historical) + читать сырые (live)   # два пути
```

## Правило (что делать)

```
close_protocol() → финализировать запись (не вычислять агрегаты)
sborshchik() → всегда читать сырые данные, для всех записей
```

## Применимость

- Системы с «живыми» и «закрытыми» записями (сессии, задачи, события)
- Data pipeline с агрегацией по временным окнам
- Любая система где есть понятие «ещё открытая» запись

## Тест

«Если убрать предкомпьютинг — нужно ли дублировать логику разбора для live-данных?» Да → предкомпьютинг создаёт дублирование, не убирает.
