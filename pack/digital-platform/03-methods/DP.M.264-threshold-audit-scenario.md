# DP.M.216 — Пороговый сценарий аудита (YAGNI для cross-component consistency)

## Назначение

Метод принятия решения «новая операционная роль vs новый сценарий аудитора» при обнаружении governance-потребности в периодической сверке консистентности между N компонентами (cross-pack, cross-service, cross-repo).

**Анти-паттерн:** «новая операционная роль на каждую обнаруженную governance-потребность». Размывает портфель ролей, конфликтует с DP.D.080 (контрольная ≠ операционная), требует ресурса на поддержку роли без realtime-потребности.

## IPO

**Input:** обнаруженная governance-потребность в проверке консистентности (cross-pack consistency, multi-service config drift, cross-repo manifest sync).

**Process:**

1. **Классифицируй природу нарушения:**
   - Realtime-блокирует работу → нужен синхронный gate (это отдельный вопрос, не этот метод).
   - Накапливается как drift → переходим к шагу 2.
2. **Проверь существующего Аудитора (R24, DP.D.080 контрольная роль).**
3. **Сформулируй пороговый сценарий:**
   - Критерий активации: N компонентов И/ИЛИ M дней с последней проверки.
   - Артефакт: отчёт-патч (что изменить в Pack-ах) + список расхождений.
4. **Зафиксируй сценарий в Pack:** `pack-extension` для существующего DP.ROLE.R24 (новый пункт в §сценарии), без новой DP.ROLE.NNN.
5. **Опытно уточни порог** (15-20 типичный диапазон для cross-pack consistency).

**Output:** расширение существующего Аудитора пороговым сценарием. Активируется только при достижении порога.

## Параметры

| Параметр | Дефолт | Комментарий |
|----------|--------|-------------|
| `n_components_threshold` | 15-20 | Минимальное количество компонентов для активации. Уточняется опытно. |
| `m_days_threshold` | 30 | Дней без последней проверки. |
| `activation_logic` | `AND` или `OR` | Зависит от критичности drift. |

## Свидетельства результата

- Запись в Pack: `DP.ROLE.R24 §сценарии` (новый пункт).
- Лог активации: дата срабатывания порога + результат проверки.
- Отчёт-патч при срабатывании.

## Когда применять

- Cross-pack consistency (Aisystant ↔ Pack ↔ DS).
- Multi-service config drift.
- Multi-repo manifest sync.
- Multi-tenant config consistency.

## Когда НЕ применять

- Realtime-блокирующее нарушение → нужен синхронный gate.
- Малое количество компонентов (< порога) — overhead больше пользы.
- Существующая операционная роль уже покрывает в realtime.

## Преимущества (vs новая операционная роль)

- Не размывается портфель ролей.
- Сохраняется граница DP.D.080 (контрольная ≠ операционная). Steward как операционка вмешивался бы в работу владельцев Pack.
- Активируется только при необходимости (по порогу) — ресурс не тратится впустую.

## Тест применимости

«Нарушение этой governance-потребности блокирует работу в realtime или накапливается?»
- Накапливается → пороговый аудит (этот метод).
- Блокирует → синхронный gate (отдельный вопрос).
