# DP.METHOD.162: Авторизацию добавлять поверх публичной базы, не вырезать из приватной

## Назначение

Метод выбора базового сервиса при слиянии двух сервисов с разными уровнями доступа (публичный + приватный).

## Правило

**База** при слиянии = публичный сервис.
**Авторизация** = добавляется как отдельный слой поверх базы.

**Запрещено:** брать приватный сервис за основу и «вырезать» из него авторизацию.

## Почему

| Подход | Дефолтное состояние при ошибке конфига |
|--------|----------------------------------------|
| База = публичный, авторизация добавлена | Fail-closed (нет доступа — ошибка) |
| База = приватный, авторизация вырезана | Fail-open (доступ без авторизации) |

При «вырезании» одна ошибка конфигурации → данные без авторизации.

## Применение в WP-410

WP-410 (mcp-unification): объединяли knowledge-mcp (публичный) и personal-knowledge-mcp (приватный).
- Предложение: взять personal-mcp за основу и убрать авторизацию. Отклонено.
- Принято: база = knowledge-mcp; реализации (поиск, embed) переехали в src/core/ без авторизационной логики; авторизация добавлена как слой.

## Паттерн

При любом слиянии сервисов с разными уровнями доступа:
1. Определить, какой сервис является публичным (наименее привилегированным).
2. Взять его за основу (fail-closed дефолт).
3. Добавить авторизационные слои для расширения доступа, не убирать существующие ограничения.

## Тест

«Если авторизационный слой потерян (неправильный конфиг, env не задан) — что отдаёт сервис по умолчанию?»
- Публичные данные → правильно (ограниченный, но безопасный дефолт).
- Все данные без проверки → неправильно, пересмотреть архитектуру.
