# DP.METHOD.197 — ArchGate: функциональная регрессия оператора перевешивает архитектурную чистоту

## Определение

При сравнении архитектурных вариантов вариант, **тихо отбирающий у живого оператора существующую функцию** (право UPDATE, право просмотра, право исправления), не является «более чистым» — он перекладывает стоимость на человека. Функциональная регрессия роли-потребителя = блокер варианта.

## IPO

- **Вход:** архитектурные варианты + перечень текущих прав/операций живых ролей-потребителей
- **Процесс:** для каждого варианта: сравнить что получает vs что теряет каждая роль-потребитель
- **Выход:** блокировка вариантов, создающих функциональную регрессию без компенсации

## Алгоритм

1. Составить список живых ролей-потребителей системы и их текущих прав/операций.
2. Для каждого рассматриваемого варианта: явно перечислить, какие права/операции теряются.
3. Оценить скрытую стоимость восстановления потерянной функции (часто = новый сервис/компонент с рекуррентной поддержкой).
4. Вариант с нескомпенсированной регрессией → отклонить или доработать до восстановления функции.

## Почему «чистая» архитектура обманывает

Вариант «отдельная простая форма» кажется чище (один путь записи, нет копий данных). Но «простая форма» по умолчанию — только INSERT. Восстановление права UPDATE превращает её в мини-CRM на поддержке. Скрытая стоимость не исчезает — она переходит из инфраструктуры в трудозатраты оператора.

## Ключевой вопрос при ArchGate

«Какие операции живых ролей-потребителей данный вариант молча отбирает? Как будет компенсирована потеря?»

## Источник

WP-183 ArchGate Directus: вариант C (своя форма вместо Directus) отклонён. Оператор — финансовая роль с регулярной потребностью в UPDATE (исправление ошибок ручного ввода). Восстановление = новый сервис с security-периметром → рекуррентный риск.
