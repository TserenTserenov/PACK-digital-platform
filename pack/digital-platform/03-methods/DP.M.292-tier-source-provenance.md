# DP.M.292 — tier_source: поле провенанса в multi-source авторизации

## Описание

При multi-source авторизации (JWT-клейм → БД → fallback) к авторизационному ответу добавляется поле провенанса `<attr>_source`, указывающее откуда получен атрибут.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Компактность ответа ↔ отладочная прозрачность | Ответ без provenance-поля легче и короче; но при неожиданном fallback debugging требует ручного трейсинга через код авторизации |
| Скорость реализации ↔ полнота источников | Быстрее замокать один источник (только claim); учесть все три (claim/db/fallback) с провенансом — больше кода на старте |
| Единообразие схемы ответа ↔ рост числа полей | Каждый multi-source атрибут добавляет `<attr>_source`; чем больше атрибутов, тем шире контракт API |
| Доверие к значению ↔ доверие к источнику | Значение "T1" само по себе не говорит, надёжно оно или деградировало; провенанс отделяет «что» от «откуда» |

## Паттерн

```typescript
type TierSource = "claim" | "persona_db" | "fallback";

interface AuthResult {
  tier: TierLevel;
  tierSource: TierSource;
  // ...
}
```

## Применимость

«Атрибут пользователя (тир/роль/квалификация) может прийти из нескольких источников с разным уровнем доверия?» → добавить `<attr>_source` поле провенанса к ответу.

## Ценность

Позволяет отлаживать неожиданные fallback-ситуации без изменения бизнес-логики. Без провенанса: видим значение "T1" — не знаем, это клейм или дефолт. С провенансом: "T1" + `tierSource: "fallback"` → понятно, что авторизация деградировала.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| «Значение уже правильное, зачем ещё поле» | Внимание фокусируется на корректности итогового значения (tier=T1), провенанс воспринимается как избыточная деталь, пока не понадобится отладка |
| «Fallback — редкий случай, не стоит отдельного поля» | Практикующий недооценивает частоту деградации multi-source цепочки; провенанс добавляется постфактум, после инцидента, а не заранее |
| «Один источник — авторизация надёжна» | Наличие значения воспринимается как признак надёжного источника; различие между claim/db/fallback стирается в восприятии, пока явно не выведено полем |
| «Провенанс — только для дебага, в проде не важен» | Поле помечается как dev-only и не документируется в контракте API; в проде именно там, где деградация критична, provenance-поле отсутствует или не мониторится |
