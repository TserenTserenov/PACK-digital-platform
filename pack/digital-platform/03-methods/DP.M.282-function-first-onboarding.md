# DP.M.282 — Function-First Onboarding

## Описание

Паттерн онбординга сложной инструментальной системы: сначала показывать что система делает (функции для пользователя), откладывать объяснение механизма (термины и архитектура).

Ключевая метафора: «ты уже носишь костюм, просто он разобран» — снимает страх «я ещё не готов», потому что человек уже в процессе использования.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Снижение тревоги пользователя ↔ точность терминологии | Метафора и function-first снижают барьер, но могут искажать или упрощать архитектуру, если не довести до точных терминов позже |
| Скорость получения ценности ↔ глубина понимания | Practice-first быстрее даёт результат, но пользователь может начать злоупотреблять функциями без понимания ограничений |
| Простота материалов ↔ корректность | Избегание терминов делает вход легче, но может скрыть важные различения, необходимые для безопасного использования |
| Единый онбординг ↔ разные уровни подготовки | Один поток function-first подходит многим, но продвинутым пользователям может не хватить глубины, а новичкам — не хватить повторений |
| Объём explainer-модуля ↔ вероятность его прохождения | Глубокая архитектура вынесена в отдельный модуль; если он слишком длинный, его пропускают, и пользователь остаётся без терминов |

## Три элемента паттерна

1. **Метафора снятия барьера** — переформулировать «ещё не готов» в «уже начал». Конкретная метафора под систему (костюм, велосипед, …).
2. **Function-First presentation** — называть что делает для пользователя, не как устроена. Примеры для IWE: «помнит», «знает стиль», «читает заметки» вместо «MCP», «скрипты», «агенты».
3. **Practice-then-Explain** — сначала 2 минуты делаем (практика), потом объясняем структуру. Глубокая архитектура (MCP/скрипты/агенты) → видео-модуль или третий семинар.

## Алгоритм применения

1. Определить 3-5 ключевых функций системы с позиции пользователя (глаголы: «запоминает», «напоминает», «предлагает»)
2. Подобрать несущую метафору (аналогия из физического мира), снимающую барьер «не готов"
3. Открыть онбординг с практикой (2-5 минут работы в системе)
4. Объяснить структуру после того, как пользователь почувствовал ценность
5. Вынести механизмы (архитектура, конфигурация) в отдельный модуль для желающих

## Тест применимости

Применимо, если: (1) система имеет ≥5 технических терминов в документации; (2) пользователь может получить ценность без понимания архитектуры.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| «Сначала объясни архитектуру, потом используй» | Классический порядок онбординга; пользователь перегружается терминами до того, как почувствовал ценность, и бросает |
| «Если не знает терминов, значит не готов» | Практикующий требует понимания MCP/скриптов/агентов перед практикой, завышая порог входа |
| «Метафора достаточна, детали — потом» | Function-first без обязательного follow-up explainer-модуля; пользователь застревает в edge cases, не понимая архитектуру |
| «Объяснительный модуль всё равно никто не смотрит» | Глубокий модуль выбрасывается или делается слишком коротким; продвинутые пользователи остаются без терминов |
| «Один онбординг подходит всем» | Игнорирование уровней подготовки: функции-first работает для многих, но не адаптируется ни под новичков, ни под опытных |
