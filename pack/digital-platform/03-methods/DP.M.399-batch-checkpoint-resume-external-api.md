# DP.M.399 — Checkpoint и resume-on-crash для batch-прогонов с внешним API

## Суть метода

Любой batch-прогон, обращающийся к внешнему API-ключу на каждую запись, обязан сохранять checkpoint каждые N записей и уметь возобновляться с последнего checkpoint при обрыве. Разовая проверка ключа перед стартом прогона не защищает от обрыва в середине выполнения.

## Проблема

Прогон без checkpoint, упавший на записи 400 из 700 (обрыв соединения, rate limit, краш процесса), теряет весь прогресс. Перезапуск с нуля не просто тратит время повторно — при внешнем API это удваивает стоимость вызовов (пилот платит за уже сделанные 400 записей ещё раз).

## Алгоритм

1. Определить размер шага checkpoint (N записей — баланс между накладными расходами записи checkpoint и объёмом теряемой работы)
2. После каждых N успешно обработанных записей — сохранить прогресс (id последней записи, промежуточный результат) в персистентное хранилище
3. При старте прогона — проверить наличие checkpoint: если есть, продолжить с последней сохранённой позиции, не с начала
4. Разовая проверка API-ключа перед стартом остаётся обязательной, но не заменяет checkpoint — она ловит только «ключ невалиден с самого начала», не обрыв в процессе

## Тест

«Если прогон упадёт на середине, что теряется — вся работа или только последние N записей?» Первое — checkpoint отсутствует, метод не применён. Второе — метод применён.

## Связи

- Применимо к любому batch-прогону с платным или лимитируемым внешним вызовом на запись
