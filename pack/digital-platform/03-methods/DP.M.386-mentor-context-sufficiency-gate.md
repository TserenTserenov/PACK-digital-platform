# DP.M.386 Mentor Context-Sufficiency Gate

## Определение

Метод собирает воедино два уже принятых решения РП-498 Ф4 (маршрутизация между ролями-компонентами и grounding-гейт для предметника) в единый явный шаг ПЕРЕД генерацией ответа Наставника (Режим 2, `MIM.R.001`), а не как самоотчёт модели внутри генерации.

Два предварительно решённых компонента:
1. **RAG-поиск (grounding-check)** — поиск релевантного `PD.METHOD.*` в PACK-personal ДО вызова генерирующей модели. Детерминированный порог релевантности, не решение самой генерирующей модели.
2. **Диспетчер-промпт (routing)** — одна модель получает описание всех 4 ролей-компонентов связки (Диагност/Навигатор/Преподаватель-лидер/Преподаватель-предметник) и правил переключения, сама решает по ходу генерации, какая роль отвечает на какую часть сообщения.

## Почему один шаг, а не два независимых прохода

`DP.SOTA.035 §4` фиксирует поле-подтверждённый паттерн: оценка достаточности контекста должна быть отдельным шагом ДО генерации, потому что модели плохо самооценивают неопределённость (RAG paradox — доля ошибок растёт именно при частично достаточном контексте, не при полном его отсутствии).

Но РП-498 уже решил маршрутизацию как ОДИН вызов модели (диспетчер-промпт), а не отдельный классификатор до генерации. Дублирование вторым независимым LLM-проходом «достаточно ли контекста» было бы избыточным. Решение: результат RAG-поиска (найден источник / не найден) передаётся ВНУТРЬ диспетчер-промпта как часть контекста, а не проверяется post-hoc после генерации и не запрашивается отдельным вызовом модели.

## Алгоритм

1. **RAG-поиск по PACK-personal** (детерминированный, вне генерирующей модели) — до вызова диспетчер-промпта:
   - Найден `PD.METHOD.*` выше порога релевантности → в контекст передаётся `method_id` + текст метода.
   - Не найден → в контекст передаётся явный флаг `no_grounding_source`.
2. **Диспетчер-промпт** (один вызов генерирующей модели) получает:
   - описание всех 4 ролей-компонентов и правил переключения между ними;
   - результат шага 1 как часть контекста (найденный метод либо флаг отсутствия);
   - cp-профиль пилота, если есть, либо явный флаг его отсутствия/устарелости.
   Модель маршрутизирует ответ между ролями-компонентами по ходу генерации. Если активируется роль-компонент Преподаватель-предметник без grounding-источника в контексте — модель обязана явно сказать «не хватает источника», а не отвечать из общих знаний (инвариант из `DP.SC.197`).

## Отличие от классического двухэтапного field-паттерна

`DP.SOTA.035` описывает два независимых прецедента: GPTCoach (3 последовательных LLM-вызова, включая отдельный шаг «использовать ли личные данные») и Google autorater (отдельный проход-оценщик достаточности контекста ДО решения, генерировать ли персонализированный ответ). Оба используют отдельный LLM-вызов именно для оценки достаточности.

РП-498 экономит этот отдельный LLM-вызов там, где оценка объективно детерминируема (grounding для предметника — RAG-релевантность, не субъективная оценка модели). Это работает только для ОДНОГО из двух рисков связки. Для второго — достаточности cp-профиля для Диагноста/Навигатора — отдельного детерминированного гейта нет: модель оценивает это внутри того же диспетчер-промпта. `DP.SOTA.035 §8` явно оставляет это открытым вопросом («нужен ли отдельный фактический guardrail помимо gate персонализации» — не закрыто), пилот осознанно принял этот компромисс как часть риска Безопасности, зафиксированного в АрхГейте (см. `DP.SC.197 §Инварианты`).

## Границы (не проектируется в этом методе)

- Конкретное числовое значение порога релевантности RAG — реализация Ф5.
- Точный текст диспетчер-промпта (формулировки правил переключения) — реализация Ф5.
- Канал встраивания (бот/браузер/self-host) — Ф5/Ф6.
