# DP.M.215 SQL NOT EXISTS guard для predicate-based row exclusion

## Описание

Паттерн исключения строк из результата запроса через `NOT EXISTS` guard на дочерней таблице. Применяется когда фильтр должен быть **статус-независимым** — исключать по факту наличия записи, не по значению поля.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Стабильность guard'а к новым статусам ↔ явность семантики статуса | `NOT EXISTS` не ломается при добавлении нового статуса, но теряет информацию о том, «какой именно статус» имеет дочерняя запись; семантика становится скрытой в факте существования |
| Защита legacy-pipeline от протечек ↔ читаемость запроса | Подзапрос `NOT EXISTS` корректно исключает перенесённых пользователей, но делает SQL менее прямым, чем простой фильтр по статусу, и требует понимания схемы |
| Минимальность изменений в legacy ↔ полнота миграции | Guard позволяет не трогать legacy-pipeline, пока идёт перенос, но откладывает полноценную миграцию и может оставить неучтённые краевые случаи |

## IPO

**Вход:** SQL-запрос; дочерняя таблица с признаком включения (например, `marathon_progress`)
**Процесс:** `AND NOT EXISTS (SELECT 1 FROM <child_table> WHERE <join_key> = <parent_key>)` — исключает все строки, имеющие запись в дочерней таблице, независимо от статуса
**Выход:** Результат запроса содержит только строки без записи в дочерней таблице

## Правило

Фильтр по конкретному статусу (`status='active'`, `status IN ('active','paused')`) — ловушка: каждый новый статус требует обновления guard'а.

Правильный паттерн: исключать по факту наличия записи в дочерней таблице, не по значению поля.

## Тест

«Покрывает ли filter все будущие статусы?» Нет → применить NOT EXISTS guard.

## Когда применять

- При добавлении новой архитектуры поверх legacy: есть дочерняя таблица новой системы, пользователи мигрируют порциями, legacy-pipeline должен работать только для тех, кого ещё не перевели.
- Когда множество статусов дочерней сущности может расширяться, а guard должен оставаться стабильным.

## Context note

Чаще всего применяется при legacy isolation — исключение пользователей новой архитектуры из legacy-pipeline. Но паттерн generic: подходит для любого статус-независимого исключения по существованию записи.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего. Epistemic stage карточки — `empirical`._

| Bias | Direction of distortion |
|------|--------------------------|
| Слепое предпочтение `NOT EXISTS` | Практикующий применяет паттерн даже там, где семантика статуса стабильна и понятна, а простой фильтр был бы чище и быстрее; внимание смещается к «статус-независимости» вместо адекватности модели |
| Игнорирование производительности | Фокус на корректности затмевает стоимость коррелированного подзапроса; на больших таблицах `NOT EXISTS` может оказаться дороже индексированного фильтра по статусу |
| Ложная уверенность в «статус-независимости» | Практикующий считает, что любой новый статус автоматически покроется guard'ом, и не пересматривает семантику join-ключа, что может привести к неожиданному включению/исключению строк |
