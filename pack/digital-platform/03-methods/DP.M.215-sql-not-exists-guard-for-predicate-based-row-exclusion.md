# DP.M.215 SQL NOT EXISTS guard для predicate-based row exclusion

## Описание

Паттерн исключения строк из результата запроса через `NOT EXISTS` guard на дочерней таблице. Применяется когда фильтр должен быть **статус-независимым** — исключать по факту наличия записи, не по значению поля.

## IPO

**Вход:** SQL-запрос; дочерняя таблица с признаком включения (например, `marathon_progress`)
**Процесс:** `AND NOT EXISTS (SELECT 1 FROM <child_table> WHERE <join_key> = <parent_key>)` — исключает все строки, имеющие запись в дочерней таблице, независимо от статуса
**Выход:** Результат запроса содержит только строки без записи в дочерней таблице

## Правило

Фильтр по конкретному статусу (`status='active'`, `status IN ('active','paused')`) — ловушка: каждый новый статус требует обновления guard'а.

Правильный паттерн: исключать по факту наличия записи в дочерней таблице, не по значению поля.

## Тест

«Покрывает ли filter все будущие статусы?» Нет → применить NOT EXISTS guard.

## Когда применять

- При добавлении новой архитектуры поверх legacy: есть дочерняя таблица новой системы, пользователи мигрируют порциями, legacy-pipeline должен работать только для тех, кого ещё не перевели.
- Когда множество статусов дочерней сущности может расширяться, а guard должен оставаться стабильным.

## Context note

Чаще всего применяется при legacy isolation — исключение пользователей новой архитектуры из legacy-pipeline. Но паттерн generic: подходит для любого статус-независимого исключения по существованию записи.
