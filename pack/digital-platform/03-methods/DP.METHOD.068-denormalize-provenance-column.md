# DP.METHOD.068: Денормализация провенанс-колонки vs отдельная canonical-таблица

## Назначение

Метод принятия решения о хранении reference-данных (провенанс, источник, аннотация) при наличии внешнего source-of-truth.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Простота структуры (денормализованная колонка) ↔ риск мёртвого инвентаря отдельной таблицы | Вариант Б (`ALTER TABLE concepts ADD COLUMN name_en_source`) избегает второго canonical и мёртвого инвентаря (108 из 686 терминов без узла в графе), но отказывается от возможности хранить в справочнике доп. метаданные, которые дала бы отдельная таблица |
| OwnerIntegrity (один факт — одно место) ↔ удобство запроса reference-данных | Денормализация ссылки в сущность защищает от второго владельца фактов (csv-словарь остаётся единственным canonical), но платит за это тем, что сама сущность (`concepts`) обрастает дополнительным полем-ссылкой вместо чистой структуры с вынесенными reference-данными в отдельную таблицу с удобными join'ами |

## Развилка

При добавлении провенанс-поля к сущности (`source`, `name_en_source`, `origin`) возникает развилка:

| Вариант А: отдельная таблица-справочник | Вариант Б: денормализованная колонка |
|----------------------------------------|--------------------------------------|
| `CREATE TABLE concept_anchor(...)` | `ALTER TABLE concepts ADD COLUMN name_en_source` |
| Отдельная структура рядом с сущностью | Поле прямо в сущности |
| Содержит термины из внешнего источника | Содержит только ссылку/метку источника |

## Критерий выбора

**Если** внешний source-of-truth (csv, Pack-файл, API) уже является canonical:

→ **Вариант Б (денормализованная колонка)**.

Причины против Варианта А:
1. **Второй canonical.** Таблица-справочник дублирует содержимое внешнего источника → нарушение OwnerIntegrity: один факт в двух местах.
2. **Инвентарь вне-графа.** Термины из csv, не имеющие соответствующего узла в графе (108 из 686), попадают в таблицу и создают «мёртвый инвентарь» — сущности вне домена без потребителей.
3. **Смешение источника и потребителя.** Таблица смешивает csv (источник) с графом (потребитель).

## Тест OwnerIntegrity

«Эта новая таблица становится вторым владельцем фактов, которыми уже владеет внешний источник?»
- Да → денормализовать reference-колонку, не создавать canonical.
- Нет (таблица хранит derived/processed данные) → отдельная таблица допустима.

## Применение в WP-439

Развилка Q1: `concept_anchor` (Вариант А) vs колонка `name_en_source` в `concepts` (Вариант Б). csv-словарь РП415 = canonical. Создание `concept_anchor` = второй canonical + 108 терминов-вне-графа как мёртвый инвентарь. Выбор: Вариант Б (denormalized column).

## Bias-Annotation

_Куда систематически съезжает внимание практикующего. Статус карточки — `draft`: пометка `tentative`._

| Bias | Direction of distortion |
|------|--------------------------|
| _(tentative)_ Рефлекс к нормализации | При проектировании provenance-поля внимание по умолчанию тянется к «create reference table» (привычный реляционный паттерн), минуя явный Тест OwnerIntegrity («эта таблица становится вторым владельцем фактов?») — тест из метода легко пропускается именно потому, что создание таблицы кажется «более правильным» дизайном по умолчанию |
| _(tentative)_ Статус canonical внешнего источника принимается на веру | Выбрав Вариант Б, внимание не возвращается к проверке, действительно ли внешний source-of-truth (csv, Pack-файл) актуален и полон — денормализованная колонка обязывает доверять внешнему источнику как canonical, но сам факт canonical-статуса в момент выбора не перепроверяется |

## Связи

- Принцип: OwnerIntegrity (один факт — одно место)
- Против паттерна: «Inventory ≠ Progress» (мёртвый инвентарь не является throughput)
- Применение: «Source-of-truth ≠ Производный» (HD #27)
