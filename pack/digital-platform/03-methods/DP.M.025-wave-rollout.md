# DP.M.025 — Волновое развёртывание (Wave Rollout)

## Описание

Стратегия безопасного масштабирования новой функциональности или когорты пользователей через последовательные волны с паузами на устранение блокеров.

**Принцип:** при неизвестной нагрузке или неполном feature coverage — запускать по нарастающей, каждая следующая волна стартует только после прохождения hard-gate блокеров предыдущей.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Скорость достижения целевого N ↔ безопасность обнаружения блокеров | Короткое окно между волнами (< 3-5 дней) быстрее доводит масштабирование до 100%, но не оставляет времени вскрыть hard-gate блокеры предыдущей волны до старта следующей — метод фиксирует минимум 3-5 дней именно ради этого зазора |
| Размер пилотной волны N₁ (~10% N) ↔ репрезентативность найденных блокеров | Маленький N₁ снижает риск на старте, но часть блокеров проявляется только на масштабе N₂ (~30-50%) — пример R1-cohort показывает, что bulk-onboarding, activity emitter и stage_evaluator вскрылись именно между волной 1 и 2, а не в самом пилоте |

## Input → Process → Output

**Input:**
- Новый сервис/feature или новая когорта с неизвестной нагрузкой
- Список hard-gate блокеров (critical bugs, missing features)
- Целевой объём пользователей N

**Process:**
1. Определить волны: N₁ (пилот, ~10% N) → N₂ (~30-50% N) → N₃ (100%)
2. Установить временные окна между волнами (минимум 3-5 дней)
3. Для каждой волны — список hard-gate блокеров, которые ДОЛЖНЫ быть закрыты до следующей волны
4. После каждой волны: мониторинг метрик, фиксация новых блокеров
5. Следующая волна — только после закрытия всех hard-gate

**Output:** Масштабирование до целевого N без критических инцидентов; каждый блокер задокументирован и закрыт

## Пример применения (R1 cohort, май 2026)

Волны: 5 → 15 → 30 участников, окна: 13 / 16-17 / 20-22 мая
Hard-gate блокеры волны 1→2: bulk-onboarding, activity emitter, stage_evaluator, UI баллов

## Антипаттерн

Добавить всех пользователей одновременно при неполном feature coverage → failure modes возникают у всей базы → невозможно изолировать и устранить инцидент.

## Применимость

- Первый запуск нового сервиса для внешних пользователей
- Добавление новой когорты к существующей платформе
- A/B-тест с риском деградации опыта
- Deploy с неизвестной нагрузкой на инфраструктуру
