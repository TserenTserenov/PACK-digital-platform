# DP.M.451 — Блокировать дамп-команды по идентичности команды, а не по форме значения

## Определение

Guard утечки секретов держит два независимых контура обнаружения: (1) сигнатурный — по форме значения в тексте (похоже на API-ключ/токен по регэкспу); (2) по идентичности команды — отдельный список команд, чей штатный вывод есть всё окружение или всё хранилище секретов открытым текстом. Команды второго класса блокируются по факту вызова, до выполнения и независимо от того, что оказалось бы в выводе.

## Проблема

Сигнатурный анализ формы (PATTERNS/ASSIGNMENT_PATTERNS) структурно не может поймать то, чего никогда не видел: специфичные для приложения токены, произвольные пароли, значения без узнаваемого префикса. Голый `env`/`printenv` без аргумента или `railway variables` печатают весь стор секретов сразу — вывод может не содержать ни одной формы, которую сканер вообще способен опознать. Итог: сканер «работает», а самый массовый канал утечки (дамп целиком) проходит.

## Метод

1. **Разделить риск по источнику.** Для каждого проверяемого класса спросить: риск определяется ТЕМ, ЧТО запущено (дамп целиком), или ТЕМ, ЧТО оказалось в выводе (форма значения)?
2. **Для класса «дамп целиком» — список идентичностей.** Отдельный denylist команд-нарушителей: `env`/`printenv` без позиционного аргумента, `railway variables`/`railway variable` и аналоги для других менеджеров секретов. Блокировка — по факту вызова, до выполнения.
3. **Позиционный аргумент меняет класс.** `printenv HOME` печатает одно значение — это не дамп; его проверяет сигнатурный контур, а не блокировка по идентичности. Denylist привязан к форме вызова (имя + отсутствие аргумента), не только к имени.
4. **Оставить сигнатурный контур для остального.** Второй контур не заменяет первый — он закрывает класс, недоступный первому по построению.

## Ключевые свойства

- **Два контура — две разные структурные гарантии.** Сигнатурный контур гарантирует «известная форма не пройдёт»; контур идентичности — «известная команда-дамп не запустится». Ни один из них не покрывает второй, и расширение списка паттернов не заменяет второй контур.
- **Denylist здесь — не blocklist по подозрительным именам.** Список закрывает конкретный, перечислимый класс (команды, чей контракт — печать всего хранилища), а не «имена, похожие на опасные»; перечислимость класса — условие применимости.
- **Проверка до выполнения.** Блокировка по идентичности не нуждается в выводе команды, поэтому не имеет окна между запуском и проверкой.

## Когда применять

**Тест:** «Есть ли команда, штатный вывод которой — целое хранилище значений, среди которых могут быть секреты без узнаваемой формы?» Да → её нужно блокировать по идентичности; сигнатурный контур по форме её не закроет ни при каком расширении списка паттернов.

## Отличие от смежного

- **DP.METHOD.163 (CI allowlist вместо blocklist для env-bindings):** та же логика «поиск по признаку пропускает неизвестные формы, явный список закрывает класс», но другой объект и слой: там — имена конфигурационных привязок в CI, здесь — идентичности исполняемых команд в runtime-guard агента; там — allowlist разрешённого, здесь — denylist перечислимого класса дампов рядом с сигнатурным контуром.
- **DP.FM.379 (самообходимый секрет-маркер):** слепое пятно сигнатурного контура в его собственном метаязыке исключений; здесь — слепое пятно сигнатурного контура на классе команд, а не на разметке.
- **DP.M.450 (сужение сканируемого текста перед сопоставлением):** тот же день и семейство guard-хуков; там — как уменьшить ложные срабатывания сигнатурного контура; здесь — какой класс сигнатурному контуру не по силам вовсе.
- **DP.D.296 (деградирующий парсер ≠ отказывающий):** политика при непонятом вводе; здесь — выбор контура обнаружения по источнику риска.

## Применимо к

Любой guard утечки секретов/окружения (pre-tool-use hook агента, pre-commit, CI-шаг), стоящий перед командами с доступом к переменным окружения или CLI менеджеров секретов (railway и аналоги).
