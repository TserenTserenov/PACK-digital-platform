# DP.METHOD.189 — Operator-first rollout

## Определение

При выкатке новой функциональности (алерты, метрики, модель LLM, конфиг поведения) в multi-tenant системе: сначала включить только на аккаунте оператора (себя), убедиться в корректности, затем расширять на managed-пользователей.

## IPO

- **Вход:** новый компонент готов к деплою; есть managed-пользователи помимо оператора
- **Процесс:** выставить `enabled=false` для managed-пользователей, `enabled=true` только для операторского аккаунта; наблюдать N единиц времени; при подтверждении — включить для остальных
- **Выход:** прогрессивный rollout с живой приёмкой оператора до расширения

## Диагностический тест

«Если это сломается в 03:00, это сломает мой собственный аккаунт или чужой?» → Запускай на своём первым.

## Применимость

1. Новые метрики/алерты — убедиться, что не шумят на реальных данных
2. Смена модели LLM (e.g., Haiku → Sonnet) — проверить quality+latency на своих данных
3. Новые конфигурационные поведения — калибровать на себе прежде чем включать для managed

## Реализация

Через feature-flag (поле `enabled` в конфиге), а не через удаление кода или отдельные деплои. Остаточный риск (latency, бюджет, нежелательное поведение) переносится на оператора — не на пользователей.
