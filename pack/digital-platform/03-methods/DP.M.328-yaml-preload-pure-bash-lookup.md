# DP.M.328 — Preload-once парсинг конфига → pure-bash lookup

## Описание

Скрипт, многократно читающий значения из YAML/JSON-конфига через дорогой внешний
интерпретатор (`python3 -c "import yaml"`, `yq`, `jq`), на каждый вызов `read_yaml()`
порождает отдельный subprocess. При N вызовах = N spawn'ов. Метод: распарсить конфиг
**один раз при старте** в параллельные bash-массивы (`_YAML_KEYS` / `_YAML_VALS`),
последующие lookup'ы — pure-bash цикл по индексам без spawn'ов.

Обобщение: любое дорогое вычисление, переиспользуемое ≥2 раз (вызов CLI, сетевой
запрос, тяжёлый парсинг), вынести в одно вычисление + дешёвое переиспользование.
Частный случай в той же правке — `SWEEP_WP_FULL`: предвычислить один раз, переиспользовать
на втором call-site.

## Forces

| Force | Tension |
|-------|---------|
| Простота построчного `read_yaml()` ↔ стоимость N subprocess-вызовов | Вызов интерпретатора на каждое поле читается прямолинейно, но масштабируется линейно по числу lookup'ов — простота кода конфликтует со временем выполнения |
| Единовременная стоимость preload ↔ выигрыш на множестве lookup'ов | Preload требует написать чуть более сложный bootstrap-код и распарсить весь конфиг сразу, даже если не все поля понадобятся — но окупается уже с 3-го обращения |
| Читаемость pure-bash поиска по массиву ↔ привычность вызова `jq`/`yq` | Индексный цикл по параллельным массивам менее идиоматичен для читателя, привыкшего видеть `yq '.key'`; выигрыш в скорости не всегда очевиден с первого взгляда на код |
| Общность метода (любое дорогое переиспользуемое вычисление) ↔ конкретность примера (YAML) | Формулировка обобщена на любые дорогие вызовы, но конкретная реализация (`_YAML_KEYS`/`_YAML_VALS`) специфична к key-value конфигу, не переносится дословно |

## IPO

| Вход | Обработка | Выход |
|------|-----------|-------|
| Конфиг + ≥3 точек чтения | Один parse при старте → bash-массивы; lookup = индексный цикл | Тот же результат, N→1 subprocess-вызовов |

## Алгоритм

```bash
# Старт: один parse в параллельные массивы
_preload_yaml() {
  local out; out=$(python3 -c 'import yaml,sys
d=yaml.safe_load(open(sys.argv[1]))
[print(f"{k}\t{v}") for k,v in d.items()]' "$1")
  while IFS=$'\t' read -r k v; do _YAML_KEYS+=("$k"); _YAML_VALS+=("$v"); done <<< "$out"
}

# Lookup: pure-bash, без spawn
read_yaml() {
  local i; for i in "${!_YAML_KEYS[@]}"; do
    [[ "${_YAML_KEYS[$i]}" == "$1" ]] && { printf '%s' "${_YAML_VALS[$i]}"; return; }
  done
}
```

## Тест применимости

«Сколько раз скрипт зовёт дорогой инструмент (python/jq/yq/awk) с одним и тем же входом?»
≥3 → применить preload-once. 1-2 → не усложнять.

## Признак нарушения

- `read_yaml()` / `jq` / `yq` внутри цикла или вызываемый на каждое поле
- Профиль скрипта показывает десятки spawn'ов одного интерпретатора за прогон

## Практический пример (Day Open, FMT-exocortex-template 51cb56d)

`day-open-scaffold.sh`: preload YAML один раз вместо ~10 `read_yaml()`-spawn'ов за Day Open;
`SWEEP_WP_FULL` предвычислен один раз и переиспользован на втором call-site.

## Bias-Annotation

| Bias | Direction of distortion |
|------|--------------------------|
| «`read_yaml()` — уже готовая абстракция, зачем её трогать» | Внимание фиксируется на наличии удобной функции-обёртки, не доходит до подсчёта, сколько раз она реально вызывается за прогон скрипта |
| «Один subprocess — это же быстро» | Оценка стоимости одного вызова верна, но систематически не переносится на оценку N вызовов в сумме за весь скрипт |
| «Профилирование — лишний шаг, и так понятно, где медленно» | Интуитивная догадка о месте узкого места подменяет фактический замер числа spawn'ов, из-за чего preload применяется не там, где реально нужен, или не применяется вовсе |
| «Это разовый скрипт, не стоит оптимизировать» | Скрипт, изначально задуманный как разовый (day-open, cron), со временем становится вызываемым многократно за день — недооценка будущей частоты вызовов |
