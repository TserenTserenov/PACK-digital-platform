# DP.M.178 — Quick-close триаж РП: трёхшаговый фильтр

## Проблема

Один числовой фильтр (бюджет ≤Xh + статус ⏳ + не зонтичный + не в ТОС) при триаже backlog'а из десятков РП даёт false-positives:
- **stale-РП** — формальный статус «in_progress», но нет git-активности неделями (пример: WP-190)
- **скрыто-заблокированные** — `blocked_by: []`, но реальный блокер — внешний endpoint не поднят (пример: WP-355 → dash.pwapps.com из WP-302)

Результат: «готовые к закрытию» попадают РП, которые на деле застряли.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Скорость триажа backlog'а из десятков РП ↔ точность отсева ложных кандидатов | Шаги 2–3 (git spot-check, blocker-проверка через curl/DNS/health-check) стоят времени на каждый прошедший шаг 1 РП, но на практике отсекают ~50% таких кандидатов — экономия на отменённых «открыть-обнаружить-закрыть» превышает стоимость проверок |
| Доверие к формальным полям (статус, бюджет, `blocked_by`) ↔ стоимость верификации реального состояния | Числовой pre-filter бесплатен и масштабируется на любой backlog, но формальный статус расходится с фактическим (stale-РП без коммитов, скрытые внешние блокеры при пустом `blocked_by: []`); метод платит двумя проверками за согласование декларации с реальностью только для финалистов, а не для всей очереди |

## Трёхшаговый фильтр

**Шаг 1 — Числовой pre-filter:**
- статус ∈ {pending, in_progress, blocked}
- бюджет ≤ N часов (порог триажа)
- не зонтичный (`umbrella: false`)
- не в ТОС (узкое место не задействовано)

**Шаг 2 — Spot-check git-активности:**
- читать `inbox/WP-N-*.md` last commit
- `git log --since="30 days ago" -- <target-path>` по основному target-репо РП
- отсутствие коммитов >30 дней → stale, исключить или перевести в `status: dormant`

**Шаг 3 — Blocker-проверка:**
- `blocked_by: []` недостаточно
- читать context-файл на упоминания внешних endpoints / аккаунтов / устройств («требует X», «ожидает Y»)
- если найдено — проверить (`curl -I`, DNS, health-check) и при недоступности — `blocked_by` неявный, исключить

## Результат на практике

На WP-триаже 2026-05-26 отсёк ~50% кандидатов, прошедших Шаг 1. Один stale-РП (WP-190) и один скрыто-заблокированный (WP-355).

## Применимость

- триаж backlog'а РП / задач / тикетов
- любая очередь, где формальный статус может расходиться с реальным
- особенно ценно для очередей десятки+ элементов, где экономия времени на отсев существенна

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| Порог триажа якорится на первых просмотренных РП | Практик калибрует «что считать подозрительным» по первым 2-3 карточкам из выборки, а не по критериям из метода — весь остальной пул оценивается относительно случайного эталона, а не порога шага 2 |
| Легко проверяемые блокеры затмевают человеческие | Внимание идёт к признакам, проверяемым HTTP-запросом (endpoint жив? токен валиден?), а блокеры класса «человек/устройство/организация» (владелец в отпуске, iPhone не у пилота, методсовет не собирался) остаются недопроверенными — формальные поля карточек их не отражают |

## Антипаттерн

Применять только числовой фильтр и доверять `blocked_by: []` → ложные старты, потерянное время на «открыть-обнаружить-закрыть».
