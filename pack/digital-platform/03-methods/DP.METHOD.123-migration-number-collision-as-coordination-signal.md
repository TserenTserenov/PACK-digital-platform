# DP.METHOD.123 — Занятый номер как сигнал параллельной работы

## Описание

В системах с последовательной нумерацией артефактов (миграции БД, документы, тикеты) коллизия номера — не только техническая ошибка, но и сигнал того, что параллельный агент уже работает над смежной задачей. Реакция: прочитать чужой артефакт, не создавать конкурирующий.

## IPO

**Input:** попытка создать артефакт с номером N; обнаружение, что N уже занят

**Process:**
1. До создания артефакта: `ls migrations/ | tail -5` (или аналог) — не только `grep max_id`
2. При коллизии: прочитать существующий артефакт с тем же номером
3. Оценить пересечение задач: совпадают → адаптировать (не дублировать); расходятся → взять следующий свободный номер и явно сослаться на прочитанный
4. Если оба агента сошлись независимо на одном техническом решении — зафиксировать как сигнал устойчивости решения

**Output:** артефакт без дубликата; при совпадении подходов — повышенная уверенность в решении

## Пример

WP-455: агент выбрал номер 275 для новой миграции. Файл уже существовал (создан параллельной peer-сессией WP-457 Ф12). Чтение показало: оба агента независимо пришли к одному техническому решению (trigger-based immutable chain). Совпадение = подтверждение верности подхода. Итог: один общий артефакт вместо конкурирующих.

## Тест применимости

«Перед созданием артефакта с номером N — была ли проверка `ls` / `find`, а не только `max(existing_ids)`?» Нет → риск пропустить сигнал коллизии.

## Антипаттерн

Вычислять `max(id) + 1` без листинга директории — пропускает артефакты, добавленные параллельными агентами с момента последней синхронизации.
