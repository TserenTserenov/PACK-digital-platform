# Тест как живая спецификация (DP.METHOD.100)

## Описание

Тест — не инструмент проверки реализации, а живая спецификация ожидаемого поведения системы. Хороший тест читается как требование: «при этом входе — этот выход, при этом поведении — этот эффект».

## IPO

**Вход:**
- Ожидаемое поведение (контракт, требование)

**Действие:**
1. Перевести требование в наблюдаемый assertion (`assert expected == actual`, не `assert True`)
2. Документировать через тест, а не через prose-документацию

**Выход:**
- Исполняемый артефакт, одновременно описывающий и верифицирующий контракт

## Инварианты

**Тест без observable assertion — не тест.** `assert True`, вечно-зелёный тест, тест без ожидаемого значения — шум, не спецификация.

**Документация устаревает; тест устаревает вместе с кодом.** При рефакторинге тест-спецификация фиксирует нарушение контракта автоматически.

## Ортогональность TDD

Метод не тождественен TDD («тест сначала»). Суть: тест = живая спецификация требования, независимо от момента написания.

## Применение

- Behavior tests (поведение системы), не unit tests реализации
- Любой артефакт с формальным контрактом: парсер, API-ответ, FSM-переход
- Ревью: «что показывает этот тест о поведении системы?» Нет ответа → тест слабый
