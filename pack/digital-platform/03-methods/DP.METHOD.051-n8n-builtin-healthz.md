# DP.METHOD.051 — n8n встроенный /healthz endpoint

## Описание

n8n предоставляет нативный `GET /healthz` endpoint (HTTP 200, body `{"status":"ok"}`), доступный без аутентификации, пока процесс жив. Отдельный воркфлоу для health-check не нужен.

## Когда применять

При деплое n8n на Railway или других хостингах, когда нужен внешний мониторинг (BetterStack, UptimeRobot и т.п.).

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Простота нативного `/healthz` (0 доп. воркфлоу) ↔ глубина проверки | Встроенный endpoint экономит время реализации (не нужен отдельный health-check воркфлоу), но проверяет только «жив ли процесс» (Ограничения), не «работает ли LLM pipeline» — экономия setup-времени обменивается на слепоту к функциональным сбоям (→ DP.FM.105) |
| Строгость keyword-check (Шаг 3) ↔ скорость настройки монитора | Обязательная проверка содержимого body (`"status":"ok"`), а не просто HTTP 200, добавляет шаг конфигурации в мониторинге (BetterStack/UptimeRobot keyword rule), но без неё монитор даёт false-green при HTTP 200 + 0 bytes — метод жертвует «настроил за минуту» ради устранения именно этого провала |

## Алгоритм

1. Настроить монитор на `GET https://<n8n-host>/healthz`
2. Ожидаемый ответ: HTTP 200, body содержит `"status":"ok"`
3. Keyword-check обязателен (HTTP 200 + 0 bytes = false-green без него)

## Ограничения

- Проверяет только «жив ли процесс», не «работает ли LLM pipeline»
- Для полной проверки пайплайна нужен отдельный probe (DP.FM.105)

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| Ручная проверка вместо настройки монитора | После ручного curl-теста, показавшего HTTP 200, внимание не доходит до настройки keyword-check в самом мониторе (Шаг 3) — практикующий считает «эндпоинт отвечает 200» достаточной валидацией и недооценивает риск false-green (200 + 0 bytes), который метод явно называет |
| Единственный чек вытесняет отдельный probe | Раз `/healthz` ощущается как «тот самый» health-check, внимание смещается в сторону единственного лёгкого чека и уходит от настройки отдельного probe для LLM pipeline (Ограничения → DP.FM.105) — наличие лёгкого рабочего решения вытесняет необходимость более трудоёмкой, но всё ещё нужной функциональной проверки |
