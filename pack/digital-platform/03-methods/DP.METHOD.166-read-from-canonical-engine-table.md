# DP.METHOD.166: Читать канонические данные из таблицы, где пишет engine

## Назначение

Паттерн определения canonical source данных при наличии production-компонента (engine),
который записывает обновления в авторитетное хранилище (БД, объектное хранилище).

## Правило

**Canonical source** = хранилище, в которое пишет production-path.

**Не читать** канонические данные из:

- Локальных JSON/YAML файлов в репо с «тестовыми» значениями
- Файлов, которые не обновляются production-путём автоматически
- Snapshot-кешей без явной синхронизации с engine-записью

## Почему опасны локальные файлы вместо БД

Тестовый файл фиксируется при создании и не обновляется автоматически. Engine пишет данные
в БД при каждом событии. Через N дней файл содержит данные, которые активно противоречат
текущему состоянию — но код читает его без предупреждения.

**Прецедент (WP-149):** `3_GP_graduate.json` в репо содержал инвертированные значения
силы/слабости. Engine пишет в таблицу `digital_twins`. При отладке читался файл → бутылочное
горлышко идентифицировалось неверно (сила ↔ слабость). Фикс: `read_rcs_profile()` переключён
на `SELECT ... FROM digital_twins WHERE user_id = %s`.

## Применение

```python
# Антипаттерн: локальный файл
with open("test_data/3_GP_graduate.json") as f:
    profile = json.load(f)

# Верно: canonical source (куда пишет engine)
profile = db.query(
    "SELECT * FROM digital_twins WHERE user_id = %s",
    user_id
)
```

## Тест

«Если engine обновил данные вчера — откуда читает код?»

- Из БД (canonical source) → верно
- Из файла в репо → потенциально устаревший → пересмотреть

## Область применения

- Генераторы персональных артефактов, читающие профиль/рейтинг пользователя
- Диагностические скрипты, определяющие приоритеты на основе данных из pipeline
- Любой код, где данные обновляются через pipeline, а читаются из отдельного места
