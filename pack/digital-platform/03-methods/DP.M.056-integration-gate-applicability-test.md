# IntegrationGate Applicability Test (DP.M.056)

## 1. Определение

IntegrationGate-каркас (Service Clause → сценарии → роль → реализация) изначально описан в DP.M.008 §IntegrationGate как блокирующий шаг для «нового инструмента, агента, детектора, системы». Этот метод фиксирует **обобщение**: каркас применим к любому repeatable workflow, а не только к программным сервисам.

## 2. Тест применимости (4 признака)

Workflow попадает под IntegrationGate, если выполняются все четыре условия:

| Признак | Вопрос | Источник в Service Clause |
|---------|--------|---------------------------|
| **Явный триггер** | Что/кто запускает workflow? | поле `trigger` |
| **Входы и выходы** | Какие артефакты на входе, какие на выходе? | поля `inputs`/`outputs` |
| **Измеримая инвариант-гарантия** | Что workflow гарантирует потребителю? | поле `invariant` |
| **Режим отказа** | Что происходит при сбое? | поле `failure_mode` |

Если все четыре признака есть — каркас применим, независимо от того, код это или процесс.

## 3. Прецедент

**WP-курсовой конвейер (CD-PIPELINE.md, 2026-05-16, commit 0746686 DS-principles-curriculum):**
- Service Clause: `DP.SC.curriculum-cd` (обещание сервиса публикации курса)
- Сценарии: 6 разных потребителей (автор, Pack-владелец, LLM-builder, пилот, релиз-менеджер, hotfix)
- Декомпозиция: 8 спринтов
- Это **не код-сервис**, а документационно-курсовой конвейер. Каркас сработал.

## 4. Применимость

- Документационные конвейеры (release notes, курсы, гайды)
- Процессы публикации контента (статьи, посты, видео)
- Регулярные ритуалы (Strategy Session, Week Close, audit cycles)
- Любой repeatable workflow с явным потребителем

## 5. Граница применимости

IntegrationGate НЕ нужен для:
- Разовых действий (одноразовый скрипт, ad-hoc исправление)
- Тривиальных правок (bugfix без изменения обещания, рефакторинг)
- Workflow без потребителя (внутренние черновики автора)

## 6. Связь с DP.FM.010

Пропуск IntegrationGate для non-code workflow — частный случай DP.FM.010 «прыжок в реализацию минуя обещание». Расширенный детектор: проверять признаки workflow ДО старта реализации, не только при создании код-сервиса.
