# Резервная копия как метод (DP.M.123)

## 1. Определение

**Резервная копия** — полная копия критичных данных IWE в независимом хранилище, позволяющая восстановить работу при отказе или потере основного источника. Метод регулярного создания таких копий — обязательная привычка в Культуре безопасности (DP.M.122) и условие BYOB (DP.IWE.008).

**Принцип:** не одна копия в одном месте, а **система копий с разной уязвимостью**.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Избыточность копий (правило 3-2-1) ↔ стоимость хранения и усилия поддержки | Метод требует 3 копии на 2 разных носителях + 1 офсайт — дороже и хлопотнее одной копии, но именно разнесённая уязвимость снимает одиночную точку отказа (SSD-баг, блокировка провайдера, локальная катастрофа) |
| Полнота покрытия данных ↔ скорость и проверяемость восстановления | Таблица приоритетов (§3) жертвует копированием всего подряд ради гарантии, что критичное (Pack-репо, заметки, БД, секреты) восстанавливается и проверяется тестом §4 за ≤10 минут без поиска инструкций |

## 2. Правило 3-2-1

Канонический минимум для критичных данных:

| Цифра | Что означает | Зачем |
|---|---|---|
| **3** копии | Исходник + 2 резервные | Одна копия — нет копии. Две копии — нет резерва после первого отказа. |
| **2** разных носителя | Например, локальный диск + облако | Один тип носителя = одна точка отказа (SSD-баг, провайдер закрылся). |
| **1** копия офсайт | Физически отдельно от других | Защита от локальных катастроф (пожар, кража, затопление). |

**Пример минимальной реализации для IWE:**
- Исходник — рабочий ноутбук (Pack-репозитории, заметки).
- Копия 1 — Git remote (GitHub / GitLab под управлением пилота).
- Копия 2 — внешний диск или второе облако с независимым доступом.

## 3. Что копировать

| Что | Приоритет | Метод |
|---|---|---|
| Pack-репозитории | Критический | Git push в remote + локальный clone на втором устройстве |
| Заметки, документы | Критический | Автоматический экспорт в Markdown + Git |
| Базы данных IWE (digital twin, agent traces) | Высокий | pg_dump на расписании + независимое хранилище |
| Секреты (env, ключи) | Высокий | Password manager + офсайт-копия мастер-ключа |
| Медиа, фото | Средний | Облачный бэкап + проверка раз в полгода |

## 4. Тест восстановления

**Резервная копия, которая не восстанавливалась — не существует.**

Раз в месяц или квартал — выполнить тестовое восстановление:
1. Выбрать случайный файл из бэкапа.
2. Восстановить его в отдельную папку.
3. Открыть и убедиться, что содержимое корректно и читается без проблем.

Если восстановление занимает больше 10 минут или требует поиска инструкций — метод недостаточен.

## 5. Различения

| Не путать с | Разница |
|---|---|
| **Синхронизация (Dropbox, iCloud)** | Sync копирует все изменения мгновенно — включая ошибочные удаления. Бэкап версионирует во времени, можно откатиться к состоянию до ошибки. |
| **Экспорт** | Экспорт — единичное действие. Бэкап — регулярный процесс с проверками. |
| **DP.M.047 (стресс-тест бэкапа)** | DP.M.047 — метод проверки восстановления через намеренное удаление и восстановление целиком (платформенный уровень). DP.M.123 — практика пилота по созданию и проверке копий собственной IWE. |
| **Git push** | Git push — частный случай бэкапа (логический). Не покрывает физические носители, секреты вне репо, БД. |

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| Создание копий затмевает тест восстановления | Внимание практика сосредотачивается на настройке копирования (Git push, pg_dump по расписанию, облачный бэкап) и не доходит до регулярного теста из §4 — хотя карточка прямо фиксирует: «резервная копия, которая не восстанавливалась — не существует» |
| Удобство синхронизации читается как наличие бэкапа | Внимание тянется к работающему «из коробки» sync (Dropbox, iCloud) как к готовому решению, и различение из §5 — sync мгновенно копирует и ошибочные удаления, тогда как бэкап версионирует во времени, — перестаёт проверяться при выборе инструмента |

## 6. Антипаттерны

- **«У меня всё в облаке, провайдер бэкапит»** — провайдер защищает себя, не доступ пилота. Блокировка аккаунта = потеря всего.
- **«Бэкап на том же диске»** — отказ диска = потеря исходника и копии одновременно.
- **«Сделаю когда понадобится»** — настройка бэкапа после катастрофы невозможна. Бэкап = страховка до аварии.
- **«Никогда не тестировал восстановление»** — нерабочий бэкап эквивалентен отсутствию бэкапа.
