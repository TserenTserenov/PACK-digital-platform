# DP.METHOD.137 — Поэтапная миграция с read-path первым и отложенным необратимым шагом

## Описание

Паттерн прохождения АрхГейта при ❌ по обратимости: необратимое действие (удаление колонки, смена идентификатора) разбивается на два этапа. Этап 1 — переключение read-path (обратимо, можно откатить). Этап 2 — физическое удаление — откладывается с явной датой пересмотра и машинной проверкой-предусловием.

## IPO

**Input:** необратимая миграция с ❌ по Эволюционируемости или Безопасности на АрхГейте

**Process:**

**Этап 1 — read-path (обратимый):**
- Переключить логику чтения на новый ключ/столбец
- Старые данные остаются, write-path не тронут
- Выкатить на pilot-ветку
- Запустить verify-скрипт против прод-БД как условие промоции

**Этап 2 — необратимый (отложенный):**
```
next_review: YYYY-MM-DD  # конкретная дата, не «когда-нибудь»
precondition: verify-script-passes-in-prod
action: DROP COLUMN / DELETE old data
```
Дата пересмотра и предусловие фиксируются в WP-контексте явно — не в голове.

**Output:** миграция с обратимым шагом 1 и управляемым необратимым шагом 2

## Когда применять

- Консолидация идентификаторов (старый → новый key)
- Удаление deprecated-колонок
- Смена primary key / сложная schema-миграция
- Любой АрхГейт с ❌ по Эволюционируемости из-за необратимости

## Антипаттерн

«Сделаем всё за один деплой» — одновременная смена read-path + удаление данных = необратимо, без возможности отката. Если что-то пошло не так в проде, восстановление стоит дорого.

## Ключевой принцип

Необратимость режется на обратимый шаг + отложенный необратимый с датой пересмотра и машинной проверкой. Связка «АрхГейт-профиль → поэтапный план» — стандартный способ пройти гейт при ❌ по обратимости.
