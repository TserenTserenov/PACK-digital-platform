# DP.M.457 — Таблица «Результат | Факт | Зависит от»

## Проблема

При актуализации координирующего РП с несколькими результатами возникает соблазн выстроить их в единую вертикальную очередь («сначала инфраструктура, потом продукт, потом продажи»). Такая очередь искусственно замораживает параллельную подготовку результатов, у которых на самом деле разные и не всегда пересекающиеся предпосылки.

## Метод

Результаты координирующего РП фиксируются таблицей из трёх колонок:

| Результат | Факт | Зависит от |
|---|---|---|
| <результат 1> | <текущее фактическое состояние> | <явные условия, если есть> |
| <результат 2> | <текущее фактическое состояние> | — (нет условия → нет блокировки) |

Порядок строк не создаёт зависимостей — подготовка может идти параллельно везде, где в колонке «Зависит от» нет явного условия. Завершение результата требует только условий, явно перечисленных в ЕГО СОБСТВЕННОЙ строке, а не факта, что более ранняя по тексту строка уже завершена.

Отдельно перечисляется, что НЕ является условием (пример из прецедента: «завершение S1/S2 и доказанный спрос — не условие полного MVP»), чтобы не домысливать зависимости, которых в таблице нет.

## Тест метода

«Можно ли стартовать результат N, не дожидаясь результата N-1?» — если да, вертикальной очереди быть не должно; зависимость (если реально есть) указывается явно в колонке «Зависит от» именно этого результата, не подразумевается порядком строк.

## Применимо

Координирующие/зонтичные РП с несколькими результатами, где часть работ реально независима, но по инерции описывается как последовательная очередь.

## Связи

- DP.D.216 (Outcome-DoD ≠ Output-DoD) — смежная тема закрытия результата по факту, не по ощущению готовности; разные типы сущности (distinction vs method).
- DP.WP.016 (Stage Dependency Map) — похожий по духу формат (явные зависимости вместо неявного порядка), но другой рабочий продукт: граф этапов устранения ОДНОГО ограничения (узлы/рёбра, роль Аналитика ограничений DP.ROLE.054, без колонки текущего факта), тогда как DP.M.457 — плоская таблица РАЗНЫХ результатов одного координирующего РП с их текущим фактическим статусом. Не дубликаты — разные рабочие продукты для разных ролей и разных вопросов («в каком порядке чинить ограничение» vs «что из результатов РП уже готово и что ещё ждёт условия»).
