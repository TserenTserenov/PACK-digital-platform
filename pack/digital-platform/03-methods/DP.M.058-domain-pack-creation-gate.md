# Гейт создания нового Pack при доменных кандидатах без дома (DP.M.058)

## 1. Контекст

При обработке внешнего источника (семинар, статья, книга, видео) extraction-pipeline даёт смесь кандидатов двух типов:

| Тип | Признак | Маршрут |
|-----|---------|---------|
| **Универсальный** | Генерализуется вне домена источника; ложится в существующий PD-Pack (PACK-personal, PACK-MIM, PACK-digital-platform) | Записать сразу в целевой Pack |
| **Доменный** | Требует новой онтологии (финансы, право, медицина и т.п.) и не имеет дома в существующих Pack'ах | Применить Гейт (см. §2) |

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Скорость записи находок ↔ связность онтологии | При разборе внешнего источника (§1: семинар/статья/книга/видео) есть соблазн сразу распределить доменные кандидаты по существующим Pack'ам «по близости» — это даёт мгновенный видимый прогресс, но Гейт (§2) требует остановиться и defer весь батч до single decision point, жертвуя скоростью закрытия extraction-сессии ради целостности будущей доменной онтологии |
| Порог применимости (§3: ≥3 связанных доменных кандидата) ↔ риск процедурного оверхеда на единичных случаях | Гейт применяется только при ≥3 семантически связанных доменных кандидатах; для одиночного кандидата (single-precedent) полный ритуал defer + single decision point избыточен, но заниженный порог рискует пропустить кластер, который проявляется только на следующей итерации накопления |
| Полнота батча (§2 п.2: «сохранить весь батч») ↔ немедленная применимость находок | Требование держать все доменные кандидаты вместе в ожидании одного решения пилота откладывает использование даже потенциально ценных инсайтов внутри батча до Strategy Session — метод жертвует немедленной применимостью ради целостности итогового решения «создаём Pack: да/нет» |

## 2. Правило (Гейт)

При обнаружении доменных кандидатов без существующего Pack'а:

1. **НЕ fragment** по существующим Pack'ам «чтобы не потерялись».
2. **Сохранить весь батч** как `inbox/extraction-reports/<date>-<source>.md` с `status: pending-review`, `verdict: defer` для каждого.
3. **Single decision point** для пилота: на ближайшей Strategy Session или специальной сессии — «создаём PACK-{domain}: да/нет?».
4. После решения — apply (если новый Pack создан) или re-route (если решено влить в существующий).

## 3. Условия применимости

- Внешний источник с ≥3 доменными кандидатами (одиночный кандидат → defer как обычный single-precedent, не Гейт).
- Доменные кандидаты семантически связаны (одна онтология), а не разрозненные паттерны.
- Текущая Pack-экосистема не содержит подходящего домена-владельца.

## 4. Тест классификации кандидата

«Кандидат — конкретизация существующего PD-понятия (D/M/SOTA) в новом домене?»

- **Да** → доменный, требует нового Pack или коллекции в extraction-report.
- **Нет, обобщение применимо к работе/мышлению вообще** → универсальный, в существующий PD-Pack.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего. Карточка на стадии `epistemic_stage: emerging` — пометка `tentative`._

| Bias | Direction of distortion |
|------|--------------------------|
| _(tentative)_ Смещение теста классификации (§4) на удобство вместо строгости | При разборе потока кандидатов внимание непроизвольно тянется к вопросу «какой Pack ближе всего по теме», подменяя обязательный тест §4 («конкретизация существующего PD-понятия в новом домене?») эвристикой поверхностного сходства — прежде чем практикующий успевает применить критерий формально |
| _(tentative)_ Недооценка порога §3 (≥3 связанных кандидата) при потоковой обработке | При последовательном разборе кандидатов внимание оценивает каждого по отдельности в момент появления и не удерживает счётчик «сколько уже накопилось доменных кандидатов без дома» — гейт своевременно не срабатывает, потому что порог проверяется постфактум, а не по ходу разбора |

## 5. Анти-паттерн: fragmentation

Распределение доменных кандидатов по существующим Pack'ам «по близости»:
- Через 2-3 месяца доменная связность разрушена: 3 кандидата в PACK-personal, 4 в PACK-MIM, 6 в PACK-digital-platform.
- Никогда не превратится в связную онтологию (нет «корневого» Pack'а для финансов / права).
- Каждое решение «куда впихнуть» — N-fold вопросов вместо одного.

## 6. Преимущество single decision point

| Антипаттерн (fragmentation) | Гейт (defer all-together) |
|------------------------------|----------------------------|
| N решений «куда впихнуть кандидат #K» | 1 решение «создаём PACK-X?» |
| Drift доменной онтологии | Связная онтология (или re-route после решения) |
| Потеря источника-контекста | extraction-report сохраняет source-метаданные |
| Невозможность изъять при reject Pack | Простое перемещение reports/ |

## 7. Пример (WP-242 Ф-Семинар-Агроскина, 17 мая 2026)

Семинар В.В. Агроскина «Финансы: паттерны и стейкхолдеры» дал 21 кандидата:

- **8 универсальных** (мышление=моделирование, объект≠описание, заземление, продукт≠рабочий продукт и др.) → записаны сразу в PACK-personal, commit `c6aa147`.
- **13 доменных** (паттерны financial modeling, ожидания внешних ролей, горизонты ролей) → сохранены в `inbox/extraction-reports/2026-05-17-agroskin-seminar.md`, все `verdict: defer`, ожидают решения по PACK-finance на ближайшей Strategy Session.
