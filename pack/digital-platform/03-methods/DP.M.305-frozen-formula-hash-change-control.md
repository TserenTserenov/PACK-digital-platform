# DP.M.305 — Frozen formula hash: версия формулы как артефакт под change-control

## 1. Принцип

Когда расчёт реализует метод из отдельного источника (Pack, РП методолога), результат обязан нести **явный хэш версии формулы** в выходе и хранилище.

```python
FORMULA_VERSION = "wp414-v1"  # меняется только через change-control РП414

def calculate_panel(user_id: int, ...) -> PanelResult:
    ...
    return PanelResult(..., formula_version=FORMULA_VERSION)
```

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Скорость правки формулы ↔ отслеживаемость истории | Быстрый inline-фикс формулы без версии закрывает баг за минуту, но стирает возможность отличить «баг в данных» от «баг в формуле» задним числом |
| Единый владелец кода ↔ разделение ролей методолог/воркер | Воркеру проще менять формулу самому по ходу разработки, но инвариант «кто считает ≠ кто оптимизирует» требует явного change-control процесса через отдельный РП |
| Компактность хранилища ↔ полнота ретроспективы | Хранить `formula_version` в каждой записи (контрактной и аудитной) — избыточность на первый взгляд, но без неё сравнение периодов с разными версиями формулы невозможно |
| Простота одной константы ↔ дисциплина PR-процесса | `FORMULA_VERSION = "..."` — тривиальная строка кода, но метод требует, чтобы её изменение всегда шло через PR со ссылкой на РП, а не как побочный эффект рефакторинга |

## 2. Инвариант разделения обязанностей

```
Кто считает (воркер)  ≠  Кто оптимизирует (методолог)  ≠  Кто проверяет (аудитор)
```

Без версионирования невозможно различить:
- «результат изменился из-за данных» vs
- «результат изменился из-за тихого рефакторинга формулы»

## 3. Процесс изменения формулы

1. Методолог создаёт новый РП (например, РП416 «обновление формулы v2»)
2. Новая версия получает идентификатор `wp416-v2`
3. Воркер обновляет `FORMULA_VERSION` через PR с явной ссылкой на РП
4. Исторические записи сохраняют старый `formula_version` — ретроспектива сопоставима

## 4. Хранение версии

- Поле `formula_version` в контрактной таблице (`<entity>_daily`)
- Поле `formula_version` в аудитной таблице (`<entity>_audit`)
- Лог воркера при каждой записи

## 5. Антипаттерн

Inline-формула без версии — рефакторинг меняет семантику молча, исторические данные несопоставимы.

## 6. Применимость

- Ночные сводки, дайджесты, панели активности с переживаемой историей
- Сертификаты достижений с формулой начисления

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| «Это же просто константа, зачем ей отдельный РП» | Внимание фиксируется на малости изменения кода (одна строка) и упускает семантическую тяжесть — эта строка определяет сопоставимость всей исторической выборки |
| «Рефакторинг формулы — не изменение поведения» | Разработчик считает переписывание формулы «тем же кодом другими словами» и не поднимает `FORMULA_VERSION`, хотя численный результат мог измениться |
| «Версия важна только для будущих записей» | Фокус на новых расчётах, забывая, что `formula_version` должен присутствовать и в аудитной таблице для симметрии — иначе аудит теряет привязку к формуле |
| «Методолог решает формулу, воркер просто пишет код» | Разделение ролей воспринимается как административная формальность, а не как техническая гарантия — воркер меняет формулу «по договорённости в чате», не дожидаясь РП |
