# DP.M.052 — DT Write API как Транзитный Канал для Браузерных Инструментов

## Определение

Паттерн использования `dt_write_digital_twin` (MCP tool) как транзитного слоя для инструментов, которым нужна запись в БД, но недоступен прямой DB-доступ (браузерный канал claude.ai).

## Проблема

Инструмент работает в VS Code (есть CLI), но не в браузере (нет прямого Neon-доступа). Прямая запись в БД возможна только из VS Code.

## Решение

Браузерная версия инструмента использует `dt_write_digital_twin` (IWE MCP tool):

```
Браузер → dt_write_digital_twin → Digital Twin → DT-worker → Neon
```

Вместо:
```
VS Code → psycopg2/asyncpg → Neon (прямо)
```

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Простота транзитного слоя (dt_write_digital_twin как единственная точка записи) ↔ задержка синхронизации | Транзитность (DT API как промежуточный буфер, DT-worker синхронизирует в Neon асинхронно) избавляет браузерный инструмент от прямого DB-доступа и знания схемы (Decoupling), но платит асинхронной задержкой между записью в DT и появлением данных в Neon — мгновенного подтверждения записи, как в VS Code-канале с прямым psycopg2, здесь нет |
| Channel-parity («тот же функционал») ↔ двойная поверхность интеграции | Обещание одинакового функционала в VS Code и браузере требует поддерживать оба пути записи (VS Code: прямой psycopg2/asyncpg; браузер: транзит через DT API) для каждого инструмента, пишущего в БД — ради единого пользовательского опыта метод удваивает, а не упрощает, поверхность реализации |

## Ключевые свойства

- **Транзитность:** DT API = промежуточный буфер, DT-worker синхронизирует в Neon асинхронно
- **Channel-parity:** пилот в браузере получает тот же функционал, что в VS Code
- **Decoupling:** инструмент не знает о схеме БД — только о DT-контракте

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| Тяга к знакомому SQL-паттерну | При интеграции нового браузерного инструмента внимание тянется к прямой реализации DB-доступа (знакомый паттерн VS Code-канала), потому что транзитный DT-слой менее заметен/очевиден, чем «просто добавить SQL-вызов» — практикующий по умолчанию воспроизводит паттерн, знакомый по другому каналу |
| Недооценка асинхронной задержки | Раз DT write API «просто работает» как буфер, внимание недооценивает асинхронную задержку DT-worker → Neon (свойство Транзитность) — предполагается согласованность чтения-после-записи между каналами без проверки, действительно ли DT-worker уже перенёс данные к моменту, когда браузерный инструмент их перечитывает |

## Тест применимости

«Инструмент пишет в БД, но нужен в браузере?» → использовать DT write API как транзит.
