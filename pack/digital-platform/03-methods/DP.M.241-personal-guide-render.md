# DP.M.241 «Порядок формирования персонального руководства» (8 шагов: S1, S2, S3, S3.5, S4, S5, S6, S7, S8)

> **Статус:** перенесено из draft `inbox/WP-371/peer-session-2026-05-30/DP.M-personal-guide-render.md` в Pack (peer-session 2026-05-30-45).

Метод реализует обещание `DP.SC.164 «Доставка персонального руководства пилоту»`. Каждый шаг S1-S7 выполняется последовательно (S8 — асинхронный feedback loop). Шаги S6 и S7 — обязательные проверки; нарушение → degraded-режим.

## S1. Определение квалификации

**Цель:** установить ступень и программу пилота, либо войти в welcome-mode при cold-start.

**Приоритеты определения квалификации (первый доступный побеждает):**
1. Самодекларация в `personal-guide/<пилот>/profile.md` (явная запись `qualification: <уровень>`).
2. Последний тест Диагноста — запись в `learning.cp_assessments` (Neon) с актуальным `cp_confirmed_stage` (не старше 90 дней).
3. RCS-fallback: `stage_raw = min(W, M1, M2, M4)` из `Память.Derived` (PD.FORM.089 §6.1).
4. Если ничего → **ступень 1 (Ученик)** с пометкой `qualification_source: default`.

**Cold-start детектор** — после fallback проверить ВСЕ 4 условия:
- [ ] cp-профиль NULL (все 6 слотов).
- [ ] Нет активных РП в `DS-my-strategy/inbox/WP-*.md` (или репо не подключён).
- [ ] Нет captures за последние 14 дней (через `personal_search` count = 0).
- [ ] Универсальное руководство программы не подключено (нет файла `docs/ru/<program>/index.md` доступного через `knowledge_search`).

Если **все 4 = true** → переход в **welcome-mode**.

**Pause-detector** — проверить `profile.md.pause_until`:
- Если `pause_until > сегодня` → переход в **paused-режим** (рендер не выпускается; событие `personal_guide.render.paused`).
- Иначе — продолжить.

**Digest-detector** — проверить `unread_streak`:
- Источник: метки чтения за последние N дней (события `personal_guide.feedback.read` от `/lesson` skill / TG / repo).
- `unread_streak = count(дней подряд без события read для daily-файла)`.
- Если `unread_streak >= 3` → переход в **digest-mode** для следующего рендера (см. подробности в S5 ниже).

### Welcome-mode (5 дней)

Daily welcome — 5 фиксированных файлов с пометкой `degraded: welcome` в frontmatter:

| День | Содержание | Источник материала |
|------|-----------|--------------------|
| 1 | «Зачем тебе персональное руководство» + инструкция подключить DS-my-strategy | PD.FORM.137 §2 (цитата с back-ref, не verbatim) |
| 2 | «Что такое контекст пилота» + первая мини-практика капчуры | PD.FORM.137 §5 (двухуровневая структура Проблемы/Задачи) |
| 3 | Первый фрагмент ступени 1 универсального руководства (часть 1) | `docs/ru/<program>/1-1-systemic-self-development/` или эквивалент |
| 4 | Первый фрагмент ступени 1 универсального руководства (часть 2) | Тот же индекс, продолжение |
| 5 | Первый weekly review (как читать weekly + как настроить расписание) | PD.FORM.137 §3 (двойственная роль, HD #56 Пользователь/Создатель) |

Weekly welcome — один файл с обзором программы (PD.FORM.137 §2 таблица 4 уровней + ссылки на универсальное руководство).

**Выход из welcome-mode** — появилось хотя бы одно из:
- `cp.*` ≥ 2 в любом слоте.
- Хотя бы 1 capture за период welcome.
- Хотя бы 1 активный РП.
→ следующий рендер уже в normal-mode.

**Истечение welcome:** после 5 дней welcome контекст всё ещё пуст → переход в `degraded: no-context` на **9 дней** (итого 14 дней с момента cold-start). После 14 дней — `suspended` (полная остановка рендера, событие `render.suspended`).

## S3. Сбор сигналов «что заботит»

**Порядок приоритетов сигналов:**
0. **`pilot_explicit_request`** — `current_request` поле из `profile.md` ИЛИ свободный текст в `personal-guide/<пилот>/requests.md` (если файл есть). Срок жизни: 1 день для daily, 1 неделя для weekly. `priority_weight: 1.0` (выше всех). **Этот сигнал также активирует бустер веса соответствующей программы в S4 (+2 к весу).**
1. Активные РП из `DS-my-strategy/inbox/WP-*.md` (если репо подключён). `priority_weight: 0.9`.
2. `WeekPlan W{N}.md` из `DS-my-strategy/current/` (если подключён). `priority_weight: 0.8`.
3. Текущие проекты — активные репозитории пилота (если подключены через GitHub App). `priority_weight: 0.7`.
4. LMS — домашние задания, ответы в курсах (через `personal_search`). `priority_weight: 0.5`.
5. Клуб — посты, обсуждения пилота (через `personal_search`). `priority_weight: 0.4`.
6. Honcho — закэшированные паттерны желаний/неудовлетворённостей. `priority_weight: 0.3`.

**Выход S3:** ранжированный список сигналов формата:
```yaml
- signal_id: <уникальный>
  source: <wp | weekplan | project | lms | club | honcho>
  tags: [<pack-ID | domain-tag>, ...]
  priority_weight: <1.0 — 0.1, по позиции в порядке выше>
  raw_ref: <WP-NNN | post-URL | capture-id>
  excerpt: <≤200 символов выдержки для контекста>
```

Объединённое **множество тегов S3** = ⋃ всех тегов всех сигналов → используется для S6 пересечения.

### S3.5. Временной контекст (для инварианта N) — обязательный подшаг

> **Зачем:** обеспечивает непрерывность нарратива. Без этого подшага сервис рискует выдавать «случайные уроки», игнорируя вчерашний контекст пилота.

**Для daily — собрать:**
1. **Вчерашний daily** `daily/<YYYY-MM-DD - 1>.md`:
   - Прочитать frontmatter: `degraded`, `focus_ref` (если есть), теги §1, §2.
   - Если файл отсутствует — пометить `previous_day: none`.
   - Если был `degraded: <reason>` — пометить `previous_day_degraded: <reason>`.
2. **Captures за последние 24h** через `personal_search` с фильтром `created_at >= now() - 24h`:
   - Добавить как сигналы с `source: capture-24h`, `priority_weight: 0.9` (выше чем стандартные captures).
3. **Активность за вчера** в DS-my-strategy:
   - `git log --since="24 hours ago"` по репо пилота — какие РП были тронуты?
   - Записи в `current/Day <вчера>.md` (если есть) — что было запланировано/сделано?

**Для weekly — собрать:**
1. **Прошлый weekly** `weekly/<YYYY-W{N-1}>.md` — frontmatter + §1 «Фокус прошлой недели».
2. **Daily-цепочка за неделю** (последние 7 файлов `daily/`):
   - Какие темы повторялись? (агрегат тегов §1 за 7 дней)
   - Какие дни были degraded? (счётчик)
3. **Captures за 7 дней**, аналогично daily.
4. **Активность за неделю** — `git log --since="7 days ago"` + WeekReport (если есть).

**Выход S3.5 (дополнение к S3):**
```yaml
temporal_context:
  previous_focus: <фокус вчера/прошлой недели или null>
  previous_focus_ref: <signal.raw_ref или null>
  previous_degraded: <reason или null>
  fresh_signals_24h: [<сигнал>, ...]  # для daily
  week_aggregate: {...}  # для weekly: повторяющиеся темы, счётчик degraded
  focus_continuity: continue | shift | first-day
```

`focus_continuity` определяется так:
- `continue`: топ-1 сигнал из S3 имеет тот же тег, что и `previous_focus_ref`.
- `shift`: топ-1 сигнал из S3 имеет другой тег — нужно объяснить смену в §1.
- `first-day`: `previous_focus = null` (welcome-mode или первый запуск).

## S4. Семантический поиск фрагментов универсального руководства

**Источник:** индекс тегов `docs/ru/<program>/index.tags.json` (предусловие сервиса — handoff WP-364 Ф6).

**Метод:**
- Для каждого сигнала S3 вычислить кандидатные фрагменты универсального руководства, чьи теги пересекаются с тегами сигнала.
- Веса источников по квалификации:

| Источник | Ученик | Работник | Стратег | Специалист | Практик |
|----------|:------:|:--------:|:-------:|:----------:|:-------:|
| `docs/personal-design/` (ЛР) | **3** | 2 | 2 | 1 | 1 |
| `docs/professional/` (РР) | 0 | **2** | **3** | **3** | **3** |
| `docs/research/` (ИР) | 0 | 0 | **2** | **3** | **3** |
| RCS-слоты | **3** | 2 | 1 | 1 | 1 |
| PACK-personal seeds | **3** | 1 | 0 | 0 | 0 |
| DS-my-strategy сигналы | 1 | **2** | **3** | **3** | **3** |
| `personal_search` + Honcho | 1 | 2 | 2 | **3** | **3** |

- Финальный ранг фрагмента = (вес источника по квалификации **+ source_weights_override из profile.md**, не ниже 0) × (количество пересекающихся тегов с S3) × (priority_weight соответствующего сигнала).
- **Если активен `pilot_explicit_request`** — программа этого запроса получает бустер +2 к весу источника `docs/ru/<requested_program>/`, перекрывая дефолты для текущей квалификации.
- Возвращается top-3 фрагмента для daily-§2, top-1 для weekly-§3.

**Fallback `degraded: no-tag-index`:** если индекс отсутствует или невалиден → выбор по последовательности оглавления (`docs/ru/<program>/index.md` `toc`), K-инвариант не применяется.

## S5. Сборка daily/weekly

### Сборка daily (5 секций)

> **Сумма-инвариант:** окна секций суммируются в окно L из DP.SC.164, **масштабированное по `daily_session_minutes` пилота** (по умолчанию 15 мин → 350-450 слов). При увеличении сессии (30/45/60 мин) все окна секций пропорционально расширяются.

> **Формула масштабирования:** `multiplier = daily_session_minutes / 15`. Окна каждой секции = базовое окно × multiplier (округление до 10 слов).

- **§1 «Фокус дня + почему сегодня это»** — формируется из топ-1 сигнала S3 + `temporal_context` из S3.5. Состоит из **двух обязательных частей**:
  - **Часть A — формула непрерывности** (по `focus_continuity` из S3.5):
    - `Refs: <signal.raw_ref>` (актуальный сигнал).
    - `continue`: «**Продолжаем** работу над <previous_focus>. <углубление/новый аспект>.»
    - `shift`: «**Вчера** занимались <previous_focus>, **сегодня** смещаемся на <новый фокус>, **потому что** <причина из топ-1 сигнала>.»
    - `first-day`: «**Первый день** в персональном руководстве. <welcome-нарратив>.»
    - Если `previous_day_degraded` ≠ null — добавить «**Вчера руководство пришло неполным** (<reason>); восстанавливаем связь с твоим контекстом.»
  - **Часть B — обоснование «Почему сегодня это»** (инвариант T):
    - 1-2 предложения с явным перечнем источников, повлиявших на выбор фокуса.
    - Формат: «Выбрано на основании <источник 1>, <источник 2>, <источник 3, если есть>».
    - Конкретика обязательна — `Refs:` (capture ID, WP-NNN, имя файла requests.md, событие из Honcho).
    - Если активен `pilot_explicit_request` — указать первым: «По твоему запросу "<краткая цитата>" + …».
  - Длина (15-мин дефолт): **30-50 слов** на часть A + **20-40 слов** на часть B (итого 50-90 слов в §1). При других длительностях — масштабируется.
- **§2 «Теория на 15 минут»** — топ-1 фрагмент из S4. Включает ссылку на источник в `docs/ru/<program>/`. Длина: **150-200 слов**.
- **§3 «Микро-практика»** — генерируется как «применить теорию §2 к контексту §1» в формате «делается за 15-30 мин в <инструмент>». `is_actionable: true` обязательно. Длина: **60-90 слов**.
- **§4 «Связь с твоими текущими задачами»** — явный мост «эта теория решает твой <ref §1>, потому что...». Длина: **70-100 слов**.
- **§5 «Что зафиксировать»** — 1-2 captures, рекомендуемых в Pack/feedback к концу дня. `target_repo: <Pack | feedback | personal-notes>`. Длина: **40-60 слов**.

**Сумма окон (для 15-мин сессии):** min = 50+150+60+70+40 = **370 слов**, max = 90+200+90+100+60 = **540 слов**. Целевое окно L=350-450; верхняя граница 450 с допуском 50 слов в S7 на эластичность; при превышении 500 — жёсткое усечение §2 (теория) с пометкой `<!-- truncated -->`. При других длительностях — окно L масштабируется по multiplier из формулы выше.

### Сборка weekly (6 секций)

> **Сумма-инвариант:** окна секций должны давать min(sum) ≥ 600 и max(sum) ≤ 1000 (соответствует DP.SC.164 инварианту L).

- **§1 «Фокус недели»** — 1-2 предложения по формуле непрерывности:
  - Если прошлый weekly существует: «**На прошлой неделе** фокус был на <previous_focus>; **на этой** — <новый фокус> на основании <причина: WeekPlan / агрегат captures / новый РП>.»
  - Если первая неделя: «**Первая неделя**: фокус — <тема>.»
  - `Refs:` на 1-3 активных РП.
  - Длина: **20-40 слов**.
- **§2 «Что в фокусе развития»** — 3-5 тезисов из S4. По 1-2 предложения каждый. Длина: **100-180 слов**.
- **§3 «Метод недели»** — один метод глубоко из топ-1 фрагмента S4. Длина: **200-300 слов**.
- **§4 «Привязка к WeekPlan»** — явный мост к 1-3 активным РП. Длина: **100-150 слов**.
- **§5 «План практики на неделю»** — **БЕЗ разбивки по дням** (жёсткий запрет; soft-подсказка «начни с понедельника» допустима). Перечень практик с приоритетом. Длина: **130-250 слов**.
- **§6 «Что отслеживать»** — 1-2 показателя для следующего weekly review. Длина: **50-80 слов**.

**Сумма окон:** min = 20+100+200+100+130+50 = **600 слов**, max = 40+180+300+150+250+80 = **1000 слов**. Точное совпадение с L-инвариантом DP.SC.164.

### Digest-mode (если `unread_streak >= 3`)

Daily выпускается с особой структурой (заменяет обычные §1-§5):
- **§1 «Что было пропущено»** — компактный сводный обзор пропущенных дней (не более 1 строки на день).
  - Формат: «За последние N дней руководство касалось: <тема 1> (день 1), <тема 2> (день 2)…»
  - Длина: 80-120 слов.
- **§2 «Сегодняшний фокус»** — обычная §1 daily + §2 теория, без N-формул («Продолжаем» / «Вчера»), потому что хроника прервана. Вместо них — фраза «**Возвращаемся к работе.** <обычное обоснование Часть B>».
  - Длина: соответствует объединённой §1+§2 обычного daily.
- **§3 «Микро-практика», §4 «Связь с задачами», §5 «Что зафиксировать»** — как обычно.
- Frontmatter: `degraded: digest-mode`, `skipped_days: N`.
- После выхода из digest-режима (пилот открыл daily) — следующий рендер возвращается к обычной N-формуле «Продолжаем работу над <предыдущий фокус>», но `previous_focus` берётся из последнего ПРОЧИТАННОГО daily, не из самого свежего.

## S7. Контракт-проверка перед push

Финальный чек-лист перед `git push`:

- [ ] **Frontmatter валиден** — все обязательные поля присутствуют (`date`/`week`, `pilot`, `qualification`, `stage`, `program`, `degraded`, `generated_at`).
- [ ] **Длина в окне L** — daily 350-450 слов, weekly 600-1000 слов. Превышение → жёсткое усечение последнего абзаца с пометкой `<!-- truncated -->`. Недобор → пометка `degraded: content` и retry в следующее окно.
- [ ] **Ссылки на универсальное руководство существуют** — для каждой ссылки в §2 (daily) / §3 (weekly) проверить HTTP 200 (или существование локального пути).
- [ ] **Нет PII в плашке degraded** — допустимо имя пилота; запрещены email, telegram_id, tokens.
- [ ] **Markdown валиден** — нет broken-таблиц, нет broken-link синтаксиса.
- [ ] **Git push успешен** — `git push origin main` exit code 0.

**Любой fail чек-листа** → НЕ push, событие `personal_guide.render.failed`, retry через 5 мин (до 3 попыток). После 3-х fails → событие финальный fail для R46.

## S8. Feedback Loop (асинхронный, не блокирует основной pipeline)

> **Цель:** обеспечить **самообучение сервиса** — Портной корректирует выборы на основе сигналов пилота о пользе, а не только догадывается.
> **Запуск:** не каждый рендер, а по расписанию (ежедневно, после daily-рендера, плюс еженедельный агрегат для weekly).

### S8.1 Сбор сигналов о чтении и пользе

Источники сигналов (за последние 24h для daily, 7d для weekly):

| Сигнал | Источник | Семантика | Вес |
|--------|----------|-----------|-----|
| `read` | `/lesson` skill (логирует открытие), TG-click на ссылку, commit «прочитал» в репо | Пилот видел контент | 1.0 |
| `useful: +1` | Чекбокс в конце daily/weekly («полезно?») | Подтверждённая ценность | 2.0 |
| `useful: -1` | Чекбокс «не полезно» | Минус-сигнал | -1.5 |
| `capture_accepted` | Capture из §5 был добавлен в Pack или feedback (по `apply-captures` skill) | Контент породил знание | 3.0 |
| `wp_action` | После прочтения daily пилот сделал commit в активный РП с тегами того же фрагмента | Контент породил действие | 2.5 |

### S8.2 Агрегация в Honcho

- Каждый сигнал записывается с тегами фрагмента, источником, программой пилота, его квалификацией.
- Раз в неделю агрегируется по тегам и источникам:
  - `tag_value_score = Σ(signal_weight × decay(age)) / read_count`
  - `source_quality = Σ(signal_weight) / total_renders` для каждого источника (Honcho, personal_search, активные РП и т.д.)
- Decay-функция: `decay(age_days) = max(0, 1 - age_days/30)`.

### S8.3 Авто-корректировка весов (предложения, не применение)

Раз в неделю Портной:
1. Сравнивает `source_quality` с дефолтной таблицей S4 по программе пилота.
2. Если расхождение > 0.5 (вес-единиц) — формирует **предложение в weekly §6 «Что отслеживать»**:
   - «Источник `<X>` за прошлую неделю давал содержательные фрагменты (capture_rate +30%). Предлагаю поднять его вес на +1 в `source_weights_override`.»
   - «Источник `<Y>` игнорировался (read но не useful). Предлагаю снизить вес на -1.»
3. Применение — только по решению пилота (он сам редактирует `profile.md`).

### S8.4 Метрики для R46 (Контролёр развития)

- Read-rate за последние 14 дней (< 50% — сигнал R46 «пилот теряет ритм»).
- Useful-rate (< 30% — сигнал R46 «контент не попадает в потребность»).
- Capture-rate (< 5% — сигнал «фрагменты не доходят до знания»).

R46 решает: подсказать пилоту скорректировать `requests.md` или `daily_session_minutes`, или эскалировать в Навигатор (R27).

### S8.5 Использование в S4 следующего рендера

Перед запуском S4 проверить:
- `pilot_explicit_request` активен? → бустер +2 для запрошенной программы.
- `source_weights_override` обновлён? → корректировка дефолтной таблицы.
- В Honcho есть `tag_value_score` для рассматриваемых тегов? → дополнительный множитель в формуле ранга.

Это замыкает цикл: пилот читает → отмечает полезность → агрегаты в Honcho → следующий рендер выбирает по уточнённым весам.

## Обзор pipeline в одной диаграмме

```
S1 определение квалификации + чтение настроек профиля
  ├── pause_until > today → paused (рендер не выходит) → return
  ├── unread_streak >= 3 → digest-mode → следующий S5 с digest-структурой
  ├── normal-mode → S2
  └── cold-start → welcome-mode (5 дней) → no-context (9 дней) → suspended

S2 активация источников по квалификации (DS-my-strategy / personal_search / Honcho / Pack / docs/ru/<program>/)

S3 сбор сигналов (активные РП → WeekPlan → проекты → LMS → клуб → Honcho)
  → объединённое множество тегов S3

S3.5 временной контекст (вчерашний daily / прошлый weekly / captures за 24h / 7d)
  → focus_continuity (continue | shift | first-day) + previous_day_degraded
  → обеспечивает инвариант N (непрерывность нарратива)

S4 семантический поиск фрагментов универсального руководства
  ├── normal: пересечение тегов × веса квалификации
  └── degraded: no-tag-index → fallback по оглавлению

S5 сборка daily/weekly по контракту секций + supporting по dirty-check

S6 self-check K-инварианта (грепы + set intersections)
  → degraded: content при нарушении

S7 контракт-проверка перед push
  → git push (Primary канал)
  → события для подписчиков (R46, TG-бот, Day Open)

S8 feedback loop (асинхронный)
  ← сигналы read/useful/capture_accepted/wp_action
  → агрегация в Honcho (tag_value_score, source_quality)
  → предложения корректировки весов в weekly §6
  → метрики для R46
  → влияние на S4 следующего рендера
```
