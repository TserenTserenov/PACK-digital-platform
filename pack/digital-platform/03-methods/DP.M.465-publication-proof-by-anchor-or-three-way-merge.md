# DP.M.465 — Доказательство сохранности своей правки: привязка вставки или трёхстороннее слияние

## Проблема

Основная проверка «моя правка долетела» сравнивает дерево байт-в-байт с ожидаемым и ломается, если между подготовкой и публикацией рядом успела легитимно измениться независимая часть файла, не относящаяся к самой вставке. Байт-точное сравнение снимка — хрупкий тест на вопрос «пережила ли публикацию именно моя правка».

## Метод

Метод доказывает, что собственная правка пережила параллельную публикацию, когда рядом успела легитимно измениться независимая часть файла. Общий постусловный тест: своя правка сохранилась после параллельной публикации. Способ его проверки выбирается по типу файла.

**Вариант 1 — структурная привязка вставки (структурированные RUN-карточки).** При провале байт-точного сравнения запасной путь проверяет не всё дерево, а что своя вставка всё ещё уникально закреплена (anchored) в опубликованном блобе. Переиспользуется примитив `anchored_insertions`, уже проверенный в `_commit_claim_supersession_has_publish_proof`. Запасной путь опциональный и по умолчанию выключен (включается env-флагом).

**Вариант 2 — трёхстороннее слияние (обычный текстовый файл, например общий реестр).** База, наш подготовленный снимок и опубликованная версия сливаются без конфликта, и результат побайтово совпадает с опубликованной версией. Так одновременно проверяются «наша правка долетела» и «чужая параллельная правка не потеряна». Независимые чужие изменения сохраняются; потеря нашего результата, конфликт, бинарные данные и смена режима файла отклоняются.

**Вход:** версия-база, наш подготовленный снимок, текущая опубликованная версия и тип файла. Для структурированной карточки при провале точного сравнения проверяется уникальная закреплённость вставки в опубликованном блобе. Для обычного текста выполняется трёхстороннее слияние. **Выход:** доказательство «наша правка сохранилась» без требования, чтобы остальное дерево совпало побайтово, либо явный отказ с названной причиной.

## Тест метода

Заранее заданы сценарии. Параллельная публикация изменила независимую строку рядом со вставкой: доказательство сохранности проходит. Наша вставка потеряна: доказательство отклоняется. Для обычного файла: конфликт слияния, бинарные данные и смена режима файла отклоняются. Для структурированной карточки: вставка отсутствует в блобе или закреплена неуникально — доказательство не принимается. Ожидания задаются независимо от проверяемого кода и сверяются с итоговым содержимым опубликованного блоба.

## Forces

| Force | Tension |
|-------|---------|
| Строгость доказательства (точное совпадение) ↔ терпимость к независимому дрейфу рядом со вставкой | Проверять сохранность именно своей правки, а не тождество всего дерева |
| Один общий тест ↔ разные форматы файлов | Постусловие одно; вариант проверки выбирается по типу файла: привязка вставки для структурированных карточек, трёхстороннее слияние для обычного текста |
| Дешевизна и общность слияния ↔ ложный успех на неподходящих данных | Отклонять бинарные данные, смену режима файла, конфликт и потерю нашего результата |
| Надёжность запасного пути ↔ риск ослабить строгую основную проверку | Запасной путь выключен по умолчанию и включается явно; используется уже проверенный примитив |

## Bias-Annotation

| Bias | Direction of distortion |
|------|--------------------------|
| «Побайтовое совпадение дерева — единственное надёжное доказательство» | Смещение к ложным отказам. Проверка: добавить случай с независимым легитимным изменением рядом со вставкой: правка сохранилась, тест не должен падать |
| «Слияние прошло без конфликта — публикация безопасна» | Смещение к ложному успеху. Проверка: требовать побайтового совпадения результата с опубликованной версией и отдельно проверять потерю нашего результата, бинарные данные, смену режима |
| «Один вариант подходит для любого файла» | Смещение к универсальности. Проверка: выбирать вариант по типу файла: привязка для структурированных карточек, слияние для обычного текста |
| «Запасной путь безопасно включить везде» | Смещение к ослаблению строгости. Проверка: держать его опциональным и выключенным по умолчанию; включение — явное решение |

## Применимо

Публикация собственной правки при параллельных изменениях того же файла: структурированные RUN-карточки (вариант 1) и обычный текстовый файл, например общий реестр (вариант 2). Метод отвечает на вопрос «пережила ли публикацию именно моя правка»; корректность самого содержимого он не проверяет. Варианты не взаимозаменяемы: принять один — значит потерять другой тип файла.
