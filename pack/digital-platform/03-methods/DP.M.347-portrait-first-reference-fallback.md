# DP.M.347 — Portrait-First Fallback: пользовательский контекст → общий справочник

## Описание

При рендере персонализированного артефакта сначала читается пользовательский контекст (portrait); если данных нет — graceful degradation на статический общий справочник. Пользовательский источник приоритетен, но система не падает при его отсутствии.

Portrait в этом методе — конкретная persisted-форма того, что DP.ARCH.007 (Проекция) описывает как runtime-компиляцию под потребителя: fallback-правило ниже — частный случай построения проекции, когда один из двух источников (Персона/Память) пуст.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Персонализация ↔ надёжность | Portrait даёт точный ответ под конкретного пользователя, но может быть пустым/неполным; общий справочник менее точен, зато всегда доступен |
| Единый интерфейс ↔ два источника данных | Потребитель ожидает один стабильный формат ответа, но за ним прячутся два разных пути получения данных с разной логикой наполнения |
| Простота реализации ↔ покрытие обеих веток | `value if value else reference.get(key)` — одна строка, но лёгкость написания провоцирует пропустить тест fallback-ветки, которая срабатывает только для части пользователей |
| Скорость для нового пользователя ↔ полнота персонализации | Fallback даёт мгновенный неперсонализированный ответ вместо ожидания заполнения профиля; экономит отклик ценой точности |

## IPO

**Input:** запрос на персонализированные данные (например, вехи текущей ступени); portrait-файл пользователя; общий справочник (milestones.md / reference)

**Process:**
1. Прочитать portrait-файл пользователя → найти нужную секцию (например, «Тренд»)
2. Если секция присутствует и непустая → использовать данные из portrait
3. Если секция отсутствует или пустая → fallback на соответствующую запись общего справочника
4. Результат одинакового типа в обоих ветках (не менять интерфейс при fallback)

**Output:** данные для рендера; в обоих случаях структура результата идентична — потребитель не знает, из какого источника пришли данные

## Паттерн

```
def get_user_data(portrait, reference, key):
    value = portrait.get(key)
    return value if value else reference.get(key)
```

## Тест охвата

Отдельный тест проверяет обе ветки: (1) portrait содержит данные → используется portrait; (2) portrait пустой → используется reference.

## Применимость

Любой сценарий персонализации где:
- Пользовательский контекст может отсутствовать (новый пользователь / незаполненный профиль)
- Нужен graceful degradation без «нет данных» ошибки
- Потребитель должен получить одинаковый интерфейс независимо от источника

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| «Portrait почти всегда заполнен, тестировать fallback не обязательно» | Внимание уходит на happy-path (portrait есть), ветка с пустым portrait не покрывается тестом и ломается незаметно для новых пользователей |
| «Fallback — это просто заглушка на крайний случай» | Практикующий недооценивает, что для новых/неактивных пользователей fallback — это основной, а не редкий путь |
| «Интерфейс результата и так одинаковый, схема не изменится» | Разработчик меняет одну ветку (например, добавляет поле в portrait-путь), забывая синхронно обновить reference-путь — интерфейс расходится незаметно |
| «Пустая секция portrait — то же самое, что отсутствующая» | Практикующий не различает `None`/отсутствие ключа и пустую строку/список — граница проверки `if value` может пропустить один из случаев |
