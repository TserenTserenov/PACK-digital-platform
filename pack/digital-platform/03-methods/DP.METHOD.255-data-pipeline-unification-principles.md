# DP.METHOD.255 — Принципы унификации конвейеров персональных данных (П1-П9)

## Описание

Девять принципов, применяемых к каждому конвейеру, описанному моделью [[DP.ARCH.010]] (С1-С9). Источник — инвентаризация 79 существующих механизмов (WP-476, 10.07.2026), критика найденных дыр и ArchGate 14.07.2026. Каждый принцип закрывает конкретную найденную дыру (не гипотетическую), формулировки прошли ВДВ-аудит 16.07.2026.

## Принципы

1. **Полнота стадий декларируется, дыры — явные.** Отсутствие стадии — осознанная запись в декларации, не молчание. Для стадии сохранности (С8) — обязательно, кроме ephemeral- и derived-recomputable-домов; невоспроизводимое сырьё без экспорта = блокер регистрации, не декларируемая дыра.
2. **Декларация данных — только через ResidencyGate ([[DP.METHOD.168]]), второй схемы не заводить.** Применяется к стороне IWE и к шву платформа↔IWE. Внутриплатформенные конвейеры используют платформенную схему согласия; соответствие двух схем — обязательное поле при регистрации конвейера.
3. **Класс проверки (стадия С4) — обязательный атрибут, не автоматизируется по умолчанию.** Три класса: автоматическая (схема/дедупликация), смысловая (LLM-судья при записи), решение живого пилота — с обязательным полем, кто фактически принял решение. Derived-факты о носителе без канала оспаривания — минимум помечаются как зеркало без подтверждённой проверки.
4. **Единая конвенция свежести: каждый факт или выдача несёт возраст.** Два уровня соответствия: полный (дата рождения факта + срок действия или явная замена) и минимальный (метка свежести в самой выдаче, для баз, где пометить каждый факт пока дорого).
5. **Сторож следит за данными, не только за процессом; каждый детектор проверяет содержание, не только наличие.** Числовой порог допустимого разрыва — обязателен для каждого потока. Самопроверка детектора обязана подтверждать искусственно внесённый разрыв (не проходить всегда зелёной) — иначе детектор проверяет только собственное существование, а не работу.
6. **Один автор на дом; производные данные пересчитываются по триггеру, не редактируются вручную.** Исключение — дома с несколькими легитимными участниками записи (например, общие текстовые журналы): там инвариант — блокировка на время записи, а не единственный процесс-автор.
7. **Прописка в реестре обязательна при создании конвейера; актуальность реестра проверяется на еженедельном подведении итогов.** Проверка — выборочная (самые старые записи + записи с просроченным сроком свежести), не полный проход каждую неделю; полный проход — на ежемесячном подведении итогов.
8. **Работающие механики эталонного конвейера переносятся как библиотека приёмов, а не как код для копирования.** Единая точка сбора с меткой источника; статус записи «не исчезает без решения»; структурированная фиксация, кто принял решение; явная механика замены устаревшего знания; трёхслойная страховка индекса.
9. **Доступ ограничивается по области действия, не по границе репозитория; при недоступной проверке согласия поток данных повышенного риска останавливается, а не продолжается.**

## Применение

К любому конвейеру персональных данных типов 2.1-2.4 при регистрации в реестре конвейеров и при ArchGate-оценке новых источников/потребителей данных.
