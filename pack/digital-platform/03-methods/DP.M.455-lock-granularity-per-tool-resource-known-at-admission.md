# DP.M.455 — Гранулярность lock'а по инструменту, не по сервису целиком

## Описание

Когда сервис предоставляет несколько инструментов/эндпоинтов, конкурирующих за общие ресурсы, гранулярность блокировки не обязана быть одной для всех: она выбирается индивидуально по архитектурному ограничению каждого инструмента — в первую очередь по тому, известен ли идентификатор ресурса в момент постановки запроса в очередь. Там, где известен — точный `(user, resource)`-lock. Там, где ресурс выбирается ПОЗЖЕ (например, LLM внутри уже запущенной фоновой задачи) — осознанный грубый `user`-lock, зафиксированный как задокументированный компромисс, а не как забытая заглушка.

## Когда возникает

Сервис отвечает клиенту сразу (`202 Accepted`) и только затем, уже в фоновой задаче, определяет, на каком именно ресурсе будет действовать. На момент постановки запроса в очередь точный идентификатор ресурса физически не существует — точный `(user, resource)`-lock для такого инструмента недостижим без изменения контракта (например, нового обязательного поля на входе).

## IPO

**Вход:** список инструментов/эндпоинтов сервиса + для каждого — известен ли идентификатор ресурса на момент постановки в очередь.
**Процесс:** для каждого инструмента по отдельности — тест «известен ли ресурс на входе?» → да: `(user, resource)`-lock; нет: `user`-lock с явной пометкой компромисса.
**Выход:** разная гранулярность блокировки по разным инструментам одного сервиса — осознанное решение под архитектурное ограничение каждого, не единое правило «один lock на сервис».

## Тест применимости

«Можно ли узнать идентификатор ресурса ДО постановки запроса в очередь / до ответа клиенту?» Да → точный lock по ресурсу. Нет (ресурс определяется позже, внутри уже стартовавшей фоновой обработки) → coarse lock по следующему по вложенности доступному идентификатору (например, user), задокументированный как компромисс.

## Отличие от соседних методов

- **DP.M.367** (per-entity advisory lock) — МЕХАНИЗМ захвата блокировки на одну сущность. Этот метод — про выбор уровня, на котором определять «сущность», когда её идентификатор не дан заранее.
- **DP.M.372** (flock: общий лок на проход vs per-item) — гранулярность по уровню РЕАЛЬНОГО ПАРАЛЛЕЛИЗМА конкурентов в рамках одного скрипта. Этот метод — гранулярность по архитектурному ограничению конкретного инструмента в рамках сервиса с разными инструментами.

## Пример

WP-7 Ф143: гонка двух параллельных запросов одного пользователя к одному governance-репозиторию в agent-runner. Единый lock по `user_id` сериализовал бы и легитимный параллелизм (разные репозитории, read-only запросы). Точный `(user, repo)`-lock оказался физически недостижим для двух конкретных инструментов (`run_strategist`, `run_extractor`), отвечающих `202` и выбирающих репозиторий позже внутри фоновой задачи. Решение: точный `(user, repo)`-lock для инструментов с известным на входе ресурсом (`create_wp`); coarse `user_id`-lock для инструментов с поздним выбором ресурса, задокументированный как компромисс.
