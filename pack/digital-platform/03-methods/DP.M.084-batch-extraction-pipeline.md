# DP.M.084: Batch-extraction pipeline из большого корпуса

## Определение

Метод извлечения знания из большого корпуса (≥500 элементов, ≥2 года, авторские заметки/посты/документация) через 4-фазный pipeline с параллельной обработкой и финальной consolidation.

## Тест применимости

> «Корпус >500 элементов, >2 года, с темами для абстракции?»

- **Да** → 4-фазный pipeline (этот метод)
- **Нет** → одиночный pass через `DP.M.001` (knowledge-extraction)

## Фазы

### Ф0. Setup

Создать реестр-таблицу с колонками:
- `тип` (кейс / история / различение / объяснение / мем / аналогия)
- `источник` (file/post ID)
- `целевой_Pack` (PACK-NNN)
- `якорный_концепт` (existing entity ID или новый)
- `форма_включения` (new entity / extension / SoTA / FM)
- `приоритет` (P1 / P2 / P3)

Структурированный output (JSON / Markdown table) для downstream-обработки.

### Ф1. Pilot Pass (Opus)

~10 элементов через **Opus single-thread**. Цель: откалибровать таксономию типов и форм включения. Выход: уточнённый шаблон реестра + примеры заполнения.

### Ф2. Batch Parallel (Sonnet × N)

4-8 параллельных Sonnet, каждый обрабатывает свой slice (по году / категории / тегу). Каждый поток заполняет свой раздел реестра в **shared-формате** (одна таблица, одна схема колонок).

Slice-стратегии:
- По году (`2020-2021 / 2022-2023 / 2024 / 2025-2026`)
- По категории (`tech / personal / strategy`)
- По тегу (`#wp-* / #note-* / #post-*`)

### Ф3. Extra Source (опционально)

Если есть второй источник того же домена (например, TG-канал, web-bookmarks, email-архив) — отдельный agent с **тем же контрактом реестра**. Не объединять с Ф2: разные форматы источников, разные эвристики.

### Ф4. Consolidation (Opus single-thread)

1. **Дедупликация** — cosine similarity по описанию + manual review борderline (similarity 0.7-0.9)
2. **Переоценка P1** — Opus читает реестр и понижает P1 → P2 при недостаточной формализуемости
3. **Выявление TODO формализаций** — кандидаты с ≥3 прецедентами в реестре → flag как «kandidat na FORM/METHOD»

### Ф6. Uncovered slice добор (опционально)

**Когда применять:** после Ф4 Consolidation, если есть uncovered slice корпуса размером ≥30 артефактов с density ≥10% по соседним обработанным slice'ам.

**Алгоритм:**

1. **Sweep по дате/тегу/источнику:** что осталось непрочитанным? Построить таблицу uncovered slices с колонками `slice`, `size`, `expected_density` (по соседним обработанным).
2. **Приоритизация:** ранжировать по `density × size` (ожидаемое число находок).
3. **Thin pass:** читать ТОЛЬКО top-N slices, фильтр на P1+P2 (P3 пропускаем — слишком дорого vs ценность).
4. **Без полного re-pass:** не возвращаемся к уже обработанным slice'ам — Ф6 покрывает gaps, не improvement.

**Тест применимости:**

> «Batch-extraction пайплайн прошёл Ф4, есть uncovered slice >30 артефактов с density ≥10% по соседним?»

- **Да** → Ф6 добор.
- **Нет** → закрыть batch как complete.

**Антипаттерн:** «забыть про uncovered, считать корпус полностью обработанным» → находки теряются навсегда (особенно при ротации pricing/relevance: posts старше года часто содержат недооценённые pattern'ы).

**Прецеденты:**

- WP-333 Ф6 (commit 877d6d1e, 18 мая 2026): январь-февраль 2026 (51 пост, не покрытые до Ф4) → 12 находок (density 23%), из них 7 P1 + 3 P2 + 3 P3. Кластер «эпоха ИИ» доминирует (8/12). Альтернатива (re-pass 2020-2023 с density 10%) — отвергнута как менее выгодная.
