# DP.METHOD.066: Probe-First (разведка ДО реализации)

## Назначение

Метод предотвращения слепой реализации на неверных предпосылках.

Проблема: карточка фазы РП делает конкретные утверждения о live-системе («есть колонка X», «связь означает Y», «N таких узлов»). Эти утверждения могут не соответствовать реальному состоянию системы на момент начала работы.

Решение: запустить read-only разведку (probe) live-системы *до* написания кода и сверить предпосылки.

## Когда применять

**Триггер:** карточка фазы содержит проверяемые фактические утверждения о live-системе:
- «Колонка `X` существует в таблице `Y`»
- «Связь `specializes` ведёт к синонимам»
- «В этом домене N узлов типа Z»
- «Функция `foo()` принимает параметр `bar`»

**Тест:** «Карточка утверждает факт о системе, который я могу проверить запросом/grep/ls, но не проверил?» → Да → probe-first обязателен.

## Шаги

1. **Идентифицировать предпосылки** — выписать все проверяемые фактические утверждения из карточки фазы.
2. **Запустить read-only probe** — SQL-запросы, grep, ls, curl без side-effects.
3. **Сравнить результат с карточкой** — совпадает / не совпадает.
4. **Если не совпадает → обновить карточку** до начала кода. Слепая реализация по карточке с неверными предпосылками = DP.FM.014 (Legacy Port Jump: прыжок в реализацию без проверки).
5. **Зафиксировать** — числа из probe включить в commit-message или WP-context.

## Применение в WP-439

Обе фазы РП439 были спроектированы на неверной фактуре:
- Ф1 (анкер): карточка ссылалась на колонку `name_en_source` (не существовала) и Part H/K FPF (не было).
- Ф2 (наследование): карточка предполагала, что `specializes` ведёт к синонимам (на данных ведёт к типам-родам — 420 детей у U.Method, имена не наследуются).

В обоих случаях read-only probe боевой системы ДО кода опроверг предпосылки.
