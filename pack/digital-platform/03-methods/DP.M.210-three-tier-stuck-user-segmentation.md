# DP.M.210 Трёхуровневая сегментация застрявших пользователей (α/β/γ)

## Назначение

Диагностировать причину «почему пользователи застряли на этапе N» путём разбивки на три семантически различимых кластера с разными corrective action.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Скорость запуска intervention ↔ диагностическая точность | Три кластера требуют SQL-диагностики и разных действий, что замедляет запуск кампании; слепой nudge быстрее, но смешивает поведенческий gap и технический bug |
| Таргетированное лечение ↔ сложность сообщения | Корректный action для α (nudge), β (контент/порог) и γ (hotfix) различается, что увеличивает операционную нагрузку, но единое сообщение для всех тратит ресурс команды и доверие пользователей |
| Поведенческая интерпретация ↔ техническая ответственность | Сегмент застрял «видимо, не мотивирован» — простая история; кластер γ требует признать, что evaluator/пайплайн может быть сломан, и переключить фокус с маркетинга на инженерию |

## Входы

- Множество пользователей, не завершивших этап N
- event_store с записями активности
- Evaluator/transition logic с известными порогами перехода

## Кластеры

| Кластер | Критерий | Диагноз | Действие |
|---------|---------|---------|----------|
| **α** | 0 domain_event (полная тишина) | Поведенческий gap | Nudge/content, мотивация |
| **β** | Есть события, но ниже порога перехода | Threshold gap | Снизить порог или улучшить контент |
| **γ** | Активность выше порога, нет перехода | Технический баг evaluator'а | Hotfix кода |

## Шаги

1. `SELECT COUNT(*) WHERE NOT EXISTS(events WHERE user_id=u.id)` → размер α
2. `SELECT COUNT(*) WHERE event_count > 0 AND event_count < threshold` → размер β
3. `SELECT COUNT(*) WHERE event_count >= threshold AND NOT transitioned` → размер γ
4. Если β=0 и γ=0 и α>0 → чистый поведенческий gap → только поведенческие инструменты
5. Если γ>0 → баг evaluator'а → hotfix приоритет над всем остальным

## Выходы

- Размеры кластеров α/β/γ
- Рекомендация по corrective action для каждого кластера

## Почему нельзя слепой nudge (аргументация, из DP.M.208)

Blind nudge для всего сегмента имеет несколько отказов:

1. **Демотивация активных (кластер α ложноположительный).** Пользователи, чью активность система не видит из-за false-negative bug (поведенческий ≠ технический bottleneck — см. DP.D.108), получают сообщение «у вас нет активности» при наличии активности. Двойной репутационный ущерб: bug + spam.
2. **Асимметрия цены задержки.** 1 день diagnostics-запроса = SQL + просмотр ≤30 пользователей сегмента. Стоимость задержки nudge на 1 день несравнима с откатом доверия активных.
3. **Риск неверного лечения.** Поведенческий (α) и технический (γ) bottleneck лечатся разными интервенциями. Nudge для кластера γ = ноль эффекта на цифры + потеря доверия — им нужен hotfix, не мотивационное сообщение.

## Гибрид (из DP.M.208)

Если кластер α очевиден заранее (cohort с zero events до применения метода) — immediate nudge параллельно с диагностикой остальных кластеров. Не блокировать низкорисковый сегмент диагностикой высокорискового.

## Применимость

- Любой продукт с funnel + event-based progress: онбординг, квалификация, достижения, подписка, марафоны
- Retention / reactivation кампании, churn-prevention
- Programmatic outreach с риском восприятия как spam

## Анти-применение (из DP.M.208)

- Случай, когда первичные события технически невозможны (например, новый функционал, никто ещё не пробовал) → nudge без диагностики OK, кластер однороден
- Очень малый сегмент (≤3 пользователя) → ручной разбор каждого, без алгоритма

## Ошибка без метода

Blind nudge для всех застрявших: α получает правильное сообщение, γ получает бесполезный nudge (им нужен hotfix). Ресурс команды тратится на коммуникацию при наличии технического бага.
