# DP.M.210 Трёхуровневая сегментация застрявших пользователей (α/β/γ)

## Назначение

Диагностировать причину «почему пользователи застряли на этапе N» путём разбивки на три семантически различимых кластера с разными corrective action.

## Входы

- Множество пользователей, не завершивших этап N
- event_store с записями активности
- Evaluator/transition logic с известными порогами перехода

## Кластеры

| Кластер | Критерий | Диагноз | Действие |
|---------|---------|---------|----------|
| **α** | 0 domain_event (полная тишина) | Поведенческий gap | Nudge/content, мотивация |
| **β** | Есть события, но ниже порога перехода | Threshold gap | Снизить порог или улучшить контент |
| **γ** | Активность выше порога, нет перехода | Технический баг evaluator'а | Hotfix кода |

## Шаги

1. `SELECT COUNT(*) WHERE NOT EXISTS(events WHERE user_id=u.id)` → размер α
2. `SELECT COUNT(*) WHERE event_count > 0 AND event_count < threshold` → размер β
3. `SELECT COUNT(*) WHERE event_count >= threshold AND NOT transitioned` → размер γ
4. Если β=0 и γ=0 и α>0 → чистый поведенческий gap → только поведенческие инструменты
5. Если γ>0 → баг evaluator'а → hotfix приоритет над всем остальным

## Выходы

- Размеры кластеров α/β/γ
- Рекомендация по corrective action для каждого кластера

## Применимость

Любой продукт с funnel + event-based progress: онбординг, квалификация, достижения, подписка, марафоны.

## Ошибка без метода

Blind nudge для всех застрявших: α получает правильное сообщение, γ получает бесполезный nudge (им нужен hotfix). Ресурс команды тратится на коммуникацию при наличии технического бага.
