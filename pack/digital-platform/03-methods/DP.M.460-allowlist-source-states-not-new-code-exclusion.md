# DP.M.460 — Allowlist исходных состояний вместо исключения нового кода

## Проблема

Предложение разработчика чинило функцию автоматического повышения тарифа исключением конкретного нового тарифного кода из области действия («чтобы не трогала новый тариф»). Формулировка через исключение хрупка: каждый СЛЕДУЮЩИЙ новый тариф снова автоматически попадёт под миграцию, пока его не исключат вручную — защита не закрыта по умолчанию, а открыта до следующего инцидента.

## Метод

Функция миграции/автоповышения тарифа проверяет допустимость по явному перечислению (allowlist), не по исключению:

1. `eligible = status == active && tariff_code in LEGACY_TECHNICAL_UPGRADE_SOURCES` — операция применяется только к тарифным кодам, явно перечисленным как подлежащие миграции, а не ко всем, кроме перечисленных как исключение.
2. Любой новый тарифный код по умолчанию НЕ подпадает под операцию, пока не добавлен в allowlist явно — защита закрыта по умолчанию.
3. Операция обязана быть идемпотентной и защищена от повторного запуска.
4. Список состояний, которые операция обязана НЕ трогать (коммерческие тарифы, отложенный переход, архивный снимок, очные выдачи), фиксируется явно — этот список одновременно и объём защиты, и готовый набор тест-кейсов: без прогона по каждому из них идемпотентность недоказуема.

## Тест метода

«Правило проверяет „входит в перечисленный список допустимых“ или „не входит в перечисленный список исключений“?» Второе — под ударом при каждом новом коде/состоянии, появляющемся после написания правила; безопасна только первая форма.

## Применимо

Любая миграция/массовая операция над записями, классифицируемыми по коду/статусу, где набор кодов/статусов со временем растёт (новые тарифы, новые типы записей) и где операция обязана не трогать записи, не прошедшие явную проверку.
