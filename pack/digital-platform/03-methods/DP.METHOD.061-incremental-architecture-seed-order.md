# DP.METHOD.061 — Инкрементальная архитектура: порядок seed (schema→seed→scaffold→logic)

## Описание

При проектировании нового компонента системы (инструмент, сервис, скилл) применять инкрементальный порядок: сначала минимальная структура (schema, seed данные, scaffold скрипт), затем бизнес-логика. Ключевое свойство: каждый шаг проверяем independent dry-run.

## IPO

**Вход:** требование к новому компоненту (что должен делать)

**Процесс:**
1. **Schema-first:** определить структуру данных / файловое дерево
2. **Seed:** создать минимальные тестовые данные / конфигурацию
3. **Scaffold:** создать пустые файлы / заглушки со структурой (без логики)
4. **Dry-run проверка:** убедиться, что scaffold работает без ошибок (ноль logic пока)
5. **Logic:** наполнить scaffold реальной логикой (итерационно)

**Выход:** работающий компонент, каждый шаг которого был проверяем независимо

## Принцип

«Schema→seed→scaffold создают доказуемо-пустой skeleton, который затем наполняется логикой. Dry-run после scaffold = guard что структура верна до написания логики.»

Контрастирует с антипаттерном «сначала логика, потом структура» — при нём ошибки структуры обнаруживаются поздно, когда логика уже написана.

## Тест применимости

«Можно ли проверить структуру компонента до написания любой бизнес-логики?» Да → seed-order применён корректно.

## Пример

```
# Schema: определить executor-catalog.yaml структуру
# Seed: добавить 2-3 minimal записи
# Scaffold: scripts/artifactor.py — parse catalog, return stub output
# Dry-run: python3 scripts/artifactor.py --input "test phrase" → stub JSON
# Logic: реализовать keyword lookup, LLM fallback
```
