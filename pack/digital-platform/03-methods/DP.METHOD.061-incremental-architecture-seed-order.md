# DP.METHOD.061 — Инкрементальная архитектура: порядок seed (schema→seed→scaffold→logic)

## Описание

При проектировании нового компонента системы (инструмент, сервис, скилл) применять инкрементальный порядок: сначала минимальная структура (schema, seed данные, scaffold скрипт), затем бизнес-логика. Ключевое свойство: каждый шаг проверяем independent dry-run.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Скорость первого видимого результата ↔ дисциплина порядка шагов 1-4 (schema→seed→scaffold→dry-run) | Соблазн сразу писать шаг 5 (logic) даёт демонстрируемый результат быстрее, но пропуск dry-run-проверки (шаг 4) откладывает обнаружение структурных ошибок на момент, когда logic уже написана поверх кривой структуры |
| Полнота seed-данных (шаг 2) ↔ скорость первого dry-run прогона | Больше seed-записей даёт более надёжную проверку scaffold на разных случаях, но каждая дополнительная тестовая запись отодвигает момент первого dry-run |
| Строгость «ноль logic пока» (шаг 3-4) ↔ давление показать полезность прототипа | Чистый scaffold без логики труднее продемонстрировать стейкхолдеру как «работающий пример», что толкает к преждевременному смешиванию logic в scaffold-шаг ещё до dry-run |

## IPO

**Вход:** требование к новому компоненту (что должен делать)

**Процесс:**
1. **Schema-first:** определить структуру данных / файловое дерево
2. **Seed:** создать минимальные тестовые данные / конфигурацию
3. **Scaffold:** создать пустые файлы / заглушки со структурой (без логики)
4. **Dry-run проверка:** убедиться, что scaffold работает без ошибок (ноль logic пока)
5. **Logic:** наполнить scaffold реальной логикой (итерационно)

**Выход:** работающий компонент, каждый шаг которого был проверяем независимо

## Принцип

«Schema→seed→scaffold создают доказуемо-пустой skeleton, который затем наполняется логикой. Dry-run после scaffold = guard что структура верна до написания логики.»

Контрастирует с антипаттерном «сначала логика, потом структура» — при нём ошибки структуры обнаруживаются поздно, когда логика уже написана.

## Тест применимости

«Можно ли проверить структуру компонента до написания любой бизнес-логики?» Да → seed-order применён корректно.

## Пример

```
# Schema: определить executor-catalog.yaml структуру
# Seed: добавить 2-3 minimal записи
# Scaffold: scripts/artifactor.py — parse catalog, return stub output
# Dry-run: python3 scripts/artifactor.py --input "test phrase" → stub JSON
# Logic: реализовать keyword lookup, LLM fallback
```

## Bias-Annotation

_Куда систематически съезжает внимание практикующего. Статус карточки — `draft`: пометка `tentative` по прецеденту WP-448 Ф12._

| Bias | Direction of distortion |
|------|--------------------------|
| _(tentative)_ Logic просачивается в scaffold раньше срока | При написании scaffold (шаг 3) внимание тянется к logic — заглушки быстро обрастают реальными ветками условий «чтобы хоть что-то работало», и граница scaffold/logic (шаг 3→5) размывается ещё до dry-run (шаг 4) |
| _(tentative)_ Переоценка того, что доказывает dry-run | После успешного dry-run (шаг 4) внимание переоценивает готовность структуры — «раз пустой skeleton прошёл проверку, структура точно верна» — и недооценивает, что dry-run проверяет только отсутствие ошибок запуска, а не архитектурную полноту (например, отсутствующие поля schema, которые понадобятся на шаге 5) |
