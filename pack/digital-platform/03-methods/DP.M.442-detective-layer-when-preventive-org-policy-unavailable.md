# DP.M.442 — Детективный слой вместо превентивного, когда org-policy недоступен по построению

## Определение

Для SaaS-платформы, встроенной поверх стороннего провайдера идентичности/хостинга, у которой ресурсы (например, репозитории) создаются в личном пространстве КАЖДОГО пользователя, а не в одной администрируемой организации-платформе — превентивные org-wide политики провайдера (аналог AWS SCP / GCP Organization Policy / GitHub «Default repository visibility») физически неприменимы: нет объемлющей организации, на которую они накладываются. Единственный остающийся рычаг защиты — детективный (реактивный) слой: подписка на события изменения состояния ресурса (вебхук) плюс права приложения на всех подключённых установках.

## Проблема

Вопрос «защищены ли по умолчанию ресурсы новых пользователей» для платформы этого типа не решается через провайдерскую политику — таких политик просто нет над личным пространством пользователя. Попытка спроектировать защиту «как обычно» (через политику провайдера) упирается в отсутствие административного домена над ресурсом.

## IPO-паттерн

| Элемент | Описание |
|---------|----------|
| Входы | Ресурс, создаваемый платформой в пространстве, не администрируемом самой платформой (личный аккаунт пользователя у стороннего провайдера) |
| Обработка | Проверить: существует ли объемлющий административный домен (организация) над ресурсом? Нет → превентивный контроль недоступен → завести детективный слой (вебхук на изменение состояния + права приложения) |
| Выходы | Обнаружение дрейфа состояния ресурса ПОСЛЕ его возникновения (не предотвращение), с минимально возможной задержкой реакции |

## Тест применимости

«Платформа обладает административным доменом (организацией) над ресурсом, который нужно защитить, или ресурс полностью в пространстве пользователя, вне контроля платформы?» Второе → превентивный контроль провайдера недоступен по архитектуре, нужен детективный слой. Первое → превентивная org-policy — нормальный первый выбор.
