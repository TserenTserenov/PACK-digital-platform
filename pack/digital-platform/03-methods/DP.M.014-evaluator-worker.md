# DP.M.014 Evaluator Worker

## Определение

**Evaluator Worker** — специализированный тип worker'а в activity-based системах, принимающий ДВА типа входных данных:
1. Сырые события за временное окно (domain_event, window 30d)
2. Уже вычисленные составные индексы (например, M-индексы из profiler)

Выход: derived classification state (например, stage_transitions).

## Отличие от Projection Worker

| Аспект | Projection Worker | Evaluator Worker |
|--------|-----------------|-----------------|
| Вход | Событийный поток (один тип) | Два типа: события + индексы |
| Выход | Проекция состояния | Классификация / ступень |
| Частота | Непрерывно / по событию | По расписанию (батч) |
| Зависимость | Независим | Зависит от предыдущего worker'а |

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Два типа входа — сырые события (непрерывно) + вычисленные индексы (батч раз в сутки) («Причина выделения в отдельный сервис»: «разные частоты обновления входных данных») ↔ выделение в отдельный сервис | Метод разрешает несовпадение частот тем, что Evaluator не встроен ни в поток событий, ни в profiler, а работает по расписанию (таблица «Отличие»: «Частота: по расписанию (батч)»), принимая оба источника асинхронно |
| Stateless-контракт (12-factor F6) ↔ single-replica enforcement при батч-расчёте («Single-replica контракт»: «разные replicas могут одновременно произвести разные stage_transitions для одного актора») | Паттерн формально stateless (можно поднять N реплик), но корректность батч-классификации требует ровно одного владельца на запуск; `pg_try_advisory_lock` — дешёвый компромисс между простотой stateless-деплоя и необходимостью exactly-once для конкретного расчёта |
| Зависимость от предыдущего worker'а в timer-chain (Evaluator «Зависит», Projection Worker «Независим») ↔ развязка через БД, а не прямой вызов («Паттерн Timer-Chain»: «каждый следующий зависит от предыдущего через БД») | Цепочка profiler → evaluator → rewards-handler создаёт последовательную зависимость по данным, но метод явно избегает синхронного вызова между сервисами, ослабляя связанность ценой задержки распространения (evaluator может отработать до появления свежих индексов) |

## Паттерн Timer-Chain

Evaluator не работает один — встраивается в timer-chain:

```
profiler (M-индексы) → evaluator (ступень) → rewards-handler (multiplier)
```

Каждый следующий зависит от предыдущего через БД, а не через прямой вызов.

## Single-replica контракт

Evaluator — stateless по 12-factor (F6), но при batch-расчётах требует single-replica enforcement, иначе разные replicas могут одновременно произвести разные stage_transitions для одного актора. Решение: `pg_try_advisory_lock` на shared БД как cheap enforcement (WP-307 Ф8, 12 мая 2026).

```sql
SELECT pg_try_advisory_lock(hashtext('stage_evaluator'));
-- TRUE → текущая replica становится owner; FALSE → выйти immediately
```

См. `memory/lessons_advisory_lock_single_replica.md`.

## Причина выделения в отдельный сервис

Разные частоты обновления входных данных:
- События поступают непрерывно
- Составные индексы считаются раз в сутки (батч)

## Bias-Annotation

_Куда систематически съезжает внимание практикующего. Статус карточки — `draft`: пометка `tentative` по прецеденту SA.METHOD.001 (WP-448 Ф12)._

| Bias | Direction of distortion |
|------|--------------------------|
| _(tentative)_ Оба входа считаются одинаково свежими | Внимание к «двум типам входа» (Определение) смещается на факт получения обоих сигналов и не разделяет их гарантии свежести — практик может считать, что раз evaluator запущен, оба источника актуальны на момент расчёта, хотя составные индексы обновляются раз в сутки батчем и могут отставать от только что поступивших событий |
| _(tentative)_ Single-replica считается решённой на уровне сервиса раз и навсегда | После первой реализации advisory_lock (`hashtext('stage_evaluator')`) внимание съезжает на «single-replica уже обеспечена» как свойство сервиса в целом; при добавлении нового batch-расчёта в тот же сервис легко забыть повторно применить `pg_try_advisory_lock` с новым ключом, специфичным для этого расчёта |

## Применимость

Любая система activity-based прогресс-трекинга с составными индексами и многоступенчатой классификацией (геймификация, квалификация, обучение).
