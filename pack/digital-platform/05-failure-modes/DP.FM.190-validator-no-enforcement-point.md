# DP.FM.190 — Валидатор без точки принуждения

## Описание

Правила проверки (валидация, санитизация, аудит атрибуции) живут только в одном слое — шлюзе, API-gateway, middleware. Минимум один сервис или путь записи технически обходит этот слой и пишет напрямую в sink. Валидация «на предпочтительном пути» — не валидация, если обходной путь существует.

«Распределены источники, sink един — валидация либо переезжает в хранилище, либо у всех кроме шлюза отзывается право прямой записи.»

## Условие возникновения

- Валидационный слой обязателен по документации и обычно используется
- Существует технический обходной путь: прямой SQL, legacy-endpoint, emergency-write, временный доступ при инциденте
- Прецедент обхода уже случался — значит, он воспроизводим

## Тест обнаружения

«Может ли кто-то технически записать в хранилище, минуя слой с правилами?» Да → правила декоративны.

Тест не требует злого умысла: достаточно технической возможности + одного исторического прецедента обхода.

## Митигация

Два честных решения (промежуточных нет):

1. **Принуждение на уровне хранилища**: триггер / constraint / row-level security — правила нельзя обойти без изменения схемы
2. **Отзыв прямой записи**: REVOKE INSERT/UPDATE у всех ролей, кроме валидирующего слоя; остальные потребители получают только SELECT
