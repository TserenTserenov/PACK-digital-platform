# DP.FM.456 — Whitelist по статическому маркеру спуфится буквальным вводом

## Тезис и механизм ошибки

Первая версия whitelist для `.iwe-paths` помечала легитимную форму команды статической строкой-маркером в тексте (`__WL_СТАТИКА__`). Атакующий, зная этот маркер — он статический, значит не секрет, и предсказуем заранее, — может вставить его буквально в свой ввод и получить `allow` без реального совпадения намерения (source `__WL_СТАТИКА__` + одноимённый файл на диске = обход гейта). Guard, построенный на распознавании статического текста, неотличим от guard'а, который атакующий может процитировать сам.

## Диагностический принцип

Whitelist-маркер, встраиваемый в проверяемый текст для распознавания «это легитимная форма», обязан быть непредсказуемым заранее (nonce, генерируемый заново на каждый процесс/вызов) — статическая строка, повторяющаяся между запусками, доступна атакующему тем же способом, что и легитимному вызывающему, и перестаёт быть доказательством происхождения.

## Границы

Различение применимо к любому механизму, где сам факт «во входе присутствует маркер X» интерпретируется как доказательство легитимности источника этого входа — если X не меняется между вызовами и не завязан на секрет/сессию, доказательства нет. Не относится к whitelist'ам, построенным на содержательной проверке (путь, контрольная сумма, подпись), не на присутствии текстовой метки.

## Проверка

«Whitelist-маркер, встроенный в проверяемую команду, одинаков между разными вызовами/процессами?» Да → маркер известен заранее и атакующему, доказательства легитимности он не даёт — воспроизведён DP.FM.456. Фикс — `GATE_NONCE`, генерируемый заново на каждый процесс (PreToolUse-вызов хука — свежий процесс), непредсказуемый заранее.
