# DP.FM.464 — `set -e` на захвате вывода обрывает блок до его собственной пропускающей ветки

## Тезис и механизм ошибки

Между двумя скриптами существует неявный контракт: вызываемый возвращает ненулевой код как **сигнал состояния**, а не как отказ, и вместе с ним отдаёт валидный вывод — решение «блокирует это или нет» по замыслу принимает вызывающий, сравнивая содержимое вывода. Прецедент: `ke-queue-stats.sh` выходил с кодом 1 при непустых diagnostics, выдавая при этом корректный JSON; блок вызывающего был написан так, чтобы сравнить числа и заблокировать только при расхождении, а пустой diagnostics пропустить.

Вызывающий захватывал вывод формой `VAR=$(cmd)` под `set -e`. Для оболочки присваивание из command substitution наследует статус команды, поэтому ненулевой код обрывал блок **на строке захвата** — до того, как исполнилась хоть одна строка его собственной логики. Внешне это выглядит как отказ проверки (`day-open`: «1/23 blocks failed»), хотя написанная ветка «пропустить, не блокировать» ни разу не выполнилась и вообще не участвовала в исходе. Фикс — `|| true` на захвате, что возвращает решение туда, где оно и было задумано: в логику блока.

## Диагностический принцип

Отличие от общего совета «не используй `set -e` бездумно»: вопрос не в том, включён ли `set -e`, а в том, **кто принимает решение о фатальности**. Если вызываемый скрипт документирует ненулевой код как содержательный сигнал (а не как сбой) и отдаёт при этом валидный вывод, то любая форма захвата этого вывода без явной нейтрализации кода передаёт решение оболочке — то есть отменяет контракт молча, ещё до его чтения. Симптом «проверка падает» неотличим от «проверка отработала и запретила», пока не прочитан код блока.

## Границы

Правило касается только вызовов, где ненулевой код — часть объявленного контракта вызываемого (сигнал состояния при валидном выводе). Там, где ненулевой код означает настоящий сбой, `set -e` на захвате отрабатывает верно и снимать его нельзя. Глухое `|| true` на всех захватах подряд воспроизводит антипаттерн из `DP.METHOD.143` — нейтрализация кода обязана быть точечной и сопровождаться комментарием, какой именно rc и почему нефатален.

## Проверка

Для каждого `VAR=$(cmd)` под `set -e`: «документирует ли `cmd` ненулевой код как содержательный сигнал при валидном выводе?» Если да — «нейтрализован ли код явно (`|| true` на этом захвате либо `set +e; rc=$?; set -e` с комментарием про конкретный rc), или блок полагается на ветку, до которой управление не дойдёт?» Второе → воспроизведён DP.FM.464. Прямой тест: прогнать вызывающий блок на входе, при котором вызываемый заведомо возвращает ненулевой код, и убедиться, что пропускающая ветка действительно исполняется.
