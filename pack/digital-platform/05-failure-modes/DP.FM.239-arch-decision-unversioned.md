# DP.FM.239 — Архитектурное решение не зафиксировано в VCS

## Паттерн

Архитектурное или модельное решение принято (обсуждено, выбрано), но не закоммичено в систему версий. Шаг по плану отмечается как «выполнен» без коммита.

## Дефекты

Такое решение обладает двумя структурными дефектами:
1. **Не проверяемо:** нельзя сверить, что реализуется именно утверждённая модель, а не произвольный вариант.
2. **Не наследуемо:** следующий агент/итерация не может опереться на зафиксированное основание — начинает с чистого листа или воспроизводит решение заново.

## Почему опасен

Failure mode тихий: нет ошибки в логах, нет красного статуса. Обнаруживается только при попытке сверки («а что именно мы согласовали?»). К тому моменту контекст может быть потерян.

## Пример

WP-437: архитектурная проверка модели волны-2 запланирована на 24-28 июня — следов в git нет. Значит, либо не сделана, либо сделана «в голове». Следующий шаг (набор участников) идёт на неутверждённой модели.

## Механизм

1. Решение принято устно или в чате
2. Шаг помечается done без артефакта (commit, ADR-файл, обновлённая спецификация)
3. Watchdog/Day-Open не видит коммита → не может обнаружить gap
4. Запуск следует за неутверждённым фундаментом

## Лечение

- Решение считается принятым только после коммита артефакта: ArchGate-запись, файл модели, обновлённый WP-context.
- Для плановых шагов с обязательным артефактом: watchdog проверяет «шаг = done, но коммита нет» → алерт.
- **DP.D.225:** квалифицировать как блокирующее предусловие (не восполнимую разведку), применять эскалацию.

- Частный случай: DP.FM.011 (P1b — провал не зафиксирован)
- Конкретизирует: DP.D.225 (просроченный шлюз = блокирующее предусловие)
