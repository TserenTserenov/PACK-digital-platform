# DP.FM.477 — Флаг принят парсером, но не прочитан подкомандой: молчаливый no-op вместо отказа

## Тезис и механизм ошибки

Общий парсер аргументов принимает флаг на любом вызове, а читает его лишь часть подкоманд. Неиспользованный флаг не даёт ни ошибки, ни предупреждения: пользователь считает его применённым и получает результат для другого объекта. Конкретный случай: `open --wp N --isolate` определяет каталог изоляции через `git rev-parse --show-toplevel` от текущей рабочей директории вызова, а не через `--repo` — этот флаг подкоманда `open` не читает вовсе (он нужен для `note-commit` и других подкоманд). Вместо целевого репозитория изолировался корневой.

Наступили на это дважды подряд: вторая попытка — с явным `--repo DS-my-strategy` — снова молча проигнорировала флаг. Цена: две пустые сессии, которые агент не может закрыть без штатного quick-close (осознанное ограничение WP-484); их оставили на истечение TTL.

## Диагностический принцип

Флаг, который парсер принял, но подкоманда не использовала, неотличим от применённого: вывод выглядит успешным. Дизайн-следствие: флаг, неприменимый для подкоманды, — это ошибка или предупреждение, а не тихий no-op; либо флаг, задающий целевой объект, обязателен и единообразно читается всеми подкомандами.

## Границы

Карточка про расхождение «принят парсером ↔ прочитан подкомандой». Тот же симптом (изоляция над каталогом вызывающего) по другой причине — отсутствие `cd` в шаге скилла — разобран в AS.FM.092. Общий принцип «явный отказ вместо молчаливого иного режима» (DP.D.229) шире; здесь зафиксирован конкретный механизм CLI. Соседний случай того же принципа — отсутствие семафора расширяет область проверки на все сессии — разобран отдельно в DP.FM.480: правка парсера не меняет дефолт области там.

## Проверка

«Каждый флаг, который принимает парсер, либо читается всеми подкомандами, где он допустим, либо отвергается на остальных с явной ошибкой?» Нет → воспроизведён DP.FM.477: принятый, но не применённый параметр даёт результат для другого объекта.
