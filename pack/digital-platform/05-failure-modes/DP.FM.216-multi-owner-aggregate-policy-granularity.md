# DP.FM.216: Политика доступа на уровне агрегатного типа с несколькими FSM-владельцами

## Описание

Агрегатный тип состояния содержит записи от двух и более разных конечных автоматов (FSM) с разными владельцами. Если политика доступа привязана к **типу целиком** (а не к каждому под-процессу отдельно), одна роль получает доступ к записям другой роли — нарушение принципа минимальных прав.

## Класс дефекта

Эскалация привилегий (privilege escalation). Формально политика «выглядит правильно», но семантически неверна — гранулярность недостаточна.

## Ситуация возникновения

```
Тип состояния: "разрешения"
  ├── FSM-A: OAuth-цикл  → владелец: OAuth-воркер
  └── FSM-B: цикл согласий → владелец: Consent-воркер

Политика (НЕПРАВИЛЬНАЯ): "читать строки типа 'разрешения', где owner = current_role"
Результат: OAuth-воркер читает согласия, Consent-воркер читает OAuth-токены
→ утечка между изолированными процессами
```

## Фикс

Политика привязывается к **конкретному событию/под-процессу**, а не к агрегатному типу:

```sql
-- Таблица-справочник: event_type → responsible_role
CREATE TABLE event_type_ownership (
  event_type TEXT PRIMARY KEY,
  owner_role TEXT NOT NULL
);

-- RLS-политика на уровне события, не типа:
CREATE POLICY event_owner_read ON domain_event
  FOR SELECT
  USING (
    event_type IN (
      SELECT event_type FROM event_type_ownership
      WHERE owner_role = current_setting('app.user_role', true)
    )
  );
```

Расхождение реестра и таблицы ловит верификационный скрипт при каждом деплое.

## Тест

«В этом агрегатном типе все события управляются одним и тем же FSM с одним владельцем?»
- Да → политика на уровне типа допустима
- Нет → политика должна быть на уровне конкретного события
