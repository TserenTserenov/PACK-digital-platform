# DP.FM.378 — дублирующий канал зависимости как латентная бомба сборки

## Паттерн

Git+https-зависимость, прописанная в `requirements.in`, дублирует пакет, уже доступный из локального wheel-файла в Dockerfile. Пока Docker-кэш не инвалидирован — дублирование не приводит к видимому эффекту (используется закешированный слой). Первая же реальная инвалидация кеша заставляет систему разрешать обе версии зависимости одновременно — сборка падает без явной связи с недавними изменениями кода.

## Механизм

1. Два независимых пути поставки одной и той же зависимости сосуществуют без конфликта, пока кеш маскирует их совместное разрешение
2. Инвалидация кеша (изменение любого более раннего слоя Dockerfile, обновление базового образа) заставляет заново резолвить обе зависимости
3. Ошибка сборки выглядит несвязанной с реальной причиной — она появляется в момент, когда меняется что-то совершенно другое

## Почему опасен

Задержка между внесением дублирующей зависимости и проявлением сбоя (до следующей инвалидации кеша) маскирует причинно-следственную связь — диагностика идёт по недавним изменениям, а не по исходному источнику дублирования.

## Лечение

Аудит зависимостей на предмет дублирования между разными механизмами поставки (requirements-файл vs vendored wheel) как часть регулярной проверки, не дожидаясь фактического обрыва сборки.
