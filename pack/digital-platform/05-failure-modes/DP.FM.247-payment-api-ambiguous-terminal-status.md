# DP.FM.247 — FAILED от платёжного API трактуется как окончательный отказ

## Описание

Статус `FAILED` от платёжного (или внешнего) API принимается за окончательный отказ без проверки контекста: из какой ветки кода он возникает и какова его семантика в данном случае.

## Пример

WP-446: Aisystant возвращал `FAILED` из двух разных веток кода. Одна ветка — финальный провал (платёж точно не прошёл). Вторая — промежуточное состояние «неизвестно, в процессе». Немедленный откат резерва бонусов при любом `FAILED` привёл бы к ложной потере бонусов у пользователей с проходящим платежом.

## Тест обнаружения

«Какой именно код выбрасывает этот статус и в каких условиях?»
- Проверить source code API (или документацию) — не предполагать единственную семантику
- Если статус может означать «неизвестно» → не производить деструктивный side effect

## Инвариант

Source-of-truth статуса платежа — реализация API, не название статуса. Реагировать деструктивным side effect (откат, отмена) только на однозначно задокументированный терминальный статус.

## Паттерн обхода

```python
if status == "SUCCEEDED":
    grant_access()
elif status in EXPLICITLY_FINAL_FAILED_STATUSES:  # задокументированные финальные
    rollback_reservation()
else:  # FAILED (промежуточный), IN_PROGRESS, UNKNOWN
    pass  # ждём следующего cron-цикла или явного webhook
```
