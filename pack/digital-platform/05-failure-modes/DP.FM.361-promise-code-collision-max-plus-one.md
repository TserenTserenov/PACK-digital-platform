# DP.FM.361 — Коллизия кода обещания при назначении по «max+1»

## Паттерн

Новому сервисному обещанию (`DP.SC.NNN`) присваивается код по правилу «максимальный существующий номер + 1», без проверки, не занят ли этот номер уже в другом сегменте реестра (например, диапазон L4-Personal и L2-Platform ведутся раздельно, но общий счётчик max+1 не видит границу диапазонов).

## Механизм

1. Реестр обещаний растёт частями из разных источников/фаз одновременно
2. Наивный «взять последний номер +1» не учитывает зарезервированные диапазоны или параллельно назначенные номера в других ветках/сессиях
3. Коллизия обнаруживается постфактум — уже созданный код совпал с занятым (`DP.SC.020` реально уже существовал под другим смыслом, пришлось переносить на `DP.SC.044`)

## Почему опасен

Коллизия ID в реестре ломает однозначность ссылок — существующие упоминания старого кода начинают указывать на два разных обещания одновременно, пока не будет проведена ручная миграция.

## Лечение

Перед назначением нового кода — grep существующего значения по всему реестру и связанным Pack-репо (не полагаться только на локальный счётчик), особенно при работе с диапазонной нумерацией (§8 CLAUDE.md — DP.SC.001-099/101-199/201-299).
