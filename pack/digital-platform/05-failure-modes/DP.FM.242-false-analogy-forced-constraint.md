# DP.FM.242 — Ложная аналогия по поверхностному сходству API: вынужденный констрейнт ≠ выбранная настройка

## Паттерн

Настройка (флаг, параметр, режим) соседнего API-объекта воспринимается как выбранная, хотя на самом деле она вынуждена внешним ограничением. При переносе на новый объект копируется следствие ограничения без проверки, действует ли само ограничение.

## Пример

```python
# Подписка: cashback ВЫНУЖДЕН — Aisystant API возвращает 403 при скидке
subscription_payment = {
    "cashback_model": True,  # не выбор, а единственный выход
    "skip_ceiling": True,
}

# Курс: флаги скопированы по аналогии «они похожи»
course_payment = {
    "cashback_model": True,  # проверки наличия ограничения не проводилось
    "skip_ceiling": True,
}
# Дефект: у курса может не быть 403-ограничения — настройка лишняя или вредная
```

## Механизм

Поверхностное сходство API (одинаковая схема, похожие поля) создаёт иллюзию взаимозаменяемости. Разница скрыта: один объект имеет внешнее ограничение (API rejection, compliance rule, DB trigger), другой — нет. Тест на наличие ограничения не проводится, потому что «сосед работает».

## Почему опасен

1. Тесты могут быть зелёными в тестовой среде, где ограничение не воспроизводится.
2. Дефект проявляется в проде при первом столкновении с ограничением (403, deadlock, compliance audit).
3. Ложный вывод «настройка работает у соседа → работает у меня» не фиксируется как риск.

## Лечение

Перед копированием настройки по аналогии — три вопроса:
1. Эта настройка у образца **выбрана** (произвольный выбор) или **вынуждена** (единственный выход при ограничении)?
2. Каким именно ограничением вынуждена?
3. Действует ли то же ограничение в моём случае?

Если ответ на вопрос 3 неизвестен → консервативный дефолт + явная проверка (U1-тест с real constraint).
