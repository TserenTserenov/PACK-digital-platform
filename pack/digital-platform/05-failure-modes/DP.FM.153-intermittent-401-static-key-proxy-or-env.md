# DP.FM.153 — Перемежающийся 401 со статическим ключом = прокси или env, не ключ

## Описание

401 со статическим ключом не может быть «иногда» — ключ либо всегда валиден, либо нет. Intermittent 401 — это оксюморон: указывает не на проблему самого ключа, а на: (а) прокси-слой (litellm, nginx, gateway) добавляет свой ключ — иногда пустой или ротированный; (б) несколько реплик сервиса, у части пустой/неверный env; (в) частичная ротация ключа — для части инстансов обновлён, для части — нет.

## Контекст возникновения

- Сервис с авторизацией по статическому ключу (API key, bearer token)
- В стеке есть прокси-слой между клиентом и upstream (LLM-прокси, reverse-proxy, gateway)
- Деплой с несколькими репликами (Railway, k8s, Fly)
- Ротация ключей без атомарного rollout на все инстансы

## Симптом

401 errors возникают периодически, но не на каждый запрос. Один и тот же ключ при ручной проверке (curl) работает; в проде — иногда отдаёт 401. Retry часто помогает (попадание в «здоровую» реплику).

## Корректные паттерны

**Диагноз-чеклист (порядок проверки):**
1. Число реплик/процессов сервиса (`railway list services`, `kubectl get pods`).
2. Совпадение env с ключом во всех инстансах (`env | grep API_KEY` на каждой реплике).
3. Есть ли прокси-слой в стеке (litellm, gateway) — какой ключ он подставляет в Authorization header.
4. История ротации ключа за последние 24ч.

**Профилактика:**
- Атомарный rollout всех реплик при ротации (no rolling update для env-секретов).
- Healthcheck с проверкой авторизации, не только TCP.
- Логирование `key_fingerprint` (хэш первых 4 байт) в каждый upstream-вызов.

## Диагностика

«Перемежающийся 401 при одном статическом ключе» — сигнал смотреть не на ключ, а на инфраструктуру вокруг него.

## Тест

«401 возникает иногда при одном ключе?» Да → искать прокси, env-несовпадение или частичную ротацию, не валидность ключа.
