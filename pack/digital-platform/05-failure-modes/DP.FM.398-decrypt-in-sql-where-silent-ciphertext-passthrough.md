# DP.FM.398: Построчный decrypt внутри SQL WHERE и молчаливый возврат шифротекста при недоступном ключе

## Симптом
Найдено холодным ревью (независимый субагент, до деплоя) при расширении column-level encryption на несколько таблиц с токенами внешней авторизации. Не инцидент в проде — предотвращено до деплоя.

## Причина
Два независимых антипаттерна защиты в одной зоне (column-level encryption):
1. Проверка токена выполняла расшифровку внутри SQL WHERE/выборки — одна строка с несовпадающим ключом (например, после ротации) кидает исключение и роняет весь запрос сразу для ВСЕХ пользователей, не только для владельца этой строки.
2. Функция расшифровки текста при недоступном/неверном ключе молча возвращала исходный шифротекст, как будто это valid plaintext — тихая утечка мусора как «рабочего» значения либо тихий отказ всех проверок токена.

## Антипаттерн → Паттерн
- **Антипаттерн:** расшифровка как часть SQL-выборки/WHERE (риск одной строки роняет весь запрос); функция расшифровки при недоступном ключе возвращает исходные байты без сигнала об ошибке.
- **Паттерн:** расшифровка — всегда risky per-row операция уровня приложения: построчный цикл с try/except, изолирующий ошибку одной строки от остальных; при недоступности/неверности ключа — явный `raise`, никогда не молчаливое прохождение шифротекста как plaintext.

## Тест обнаружения
«Расшифровка происходит внутри SQL-запроса (WHERE/SELECT-выражение) или в цикле приложения с изоляцией ошибки по строке?» Первое → риск полного отказа запроса от одной строки. «Функция расшифровки при недоступном ключе — что возвращает?» Тихий возврат шифротекста/пустоты → маскируется под valid-значение.

## Применимость
Любая система column-level encryption (не только Postgres) — расшифровка нескольких строк батчем/запросом создаёт тот же риск.
