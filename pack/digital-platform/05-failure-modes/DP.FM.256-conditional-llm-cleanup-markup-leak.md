# DP.FM.256 — Conditional LLM cleanup: постобработка зависит от входных данных → частичная утечка разметки

## Паттерн

Очистка/нормализация вывода LLM (strip XML-тегов, удаление разметки) реализована как условная ветка: выполняется только при наличии ожидаемых полей во входных данных. При нестандартном входе (отсутствии полей) ветка не срабатывает, и сырой ответ модели попадает в вывод как есть.

## Пример

```python
def _parse_translation_response(response, fm_values):
    body = response.choices[0].message.content
    if fm_values:  # очистка только если есть переводимый frontmatter
        body = body.replace("<body>", "").replace("</body>", "")
    return body

# Файлы без title/description/summary: fm_values = {} → очистка пропускается
# Результат: <body> тег оказывается на первой строке опубликованного файла
```

## Механизм

Разработчик добавил strip XML-маркеров только в ветку, где они «очевидно нужны». Файлы без frontmatter прошли через функцию без очистки — и получили сырой ответ модели. 13 из 38 опубликованных файлов были затронуты.

## Почему опасен

1. Ошибка проявляется только на подмножестве входных данных (без frontmatter) — тест с «обычным» файлом не поймает.
2. В продакшене файл выглядит корректным, но содержит технический мусор на первой строке.
3. Сложно обнаружить ретроспективно: нужен grep по опубликованным файлам.

## Лечение

- Постобработка вывода LLM должна быть **безусловной**: strip/normalize применяется к любому ответу модели, независимо от входных свойств.
- Тест: «что произойдёт, если входной файл не содержит ожидаемых полей?» — если ответ «очистка пропустится», это ошибка дизайна.
- Минимальный acceptance-тест: опубликованный файл не должен содержать XML/HTML теги на первой строке.

## Обнаружение

```bash
grep -r "^<[a-zA-Z]" published/ | head
```
