# DP.FM.197 — Replay-инструмент принят за буфер входящих: «у нас уже есть что-то похожее» без проверки направления потока

## Описание

Разработчик идентифицирует существующий replay-инструмент как решение для задачи приёма ненадёжных входящих событий, ссылаясь на внешнее сходство («тоже работает с событиями»). Реальное направление потока у replay-инструмента — **source → sink replay** (из надёжного хранилища к отстающим витринам), а не **incoming → store**. Задача остаётся нерешённой, но «решение» объявлено найденным.

## Пример

WP-457 Ф12 К3: `outbox_replay.py` принят за механизм буферизации входящих `consent_grant`-событий при ненадёжной доставке. Прямая проверка кода (ход 4) показала: инструмент читает уже зафиксированные события из immutable-журнала и применяет их к отстающим проекциям (projection replay). Входящие события, которые ещё не были записаны, обрабатывать не может.

## Тест обнаружения

«Инструмент принимает события, которые ещё не записаны, и обеспечивает их надёжное сохранение?»
Нет → это не буфер входящих, это replay из уже надёжного хранилища.

Проверка: «В каком направлении идёт поток? source→sink или sink replay from source?»

## Инвариант

Replay = чтение из надёжного хранилища и применение к потребителям. Incoming buffer = приём до первой надёжной записи. Одно не заменяет другое.

## Митигация

При поиске «готового решения» в репозитории: проверить направление потока данных инструмента (не только имя, не только «работает с событиями»).
