# [DP.FM.283] Dead Pipeline Step with No Output Consumer

## Суть паттерна

В конвейере существует шаг, который **объявляет Выход (артефакт/отчёт), но у этого Выхода нет потребителя внутри контура**. Шаг выполняется, тратит ресурсы и иногда маскирует ошибки — но его результат не влияет на последующие шаги. ВДВ-модель (Вход → Действие → Выход) нарушена: Выход есть, потребителя нет.

## Инцидент

WP-5 ВДВ-аудит открытия дня: шаг «сформировать отчёт» стоял ПОСЛЕ обновления снапшота, но ПЕРЕД его чтением:

- шаг 1: обновить снапшот
- шаг 2: сформировать отчёт — **мёртвый шаг** (отчёт объявлен Выходом, потребителя в шаге 3 нет)
- шаг 3: читать снапшот — читаешь устаревший (pre-refresh)
- шаг 4: читать отчёт

Нарушение порядка refresh → read: пользователь читает данные до обновления, ошибки нет, разрыв невидим.

## Механизм

1. Шаг объявлен в процессе, но его Выход не связан ни с одним последующим шагом.
2. При этом шаг может быть «логически правильным» — он работает, не падает.
3. Разрыв обнаруживается только при ВДВ-аудите: «кто потребляет Выход этого шага?»

## Тест на провал

«Если убрать этот шаг — что изменится в результате последующих шагов?» Ничего — мёртвый шаг.

«Кто является потребителем Выхода шага X?» Нет ответа внутри контура — FM.283.

## Детектор

**ВДВ-проверка каждого шага:** для каждого шага явно указать потребителя его Выхода. Шаг без потребителя — кандидат на удаление.

## Защита

1. **ВДВ-аудит pipeline:** для каждого шага зафиксировать `{Вход, Действие, Выход, Потребитель}`. Шаг с пустым `Потребитель` — мёртвый.
2. **Порядок refresh → read:** обновление данных должно стоять НЕПОСРЕДСТВЕННО перед их чтением, без промежуточных шагов.
3. **Граф зависимостей:** нарисовать flow — кто от кого зависит. Изолированный шаг (нет входящих стрелок от него ни к кому) — dead step.
