# DP.FM.188 — Общий ключ владельца БД у нескольких сервисов — структурная неатрибутируемость записи

## Описание

Несколько сервисов используют одну учётную запись владельца базы данных для записи. Любая аномальная запись принципиально неотличима от легитимной: дверь одна, ключ общий. Расследование упирается не в «ненайденный файл», а в архитектурный факт.

**Класс:** data-layer attribution

## Пример

WP-454: `information_schema` показала одну shared-owner учётную запись как единственного технического кандидата-писателя после исчерпания перебора кода (5 раундов grep). Конкретный сервис-автор аномальной записи — недиагностируем без изменения архитектуры.

## Тест обнаружения

«Можно ли постфактум определить, какой именно сервис сделал конкретную аномальную запись?» Нет → DP.FM.188 присутствует.

## Инвариант

Shared-credential доступ делает инциденты записи структурно нерасследуемыми постфактум. Операционные логи ОС помогают частично, но не заменяют атрибуцию на уровне данных.

## Митигация (согласованный план)

1. **Per-service роли** с минимальными правами (замена общего ключа)
2. **Метка процесса и run-ID** в каждой записи — атрибуция на уровне данных, не только прав
3. **Инвентаризация** всех потребителей общего ключа ДО урезания его прав
