# DP.FM.449 — Правило восстановления «живой потомок PID владельца» структурно невыполнимо при retry из планировщика

## Тезис и механизм ошибки

Условие reclaim семафора смешивает два разных вопроса: «жив ли владелец» (проверяемо через `ps -p`/`kill -0`) и «происходит ли текущий вызов от владельца» (`_owner_pid_is_live_ancestor`, проверяемо только внутри одного дерева процессов). Для интерактивного продолжения второе условие осмысленно. Для планировщика (cron/systemd retry) оно невыполнимо структурно: предыдущий процесс по определению уже завершился — иначе не было бы retry — а новый процесс, запущенный планировщиком, всегда независим и не является потомком старого. Единственный автоматический путь восстановления в результате всегда fail-closed, что каждую ночь блокирует открытие дня и недели.

## Диагностический принцип

Общий тест для любого правила восстановления: смоделировать вызывающего из самого частого реального контекста (cron/systemd retry) и проверить, существует ли хотя бы один путь, по которому правило пропускает. Если единственный путь восстановления требует условия, невыполнимого именно в штатном retry-контексте — правило спроектировано для другого сценария (интерактивное продолжение) и ошибочно применено к автоматическому.

## Границы

Различение не говорит, что проверка родства процессов бесполезна вообще — для интерактивного продолжения той же сессии человеком она осмысленна и защищает от чужого вмешательства. Проблема — в применении этого условия как ЕДИНСТВЕННОГО автоматического пути восстановления там, где основной вызывающий контекст — планировщик, а не интерактивное продолжение.

## Проверка

Смоделировать вызов из независимого процесса (не потомка записанного PID), при живом или мёртвом владельце по `ps -p`. Если единственный путь reclaim требует ancestry-проверки — воспроизведён тупик. Контрпример: успешный reclaim по независимому от ancestry критерию (например, TTL + живость по `kill -0` без требования родства) не должен требовать ancestry вообще.
