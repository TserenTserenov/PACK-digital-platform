# DP.FM.232 — Phantom field: моделировать поле, которого нет в реальном выходе источника

## Паттерн

Проектировщик «видит» в выходе функции / сервиса поле, которого там нет. Прототип шва (seam) строится на воображаемой сигнатуре, проходит внутреннее ревью и тесты, но при миграции обнаруживается несуществующий контракт.

Типичный случай: код ожидает `opt_out_category` в выходе `analyze()`, реальный возврат которого — `{rule_id, nudge_key, nudge_payload, cooldown_days}`. Категории там нет — нужен явный слой перевода.

## Механизм ошибки

1. Проектировщик видит downstream-потребителя поля (например, фильтр по категории) и предполагает, что upstream-источник уже его выдаёт
2. Прототип шва строится на воображаемой сигнатуре — тесты проходят на mock-данных, где поле подставлено вручную
3. Cold-context ревьюер или реальная интеграция выявляет расхождение (реальная функция поля не возвращает)

## Правильный порядок диагностики / Фикс-паттерн

1. **Сверить реальную сигнатуру возврата:** открыть исходный код источника, проверить return type / response schema — не полагаться на предположение
2. **Добавить явный слой перевода** (например, `_RULE_TAXONOMY: dict[str, str]` — `rule_id → категория`), не зашивать несуществующее поле
3. **Честно пометить в design-документе:** новый слой перевода = новая работа при миграции, не готовая обёртка

## Тест обнаружения

«Поле, на которое опирается код, реально есть в возврате источника, или я его домыслил?»
- Домыслено → phantom field; добавить явный слой перевода
- Есть в реальной сигнатуре → ложная тревога
