# DP.FM.205 — Промежуточный статус FSM без confirm-пути = limbo навсегда

## Описание

При введении нового промежуточного статуса в конечный автомат (FSM) без одновременного добавления штатного пути выхода из этого статуса — записи застревают в limbo: они не являются ни предварительными, ни финальными. В append-only хранилищах это усугубляется: обычный UPDATE недоступен, ручное изменение в базе неконтролируемо.

## Пример

WP-454 (панели пользователя): введён статус `требует_проверки`. Путь `confirm_panel()` не был добавлен в тот же PR. Панели в этом статусе:
- `panel_check.py` корректно не считал их финальными (side effect)
- `panel_render.py` отображал их данные без баннера предупреждения (silently leaked)
- Выйти из статуса через обычный flow было невозможно

## Диагностика

Признак: статус в базе не меняется несмотря на завершённость обработки. Объект «завис» между двумя состояниями на неопределённый срок.

Тест: «есть ли в коде метод, переводящий этот статус в следующий штатный?»
- Нет → FM.205 применим

## Исправление

Правило: каждый новый промежуточный статус в FSM требует явного выхода из него — `confirm_NNN()` / `approve_NNN()` / `finalize_NNN()` — введённого в том же PR, что и сам статус.

Для append-only хранилищ: метод выхода = запись новой строки с finalized-статусом, не UPDATE.
