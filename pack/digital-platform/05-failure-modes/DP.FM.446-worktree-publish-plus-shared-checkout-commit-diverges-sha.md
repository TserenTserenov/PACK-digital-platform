# DP.FM.446 — Смешанная публикация сессии (общий чекаут + worktree) даёт два SHA одного коммита

## Тезис и механизм ошибки

DP.M.414 закрывает гонку «точное совпадение SHA перед публикацией» через fetch+cherry-pick+retry поверх общего шлюза координации — для публикации коммитов ОДНИМ путём. Не покрытый случай: сессия публикует разные коммиты разными путями в рамках одной сессии. Первый коммит сессии успевает лечь напрямую в общий чекаут (до того как чекаут оказывается занят чужими незакоммиченными правками); оставшиеся коммиты той же сессии уходят в origin через изолированный worktree-шлюз (DP.M.414). Origin получает пересозданную версию первого коммита с тем же сообщением, но новым SHA — локальная ветка общего чекаута продолжает хранить старый SHA как «свой».

## Наблюдаемый эффект

В конкретном случае — расхождение локальной ветки общего чекаута DS-ecosystem-development с origin/main на 17 локальных / 24 удалённых коммита при одинаковом сообщении первого коммита под разными SHA (`24665767` локально vs `1dac87b1` в origin). Любой инструмент, считающий факты сессии по локальному `git log` общего чекаута (метрики Close, session-close-feed, day-open дайджест), недосчитывает часть или всю сессию — не потому что коммит потерян в origin, а потому что локальная копия разошлась.

## Границы

Документ не утверждает, что worktree-публикация (DP.M.414) сама по себе ошибочна — метод исправно решает гонку, для которой спроектирован. Расхождение возникает только при смешанном пути (часть коммитов сессии — напрямую в общий чекаут, часть — через worktree), не при последовательном использовании только одного из путей на всю сессию.

## Лечение (кандидат-правило)

После публикации части сессии через worktree — либо сразу обновить общий чекаут до актуального origin (fetch + синхронизация, если чекаут не занят другой сессией), либо любой инструмент, считающий факты сессии, обязан читать `origin/<branch>`, а не локальный HEAD общего чекаута.
