# DP.FM.382 — чистый локальный дифф не гарантирует зелёный CI

## Паттерн

Уверенность «мой diff чистый (shellcheck/bash -n прошли локально) → CI будет зелёным» — ложная логическая связка. `main` мог быть уже красным (сломан кем-то другим) ещё до данного изменения — локальная чистота диффа никак не проверяет состояние ветки, в которую он вливается.

## Механизм

1. Проверка перед пушем ограничена локальным diff (изменёнными строками)
2. Состояние `main`/базовой ветки на момент проверки неизвестно локальной проверке
3. `main` уже был красным по независимой причине — CI после пуша показывает failure, не имеющий отношения к текущему изменению

## Почему опасен

Разработчик тратит время на расследование «что я сломал», хотя реальная причина red CI — не в его изменении вообще; ложная атрибуция причины сбоя себе.

## Лечение

Перед пушем/после него — явно проверять `gh run list` (или аналог) на СВОЙ конкретный коммит, а не полагаться на локальную чистоту диффа как индикатор ожидаемого статуса CI.
