# DP.FM.455 — Whitelist матчит текст команды, не резолвленное значение переменной

## Тезис и механизм ошибки

Whitelist для `source|. "$HOME/.iwe-paths"` в `dry-run-gate.sh` допускал сорсинг только этого конкретного файла — но проверял синтаксическую форму команды, не итоговое резолвленное значение `$HOME` на момент исполнения. `HOME=/tmp/evil; . "$HOME/.iwe-paths"` проходил как allow текстово, но при реальном исполнении bash сорсит `/tmp/evil/.iwe-paths` — классификатор разбирает составную команду на сегменты независимо и не помнит присваивания из предыдущих сегментов. Присваивание `HOME=` где угодно раньше в той же составной команде отзывает намерение whitelist без изменения его текстового паттерна.

## Диагностический принцип

Whitelist, построенный по синтаксической форме команды (какой файл ПОИМЕНОВАН в тексте), не эквивалентен whitelist по фактическому исполнению (какой файл будет реально прочитан) — если аргумент команды зависит от переменной окружения, любое присваивание этой переменной где-либо раньше в составной команде меняет исполнение, не меняя текст проверяемого сегмента. Классификатор, разбирающий составную команду на независимые сегменты, теряет этот эффект по конструкции.

## Границы

Различение применимо к guard'ам/whitelist'ам, чей allow-паттерн ссылается на путь, зависящий от переменной окружения, разрешаемой самим shell в момент исполнения — а не к паттернам, работающим с буквальными, не подставляемыми строками.

## Проверка

«Whitelist проверяет синтаксическую форму команды (какое имя переменной/пути написано в тексте) или резолвит эту переменную с учётом всех присваиваний ранее в составной команде?» Только первое → воспроизведён DP.FM.455. Фикс — пре-скан всей составной команды на присваивания `HOME=`/`IWE_PATHS_FILE=` в любом месте, отзывающий whitelist для команды целиком; второй раунд холодного ревью (Codex) на этот фикс добил ещё 3 формы присваивания (`readonly`/`declare`/`typeset`/`local`/`export`) и anchoring-пробел (присваивание не первым словом сегмента).
