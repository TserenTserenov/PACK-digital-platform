# DP.FM.472 — Fallback по коду возврата пропускает «успех с пустым результатом»

## Тезис и механизм ошибки

Существующий bash-fallback на альтернативную (python3) реализацию срабатывал только при ненулевом коде возврата python3-процесса. Платформо-зависимое декодирование портило кириллический заголовок в пустой slug, но python3 при этом завершался с кодом 0 — успешный код возврата не гарантирует пригодный результат, поэтому существовавший fallback никогда не срабатывал.

Цепочка отказа: `create-wp.sh` вызывает python3-хелпер для транслитерации кириллического заголовка в slug; на платформе с недетерминированным декодированием stdin (не гарантированно UTF-8, напр. Windows Git Bash) хелпер декодирует некорректно и возвращает пустую/дефектную строку; python3-процесс при этом завершается с кодом 0 (сам процесс не упал); bash-fallback проверяет только `$?`, видит 0, не активируется, и пустой slug уходит дальше по пайплайну.

## Диагностический принцип

Контракт «fallback срабатывает при ошибке» молчаливо сужен до «fallback срабатывает при крахе процесса», хотя реальная граница негодности результата — «результат пуст/дефектен» — шире множества случаев с ненулевым кодом возврата. Успешное завершение процесса — необходимое, но не достаточное условие пригодности результата.

## Границы

Применимо к fallback на альтернативную реализацию, условие активации которого — только код возврата основного процесса; особенно там, где результат зависит от платформенной кодировки (в источнике — Windows Git Bash). Fallback, который активируется и по пригодности результата, этому отказу не подвержен.

## Проверка

«Fallback на альтернативную реализацию активируется по коду возврата или по пригодности результата?» Только по коду возврата → воспроизведён DP.FM.472: успешный, но пустой/дефектный результат проходит без fallback.

Контрмера: fallback должен срабатывать на «результат пуст» ИЛИ «код возврата ненулевой», не только на второе. Дополнительно: явный `errors='replace'` при явном `utf-8`-декодировании (`sys.stdin.buffer.read().decode('utf-8', errors='replace')`) — детерминированное поведение независимо от локали платформы, вместо неявного платформенного кодека по умолчанию.

## Происхождение и статус проверки

Источник: git commit `acd8fb2` в `FMT-exocortex-template`, `scripts/create-wp.sh` (кириллическая транслитерация заголовка). Связь: issue #851, FMT-exocortex-template#857. Часть партии находок FMT-exocortex-template 2026-09-17 вместе с `DP.FM.471` (heredoc-парсер) и `AS.FM.096` (перенос набора файлов под `set -eu`): общий переносимый принцип — успешный код возврата ≠ пригодный результат.

Смежно, не дубль:
- `DP.D.299` (код возврата конвейера без `pipefail` отражает только последнюю команду) — другой механизм: там код возврата конвейера искажается отсутствием `pipefail`. Здесь процесс вернул 0, результат пуст, а fallback срабатывал только на ненулевой код.
- `DP.FM.461` (молчаливый fallback маскирует всегда-ломаный primary path) — там путь к primary НИКОГДА не совпадал (100% fallback, правдоподобный результат маскирует постоянную поломку резолюции пути). Здесь primary СРАБАТЫВАЕТ (python3 запускается и завершается успешно), но условие активации fallback (только код возврата) слишком узкое, чтобы поймать некачественный результат. Общая тема «fallback», разный механизм и разная причина отказа.

Описанная проверка задаёт критерий приёмки. Её прохождение исходной реализацией этой карточкой не утверждается.
