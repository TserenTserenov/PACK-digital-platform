# DP.FM.413: Тестовый раннер обязан различать «упал с крашем» и «прошёл»

## Симптом
Два независимых проявления одного и того же класса, найденные в разных файлах с разницей в несколько дней. (1) Тест выглядел бы зелёным именно в том сценарии, который должен был его провалить (хук крашится вместо блокировки — сигнал реальной дыры, а не успеха). (2) Тестовый хелпер `assert_refuses()`, проверяющий только код возврата вызова, репортует «ok» на сценарии, где сам вызов упал с исключением, а не выполнился и штатно отказал — маскируя падение вызова под успешный отказ; 17 из 61 теста класса молчаливо перестали проверять свою настоящую логику.

## Причина
При написании regression-тестов на фикс security-хука холодная проверка нашла, что сам тестовый раннер не различал два разных исхода прогона — «процесс упал с крашем» и «процесс успешно прошёл» — и классифицировал их одинаково. Отдельно нашли ту же болезнь ARG_MAX в собственной тестовой фикстуре: сборка JSON для теста через argv `python3`-скрипта на крупных данных упиралась в тот же лимит, что чинили в проверяемом коде.

Второе, независимое проявление (session-close 2026-09-15, `scripts/tests/session-guard-declared-terminal-proof-smoke.py`, коммит `3251ebc97f`): прямой вызов изменённой функции в тестовом файле не обновили под новую сигнатуру аргументов (добавили ещё один позиционный аргумент во второй раз подряд после первого такого же случая). Вызов упал с исключением — но хелпер `assert_refuses()` интерпретирует ЛЮБОЙ ненулевой код возврата как «функция отказала, как ожидалось», включая код возврата от краша самого вызова: «the mismatch crashed 3 tests directly and, more seriously, made the other 17 tests in the same class... report "ok" purely because the crash's own non-zero exit code satisfied their assert_refuses() check, without the actual logic under test ever running». В результате 17 из 61 теста класса молчаливо перестали проверять реальную логику отказа, репортуя «ok» по совершенно случайной причине. Найдено независимым холодным ревью (субагент, отдельный контекст) во второй раз подряд на том же файле — прямое живое подтверждение правила P1 (DP.SC.172): тест без проверки именно наблюдаемого результата запрещён, потому что маскирует ложный «зелёный» прогон.

Оба механизма — конкретные проявления одного и того же класса: раннер верхнего уровня путает «упал с крашем» с «прошёл»; тестовый хелпер внутри теста (`assert_refuses()`) путает «упал с крашем» с «ожидаемо отказал». В обоих случаях крах вызова и штатный отрицательный результат неотличимы для классификатора, хотя означают противоположное: в первом случае — дыра в защите; во втором — тест вообще не проверил заявленную логику.

## Антипаттерн → Паттерн
- **Антипаттерн:** классификатор результата теста сворачивает exit-код/статус в бинарное «зелёное/красное».
- **Паттерн:** различать третье состояние (упал с крашем/по таймауту/по сигналу) отдельно от «прошёл»/«провалился» штатно.

## Переносимый принцип

Exit-код/статус тестового раннера — не бинарный сигнал «зелёное/красное», у процесса есть третье состояние (упал с крашем/по таймауту/по сигналу), и если классификатор результата тестов сворачивает его в «прошёл», регресс именно в устойчивости к аномальному входу остаётся незамеченным сколь угодно долго.

## Тест обнаружения
«Тестовый раннер проверяет только exit-код 0 vs ненулевой, без различения краша (сигнал/таймаут) от штатного провала?» Да → тест, который должен провалиться крашем проверяемого кода, может выглядеть пройденным.

## Применимость
Любая тестовая инфраструктура, проверяющая устойчивость кода к аномальному/крупному входу — на двух уровнях: (1) верхнеуровневый раннер, классифицирующий исход прогона процесса/теста в целом; (2) вспомогательные ассерты-хелперы ВНУТРИ теста (например, `assert_refuses()`), проверяющие один конкретный вызов на «ожидаемый отказ». Оба уровня обязаны различать «вызов/процесс упал с крашем» от «вызов/процесс штатно выполнился и дал ожидаемый результат (в т.ч. отрицательный)».
