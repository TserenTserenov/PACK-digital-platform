# DP.FM.425 — HTTP 409 (stale sha) — транзиентный конфликт, не постоянная ошибка 4xx

## Симптом
Общая функция HTTP-запросов ретраила только 5xx по эвристике «4xx — ошибка клиента, повторять бессмысленно». `gh_request()` не повторяла 409. Боевой случай (2026-09-07, 1 из 6 пилотов): PUT с устаревшим `sha` осиротил файл руководства пилота на ночь.

## Механизм
409 conflict на PUT с устаревшим `sha` по своей природе — сигнал «кто-то другой только что записал тот же путь», то есть транзиентная гонка конкурентной записи, а не постоянная проблема самого запроса. Общее правило «ретраить только 5xx» верно как эвристика по умолчанию, но 409 — специфическое исключение: сигнализирует не невалидный запрос, а устаревшее предположение о состоянии сервера.

Отдельная находка холодного ревью (до деплоя): код восстановления после 409 сам находился внутри `except`-блока — если повторное чтение падает своим исключением, оно могло вылететь непойманным мимо всей функции. Путь восстановления от одной ошибки сам был источником новой необработанной ошибки.

## Фикс
Перечитать контент+sha и повторить PUT до 2 раз, вернуть «unchanged», если конкурирующий писатель уже опубликовал точно то же содержимое. Код повторного чтения внутри `except` отдельно обёрнут, чтобы его собственное исключение не вылетало непойманным.

## Тест обнаружения
«HTTP-клиент ретраит по правилу "только 5xx"? Среди используемых эндпоинтов есть PUT/POST с optimistic concurrency (sha/ETag/version-параметр)?» Да → 409 требует собственной retry-политики (re-read + retry), не общего "4xx = не ретраить". Отдельно: «код восстановления внутри except сам может бросить исключение?» Да → обернуть отдельно, не полагаться на внешний catch.

## Применимость
Любой HTTP-клиент к API с optimistic concurrency control (GitHub Contents API и аналоги, где запись защищена версионным параметром) — не только этот скрипт.
