# DP.FM.427 — Скопированное предположение о схеме БД тихо возвращает NULL вместо исключения

## Симптом
Функция `get_email_from_ory_id()` обращалась к `traits->>'email'`, скопировав это обращение из другого скрипта (`admin_link_user.py`). Для таблицы `persona.ory_identity` предположение оказалось неверным: `email` там — отдельная типизированная колонка верхнего уровня, а `traits` — не связанный с логином business-профиль, для проверенного аккаунта вообще без ключа email. `/subscription` молча откатывался на нейтральное сообщение «активна» без email — не крашился, не логировал, ничего не сигнализировал.

## Механизм
Копирование обращения к полю/колонке из чужого, пусть и рабочего, скрипта переносит вместе с кодом и предположение о СХЕМЕ данных — которое не проверяется синтаксисом и не гарантированно совпадает даже для похожих по смыслу таблиц. Для JSONB-путей это усугубляется тем, что несуществующий ключ (`->>'email'` на JSONB без такого ключа) возвращает SQL NULL, а не исключение — баг маскируется под «данных пока нет», а не «код неправильный».

## Фикс
Обращение заменено на прямую типизированную колонку `email`.

## Тест обнаружения
«Обращение к полю/колонке скопировано из другого скрипта/модуля?» Да → схема ЭТОЙ таблицы проверена отдельно, не унаследована вместе с кодом. Отдельно для JSONB: «путь `->>'key'` может тихо вернуть NULL вместо исключения при отсутствии ключа?» Да → несовпадение схемы неотличимо от «данных нет» без явной диагностики NOT NULL/IS NULL.

## Применимость
Любое копирование SQL/ORM-обращения из соседнего модуля для похожей, но не идентичной таблицы — особенно при работе с JSONB/schemaless-полями, где отсутствие ключа не эквивалентно ошибке доступа.
