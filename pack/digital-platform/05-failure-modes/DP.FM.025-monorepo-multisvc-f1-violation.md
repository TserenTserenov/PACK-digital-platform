# DP.FM.025 — Монорепо-мультисервис: нарушение 12-factor F1

## Паттерн

Несколько логически независимых сервисов живут в одном git-репозитории. Каждый сервис имеет отдельную точку входа и отдельный runtime (LaunchAgent / systemd unit).

**Сигнал при аудите:** в одном репо несколько `*.service` или `com.*.plist` файлов с разными `ExecStart`.

## Последствие (нарушение F1)

12-factor F1: «один codebase → одно приложение». При нарушении:
- Нельзя версионировать сервисы независимо (тег `v1.2.0` означает ВСЕ сервисы)
- Нельзя деплоить и откатывать независимо
- Изменение одного сервиса создаёт «шум» в истории другого
- CI/CD нельзя настроить per-service без сложных path-фильтров

## Правило

Каждый сервис с отдельным runtime = отдельный репозиторий (или sub-path с независимым CI и версионированием).

## Когда монорепо допустимо

Если сервисы **не имеют отдельных runtime unit**: библиотеки, shared utilities, инфраструктурные скрипты без собственного lifecycle.

## Процесс декомпозиции legacy monorepo

1. Перечислить все точки входа (`grep -r "ExecStart\|__main__" .`)
2. Для каждой: оценить отдельный lifecycle → да = кандидат на выделение
3. Выделять по одному с сохранением git-истории (`git filter-repo --subdirectory-filter`)
