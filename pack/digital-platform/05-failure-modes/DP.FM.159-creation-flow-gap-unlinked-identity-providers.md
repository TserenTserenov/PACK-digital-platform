# DP.FM.159 — Creation-flow gap между связанными identity-провайдерами

## Описание

Если две identity-системы связаны ETL'ом, но ETL односторонний (читает из Ory, не пишет в Ory), регистрация в первой системе (LMS) не создаёт идентичность во второй (Ory/Kratos).

## Механизм возникновения

1. Пользователь регистрируется в LMS → аккаунт создан в LMS.
2. ETL синхронизирует данные из Ory в LMS (read-only direction).
3. Пользователь переходит на Ory-форму входа → вводит LMS-пароль → отказ.
4. UX-симптом: «не принимает пароль» (пользователь думает, что аккаунт существует).
5. Реальная причина: аккаунт в Ory не создан ни разу.

## Диагностика

«Существует ли путь регистрации только в системе А, после которого система Б не знает пользователя?» Да → creation-flow gap.

Конкретный маркер: пользователь завершил регистрацию в A, но на форме входа B видит только «введите пароль» (нет кнопки «уже зарегистрированы через A»).

## Три решения

| Вариант | Описание | Когда применять |
|---------|----------|-----------------|
| **(1) Eager creation** | При регистрации в А — сразу создать аккаунт в Б | Если оба провайдера в control-zone |
| **(2) JIT provisioning** | Создать аккаунт в Б при первом обращении через посредника | Если есть client-mediated flow (см. DP.D.139) |
| **(3) UX gate** | Перед формой входа Б — детектировать «не зарегистрирован» и направить на регистрацию | Hotfix без изменения provisioning architecture |

Текущий фикс в IWE: вариант (3) — T0 gate в боте.

## Тест

«Можно ли пройти registration-flow только в системе А и попасть на login-форму Б?» Да → creation-flow gap активен.
