# DP.FM.420 — Обязательный cleanup вложен в блок, чьё условие — доступность несвязанного опционального компонента

## Паттерн

Снятие обязательства (cleanup критичного persistent-состояния) физически размещено внутри `if`-блока, отвечающего за ДРУГУЮ задачу (запись в журнал через `ledger-append.sh`), доступную только при наличии опционального компонента. На инсталляции без этого компонента (немигрированный шаблон) блок целиком не исполняется — и cleanup, логически с журналом не связанный, молча пропускается вместе с ним.

## Механизм

1. Два разных побочных эффекта (журналирование + снятие обязательства) исторически оказываются в одном `if`-блоке, потому что оба относились к одному и тому же событию (закрытие пир-сессии) по времени.
2. Условие блока пишется под нужды журналирования (доступность `ledger-append.sh`); cleanup неявно наследует то же условие, хотя логически от журнала не зависит.
3. На инсталляции, где `ledger-append.sh` отсутствует, весь блок не исполняется — cleanup пропадает вместе с журналированием, без индикации ошибки.
4. Предыдущая версия дополнительно использовала для guard'а переменную классификации канала, вычисленную внутри того же блока для нужд логирования, а не собственное свидетельство того, что данная сессия — пир-сессия — усугубляет связку.

## Почему опасен

Cleanup, разделяющий условие с логически несвязанным кодом, перестаёт срабатывать бесшумно при любом изменении окружения, которое отключает этот несвязанный код. Дефект не воспроизводится в среде разработчика (где компонент есть) — только на инсталляциях без него, то есть именно там, где его сложнее всего заметить.

## Антипаттерн → Паттерн

- Антипаттерн: `if ledger_component_available: log_event(); clear_obligation()`
- Паттерн: cleanup выносится из блока журнала и получает собственное условие на собственном свидетельстве (`if close_path == "peer-session": clear_obligation()`); журналирование остаётся под своим условием отдельно.

## Тест обнаружения

«У этого cleanup/обязательного побочного эффекта — собственное условие на собственном свидетельстве, или он находится внутри блока, решающего другую задачу?» Если внутри чужого блока → проверить, что произойдёт, если внешний (несвязанный) компонент недоступен.
