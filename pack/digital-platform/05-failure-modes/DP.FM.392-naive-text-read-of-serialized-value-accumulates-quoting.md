# DP.FM.392: Naive text read of serializer-quoted value accumulates escaping on every round-trip

## Симптом

Значение, которое YAML-сериализатор оборачивает в кавычки (например, чтобы ISO-строка не превратилась в YAML-timestamp), читается обратно текстовым инструментом (`grep`+`cut`) вместо парсера того же формата. Каждый повторный вызов добавляет ещё один слой кавычек поверх уже закавыченного значения: `'...'` → `'''...'''` → `'''''''...'''''''` за 3-4 вызова.

## Корневая причина

Чтение и запись значения используют разные слои интерпретации формата: запись идёт через структурный сериализатор (YAML dump, добавляющий кавычки по своим правилам), а чтение — через текстовый инструмент, не знающий о кавычках как о синтаксисе сериализации и трактующий их как часть самого значения. Каждый цикл запись→чтение→запись добавляет ещё один слой, потому что читающий код никогда не снимает то, чего, по его модели, не существует.

## Антипаттерн → Паттерн

- **Антипаттерн:** читать значение, записанное структурным сериализатором, текстовыми инструментами (`grep`, `cut`, `sed`) без знания о синтаксисе кавычек этого формата.
- **Паттерн:** читать тем же парсером, которым записано (`yaml.safe_load` для YAML), либо, для самовосстановления уже испорченных черновиков, явно снимать уже существующие обёрточные кавычки перед проверкой/использованием значения.

## Тест обнаружения

Найти значение, обёрнутое сериализатором в кавычки/экранирование, и проверить путь чтения: если это `grep`/`cut`/`sed` без парсера того же формата — при следующем цикле запись→чтение количество слоёв экранирования увеличится на один. Быстрая проверка на уже живых данных: несколько вложенных слоёв одинаковых кавычек вокруг значения = паттерн уже сработал.

## Связанные документы

- Общий принцип: значение, записанное структурным сериализатором, нужно читать тем же парсером, а не текстовыми инструментами — применимо не только к YAML (JSON, TOML, любой формат с собственными правилами экранирования).
