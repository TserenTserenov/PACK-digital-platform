# DP.FM.162 — РП-контекст: vapor-claim о готовом компоненте

## Паттерн

Карточка РП пишется в момент создания (часто из памяти/намерения), а код живёт своей жизнью. Между ними дрейф: чем дольше РП лежит в `pending`, тем выше шанс, что фраза «уже есть готовый X» либо устарела, либо никогда не была верна. Если на этапе проектирования брать claim'ы карточки за якорь без проверки — дизайн встаёт на пустоту.

**Сигнал при чтении РП-контекста:** формулировки вида «переиспользуй компонент Y», «уже есть post_voice_note», «X содержит готовый клиент Z».

## Последствие

- Переоценка готовности → ложно «осталось мало»
- Скрытый scope: «дописать обвязку» оборачивается «построить с нуля»
- Неверная оценка часов в момент open-loop/problem-framing
- MVP стоит на vapor-компоненте → отказ на интеграции

## Правило (расширение WP Gate)

При problem-framing / дизайне, когда контекст РП утверждает «переиспользуй / уже есть / содержит компонент Y» — **первым** шагом `grep` имени Y по целевым репо.

```bash
grep -r "post_voice_note\|<имя_компонента>" ~/IWE/<репо>/
```

- **Найдено в коде** → claim верен, продолжать дизайн на reuse
- **Не найдено** → правь дрейф в карточке РП, пересчитывай объём от «строим», не от «reuse»

## Тест обнаружения

1. РП лежит в pending > 14 дней и содержит конкретные имена компонентов? → ⚠️ риск vapor-claim
2. Имя компонента из РП-контекста gripable в коде? Нет → vapor-claim подтверждён
3. Автор контекста = автор кода компонента? Нет → выше риск дрейфа

## Профилактика

1. `grep` claim'ов карточки **до** дизайн-сессии (расширение WP Gate чеклиста)
2. При закрытии РП обновлять связанные карточки родственных РП (cross-WP context refresh)
3. Старая карточка ≥ 30 дней без коммитов → пересмотр claim'ов на следующем Day Open
