# DP.FM.195: Retroactive history cleanup to hit deadline

## Описание

При обнаружении систематической ошибки измерения предпринимается попытка «вычесть» вклад известной причины из прошлых данных — чтобы сохранить нужный результат (счётчик, дедлайн, метрику). Это подгонка данных, маскирующаяся под «честную поправку».

## Сигнал

- Найдена системная ошибка, объясняющая N прошлых «позитивных» измерений
- Предлагается retroactive correction: «уберём её вклад, и дедлайн сохранится»
- Альтернатива (перезапуск счётчика) отвергается как «слишком строгая»

## Почему это ошибка

Если детектор систематически ошибался, прошлые «чистые» дни не гарантированно чисты: под известной причиной могли скрываться и настоящие сбои. Ретроактивное вычитание одной причины не восстанавливает истину — оно заменяет одну ложь другой.

**Тест:** «Если бы я обнаружил эту причину год назад и тогда же её устранил — стал бы я считать эти дни чистыми?» Нет → retroactive cleanup неправомерен.

## Правильная реакция

1. Задекларировать: «данные за период X — Y загрязнены известной ошибкой»
2. Перезапустить счётчик с момента устранения ошибки
3. Не переносить исторические данные через точку перезапуска

## Контекст возникновения

WP-436 watchdog: выявлена ложная тревога на долгоживущие демоны (DP.D.188). Предлагалось «вычесть» её из прошедших дней, чтобы сохранить дату 7 июля. Принятое решение: перезапуск счётчика с 05.07.
