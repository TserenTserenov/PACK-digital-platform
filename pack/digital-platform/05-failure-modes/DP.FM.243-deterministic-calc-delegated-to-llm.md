# DP.FM.243 — Детерминированный расчёт делегирован LLM: правдоподобная заглушка вместо результата

## Паттерн

Задача с единственным правильным ответом, вычислимым арифметикой (сумма, фильтр, парсинг структуры), делегирована LLM. LLM возвращает правдоподобное число — не результат вычисления, а заглушку, неотличимую на вид от правильного ответа.

## Пример

```python
# DayPlan fill-prompt: LLM генерирует строку бюджета
# LLM не суммирует таблицу — ставит правдоподобное число из контекста
# Итог: "~2h РП / ~1h физ" выглядит правильно, но никогда не равно реальной сумме

# Фикс: детерминированный постпроцессор
# day-open-budget-patch.py — запускается после LLM-fill
def patch_budget_line(dayplan_path):
    df = parse_wp_table(dayplan_path)
    total_wp_hours = df["budget_h"].sum()
    rewrite_budget_line(dayplan_path, total_wp_hours)
```

## Механизм

LLM оптимизирован на правдоподобие, не на арифметическую точность. При наличии контекста (прошлые значения, шаблон строки) он выдаёт число «в правильном диапазоне». Результат не верифицируется, потому что «похоже на правду».

## Почему опасен

1. Заглушка неотличима от правильного ответа при беглом чтении.
2. Проходит acceptance, если тест проверяет наличие числа, а не его точность.
3. Дефект накапливается тихо: решения принимаются по стабильно неверным данным.

## Лечение

- Чисто-детерминированные шаги (суммы, фильтры, парсинг) — только в код, не в LLM-промпт.
- LLM — только там, где есть реальная неопределённость (интерпретация, выбор при неполных данных).
- В pipeline: детерминированный постпроцессор после LLM-fill перезаписывает вычислимые поля.
- Acceptance-тест детерминированных полей: проверять значение, не только наличие.
