# DP.FM.077 — Overstated Validator Coverage in Documentation

## Суть паттерна

Документация автоматического детектора/линтера/валидатора формулируется как «детектор N автоматически ловит этот класс ошибок». Реально детектор покрывает только subset (например, regex по конкретным путям `roles/strategist/prompts/`). Читатель получает **ложное чувство защиты**: полагается на автоматику для всего класса, и дрейф вне scope проходит мимо.

Парный паттерн к DP.FM.005 (Model-Reality Drift): там расходится концепт и код; здесь расходится **документация о валидаторе** и **реальное поведение валидатора**.

## Механизм

1. Разработчик создаёт детектор с ограниченным scope (regex по подмножеству путей, проверка только одного формата).
2. В документации (README/RELEASE-PROCESS/manual) пишет «детектор N автоматически ловит X» без указания scope.
3. Пользователь читает доку → формирует ментальную модель «X защищён автоматически».
4. Случай X возникает вне scope → детектор молчит → дрейф попадает в production.
5. Пост-инцидент: «но ведь у нас же детектор!» — обнаруживается gap между декларацией и реальностью.

## Симптомы

- Дрейф ловится только при ручном code review, хотя для него «есть детектор».
- В пост-инцидентах формулировка «мы думали, это покрыто детектором».
- Документация содержит абсолюты: «всегда», «для всех», «автоматически», без указания scope.

## Профилактика (правило документирования валидаторов)

1. **Явно указать subset:** «detector X в file Y ловит этот случай **для подмножества Z**, но только для этого подмножества».
2. **Для остального — ручная проверка:** конкретная grep-команда / чеклист / визуальный обход.
3. **Запрет формулировок** «автоматически», «всегда», «для всех» без подтверждённого scope.

**Тест документации:** «Может ли читатель составить тест-кейс, где детектор не сработает, прочитав описание?» Нет → описание слишком абсолютно.
