# DP.FM.443 — Сужение idempotency-ключа ради починки гонки блокировок — компенсация не того слоя (near-miss)

## Паттерн

Гонка двух конкурирующих запросов чинится корректным lock'ом на уровне БД. Отдельно от этого, идемпотентность повторных вызовов того же инструмента реализована через fingerprint-ключ, включающий параметры контента запроса (`prompt`, `artifacts`). После введения lock'а возникает соблазн упростить fingerprint, убрав из него параметры контента — раз новый lock и так гарантирует корректность против гонки. Это ошибка: idempotency-ключ используется не только во время активной гонки (короткого окна in-flight запроса) — если убрать контент из ключа навсегда, а не только на время in-flight, ЛЮБОЙ последующий вызов того же инструмента с ДРУГИМИ аргументами получит закешированный ответ первого вызова.

## Механизм

1. Две независимые задачи защиты делят один артефакт: (а) не допустить двойной обработки одного запроса во время гонки (in-flight), (б) не повторять реальную работу при точном повторе того же запроса (кэш идемпотентности) — обе используют один и тот же fingerprint-ключ.
2. Фикс задачи (а) через БД-lock снимает необходимость в fingerprint для гонки → рождается предложение упростить fingerprint, убрав контентные параметры.
3. Предложение принимается консенсусом нескольких участников — упускается, что fingerprint без контента нарушает задачу (б): кэш идемпотентности превращается в вечную заглушку «первый ответ на любой вызов».
4. Ошибка находится ДО коммита при повторном прочтении собственной реализации — самокоррекция, изменение не попадает в код.

## Почему опасен

Консенсус нескольких участников пир-сессии не является достаточной проверкой для изменения scope разделяемого механизма, используемого потребителями, явно не упомянутыми в текущем обсуждении. Ошибка живёт в зоне, где два разных требования (защита от гонки + кэш повторов) исторически делят один артефакт.

## Correct Alternative

Гонку лечить lock'ом на своём уровне (БД-constraint / advisory lock). Fingerprint idempotency-кэша не трогать — он отвечает за ДРУГОЕ требование с другим временем жизни, чем узкое окно гонки. Если оба требования действительно нужно объединить — явно спроектировать это отдельным решением с рассмотрением ВСЕХ потребителей текущего fingerprint.

## Тест

«Это изменение сужает область действия механизма, который используют потребители, не участвующие в текущем обсуждении?» Да → искать причину проблемы в её собственном слое, не менять чужой смежный механизм ради удобства.
