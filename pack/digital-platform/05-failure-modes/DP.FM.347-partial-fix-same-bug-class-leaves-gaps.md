# DP.FM.347 — Partial fix одного экземпляра bug-класса

## Паттерн

При обнаружении ошибки в конкретном месте кода (файл A) — фикс применяется только к файлу A. Тот же баг-класс существует в файлах B, C, D, ... и остаётся нетронутым. Создаётся иллюзия безопасности: «мы починили это», хотя системный паттерн жив.

## Пример

```
# Обнаружен unconditional overwrite в update.sh для settings.json:
cp "$TEMPLATE/settings.json" "$IWE/.claude/settings.json"  # без guard

# Фикс закрывает только этот файл:
if ! is_author_mode; then cp ...; fi  # settings.json защищён

# Тот же паттерн остаётся в repair_pass() и Step 6 для .claude/skills/, .claude/hooks/, .claude/rules/:
cp "$TEMPLATE/.claude/skills/"* "$IWE/.claude/skills/"  # без guard — ЖИВЁТ

# Результат: 66 файлов перезаписаны двумя волнами (10.07 и 11.07 01:02–04:32)
```

## Механизм

1. Bug-класс «X без guard» применён в N местах
2. Обнаружен экземпляр 1 → исправлен
3. Экземпляры 2..N не проверены (нет систематического поиска)
4. Фиксированный экземпляр 1 создаёт ложное ощущение «паттерн закрыт»
5. Экземпляры 2..N срабатывают позже, причиняя реальный ущерб

## Почему опасен

- Частичный фикс меняет ожидания без изменения риска (систематически)
- Ущерб от второй волны сбоев — неожиданный (казалось, починили)
- Чем длиннее время между экземплярами → тем труднее связать с первопричиной

## Лечение

При обнаружении bug-экземпляра:
1. Немедленно grep по кодовой базе на паттерн («все места `cp` без `is_author_mode` guard»)
2. Закрывать bug-класс целиком, не один экземпляр
3. В commit message явно указывать: «закрыт класс, проверены N мест» vs «закрыт экземпляр»
4. Тест на полноту: регрессионный тест, проверяющий каждое место применения паттерна
