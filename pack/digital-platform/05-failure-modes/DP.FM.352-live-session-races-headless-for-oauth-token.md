# DP.FM.352 — Живая сессия вступает в гонку с headless за OAuth-токен

## Паттерн

Живой интерактивный процесс агента (например Kimi Code пилота, открытая вручную сессия) и параллельные headless-вызовы того же агента делят один файл OAuth-токена. Оба процесса могут одновременно читать/обновлять токен — тот же класс гонки, что уже наблюдался в чисто headless-headless сценарии.

## Механизм

1. Токен хранится в общем файле, к которому имеют доступ все процессы одного агента (интерактивные и headless)
2. Живая сессия пилота и фоновый headless-вызов запускаются в перекрывающееся время
3. Оба читают/обновляют файл токена без координации — результат зависит от порядка выполнения (race)

## Почему опасен

- Проблема не ограничена сценарием «несколько headless-вызовов одновременно» — она возникает и при простом одновременном использовании интерактивной сессии и фонового задания
- Разработчик может считать, что «раз я работаю руками, фоновые задания подождут» — ложное предположение

## Лечение

Применить то же решение, что и для headless-headless гонки (файловая блокировка / single-flight на уровне файла токена), не делая исключения для интерактивного канала.
