# DP.FM.407: Grep первого совпадения ломается на легитимно пустом значении структурированного поля

## Симптом
Почти треть завершённых карточек (28%) законно несли `gather-session-facts.wp: ''` (сессия стартовала без явного `--wp`), и grep на пустую строку не матчился вовсе — тихий пропуск, не ошибка.

## Причина
Извлечение номера РП из карточки закрытия было реализовано как grep первого попавшегося вложенного поля `wp` в тексте — работает, пока это поле не встречается пустым.

## Антипаттерн → Паттерн
- **Антипаттерн:** поиск значения текстовым grep по «первому совпадению» в структурированных данных (YAML/frontmatter).
- **Паттерн:** структурный разбор фронтматтера (PyYAML) с явным порядком приоритета источников (`gather-session-facts.wp` авторитетно, `wp-context-update.wp` — только если первое пусто) плюс нормализация форм записи номера.

## Тест обнаружения
«Значение извлекается текстовым grep по первому совпадению из YAML/frontmatter с несколькими кандидатными источниками?» Да → легитимно пустые/альтернативные значения поля, которые в тестовых данных могут вообще не встретиться, незаметно ломают поиск.

## Применимость
Любое извлечение значения из структурированных данных (YAML/frontmatter) с несколькими возможными источниками одного поля.

## Смежный вариант — субагент-верификатор ищет текст буквально

Тот же принцип срабатывает и там, где «grep» — не команда, а поведение LLM-субагента: если задача верификатора сформулирована как «найди строку X в файле», а искомая запись в реестре легитимно оформлена иначе (например, жирным текстом, другим порядком слов, синонимом), субагент даёт ложный отказ («не нашёл»), хотя запись фактически на месте. Тест обнаружения тот же: ищется ли значение по буквальному совпадению текста, когда легитимные альтернативные формы записи в принципе возможны? Да → задачу верификатору стоит формулировать через смысл записи, не через точную строку.
