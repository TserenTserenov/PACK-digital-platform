# DP.FM.399: Nullable булево поле стороннего API проверено строгим сравнением с False без ветки на None

## Симптом
Не воспроизведено эмпирически — найдено при чтении кода манифест-флоу создания репозитория через GitHub App, эскалировано пилоту.

## Причина
Проверка `selected_repo["private"] is False` не сработает, если сторонний API вернёт `None` (приватность не установлена или наследуется от шаблона) вместо явного `True`/`False`. Строгая проверка `is False` пропускает случай `None` молча — репозиторий остаётся публичным без предупреждения.

## Антипаттерн → Паттерн
- **Антипаттерн:** nullable булево поле внешнего API проверяется через строгое сравнение с `True`/`False` без явной ветки на `None`.
- **Паттерн:** явная обработка всех трёх состояний (`true`/`false`/`не задано`) — либо проверка через «не равно True», либо отдельная ветка на `None` с явным решением, что делать при неизвестном значении.

## Тест обнаружения
«Поле стороннего API документировано как nullable/optional булево? Код сравнивает строгим сравнением с `True`/`False`?» Да → добавить явную ветку на `None`, не полагаться на сравнение по идентичности.

## Применимость
Любая интеграция со сторонним API, где булево поле может прийти как `null`/`None` (не установлено или наследуется) — не только GitHub App.

## Отличие от смежного
- **DP.FM.051 (ON CONFLICT nullable UNIQUE):** там nullable-семантика UNIQUE-индекса Postgres при UPSERT; здесь nullable булево поле внешнего API при строгом сравнении. Разные механизмы, оба про nullable, не дубли.
